# 《巡梦》梦境记录 Web 应用产品设计报告（参赛版）

## 摘要

本报告为第二期灵治擂台赛参赛作品《巡梦》的完整产品设计方案，严格匹配赛题必做项、评分标准与提交要求，主打「情绪治愈 + 轻量化记录」的核心产品差异点，采用指定 Langchain+Langgraph+Langsmith 技术栈构建 AI 能力，以 Flutter 作为跨平台前端框架，参考 Dreamoo、My Dream Chronicle 等头部梦境产品的 UI/UX 与功能设计优势。方案聚焦个人参赛场景，优先在满足核心功能合规性的前提下，通过精细化情绪体验设计与端到端工程质量，同时覆盖产品设计维度与技术工程维度的综合加分项。

## 1. 赛事背景与产品定位

### 1.1 赛事需求解读

本次赛题《巡梦》要求打造一款围绕「做梦」的 Web 应用，核心目标是帮助用户记录、管理梦境，并**沉浸式承接用户情绪**—— 这也是区别于普通工具类产品、决定作品排名优劣的核心评价标准[(75)](https://blog.csdn.net/woshihuanglaoshi/article/details/159998131)。从评审标准看，作品需同时覆盖两大维度：一是作为梦境工具的基础合规性，二是作为情绪承接类产品的设计共情能力 —— 二者缺一，都只会让作品停留在普通功能级工具的水准，无法形成竞赛优势[(79)](https://m.wandoujia.com/apps/8432827/history_v10500)。

硬性必做项覆盖五大模块，缺一则会直接进入低分评审区间，分别是：



* **梦境记录**：支持文本录入，且至少提供一种其他录入方式（如语音、图片、手绘等）；

* **梦境管理**：支持历史梦境查阅、具备日历视图（按日期聚合梦境、可从日历跳转至详情页）；

* **数据持久化**：用户刷新 / 重新打开应用后，数据仍保留；不同用户、不同会话之间的数据严格隔离；

* **情绪关联**：产品需与梦境情绪产生至少一种关联形式（如情绪标记、情绪可视化、AI 情绪解读等）；

* **可稳定演示**：需提供可流畅运行的版本（本地、内网均可），确保评审现场无功能卡顿、崩溃等意外状况[(75)](https://blog.csdn.net/woshihuanglaoshi/article/details/159998131)。

本次竞赛的评分规则中，产品设计与工程质量的权重分布形成了明确的差异化评价逻辑：



* **产品选手赛道**：设计与表达类分项占比高达 50%，核心考核「核心链路情绪映射能力」「交互与交付完整度」「鲁棒性和边界处理」三大维度，重点看情绪设计能否与用户梦境感受精准匹配、交互是否符合 “轻量化记录” 的核心使用场景；

* **技术选手赛道**：工程质量权重更高，核心考核模块边界划分、代码规范度、可维护性、异常处理机制，以及技术方案对产品设计的支撑效率；

* **通用评分项**：所有选手需额外比拼提交及时性、运行响应速度、核心流程耗时控制这三项「时间效率」指标[(79)](https://m.wandoujia.com/apps/8432827/history_v10500)。

### 1.2 现有作品参考分析

为在短周期内实现设计与工程的双重最优解，本次设计参考了两款头部梦境产品的成熟优势作为差异化创新基础：



* **Dreamoo（AI 梦境社交应用）** ：作为全球首款 AI 梦境社交应用，其核心优势是通过 AI 技术将抽象梦境落地为可视化内容，完美贴合「情绪承接」的赛题核心构思逻辑 —— 它将用户模糊的梦境记忆（如追逐、飞翔、故人重逢等场景），通过算法转化为可留存、可分享的具象画面，解决了 “梦境难以被记录、无法被准确理解” 的行业级用户痛点[(9)](https://m.duote.com/ios/480517.html)。其功能设计遵循「记录 - 可视化 - 解读 - 分享」的完整用户旅程，精准覆盖用户从记录梦境到探索潜意识再到社交表达的全链路需求；而在情绪体验层面，AI 生成的梦境视觉内容与专业解读的联动机制，形成了 “用户记录梦境→AI 转译内容→内容唤起情绪→解读承接情绪” 的闭环体验，让产品的情绪承接能力有了功能落地支撑[(9)](https://m.duote.com/ios/480517.html)。

* **My Dream Chronicle（梦境日记应用）** ：主打「纸质日记本」的拟物化风格，核心优势是通过精细化的交互与视觉设计，强化用户对梦境内容的珍视心理 —— 这恰好匹配了 “梦境是私密回忆” 的用户普遍认知，与本次《巡梦》产品 “安放情绪” 的核心设计目标高度契合[(77)](https://ftium4.com/ux-weekly-245.html)。其 UI/UX 设计的成熟度是最值得复用的竞争优势：为适配用户枕边使用的核心场景，它采用了低饱和度暗夜主题、紫色流光视觉元素；为降低记录门槛、强化沉浸感，它内置了白噪音录制功能、优化了语音转写识别精度；为提升梦境回顾的仪式感，它设计了符合真实物理惯性的翻页动效 —— 这些设计都击中了用户在梦境类产品上的核心体验诉求[(77)](https://ftium4.com/ux-weekly-245.html)。

综合两款产品的优势，行业级梦境产品的核心体验逻辑可归纳为三点，这也是本次设计需要重点复用的竞赛级加分项：



* **沉浸式记录体验**：以语音、轻量化编辑等功能降低用户记录门槛，用暗夜模式、白噪音等场景化元素贴合枕边使用场景；

* **可视化情绪承接**：通过 AI 技术将抽象梦境、看不见的情绪转化为具象内容，用直观的视觉交互让用户 “看见自己的潜意识”；

* **系统化梦境管理**：用日历、标签、搜索等功能降低用户整理梦境的成本，提升长期留存意愿[(77)](https://ftium4.com/ux-weekly-245.html)。

### 1.3 产品核心定位

结合赛事规则限制、成熟产品优势复用与技术栈约束，本次作品定位为**轻量化、私密化、AI 陪伴式的跨平台梦境记录应用**—— 区别于 Dreamoo 的 “社交属性”，本产品弱化社交、强化 “用户与自我梦境的独处连接”，更精准地锚定 “安放情绪” 的产品核心目标[(12)](https://www.iesdouyin.com/share/video/7537169950964829455)。设计上以「不打扰用户情绪」为最高原则，功能仅聚焦用户的核心需求：快速记录梦境、有条理回顾梦境、得到情绪抚慰，且所有功能设计都必须支撑 “现场流畅演示” 的竞赛核心要求[(12)](https://www.iesdouyin.com/share/video/7537169950964829455)。

本次设计的核心竞争优势为「轻量化记录 + 精准化情绪闭环 + 高质量工程支撑」，在满足必做项的基础上，重点打造三大加分亮点，形成竞赛差异化优势：



* **轻量化记录适配**：适配用户晨起、睡前的 “半梦半醒” 使用场景，提供语音转文字、AI 摘要、情绪标签一键勾选功能，让用户在记忆模糊时也能快速完整记录梦境细节；

* **沉浸式情绪承接**：参考 Dreamoo 的 AI 可视化能力，将梦境文字转化为具象图像；参考 My Dream Chronicle 的交互体验，用拟物化翻页、暗夜风格、白噪音元素打造专属氛围；并通过 AI 情绪解读、个性化安抚文案、动态情绪壁纸实现 “记录梦境 - 识别情绪 - 承接情绪 - 反馈体验” 的闭环；

* **可靠工程质量支撑**：采用企业级 Langchain 生态技术栈，保障多用户场景下的数据安全、同步稳定与大规模扩展能力；前端选用 Flutter 框架，保障多端体验一致性，用工程质量强化设计的竞争力[(57)](https://docs.langchain.com/oss/javascript/deepagents/going-to-production)。

### 1.4 目标用户与使用场景

本次设计的目标用户精准锚定**有长期梦境记录需求、关注内心情绪变化、希望通过梦境探索自我潜意识**的核心人群 —— 这群用户普遍对 “快速记录转瞬即逝的梦境细节” 有强需求，且非常在意记录过程中的隐私感与沉浸感，恰好匹配《巡梦》产品的核心功能定位[(79)](https://m.wandoujia.com/apps/8432827/history_v10500)。

核心使用场景覆盖用户从 “梦境产生” 到 “回顾整理” 的完整链路，完全贴合产品 “轻量化记录 + 情绪承接” 的设计逻辑，所有场景都将在竞赛版本中落地为可演示的核心功能：



* **场景 1：晨起 / 睡前快速记录**：用户处于半梦半醒状态，不愿长时间打字，可通过语音转文字功能快速记录梦境，AI 自动补充摘要、提取关键词、匹配情绪标签；整个记录过程不超过 3 步，能有效留住转瞬即逝的梦境细节；

* **场景 2：日间整理与情绪回顾**：用户在空闲时间希望重新梳理梦境细节、整理情绪，可通过日历视图快速定位历史梦境，按情绪、标签检索相关记录；在阅读梦境时，页面会自动匹配与梦境情绪基调相符的背景氛围、轻量音效，强化情绪共鸣；

* **场景 3：长期情绪自我追踪**：用户记录梦境一段时间后，希望了解自身情绪变化规律、获取心理状态参考，可通过情绪统计图谱、梦境符号词云可视化呈现长期趋势，辅助用户获取自我潜意识的认知参考[(9)](https://m.duote.com/ios/480517.html)。

## 2. 技术栈选择与适配方案

为保障参赛方案的落地效率、演示稳定性和工程可维护性，技术栈需同时满足「产品设计效果支撑」「多用户数据同步与隔离」「后端管理能力」三大核心诉求，且必须与 Langchain 生态无缝适配 —— 这是支撑上层产品设计效果的基础，也是技术赛道的核心评分项。

### 2.1 前端跨平台框架选择

本次产品设计的 UI/UX 效果需要高性能跨平台渲染能力支撑，而 Flutter 是唯一能同时满足「产品级 UI 风格一致性」「多端性能稳定性」「开发效率」三大前置要求的方案，可实现 Web、移动、桌面端的跨平台覆盖 —— 完全匹配本次参赛作品 “一次开发、多端部署” 的效率要求[(66)](https://blog.csdn.net/2501_93575716/article/details/155716708)。

选择 Flutter 的核心技术支撑价值，本质是为产品设计提供了三个不可替代的竞争优势：



* **产品级 UI 体验还原能力**：Flutter 的核心优势在于其底层自绘渲染引擎（而非依赖原生组件），能在不同平台下完全一致地还原产品设计的暗夜风格、紫色流光视觉细节，精准复刻拟物化翻页、动态情绪背景等复杂交互动效 —— 从技术上保障了 Dreamoo、My Dream Chronicle 的优秀设计不会因平台差异打折扣；

* **原生级性能支撑**：Flutter 的自绘引擎架构保障了页面滚动、复杂交互动画的稳定帧率，不会因视觉效果复杂出现卡顿、崩溃现象 —— 这为评审现场的流畅演示提供了最基础的技术保障；

* **开发效率与可维护性**：Flutter 的热重载功能可以实现 “代码修改、实时预览” 的效果，大幅提升调整交互细节、还原视觉效果的开发效率；同时，其单代码跨端部署的特性，能有效避免多端适配带来的冗余开发成本，让个人参赛的精力能集中在体验优化上[(65)](https://www.alignstudios.co.uk/post/comparing-nuxt-3-and-flutter-choosing-the-right-tool-for-your-project/)。

Flutter 的组件化思想，也为本次产品设计的核心场景落地提供了成熟支撑：采用 Material Design 3 规范搭建深邃靛蓝色为主色调的视觉体系，构建出梦境记录、日历回顾、情绪统计等核心场景的专属页面，完美还原产品设计的所有交互细节[(75)](https://blog.csdn.net/woshihuanglaoshi/article/details/159998131)。

### 2.2 人工智能层（Langchain + Langgraph + Langsmith）

这是实现「情绪承接」核心产品设计效果的技术支撑骨架，决定了 AI 反馈内容的精准度、用户核心链路的体验流畅度 —— 方案的设计逻辑，是从技术上保障 AI 能力完全匹配产品设计的「情绪闭环」逻辑[(57)](https://docs.langchain.com/oss/javascript/deepagents/going-to-production)。

各组件的具体适配方案，完全围绕产品设计的核心链路展开：

#### 2.2.1 Langchain：应用框架与 AI 能力核心支撑

作为整个 AI 能力的基础支撑框架，Langchain 将在上层产品设计与底层模型能力之间，提供标准化的复用接口，保障产品设计的核心效果稳定落地。在本次方案中，Langchain 的核心适配价值集中在三个维度，完全覆盖产品设计的核心 AI 功能需求：



* **模型封装能力**：为 AI 情绪识别、梦境摘要、文生图、个性化安抚文案生成等核心场景提供标准化模型调用接口；

* **Prompt 工程优化**：对所有 AI 交互的提示词（如情绪解读、反馈文案）做统一封装、版本化管理，保障不同用户、不同使用场景下的输出风格与产品视觉体验完全匹配；

* **输出解析与校验**：将 AI 输出的结果解析为结构化数据，便于前端渲染展示；同时增加合规性校验逻辑，对不符合产品情绪风格的结果进行过滤、重试，保障体验的一致性[(57)](https://docs.langchain.com/oss/javascript/deepagents/going-to-production)。

#### 2.2.2 Langgraph：核心链路流编排与状态管理

Langgraph 是 Langchain 生态中分布式能力最强的组件，为用户的核心链路提供工作流编排与唯一状态源支撑 —— 这是实现产品设计「记录 - 情绪识别 - 反馈 - 回顾」闭环体验的技术基础，也是保障多用户、高并发场景下数据一致性的关键支撑[(58)](https://blog.csdn.net/hiwangwenbing/article/details/161487080)。

其适配产品设计的核心逻辑，是将梦境记录的完整流程，抽象为一个有向图结构进行模块化编排：



* **节点（Node）** ：将用户从 “新建记录” 到 “数据存储” 的完整操作链路，拆分为语音转写、文本优化、情绪识别、标签提取、图像生成、反馈文案生成六个独立任务节点；

* **边（Edge）** ：按照产品设计的情绪体验逻辑，定义六个任务节点的执行顺序；

* **状态（State）** ：以用户操作会话为维度，定义贯穿整个流程的全局唯一状态，作为数据同步的唯一事实源；

* **检查点（Checkpointer）** ：把每个任务节点的执行进度、处理结果，持久化到外部共享存储中，确保任务不丢失、数据不混乱、用户间互不干扰[(63)](https://juejin.cn/post/7537879474639896617)。

该工作流的核心技术价值，是通过状态管理机制，保障多用户、高并发场景下的数据隔离性：每个用户的流程状态都通过用户 ID 与所属租户进行严格标记，不同用户的工作流之间完全隔离、互不干扰 —— 从技术设计上，避免了不同用户的数据、状态出现串读、乱读的问题[(58)](https://blog.csdn.net/hiwangwenbing/article/details/161487080)。

#### 2.2.3 Langsmith：测试、调试与 AI 效果优化

Langsmith 是本次设计方案中 AI 应用的全流程监控与调试支撑平台，也是保障 AI 情绪反馈效果匹配产品设计标准的核心技术抓手。从竞赛维度看，它既能保障技术层 AI 输出的稳定性，又能支撑产品层持续优化核心情绪体验 —— 同时覆盖技术与产品的双向评分要求[(46)](https://blog.csdn.net/Rainsirius/article/details/154791534)。

Langsmith 的适配逻辑，完全围绕优化 AI 情绪体验的目标展开，核心覆盖三大维度：



* **Prompt 迭代优化**：AI 情绪解读、安抚文案、文生图的效果，决定了产品情绪体验的质感，而 Langsmith 的核心能力之一，是支持在不修改业务代码的情况下，对 prompt 进行版本管理与 A/B 测试 —— 这恰好满足了优化 AI 输出风格的核心需求；

* **AI 工作流性能监控**：Langsmith 可以全程监控 Langgraph 编排的每个任务节点的执行成功率、耗时、模型输出质量，快速定位异常节点并配置告警规则 —— 这为竞赛现场演示的稳定性提供了技术保障；

* **输出质量分析与优化**：通过收集、分析用户对 AI 结果的反馈数据，可以快速调整 prompt 策略、优化情绪识别的精准度，让 AI 输出风格与产品情绪体验的匹配度持续提升[(20)](https://juejin.cn/post/7631040435458261038)。

此外，Langsmith 支持多租户隔离与集中化用户权限管理，完全匹配多用户场景下的数据安全隔离要求。

### 2.3 数据持久化与同步层

为满足「数据持久化、多用户数据隔离」两大赛题硬性要求，本次方案采用「MongoDB Atlas+LangGraph 官方数据持久化能力」的成熟技术组合，作为数据支撑层 —— 这是 Langchain 生态的官方推荐搭配，从技术上预先规避了数据不兼容、同步不稳定的风险[(22)](https://blog.langchain.com/announcing-the-langchain-mongodb-partnership-the-ai-agent-stack-that-runs-on-the-database-you-already-trust/)。

该方案的核心适配逻辑，是通过不同组件的分层协同，分别匹配产品设计对 “数据持久化”“数据隔离” 的不同要求，在保障数据可靠性的前提下，实现与上层技术栈的无缝适配：



* **数据持久化**：利用 LangGraph 官方的 Checkpointer 机制，将用户的所有操作状态（如梦境记录的临时存储、AI 处理中间结果）、梦境全量数据，以用户 ID 为分区键，持久化到 MongoDB Atlas 的共享存储集群中；

* **数据同步**：通过 LangGraph 的分布式状态共享能力，实现用户数据在多端、多节点之间的实时同步；

* **数据隔离**：采用 Langchain 官方生产级方案中的「多租户隔离」设计逻辑，在数据写入时，将用户 ID 与数据绑定作为属主元数据；在用户读取数据时，后端数据查询过滤器自动根据当前用户的属主元数据做匹配筛选 —— 这一方案天然满足 “不同用户、不同会话间数据隔离” 的硬性要求[(57)](https://docs.langchain.com/oss/javascript/deepagents/going-to-production)。

### 2.4 后端管理与集成

本次方案采用「Node.js+Express」作为后端基础服务框架，原因是该技术栈与 Langchain 生态的适配性成熟度最高，且对 Flutter 跨平台框架的支撑性足够完善，能在短周期内完成高可用接口的开发与联调，完全满足现场演示对稳定性的要求[(57)](https://docs.langchain.com/oss/javascript/deepagents/going-to-production)。

后端服务的核心适配价值，是提供标准化的能力支撑接口，将上层技术栈的能力统一封装，供前端调用，核心覆盖三大维度：



* **AI 能力接口**：对前端提供梦境记录、情绪识别、统计分析的标准化 API，完全覆盖 Flutter 前端的业务场景调用需求；

* **用户会话管理**：提供注册、登录、会话校验等基础接口，实现用户系统的基础对接；

* **数据管理能力**：提供梦境数据的增删改查、同步备份接口，支撑前端的所有数据操作场景。

同时，方案采用 Langchain 生态官方推荐的「Bearer Token」身份认证机制，所有的 API 请求、用户资源访问都必须携带合法的身份令牌，确保接口级的用户数据隔离安全 —— 从技术上，保障了多用户场景下的数据隐私安全。

功能设计的核心目标，是在满足 “至少一种非文本录入方式” 必做项的基础上，匹配用户晨起、睡前的 “半梦半醒” 使用场景 —— 核心是降低记录门槛，让用户在记忆模糊时也能快速、完整地记录梦境细节。本次采用「语音录入 + 文本编辑」的成熟组合方案，是经过市场验证的、适配梦境记录场景的最优选择[(9)](https://m.duote.com/ios/480517.html)。

#### 3.1.1 核心录入流程

整个记录流程被设计为 3 步闭环，完全贴合用户在梦境记录场景下的核心诉求，是经过市场验证的成熟逻辑：



1. **Step1：选择录入方式**：用户在应用首页点击「记录梦境」按钮后，可在弹出的操作菜单中，自主选择语音录入、文本录入两种模式 —— 按钮布局位置、操作区域大小，均参考了主流应用的 “单手操作舒适区” 设计；

2. **Step2：内容补充与 AI 优化**：语音录入完成后，应用自动将语音转成文字内容，用户可对转写结果进行二次编辑修正；AI 能力会自动对梦境内容进行精简摘要、提取关键标签、识别情绪基调、生成匹配的初步情绪标签；

3. **Step3：保存与可视化生成**：用户完成编辑后点击「保存」按钮，AI 会根据梦境的文字描述、情绪基调，自动生成匹配的意境图片；随后，系统将梦境所有相关内容（文字、图片、情绪标签等），同步存储到后端数据库，并自动跳转至梦境详情页。

#### 3.1.2 语音录入适配设计

该功能是本次设计的核心非文本录入方式，完全参考了 Dreamoo 与 My Dream Chronicle 的成熟功能逻辑，适配用户 “半梦半醒” 的核心使用场景 —— 设计目标是，让用户在不想打字、记忆模糊时，也能通过语音快速完整记录梦境细节，不错过任何转瞬即逝的梦境片段[(9)](https://m.duote.com/ios/480517.html)。

功能的交互与技术适配逻辑，完全围绕场景体验优化展开，提前规避了演示级的技术风险：



* **交互适配逻辑**：录入页面采用大尺寸按钮设计，适配用户晨起、睡前的触控操作；按钮提供 “录制中” 的动态视觉反馈，让用户清晰感知录制状态；

* **技术适配逻辑**：调用浏览器自带的原生语音识别能力，实现语音转文字的实时转写；在转写过程中，自动过滤无意义的语气词、停顿，优化转写内容的可读性；

* **场景适配逻辑**：支持后台录制功能 —— 即使用户关闭屏幕，录制仍在继续，避免了因设备屏幕亮度变化、误触屏幕导致记录中断的问题；

* **体验增强设计**：提供「白噪音陪伴」开关选项，用户在记录梦境时，可选择伴随轻量、舒缓的白噪音（如雨声、林间风声、夏夜虫鸣等），进一步强化沉浸感，平复情绪。

#### 3.1.3 文本录入适配设计

该功能是本次设计的补充录入方式，适配用户希望完整记录梦境细节的场景 —— 其交互设计逻辑，完全参考了成熟产品的梦境记录框，符合用户的常规记录习惯[(79)](https://m.wandoujia.com/apps/8432827/history_v10500)。

* **引导式录入交互**：提供「标题 + 正文」的结构化录入布局，正文区域默认展示 “梦中最让你印象深刻的画面是什么？”“你在梦中的情绪是怎样的？” 这类引导式问题，降低用户的记录成本；

* **AI 辅助优化能力**：在用户输入梦境内容后，AI 能力会自动对内容进行精简摘要，提取梦境中的关键场景、人物、事件，生成高频标签，方便后续的梦境分类、检索管理；

为进一步强化 “轻量化记录” 的产品优势，本次方案在核心录入方式之外，增加了图片上传、手绘涂鸦两种备选录入方式 —— 用户可根据实际需求，自主选择添加手绘草稿、实景照片，或者用涂鸦工具快速勾勒梦境里的场景、人物，让梦境记录更生动、更具纪念意义[(9)](https://m.duote.com/ios/480517.html)。

### 3.3 数据持久化与多用户数据隔离设计

该模块是支撑所有上层产品功能的技术保障层，设计方案完全匹配赛题对数据持久化、多用户数据隔离的双重必做项要求 —— 采用与 Langchain 生态完全适配的成熟技术方案，提前规避了功能级的演示风险。

#### 3.3.1 数据持久化适配设计

采用 Langchain 生态官方推荐的「MongoDB Atlas+LangGraph Persistence Layer」技术方案，保障所有用户数据、操作状态的可靠持久化 —— 这是经过大量企业级场景验证的成熟方案，完全满足现场演示对数据稳定性的要求[(22)](https://blog.langchain.com/announcing-the-langchain-mongodb-partnership-the-ai-agent-stack-that-runs-on-the-database-you-already-trust/)。

方案的适配逻辑，是通过分层存储设计，保障数据的完整性与读取效率：



* **全量数据存储**：将用户的梦境记录、标签、情绪等核心业务数据，以用户 ID 为分区键，统一持久化到 MongoDB Atlas 中，实现数据的可靠存储；

* **操作状态存储**：利用 LangGraph 的 Checkpointer 机制，将用户在 AI 工作流中的操作状态、中间处理结果（如语音转写的临时文本、AI 生成的待确认情绪标签），实时保存到外部共享存储中，确保任务不丢失、数据不混乱；

* **本地缓存适配**：在浏览器端采用 IndexedDB 作为本地缓存，存储用户最近的梦境记录、情绪标签等常用数据，提升用户的页面访问速度；

* **数据备份机制**：在 MongoDB Atlas 中设置定时自动备份策略，确保数据可恢复，进一步保障演示场景下的数据可靠性。

#### 3.3.2 多用户数据隔离适配设计

采用 Langchain 官方生产级方案中的「多租户隔离」设计逻辑，从技术上实现不同用户、不同会话间的数据严格隔离 —— 这是经过企业级场景验证的成熟方案，完全满足现场演示对数据安全性的要求[(57)](https://docs.langchain.com/oss/javascript/deepagents/going-to-production)。

方案的适配逻辑，是在数据读写的全链路中，加入用户身份、资源权限的校验逻辑，从技术设计上避免了用户数据串读、乱读的风险：



* **用户标识体系**：使用 Langgraph 的跨线程持久化能力，在用户登录后，生成全局唯一的用户 ID 与会话 ID，作为区分用户、会话的唯一标识；

* **数据隔离规则**：在数据写入时，将用户 ID 与所属租户信息，作为属主元数据标记到所有数据上；在用户读取数据时，后端数据查询过滤器自动根据当前用户的属主元数据做匹配筛选 —— 不同用户的资源在逻辑上完全隔离，互不干扰；

* **会话隔离规则**：使用 LangGraph 的线程 ID 管理能力，区分同一用户的不同会话场景；

* **访问权限控制**：采用 Langchain 的授权处理器，对每一次资源访问请求进行身份与权限校验，确保用户只能访问自己所属租户、自己拥有的资源；

* **技术验证保障**：Langsmith 平台的监控能力，全程对所有用户的数据访问、操作调用进行链路追踪，便于快速发现、排查异常情况。

#### 3.3.3 数据同步适配设计

采用「LangGraph 分布式状态共享 + MongoDB Atlas 全局数据同步」的技术方案，保障用户数据在多端、多场景的实时同步 —— 这是与 Langchain 生态适配的成熟方案，完全满足现场演示对数据一致性的要求[(58)](https://blog.csdn.net/hiwangwenbing/article/details/161487080)。

方案的适配逻辑，是通过技术架构，将用户数据的同步过程对上层业务完全透明化，保障用户在多端、多场景下的数据体验一致性：



* **多端同步能力**：通过 LangGraph 的 Checkpointer 机制，将用户的操作状态、梦境数据实时同步到 MongoDB Atlas 中，同一用户在不同设备、不同浏览器上的所有数据，都能实时保持一致；

* **读写分离适配**：技术架构上，采用读写分离的设计逻辑，以应对用户在不同场景下的数据访问流量，保障数据同步的效率；

* **冲突解决机制**：在用户数据发生版本冲突时，自动以最后一次修改时间为基准进行覆盖合并，解决多端数据冲突的问题；

* **异常重试机制**：在数据同步出现网络异常时，自动重试同步请求；如果重试失败，将数据临时存储到本地，待网络恢复后再自动同步，避免数据丢失。

该模块是满足 “情绪关联” 必做项的基础能力支撑，也是区别于普通梦境工具的**产品核心竞争力加分项**—— 设计目标是，通过 AI 技术与产品交互设计的联动，实现从 “识别用户情绪” 到 “承接用户情绪” 再到 “反馈用户情绪” 的闭环体验，让用户的情绪从被记录到被看见，再到被安放。

这是情绪关联系统的基础能力支撑，设计逻辑采用「用户手动标记 + AI 自动识别」的成熟组合方案 —— 既覆盖了 “情绪关联” 的必做项要求，又为后续的情绪反馈提供了精准的底层数据支撑[(9)](https://m.duote.com/ios/480517.html)。

方案的适配设计逻辑，完全围绕提升情绪识别精准度的目标展开：



* **手动标记交互设计**：用户在记录梦境、编辑梦境的环节，可在预设的情绪列表中一键勾选匹配的情绪标签；应用提供 “情绪轮盘” 选择交互，用户可在记录梦境后，主动调整情绪标签，确保情绪数据的精准度；

* **AI 自动识别技术设计**：利用 Langchain 封装的大模型能力，对用户的梦境文本进行情感分析、关键词提取，自动识别梦境内容的情绪基调，推荐匹配的情绪标签；

* **情绪数据可视化设计**：将识别出的情绪基调，以不同色彩的圆点标记在日历对应日期的单元格上，让用户在日历视图上就能直观掌握当天的梦境情绪概况；

* **识别结果存储设计**：将情绪识别的结果，与梦境数据关联存储到数据库中，作为后续情绪统计、AI 情绪反馈的基础数据支撑。

#### 3.4.2 AI 情绪反馈适配设计

这是实现产品 “安放情绪” 核心目标的关键能力支撑，决定了产品情绪体验的质感 —— 设计逻辑完全围绕「承接用户情绪」的核心目标展开，通过 AI 技术与产品交互设计的联动，给用户提供情绪价值的深度反馈。

方案的适配设计逻辑，完全匹配用户的情绪基调，形成 “记录梦境 - 识别情绪 - 反馈体验 - 承接情绪” 的闭环体验：



* **反馈内容生成逻辑**：基于 AI 识别的情绪结果，由 Langgraph 编排的工作流，调用 Langchain 封装的大模型生成三类个性化内容：


  * 梦境解读内容：基于梦境的文本内容、情绪基调，生成采用非专业术语的通俗化解读内容，重点给出缓解焦虑、改善睡眠的实用心理建议；

  * 意境视觉内容：根据梦境的文字描述、情绪基调，生成匹配的意境图片，将用户的抽象梦境、看不见的情绪转化为可视化的内容；

  * 情绪陪伴内容：根据梦境的情绪基调，生成匹配的安抚文案、轻量音效建议 —— 比如，针对噩梦，给出 “这只是一个普通的梦，现实中你很安全” 这类具有安抚效果的文案，搭配轻柔、舒缓的音乐建议；

* **反馈体验适配逻辑**：在用户保存梦境、跳转至详情页的过程中，采用与情绪基调匹配的动态加载动效；内容生成的整个过程，对用户完全透明，无任何突兀感；

* **异常降级设计**：如果 AI 服务在演示现场出现异常，系统会自动展示预设的通用安抚文案，避免因技术问题导致情绪体验闭环中断。

#### 3.4.3 情绪可视化与统计适配设计

这是情绪关联系统的补充能力支撑，帮助用户长期直观追踪自己的情绪变化 —— 设计逻辑完全参考了成熟产品的同类方案，让用户能够直观感知自己的潜意识情绪变化规律[(9)](https://m.duote.com/ios/480517.html)。

方案的适配设计逻辑，完全围绕 “直观感知” 的目标展开：



* **情绪趋势统计能力**：提供「情绪统计」专属页面，以折线图、饼图的形式，展示用户近 7 天、近 30 天的梦境情绪分布比例、波动变化，直观呈现用户的情绪变化规律；

* **梦境符号可视化能力**：基于 AI 提取的梦境关键词、主题，生成词云或相关标签云，直观展示用户梦境的高频元素、常见主题；

* **日历视图联动能力**：在日历视图中，点击情绪图例，可筛选出对应情绪的所有梦境记录，直观展示情绪与梦境内容的对应关系；

* **视觉体验强化逻辑**：所有统计图表的配色，都与对应情绪标签的色调保持完全一致，让用户在浏览统计数据时，视觉体验保持连贯统一。

#### 3.4.4 情绪陪伴氛围适配设计

这是情绪关联系统的隐性核心加分项，决定了产品情绪体验的质感 —— 设计逻辑完全围绕「安放情绪」的核心目标展开，通过视觉、听觉的多维度联动，强化与用户梦境情绪的共鸣感，让用户在专属私密的场景中，慢慢沉淀、梳理自己的情绪。

方案的适配设计逻辑，完全匹配用户的情绪基调：



* **全局视觉氛围适配逻辑**：应用根据用户的梦境情绪、系统时间，自动切换对应的主题壁纸 —— 比如，夜间记录梦境时，默认采用深色模式、暗色调星空背景；回顾愉悦类梦境时，自动切换为暖色调、星光渐变背景；

* **全局听觉氛围适配逻辑**：提供「白噪音」专属设置面板，用户可选择伴随类的轻量循环背景音效（如雨声、林间风声、夏夜虫鸣等），音效可以在用户翻阅梦境、查看详情时自动播放；

* **交互动效氛围适配逻辑**：在用户完成保存梦境、切换日历视图、翻页查看梦境详情的操作时，提供与当前情绪基调匹配的微动效；

* **场景化细节适配逻辑**：参考 My Dream Chronicle 的设计，在无数据的空白状态下，展示与整体风格统一的温馨插画，避免用户面对空白界面产生茫然情绪。

### 3.5 其他交互设计：保障演示级鲁棒性与边界处理

该模块是支撑所有上层产品功能的补充层，也是竞赛评分维度中「鲁棒性和边界处理」的核心支撑项。设计上重点处理用户可能出现的各种异常操作、输入边界情况，保证核心流程的交互完整性，确保演示过程中不出现崩溃、死锁、无响应等问题[(79)](https://m.wandoujia.com/apps/8432827/history_v10500)。

#### 3.5.1 空状态处理适配设计

针对用户无梦境记录、网络异常、AI 服务异常等场景，设计了专属的空状态落地页，提供场景化的引导文案、解决建议，而不是直接粗暴地显示 “系统异常”“暂无数据” 的提示，避免让用户产生操作挫败感[(79)](https://m.wandoujia.com/apps/8432827/history_v10500)。

以 “无历史记录” 场景为例，空状态页面将展示产品 IP 的温馨插画，搭配 “快点击底部的加号，记录你的第一个梦境吧～” 的引导性文案，让用户明确下一步的操作方向。

#### 3.5.2 输入边界处理适配设计

针对用户可能出现的超长文本、特殊字符、连续快速点击、重复提交等异常操作，做了针对性的拦截、校验与提示处理，避免功能异常、数据重复提交，保证核心流程的交互完整性[(79)](https://m.wandoujia.com/apps/8432827/history_v10500)。

方案的核心处理逻辑如下：



* **超长文本处理**：在用户输入文本内容时，实时统计字符数量，在接近上限时，主动给出 “您的输入内容已接近字符上限，建议您分段记录” 的温馨提示；

* **特殊字符处理**：对用户输入的内容进行合规性校验，对系统无法处理的特殊字符进行自动过滤或转义，避免引发系统异常；

* **重复提交处理**：在用户点击「保存」按钮后，立即将按钮置灰、防止重复点击，并显示 “保存中...” 的加载状态；

* **内容丢失预防处理**：在用户编辑梦境的过程中，应用将每隔一定时间自动备份草稿到本地存储中，避免因突发网络中断、页面关闭导致内容丢失。

#### 3.5.3 网络 / 系统异常处理适配设计

针对网络切换、网络中断、AI 服务异常等可能影响演示效果的场景，设计了友好的落地提示页与异常恢复机制，避免功能崩溃、阻塞核心流程，确保演示过程无不可逆故障发生[(79)](https://m.wandoujia.com/apps/8432827/history_v10500)。

方案的核心处理逻辑如下：



* **网络异常处理**：如果用户的网络连接出现异常，应用将自动切换到「本地模式」，允许用户继续记录、查阅本地已有的梦境数据；在网络恢复后，自动将本地离线数据同步到服务器，保证数据不丢失；

* **服务异常处理**：如果后端 AI 服务在演示现场出现异常，应用将自动降级为 “基础记录模式”，关闭 AI 相关功能，保留核心的记录、日历查阅功能；

* **全局异常捕获处理**：对所有的接口调用、用户操作增加了异常捕获机制，在出现异常后，自动尝试恢复或引导用户回到安全的操作路径；

* **异常信息反馈设计**：对于不可恢复的异常，将展示 “遇到了一点小问题，请稍后再试” 的温馨提示，而非直接显示技术报错信息。

#### 3.5.4 演示场景适配优化设计

为了进一步保障评审现场的演示稳定性，方案专门设计了专属的演示落地优化逻辑，提前规避可能影响演示效果的潜在问题[(79)](https://m.wandoujia.com/apps/8432827/history_v10500)。

方案的核心演示适配逻辑如下：



* **演示数据预置**：在演示版本中，提前预置了多条不同情绪、不同类型的完整梦境记录，覆盖所有功能的演示场景；

* **性能专项优化**：对核心的梦境记录、日历切换、详情加载流程进行了专项性能优化；

* **多预案准备**：提前准备了离线、在线两种演示环境适配方案，两种方案的功能体验完全一致；

* **演示操作路径规划**：梳理了 “快速记录→日历查看→梦境详情→情绪统计→离线模式” 的标准演示操作路径，整个演示流程不超过 3 分钟，覆盖所有必做功能与加分亮点。

## 4. 产品 UI/UX 设计细节

本次设计的 UI/UX 细节，完全基于「情绪承接」的产品核心目标，参考 Dreamoo、My Dream Chronicle 的成熟视觉与交互设计风格 —— 在短周期内，实现成熟产品级的体验效果，同时保证技术落地的可行性、演示的稳定性。

### 4.1 设计风格语言

采用**暗夜静谧风格 + 拟物化设计**的成熟组合方案，与头部梦境产品保持一致，强化产品的 “梦境、情绪” 主题调性 —— 核心是通过视觉、听觉的多维度联动，营造出私密、放松的使用氛围，完美适配用户枕边使用、记录内心私密梦境的场景。

#### 4.1.1 色彩体系设计

色彩是情绪类产品的核心视觉传递元素，本次设计的色彩方案，完全参考了成熟产品的睡眠 / 梦境类应用的色彩逻辑，主打深色模式适配夜间场景，用低饱和度的色彩，精准传递 “静谧、神秘、放松” 的产品核心感知。

方案的核心色彩逻辑如下：



* **主色调**：选择深邃的靛蓝色（#0F172A）作为主色调，象征梦境的神秘与无限可能 —— 这是睡眠、梦境类产品的首选主色调，不会对用户的夜间视觉产生强光刺激；

* **辅助色**：用紫色（#8B5CF6）、蓝绿色（#06B6D4）作为辅助色，用于重要信息操作按钮、核心交互元素的视觉强化；

* **情绪色**：用不同的色彩，直观标记不同的情绪基调，让用户在日历视图、梦境卡片上快速区分梦境的情绪基调；

* **中性色**：采用深灰、浅灰、白色作为文本、背景、分割线的中性色，保障内容的可读性，同时强化视觉层次感[(75)](https://blog.csdn.net/woshihuanglaoshi/article/details/159998131)。

#### 4.1.2 字体体系设计

采用**系统无衬线字体**的成熟选择方案，目的是保证在不同平台、不同设备上的显示一致性，避免因字体兼容问题导致的视觉布局异常 —— 这是保障演示效果的基础要求，能有效提升梦境内容的可读性。

方案的核心字体逻辑如下：



* **中文字体**：优先采用系统默认的中文字体；

* **英文 / 数字字体**：优先采用系统默认的无衬线英文字体；

* **字体层级设计**：为了保障用户在夜间场景下的阅读舒适度，所有字体颜色与背景色的对比度，都达到了 WCAG 无障碍阅读标准；

* **字体应用规则**：采用清晰的字体层级布局，让整个内容的视觉层级关系一目了然[(75)](https://blog.csdn.net/woshihuanglaoshi/article/details/159998131)。

#### 4.1.3 图标与意象化元素设计

采用**线性图标 + 意象化元素**的组合方案，风格与产品整体视觉效果保持完全一致 —— 通过意象化的视觉元素，强化产品的 “梦境、情绪” 主题调性，更好地传递产品的核心特质。

方案的核心元素设计逻辑如下：



* **图标体系**：采用线性风格的图标设计，核心功能图标采用拟物化设计；

* **意象化元素**：采用月亮、星云、星星、萤火虫、气流等梦境相关的意象化视觉元素，作为页面的背景装饰、细节点缀；

* **IP 形象设计**：设计了一个轻盈、漂浮状的星云形态的 IP 形象，作为产品与用户之间情绪沟通的视觉锚点；

* **视觉强化设计**：在重要的功能区域、可交互操作区域，加入了轻微的流动渐变、阴影变化效果，区分页面的不同功能层级，强化视觉层次感[(75)](https://blog.csdn.net/woshihuanglaoshi/article/details/159998131)。

### 4.2 核心应用交互体验设计

本次设计的交互细节，完全参考成熟产品的梦境记录、日历查阅、情绪反馈逻辑 —— 所有交互动效的设计目的，都是为了强化用户的沉浸式体验感，让用户在不知不觉中完成操作、感受情绪承接。

#### 4.2.1 导航与路由交互设计

采用**底部标签导航 + 路由堆栈**的成熟组合方案，适配移动端、桌面端的不同使用场景 —— 这是用户移动应用的主流导航设计模式，符合大多数用户的使用习惯。

方案的核心导航交互逻辑如下：



* **导航布局设计**：在移动端，底部设置标签导航栏，放置「记录」「日历」「统计」「我的」4 个一级功能入口；在桌面端，采用侧边栏导航的适配形式；

* **路由交互设计**：采用符合用户直觉的路由交互逻辑；

* **场景适配设计**：在桌面端，支持用快捷键操作来快速提交、保存、切换梦境内容；

* **微交互设计**：对所有的可交互元素，都增加了适配情绪基调的微交互动效，让用户的操作反馈更直观，提升交互质感[(77)](https://ftium4.com/ux-weekly-245.html)。

#### 4.2.2 梦境记录流程交互设计

这是产品的**核心体验入口**，设计目标是让用户在半梦半醒、记忆模糊的状态下，能快速完成记录操作 —— 交互逻辑完全围绕 “轻量化记录、不打扰用户” 的核心原则展开，让用户以最少的认知负担，完成整个记录流程。

方案的核心记录流程交互逻辑如下：



* **记录入口设计**：在首页底部，设置一个直径足够大的、呈发光状态的「+」按钮，作为新建梦境记录的入口；

* **录入方式选择交互**：用户点击「+」按钮后，弹出录入方式选择的底部操作菜单，提供 “语音录入”“文本录入” 两个选项，菜单的弹出动效，与整体情绪氛围保持协调；

* **语音录入交互**：用户选择「语音录入」后，自动进入录音准备状态，录入页面的背景将实时显示情绪相关的动态壁纸；

* **文本录入交互**：用户选择「文本录入」后，跳转至新建梦境页面，正文区域默认展示引导式问题，让用户明确记录方向；

* **优化与编辑交互**：用户在完成语音或文本录入后，可在编辑页面对内容进行二次编辑修正；AI 摘要、提取的关键词、情绪标签将以可视化标签的形式，呈现在文本框的上方，用户可直接点击修改；

* **保存与反馈交互**：用户点击「保存」按钮后，按钮会显示 “保存中...” 的加载状态，直到 AI 处理完成、数据完全写入后端存储，才跳转至梦境详情页；

* **场景适配优化**：用户在记录过程中，屏幕不会自动锁屏，避免因屏幕关闭导致记录中断[(9)](https://m.duote.com/ios/480517.html)。

#### 4.2.3 日历视图与梦境列表交互设计

这是产品的**核心管理入口**，设计目标是让用户快速定位、回忆历史梦境细节 —— 交互逻辑完全遵循成熟产品的用户交互习惯，降低用户的使用学习成本。

方案的核心日历视图交互逻辑如下：



* **视图布局设计**：日历视图默认以月度视图模式展示，占据页面的上半区域，日历的每个日期单元格都采用了足够高的对比度；

* **日期标记交互**：有梦境记录的日期单元格，下方会显示不同色彩的小圆点，直观标记当天梦境的情绪基调；

* **梦境列表展示交互**：用户点击对应日期后，日历下方会自动展开当天的梦境摘要列表；

* **梦境卡片交互设计**：梦境卡片采用 “左对齐文字 + 右对齐情绪指示器” 的布局设计，卡片本身有阴影效果、有明显的 “可点击” 视觉暗示；

* **列表跳转交互**：用户点击梦境卡片后，页面将以拟物化翻页的动效切换方式，展示梦境的完整内容；

* **日历切换交互**：用户可通过点击日历的「上一月」「下一月」按钮，或左右滑动手势，切换日历的月份；

* **数据加载优化**：日历视图的所有梦境数据，都采用异步懒加载的策略，优先加载当前可视区域的内容，保证页面的响应速度[(75)](https://blog.csdn.net/woshihuanglaoshi/article/details/159998131)。

#### 4.2.4 梦境详情页交互设计

这是产品的**核心情绪落地入口**，设计目标是让用户沉浸式回顾梦境、承接情绪 —— 交互逻辑完全围绕「强化情绪共鸣」的目标展开，通过视觉、听觉的多维度联动，让用户在专属私密的场景中，慢慢沉淀、梳理自己的情绪。

方案的核心详情页交互逻辑如下：



* **内容布局设计**：采用「配图 + 正文 + 解读 + 统计」的区块布局，视觉重心先放在 AI 生成的意境配图上，图片会根据用户的滚动进度，产生 parallax 滚动视差效果；

* **氛围适配交互**：详情页的背景壁纸、音效、主题色，会自动与当前梦境的情绪基调匹配；

* **正文阅读交互**：梦境的正文内容采用 “行高≥1.5 倍” 的舒适阅读排版，用户在阅读正文时，屏幕不会自动锁屏；

* **解读内容展示交互**：用户在阅读完正文内容后，向下滑动页面，AI 生成的解读内容会逐步过渡到用户视野中；

* **操作交互设计**：在详情页的底部，设置「删除」「编辑」「分享」功能按钮，按钮的排列方式符合用户单手操作的舒适区；

* **跳转交互设计**：用户点击「返回」按钮后，页面将以翻页回退的动效，切换回日历视图页面；

* **场景适配优化**：如果用户在详情页停留超过一定时间无任何操作，应用将自动调低屏幕亮度，降低眼部疲劳感[(9)](https://m.duote.com/ios/480517.html)。

#### 4.2.5 情绪统计与可视化交互设计

这是产品的**核心长期留存入口**，设计目标是让用户直观感知自己的情绪变化规律 —— 交互逻辑完全遵循成熟产品的数据分析可视化方案，降低用户的认知成本。

方案的核心情绪统计交互逻辑如下：



* **布局设计**：情绪统计页面采用「情绪分布饼图 + 情绪趋势折线图 + 梦境关键词词云」的组合布局，所有图表的配色，都与对应情绪标签的色调保持完全一致；

* **饼图交互**：用户点击饼图中的某个情绪板块，下方的折线图将自动筛选出该情绪的月度变化曲线，同时展示对应情绪的所有梦境记录列表；

* **折线图交互**：用户移动光标到折线图的某个节点上，将弹出浮层显示当天的梦境记录详情、情绪波动值；

* **词云交互**：用户点击词云中的某个关键词，将自动筛选出包含该关键词的所有梦境记录列表；

* **日历联动交互**：用户在统计页面点击某个情绪图例，日历视图将自动同步筛选并标注出对应情绪的所有梦境记录；

* **数据加载优化**：所有统计图表的数据，都采用异步懒加载的策略，优先加载用户当前可视区域的内容，保证页面响应速度[(75)](https://blog.csdn.net/woshihuanglaoshi/article/details/159998131)。

#### 4.2.6 核心场景动效设计

为了强化产品的 “梦境、情绪” 主题调性，提升用户的沉浸式体验感，本次设计在核心场景中，加入了**轻量化、符合情绪基调**的动效方案 —— 所有动效的设计原则，是为了更好地传递产品的情绪、更好地表达交互逻辑，而不是为了 “炫技” 而增加动效。

方案的核心动效设计逻辑如下：



* **加载动效**：采用与整体风格统一的、轻量化的加载动效，而不是通用的加载素材；

* **路由切换动效**：采用符合用户直觉的路由切换动效；

* **交互微动效**：对所有的可交互元素，都增加了适配情绪基调的微动效；

* **氛围动效**：在背景中加入了轻量化的、与情绪基调匹配的氛围动效；

* **图表动效**：情绪统计图表的加载、数据变化，采用轻量化的帧动画效果；

* **场景化动效**：在无梦境记录、网络异常的空状态下，加入了与整体风格统一的、轻量化的场景化动效；

* **动效开关适配**：考虑到演示场景下的性能需求，所有动效都提供了统一的关闭入口 —— 如果现场设备性能有限，可提前关闭所有动效，保证功能演示的稳定性[(77)](https://ftium4.com/ux-weekly-245.html)。

## 5. 技术架构落地与工程质量支撑方案

为保障产品设计效果的落地质量、现场演示的稳定性，技术架构方案需同时满足「支撑产品 UI/UX 效果」「多用户数据隔离」「高可用性能」三个核心要求，并且要在功能、性能、稳定性之间找到最佳的平衡 —— 这是技术赛道的核心评分项，也是支撑上层产品设计效果的基础保障。

### 5.1 前端架构设计

采用 Flutter 作为跨平台框架，保障多端体验一致性 —— 技术设计逻辑完全围绕「还原产品设计效果」的目标展开，在架构层面提前规避了影响演示效果的潜在问题。

#### 5.1.1 项目组织结构

采用**分层架构 + 模块化**的组合方案，按功能模块拆分组件，做到低耦合、高内聚 —— 这是为了适应个人参赛的短周期开发场景，提升代码的可维护性、功能复用性，降低联调成本。

方案的核心分层逻辑如下：



* **路由层**：采用 Flutter 的官方路由管理方案，统一管理所有页面的路由跳转逻辑，提供标准的路由跳转方法，实现路由堆栈的精准管理；

* **视图层**：按功能模块拆分组件，将页面拆分为多个独立的可复用小组件；

* **业务逻辑层**：将所有的业务逻辑、状态管理，统一抽离为独立的 Provider 状态管理，与视图层完全分离；

* **服务层**：封装所有的后端接口调用、AI 能力调用，对上层提供统一的标准化调用入口；

* **数据层**：封装所有的本地存储、数据同步逻辑，对上层提供统一的标准化数据操作入口；

* **资源层**：统一管理所有的图片、音频、动画资源，采用压缩、雪碧图等方式，降低资源体积，提升加载速度；

* **工具类层**：封装所有的通用工具方法，提供统一的加密 / 解密、日期格式化、日志打印、异常捕获处理方法；

* **适配层**：对不同平台、不同浏览器的兼容适配逻辑进行统一封装，保障多端体验一致性[(66)](https://blog.csdn.net/2501_93575716/article/details/155716708)。

#### 5.1.2 核心技术适配支撑

为了保障产品设计效果的高质量落地，对前端技术做了针对性的选型适配，核心围绕「还原产品设计效果」的目标，完全覆盖产品设计的所有交互、视觉需求。

方案的核心技术适配逻辑如下：



* **状态管理**：采用官方推荐的 Provider 模式，实现跨页面、跨组件的状态共享 —— 所有的用户数据、梦境状态，都通过 Provider 进行统一管理，确保数据的单向流传递；

* **路由管理**：采用官方推荐的 Router 组件，统一管理所有页面的路由跳转逻辑；

* **网络请求**：采用 Dio 作为网络请求库，封装所有的后端接口调用逻辑；

* **本地存储**：采用 Hive 作为本地存储库，封装所有的本地数据读写逻辑；

* **音频播放**：采用 Just\_Audio 作为音频播放库，封装所有的白噪音播放、录制逻辑；

* **动画渲染**：采用 Lottie 作为动效方案，轻量化实现所有核心场景动效；

* **图表渲染**：采用 FlChart 作为图表方案，轻量化实现情绪统计图表的所有效果；

* **AI 适配支撑**：采用 Flutter 的 WebView 组件，加载 AI 能力的官方应用地址，实现与 AI 能力的适配；

* **多端适配支撑**：采用 Flutter 的 MediaQuery 组件，封装所有的响应式布局适配逻辑，保障多端体验一致性[(66)](https://blog.csdn.net/2501_93575716/article/details/155716708)。

#### 5.1.3 性能专项优化支撑

为了保障现场演示的稳定性、交互操作的流畅性，对前端性能做了针对性的优化设计，在架构层面提前规避了可能影响演示效果的潜在问题。

方案的核心性能优化逻辑如下：



* **资源优化**：对所有的图片、音频、动画资源，采用压缩、格式转换的方式进行轻量化处理；

* **路由优化**：采用路由懒加载的方式，将不同路由对应的组件分割成不同的代码块，只有当路由被访问时，才会加载对应组件；

* **渲染优化**：采用 ListView 的 itemBuilder 按需创建子组件，配合 AutomaticKeepAliveClientMixin 缓存列表项的渲染状态，保证长列表滚动的流畅性；

* **状态管理优化**：将页面状态与全局状态进行分离，尽可能缩小状态管理的刷新范围，减少不必要的组件重渲染；

* **请求优化**：对所有的网络请求，采用节流、防抖、缓存复用的策略，减少无效的网络请求；

* **本地存储优化**：采用 Hive 作为本地存储方案，存储用户常用数据；

* **动画优化**：采用 Lottie 轻量化的矢量动画格式，减少对主线程的阻塞；

* **性能监控支撑**：在开发阶段，加入了性能监控面板，实时监测页面的加载时间、交互帧率、资源加载情况，便于快速定位、修复性能瓶颈[(66)](https://blog.csdn.net/2501_93575716/article/details/155716708)。

### 5.2 后端架构设计

采用 Langchain 生态技术栈，保障多用户场景下的数据安全、同步可靠 —— 技术设计逻辑完全围绕「支撑产品核心情绪体验」的目标展开，在架构层面提前规避了影响演示效果的潜在问题。

#### 5.2.1 项目组织结构

采用**分层架构 + 模块化**的组合方案，按功能模块拆分服务，做到低耦合、高内聚 —— 这是为了适配 Langchain 生态的技术特性，提升代码的可维护性、可测试性，降低联调成本。

方案的核心分层逻辑如下：



* **路由层**：采用 Express 的路由机制，统一管理所有的 API 接口，将不同功能的接口路由，拆分到独立的文件中；

* **控制器层**：封装所有的入参校验、响应数据格式化、返回结果统一处理逻辑，调用 service 层的业务逻辑；

* **业务逻辑层**：封装所有的核心业务逻辑，调用 DAO 层进行数据操作，编排 Langgraph 的 AI 工作流；

* **数据访问层（DAO）** ：封装所有的 MongoDB Atlas 数据操作、增删改查方法，对上层提供统一的标准化数据操作入口；

* **AI 服务层**：封装所有的 Langchain、Langgraph、Langsmith 的适配逻辑，对上层提供统一的标准化 AI 调用入口；

* **模型层**：定义所有的结构化数据模型、AI 交互输出模型，统一管理数据结构；

* **工具类层**：封装所有的通用工具方法，提供统一的加密 / 解密、日期处理、统一返回格式、异常处理方法；

* **配置层**：统一管理项目的所有配置变量，支持多环境配置；

* **适配层**：对不同的 AI 模型、不同的数据库版本，进行统一的适配逻辑封装，保障上层业务逻辑无感知适配[(57)](https://docs.langchain.com/oss/javascript/deepagents/going-to-production)。

#### 5.2.2 AI 工作流设计

这是实现「情绪承接」产品核心效果的技术骨架，采用 Langgraph 编排 AI 工作流，与上层业务逻辑完全解耦 —— 设计逻辑完全匹配产品的核心情绪体验链路，保障 AI 输出的稳定性、精准度。

方案的核心 AI 工作流编排逻辑如下：



* **工作流拆分**：将用户从「新建记录」到「数据存储」的完整工作流，拆分为语音转写、文本优化、情绪识别、标签提取、图像生成、反馈文案生成 6 个独立任务节点；

* **任务节点编排**：按照产品设计的情绪体验逻辑，定义六个任务节点的执行顺序；

* **状态管理设计**：使用 Langgraph 的 StateSchema，定义贯穿整个流程的全局唯一状态；

* **持久化设计**：使用 LangGraph 的 Checkpointer 机制，将每个任务节点的执行进度、处理结果，持久化到 MongoDB Atlas 中；

* **权限校验设计**：在工作流的每个任务节点开始执行前，进行用户身份、资源权限的校验；

* **异常处理设计**：在工作流的每个任务节点，增加了完善的异常捕获、降级处理逻辑；

* **监控与调试支撑**：将所有的工作流执行日志、模型输出结果，实时上报到 Langsmith 平台，便于后续的问题排查、prompt 迭代优化[(58)](https://blog.csdn.net/hiwangwenbing/article/details/161487080)。

#### 5.2.3 核心技术适配支撑

为了保障产品设计效果的高质量落地，对后端技术做了针对性的选型适配，核心围绕「保障多用户数据安全、AI 输出稳定」的目标，完全覆盖产品设计的所有情绪体验需求。

方案的核心技术适配逻辑如下：



* **Web 服务框架**：采用 Express 作为基础 Web 服务框架，采用 body-parser、cors 等中间件，统一处理跨域、请求解析、权限校验；

* **AI 能力适配**：采用 Langchain 封装所有的模型调用，Langgraph 编排所有的 AI 工作流，Langsmith 监控所有的 AI 输出；

* **数据库适配**：采用 Mongoose 作为 MongoDB 的 ODM 工具，封装所有的数据操作逻辑；

* **分布式状态共享适配**：采用 LangGraph 的 Checkpointer 机制，实现多节点、多进程的分布式状态共享；

* **安全适配**：采用 Helmet 隐藏后端技术信息，采用 Rate-Limit 中间件限制单 IP 的请求频次，使用 MongoDB 的严格校验机制，防止 SQL 注入攻击；

* **日志与监控适配**：采用 Winston 作为日志工具，统一记录所有的访问日志、AI 工作流执行日志、错误日志；

* **多环境适配**：配置开发、测试、演示三套环境，分别对应不同的数据库、AI 服务配置；

* **降级适配**：在配置中心，设置所有 AI 功能的总开关 —— 如果 AI 服务在演示现场出现异常，可一键关闭 AI 功能，保留核心的记录、日历查阅功能，确保演示流程不中断[(57)](https://docs.langchain.com/oss/javascript/deepagents/going-to-production)。

#### 5.2.4 性能专项优化支撑

为了保障现场演示的稳定性、多用户并发场景下的响应速度，对后端性能做了针对性的优化设计，在架构层面提前规避了可能影响演示效果的潜在问题。

方案的核心性能优化逻辑如下：



* **AI 工作流优化**：将六个任务节点的执行过程，调整为异步执行的模式，提前返回响应；

* **数据库优化**：为常用的数据库查询字段，设置合理的索引，优化查询速度；

* **分布式状态共享优化**：采用 Redis 作为缓存，将高频访问的用户数据、工作流状态，进行高频数据缓存复用；

* **并发优化**：设置合理的线程池大小，应对多用户的并发请求；

* **请求优化**：对所有的 API 接口，采用合并、缓存、复用的策略，减少无效的网络请求；

* **日志优化**：采用多级别、多维度日志配置，在生产级演示环境中，关闭 debug 级别的日志输出；

* **性能监控支撑**：在演示环境中，采用 Clinic.js 作为性能监控工具，实时监测 Node.js 的内存占用、CPU 负载、事件循环延迟，便于快速定位、修复性能瓶颈[(57)](https://docs.langchain.com/oss/javascript/deepagents/going-to-production)。

### 5.3 数据持久化方案设计

采用「MongoDB Atlas+LangGraph 官方数据持久化能力」的成熟技术组合，是 Langchain 生态的官方推荐搭配，满足赛题对数据持久化、多用户数据隔离的必做项要求 —— 设计逻辑完全围绕「保障数据安全、同步稳定」的目标展开，在架构层面提前规避了数据丢失、同步异常的潜在问题。

#### 5.3.1 核心存储介质选择

为了保障数据的可靠性、读取效率，对存储介质做了针对性的选型适配，完全覆盖产品设计的多场景数据需求。

方案的核心存储介质适配逻辑如下：



* **MongoDB Atlas**：作为主存储介质，存储所有的用户数据、梦境全量数据、AI 分析结果；

* **Redis**：作为缓存介质，存储用户的常用数据、AI 工作流状态、权限校验信息；

* **IndexedDB**：作为本地存储介质，存储用户的常用数据、离线操作记录；

* **Checkpointer 存储**：采用 MongoDB Atlas 作为 LangGraph Checkpointer 机制的持久化存储介质；

* **静态资源存储**：采用 MongoDB Atlas 的 Bucket 存储 AI 生成的图片、用户上传的附件，通过内网 CDN 提供访问服务，保证读取速度[(22)](https://blog.langchain.com/announcing-the-langchain-mongodb-partnership-the-ai-agent-stack-that-runs-on-the-database-you-already-trust/)。

#### 5.3.2 数据模型设计

为了保障数据的一致性、读取效率，对核心数据模型做了针对性的设计，完全覆盖产品设计的多场景数据需求。

方案的核心数据模型设计逻辑如下：



* **用户数据模型**：存储用户的基本信息，以用户 ID 为唯一标识，记录用户名、加密后的密码、情绪偏好、设置信息等；

* **梦境数据模型**：存储所有的梦境记录，以用户 ID + 梦境 ID 为联合唯一标识，记录梦境的标题、正文、情绪标签、AI 生成的配图、解读文案、记录时间等；

* **标签数据模型**：存储所有的用户自定义标签，以用户 ID + 标签 ID 为联合唯一标识，记录标签的名称、类型、使用次数等；

* **情绪统计数据模型**：存储所有的情绪统计结果，以用户 ID + 统计日期为联合唯一标识，记录每天的情绪分布、波动变化、高频标签等；

* **AI 工作流状态模型**：存储 LangGraph 编排的 AI 工作流状态，以用户 ID + 会话 ID + 节点 ID 为联合唯一标识，记录每个任务节点的执行进度、处理结果；

* **资源元数据模型**：存储所有的静态资源元数据，以用户 ID + 资源 ID 为联合唯一标识，记录资源的路径、类型、大小等；

* **索引优化设计**：为所有常用的查询字段（用户 ID、梦境 ID、记录时间、情绪标签），设置单独的联合索引，优化数据的查询速度[(22)](https://blog.langchain.com/announcing-the-langchain-mongodb-partnership-the-ai-agent-stack-that-runs-on-the-database-you-already-trust/)。

#### 5.3.3 多用户数据隔离设计

采用 Langchain 官方生产级方案中的「多租户隔离」设计逻辑，从技术上实现不同用户的数据严格隔离 —— 这是经过企业级场景验证的成熟方案，完全满足赛题对多用户数据隔离的硬性要求，在架构层面提前规避了用户数据串读、乱读的风险。

方案的核心数据隔离逻辑如下：



* **用户标识体系**：使用 Langgraph 的跨线程持久化能力，在用户登录后，生成全局唯一的用户 ID 与会话 ID，作为区分用户、会话的唯一标识；

* **数据隔离规则**：在数据写入时，将用户 ID 与所属租户信息，作为属主元数据标记到所有数据上；在用户读取数据时，后端数据查询过滤器自动根据当前用户的属主元数据做匹配筛选 —— 不同用户的资源在逻辑上完全隔离，互不干扰；

* **会话隔离规则**：使用 LangGraph 的线程 ID 管理能力，区分同一用户的不同会话场景；

* **访问权限控制**：采用 Langchain 的授权处理器，对每一次资源访问请求进行身份与权限校验，确保用户只能访问自己所属租户、自己拥有的资源；

* **存储隔离规则**：在 MongoDB Atlas 中，为不同用户创建独立的集合空间，保障不同用户的数据文件物理隔离；

* **权限降级适配**：在演示环境中，关闭用户注册、修改信息的接口权限，仅预置几个测试账号，避免出现越权访问问题[(57)](https://docs.langchain.com/oss/javascript/deepagents/going-to-production)。

#### 5.3.4 数据同步设计

采用「LangGraph 分布式状态共享 + MongoDB Atlas 全局数据同步」的技术方案，保障用户数据在多端、多场景的实时同步 —— 这是与 Langchain 生态适配的成熟方案，在架构层面提前规避了数据同步失败、冲突的潜在问题。

方案的核心数据同步逻辑如下：



* **多端同步能力**：通过 LangGraph 的 Checkpointer 机制，将用户的操作状态、梦境数据实时同步到 MongoDB Atlas 中，同一用户在不同设备、不同浏览器上的所有数据，都能实时保持一致；

* **读写分离适配**：技术架构上，采用读写分离的设计逻辑，以应对用户在不同场景下的数据访问流量，保障数据同步的效率；

* **冲突解决机制**：在用户数据发生版本冲突时，自动以最后一次修改时间为基准进行覆盖合并；

* **异常重试机制**：在数据同步出现网络异常时，自动重试同步请求；如果重试失败，将数据临时存储到本地，待网络恢复后再自动同步；

* **同步策略适配**：针对不同的网络环境，设置不同的同步请求间隔，在保证数据实时性的同时，减少对服务端的压力；

* **同步开关适配**：在演示环境中，提供数据同步的统一开关 —— 如果现场网络环境较差，可关闭同步功能，将数据临时存储在本地，保证演示流畅性[(58)](https://blog.csdn.net/hiwangwenbing/article/details/161487080)。

* **资源释放处理设计**：在页面销毁、用户会话结束时，统一释放所有的资源、请求、订阅，避免内存泄漏；
