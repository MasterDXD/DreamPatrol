# 深度拆解-深化推理全链路

> 版本：2.73.4 | 更新时间：2026-06-02

---

## 概述

深化推理是Harness框架的质量保障机制，通过迭代精化提升输出质量。本文拆解从触发到收敛的完整链路。

## 链路概览

```
任务触发 → DeepeningOrchestrator.execute() → 迭代循环 → ConvergenceDetector.check() → 结果缓存
              ↓                                ↓                ↓
         附加子模块                       质量评分           收敛检测
    (MetricsCollector, Cache,      (QualityScorer)     (阈值: 0.95)
     StrategyPlugin, EventStore)
```

## 阶段一：深化触发

### 触发条件

1. Skill的`enforcement`为`strict`且质量评分低于阈值
2. 用户通过`/deepen`命令显式触发
3. PhaseOrchestrator检测到阶段完成条件中的质量不达标

### 初始化

```javascript
orchestrator.attachMetricsCollector(metricsCollector)
  .attachCache(cache)
  .attachStrategyPlugin(strategyPlugin)
  .attachReportGenerator(reportGenerator)
  .attachConvergenceDetector(convergenceDetector)
  .attachQualityScorer(qualityScorer)
  .attachEventStore(eventStore)
  .attachGeneratorVerifier(generatorVerifier)
  .attachSubagentExecutor(subagentExecutor)
  .attachThoughtRetrieverCycle(thoughtRetrieverCycle);
```

## 阶段二：迭代深化循环

### 执行流程

```
for each iteration (maxIterations):
  1. 执行当前策略 → 生成输出
  2. QualityScorer.score(output) → 质量评分
  3. ConvergenceDetector.check(scores) → 收敛检测
  4. if converged: break
  5. StrategyPlugin.adapt(output, score) → 调整策略
  6. MetricsCollector.record(iteration, score) → 记录指标
  7. EventStore.append(event) → 记录事件
```

### 收敛检测算法

```javascript
ConvergenceDetector.check(scoreHistory):
  if scoreHistory.length < 2: return false
  recentAvg = average(last 3 scores)
  overallAvg = average(all scores)
  improvement = recentAvg - overallAvg
  return improvement < convergenceThreshold  // 默认0.01
```

### 质量评分维度

| 维度 | 权重 | 说明 |
|------|------|------|
| 完整性 | 0.3 | 输出是否覆盖所有要求 |
| 准确性 | 0.3 | 输出是否正确无误 |
| 一致性 | 0.2 | 输出是否内部一致 |
| 可操作性 | 0.2 | 输出是否可直接执行 |

## 阶段三：结果缓存与报告

### 缓存策略

- 相同输入+上下文 → 直接返回缓存结果
- LRU淘汰：缓存满时淘汰最久未使用
- TTL过期：缓存条目超时自动失效

### 报告生成

```javascript
reportGenerator.generate(iterations, scores, finalOutput):
  return {
    totalIterations,
    initialScore,
    finalScore,
    improvement,
    convergenceReached,
    timeline: iterations.map(i => ({ iteration: i.num, score: i.score, strategy: i.strategy })),
  }
```

## 自适应深度控制

AdaptiveDepthController通过关键词信号在四个维度评估任务复杂度，动态映射到四个深度级别，控制深化推理的迭代次数。

### 复杂度评估维度

| 维度 | 权重 | 关键词信号 | 说明 |
|------|------|-----------|------|
| scope（范围） | 0.35 | 构建、系统、平台、架构、重构、全栈、design、system、platform、refactor | 检测任务是否涉及系统级/架构级变更 |
| risk（风险） | 0.35 | 安全、关键、生产、合规、security、critical、production、compliance | 检测任务是否涉及安全/生产/合规风险 |
| reasoning（推理） | 0.20 | 推理、分析、优化、决策、reasoning、analysis、optimize、decision | 检测任务是否需要深度推理/分析 |
| dependencyDepth（依赖深度） | 0.10 | — | 由`task.depends_on`数组长度决定，每项+0.2，上限1.0 |

### 深度级别映射

```javascript
score = min(1, scope * 0.35 + risk * 0.35 + reasoning * 0.2 + depDepth * 0.1)

if (score < 0.25)  → quick      (depth=1, 1轮迭代)
if (score < 0.50)  → standard   (depth=2, 2轮迭代)
if (score < 0.75)  → deep       (depth=3, 3轮迭代)
if (score >= 0.75) → intensive  (depth=4, 4轮迭代)
```

### 评估流程

```
任务对象 → 提取description/prompt文本
                ↓
     遍历SCOPE_KW → 累加scope信号（每匹配+0.4，上限1.0）
     遍历RISK_KW  → 累加risk信号（每匹配+0.45，上限1.0）
     遍历REASON_KW → 累加reasoning信号（每匹配+0.4，上限1.0）
     计算depDepth  → min(1, depends_on.length * 0.2)
                ↓
     加权求和 → 映射深度级别 → 发出'complexity-assessed'事件
```

### API

| 方法 | 返回值 | 说明 |
|------|--------|------|
| `assessComplexity(task)` | `{score, level, depth, signals}` | 完整复杂度评估 |
| `getRecommendedDepth(task)` | `number` (1-4) | 推荐深度数值 |
| `getRecommendedLevel(task)` | `string` | 推荐深度级别名称 |

## 收敛检测算法详解

ConvergenceDetector通过五重检测机制判断迭代深化过程是否已收敛，向编排器发出收敛信号和操作建议。

### 配置参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `qualityThreshold` | 0.85 | 质量收敛阈值 |
| `maxIterations` | 10 | 最大迭代次数 |
| `minImprovementRate` | 0.01 | 最小改进率 |
| `stabilityVariance` | 0.01 | 稳定性方差阈值 |
| `stabilityWindow` | 3 | 稳定性检测窗口大小 |
| `coverageThreshold` | 0.8 | 覆盖率阈值 |
| `dimensionBalanceThreshold` | 0.3 | 维度平衡阈值（最大维度差） |
| `qualityDegradationThreshold` | 0.1 | 质量退化阈值 |

### 五重检测流程

```
check(executionId, data)
  │
  ├─ 1. 质量阈值检测
  │     qualityScore >= qualityThreshold
  │     → converged=true, reason='quality-threshold-met', recommendation='sufficient'
  │
  ├─ 2. 最大迭代检测
  │     history.length >= maxIterations
  │     → converged=false, reason='max-iterations-reached', recommendation='increase-depth-or-abort'
  │
  ├─ 3. 稳定性检测（_checkStability）
  │     窗口内方差 < stabilityVariance 且 均值 >= threshold*0.9
  │     → converged=true, reason='stable-and-sufficient', recommendation='sufficient'
  │     窗口内方差 < stabilityVariance 但 均值 < threshold*0.9
  │     → converged=true, reason='plateau-detected', recommendation='increase-depth'
  │
  ├─ 4. 质量退化检测（_checkDegradation）
  │     当前分数 < 上次分数 - qualityDegradationThreshold
  │     → converged=true, reason='quality-degrading', recommendation='decrease-depth'
  │
  └─ 5. 未收敛
        → converged=false, reason='not-converged', recommendation='increase-depth'
```

### 信号对象结构

```javascript
{
  qualityScore: { value: 0.87, passed: true },
  dimensionBalance: { value: 0.15, passed: true }  // 仅当维度数>=2时存在
}
```

### 收敛原因与建议映射

| 收敛原因 | 含义 | 推荐操作 |
|---------|------|---------|
| `quality-threshold-met` | 质量达标 | `sufficient` — 无需继续 |
| `stable-and-sufficient` | 稳定且接近阈值 | `sufficient` — 可接受 |
| `plateau-detected` | 进入平台期 | `increase-depth` — 增加深度 |
| `quality-degrading` | 质量退化 | `decrease-depth` — 降低深度 |
| `max-iterations-reached` | 迭代次数耗尽 | `increase-depth-or-abort` |
| `not-converged` | 未收敛 | `increase-depth` — 继续深化 |

### 历史记录管理

- 每个执行ID维护独立历史记录（`Map<executionId, Array>`）
- 最大历史执行数默认100，超出时淘汰最早记录
- 单条历史超过`maxIterations`时自动移除最早条目

## 可靠性保障机制

深化子系统通过熔断器、限流器和重试策略三个组件协同工作，确保深化推理在高负载和异常情况下的稳定运行。

### 三组件协同架构

```
请求进入
  ↓
DeepeningRateLimiter.acquire()  ── 并发+时间窗口限流
  ↓ (允许)
DeepeningCircuitBreaker.execute()  ── 熔断保护
  ↓ (通行)
DeepeningRetryPolicy.execute()  ── 自动重试
  ↓
执行业务逻辑
  ↓
结果返回 / 异常处理
```

### 熔断器（DeepeningCircuitBreaker）

管理命名熔断器的状态转换，为深化执行提供容错保护。

#### 状态机

```
         连续失败 >= failureThreshold
  CLOSED ──────────────────────────→ OPEN
    ↑                                  │
    │ 连续成功 >= successThreshold      │ resetTimeout超时
    │                                  ↓
    └──────── HALF_OPEN ←─────────────┘
              试探性放行（maxHalfOpenCalls=1）
```

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `maxCircuits` | 100 | 最大熔断器数量 |
| `failureThreshold` | 5 | 触发熔断的连续失败次数 |
| `successThreshold` | 3 | 半开恢复到关闭的连续成功次数 |
| `resetTimeout` | 30000ms | 打开→半开自动恢复超时 |

#### 关键行为

- 容量满时优先淘汰`closed`状态熔断器，其次淘汰最早创建的
- `execute()`方法在`open`状态下自动检查`resetTimeout`，超时则转为`half_open`
- `half_open`状态限制并发试探调用数（`maxHalfOpenCalls`），超出则拒绝
- 支持`forceOpen`/`forceClose`/`forceHalfOpen`强制状态覆盖

### 限流器（DeepeningRateLimiter）

多维度限流，提供并发、时间窗口和令牌桶三维度限流能力。

#### 三维度限流模型

| 维度 | 参数 | 默认值 | 说明 |
|------|------|--------|------|
| 并发 | `maxConcurrent` | 10 | 最大同时执行数 |
| 每分钟 | `maxPerMinute` | 60 | 每分钟最大请求数 |
| 每小时 | `maxPerHour` | 1000 | 每小时最大请求数 |

#### 令牌桶模型

```javascript
createBucket(name, { rate: 10, capacity: 10 })
// rate: 每refillInterval填充的令牌数
// capacity: 桶最大容量
// refillInterval: 填充间隔（默认1000ms）

tryConsume(name, count)
// 令牌充足 → allowed=true, tokensRemaining=N
// 令牌不足 → allowed=false, retryAfter=ms
```

#### Agent自定义限流

```javascript
rateLimiter.setAgentLimit('agent-id', { maxPerMinute: 30 });
// 为特定Agent设置独立的每分钟速率限制
```

### 重试策略（DeepeningRetryPolicy）

可配置重试策略管理器，支持四种退避策略。

#### 退避策略对比

| 策略 | 延迟计算 | 适用场景 |
|------|---------|---------|
| `fixed` | `baseDelay` | 固定间隔，简单场景 |
| `linear` | `baseDelay * attempt` | 线性增长，温和退避 |
| `exponential` | `min(baseDelay * 2^(attempt-1), maxDelay)` | 指数增长，通用场景 |
| `exponential_jitter` | `min(baseDelay * 2^(attempt-1) * random(0.5,1.0), maxDelay)` | 带抖动，防惊群 |

#### 策略定义与执行

```javascript
retryPolicy.definePolicy('deepening-retry', {
  maxRetries: 3,
  baseDelay: 100,
  maxDelay: 30000,
  backoffStrategy: 'exponential_jitter',
  retryableErrors: ['TIMEOUT', 'RATE_LIMITED']
});

const result = await retryPolicy.execute('deepening-retry', asyncFn);
// 自动重试，最多3次，带指数抖动退避
```

#### 可重试错误过滤

- 定义策略时指定`retryableErrors`关键字列表
- 执行时捕获错误，检查错误消息是否包含任一关键字
- 不匹配则立即抛出（`nonRetryable`事件），不浪费重试次数

## Token感知深化

TokenAwareDeepening根据剩余Token预算动态调整深化深度和迭代次数，确保深化推理在预算约束下高效执行。

### 预算检查机制

```javascript
const tokenManager = new TokenManager({ budget: 1000000000 });
const tad = new TokenAwareDeepening({
  minBudgetRemaining: 1000,   // 最低剩余Token（绝对值或比例）
  maxIterationCap: 10         // 最大迭代次数上限
});

const { maxIterations, reason } = tad.calculateMaxIterations(tokenManager, sessionId);
```

### 迭代次数计算逻辑

```
1. 获取Token使用情况 → remaining, budget
2. 判断预算临界状态：
   - 若minBudgetRemaining为比例(0~1)：remainingRatio < minBudgetRemaining → 1次迭代
   - 若minBudgetRemaining为绝对值：remaining < minBudgetRemaining * 0.1 → 1次迭代
3. 计算原始最大迭代：floor(remaining / 2000)
4. 应用上限：min(rawMax, maxIterationCap)
5. 保证最少1次迭代：max(1, cappedMax)
```

### 深度级别推荐

```javascript
tad.recommendDepth(tokenManager, sessionId, complexity);
// complexity > 0.7 → 'intensive'
// complexity > 0.5 → 'deep'
// complexity < 0.25 → 'quick'
// 其他 → 'standard'
```

### Token效率追踪

```javascript
tad.recordIterationCost(sessionId, iteration, tokensUsed, qualityScore);
// efficiency = qualityScore / tokensUsed

tad.getEfficiencyReport(sessionId);
// → { totalRecords, totalTokensUsed, averageQuality }
```

| 方法 | 说明 |
|------|------|
| `calculateMaxIterations(tokenManager, sessionId)` | 根据预算计算最大迭代次数 |
| `canAffordIteration(tokenManager, sessionId, tokenCost)` | 检查是否可支付指定Token消耗 |
| `recordIterationCost(sessionId, iteration, tokensUsed, qualityScore)` | 记录单轮消耗和效率 |
| `getEfficiencyReport(sessionId)` | 获取会话Token效率报告 |
| `recommendDepth(tokenManager, sessionId, complexity)` | 综合预算+复杂度推荐深度 |

## 事件驱动深化

深化子系统通过DeepeningEventStore和DeepeningEventReplay实现完整的事件记录、查询和回放机制。

### 事件类型

| 事件类型 | 枚举值 | 触发时机 |
|---------|--------|---------|
| 执行启动 | `execution-start` | 深化执行开始 |
| 执行完成 | `execution-complete` | 深化执行结束 |
| 迭代完成 | `iteration-complete` | 每轮迭代结束 |
| 收敛检测 | `convergence-detected` | 收敛条件满足 |
| 缓存命中 | `cache-hit` | 缓存命中已有结果 |
| 缓存未命中 | `cache-miss` | 缓存未命中 |

### 事件存储（DeepeningEventStore）

#### 存储结构

```javascript
{
  id: timestampId(),        // 时间戳唯一ID
  type: 'iteration-complete',
  data: { executionId, iteration, score },
  timestamp: Date.now(),
  sequence: ++sequenceNumber  // 递增序列号
}
```

#### 索引机制

- **类型索引**（`_byType`）：按事件类型计数，O(1)查询
- **执行ID索引**（`_byExecution`）：按执行ID分组计数，O(1)查询
- **环形缓冲**（RingBuffer）：固定容量，自动淘汰最早事件

#### 查询能力

```javascript
eventStore.getByType('iteration-complete');           // 按类型查询
eventStore.getByExecution('exec-123');                 // 按执行ID查询
eventStore.getExecutionTimeline('exec-123');           // 执行时间线
eventStore.query({                                     // 多条件查询
  type: 'iteration-complete',
  executionId: 'exec-123',
  since: startTime,
  until: endTime
});
eventStore.getDashboard();                             // 仪表盘数据
```

#### 磁盘持久化

```javascript
const es = new DeepeningEventStore({
  persistToDisk: true,
  persistPath: '/data/deepening-events',
  autoFlushInterval: 5000,    // 自动刷盘间隔
  autoFlushThreshold: 50      // 未刷盘事件数阈值
});
```

- 支持同步/异步双路径读写（`_writeToDisk`/`_writeToDiskAsync`）
- 自动刷盘：间隔定时器 + 未刷盘计数阈值双重触发
- 启动时自动从磁盘恢复事件和序列号
- 关闭时强制刷盘

### 事件回放（DeepeningEventReplay）

#### 回放模式

| 模式 | 方法 | 特点 |
|------|------|------|
| 同步回放 | `replay(options)` | 立即逐个触发，无延迟 |
| 异步回放 | `startReplay(options)` | 支持速度控制，可中断 |

#### 自定义过滤器

```javascript
replay.registerFilter('high-score', e => e.data && e.data.score >= 0.8);
replay.registerFilter('recent', e => e.timestamp > Date.now() - 3600000);

replay.replay({ filters: ['high-score', 'recent'] });
```

#### 异步回放速度控制

```javascript
await replay.startReplay({ speed: 100 });  // 每事件间隔100ms
replay.stopReplay();                        // 中断回放
replay.isPlaying();                         // 检查回放状态
```

### 事件存储与回放的协作

```
深化执行 → EventStore.record() → RingBuffer + 索引更新
                                        ↓ (可选)
                                   磁盘持久化
                                        ↓
EventReplay.record() ← 外部事件源
        ↓
  getEvents(filters) → 按条件检索
        ↓
  replay() / startReplay() → 逐事件触发'replay'事件
```

## 深化策略插件

DeepeningStrategyPlugin实现五种可插拔策略，根据执行上下文动态决定是否继续深化及深度级别。

### 策略类型

| 策略 | 枚举值 | 决策逻辑 | 适用场景 |
|------|--------|---------|---------|
| 固定深度 | `fixed-depth` | 迭代次数 < maxIterations → 继续 | 简单任务，可预测迭代需求 |
| 自适应 | `adaptive` | 质量<0.5→intensive, <阈值→deep, 其他→standard | 通用场景，质量驱动 |
| 收敛驱动 | `convergence-driven` | 收敛→停止，否则继续 | 需要精确收敛控制 |
| 预算感知 | `budget-aware` | 剩余/预算<0.1→停止，>0.5→deep | Token预算紧张 |
| 质量优化 | `quality-optimized` | 质量>=0.9→停止，否则intensive | 追求最高质量 |

### 策略决策接口

```javascript
const plugin = new DeepeningStrategyPlugin('my-strategy', {
  type: 'adaptive',
  maxIterations: 6,
  qualityThreshold: 0.85,
  enabled: true
});

const result = await plugin.decide({
  iteration: 3,
  qualityScore: 0.72,
  improvementRate: 0.05,
  convergenceStatus: { converged: false },
  tokensRemaining: 50000,
  tokensBudget: 100000
});
// → { shouldContinue: true, depthLevel: 'deep', reason: 'within-iterations' }
```

### 自定义策略扩展

通过注册新策略函数扩展策略类型：

```javascript
plugin._strategies.set('custom-strategy', (ctx) => {
  const shouldContinue = ctx.qualityScore < 0.95 && ctx.iteration < 8;
  return {
    shouldContinue,
    depthLevel: ctx.qualityScore < 0.6 ? 'intensive' : 'deep',
    reason: shouldContinue ? 'custom-logic' : 'custom-stop'
  };
});

plugin._config.type = 'custom-strategy';
```

### 策略与编排器的集成

```
DeepeningOrchestrator._shouldStopIterating()
  │
  ├─ 1. StrategyPlugin.decide(context)
  │     → shouldContinue=false → 停止迭代
  │
  ├─ 2. ConvergenceDetector.check(executionId, data)
  │     → converged=true → 停止迭代
  │
  └─ 3. 收敛阈值直接比较
        qualityScore >= convergenceThreshold → 停止迭代
```

策略插件具有最高优先级，可在收敛检测之前提前终止迭代。

## 深化与Skill的集成

iterative-deepening Skill是深化推理子系统的用户侧入口，定义了触发条件、执行步骤和质量门禁。

### Skill元数据

| 属性 | 值 |
|------|-----|
| skill_id | `iterative-deepening` |
| 适用Agent | task-worker, domain-analyst, quality-assurance |
| 阶段 | module-development |
| 优先级 | 2 |
| enforcement | recommended |
| 成功率 | 83% |
| 生产验证 | ✅ |

### 自动触发条件

1. 用户提及"深化"/"迭代"/"多轮"/"deepening"/"iterate"/"refine"
2. 任务复杂度评估返回`deep`或`intensive`
3. 前一次迭代质量分数低于阈值
4. 收敛检测器报告`not-converged`

### 执行步骤

```
Step 1: 任务复杂度评估
  AdaptiveDepthController.assessComplexity(task)
  → 4维信号评估 → 深度级别映射

Step 2: 原始上下文注册
  LTIContextInjector注入原始需求
  → 防止多轮迭代目标漂移

Step 3: 循环深化执行
  RecurrentDeepeningScheduler / ProgressiveDeepening
  → 每轮聚焦前一轮弱点 → 质量评估 → 收敛判断

Step 4: 收敛检测
  ConvergenceDetector.check()
  → 5种信号融合 → 收敛原因 + 操作建议

Step 5: 结果输出
  → 质量分数曲线 + 收敛原因 + 焦点区域
```

### 与其他Skill的协作

| 协作Skill | 触发条件 | 协作方式 |
|-----------|---------|---------|
| tdd-implement | 每轮迭代中 | 应用RED-GREEN-REFACTOR |
| code-review | deep/intensive级别 | 自动触发代码审查 |
| verification-before-completion | 最终输出前 | 强制验证 |
| systematic-debugging | 收敛原因为quality-degrading | 触发调试流程 |

### 质量门禁

- 每轮迭代必须产生可验证的输出
- 质量分数必须单调递增（允许微小波动）
- 最终输出的qualityScore必须 ≥ 0.7

### 因果输入/输出

| 类型 | 名称 | 说明 |
|------|------|------|
| 输入 | architecture-document | 架构设计文档（可选） |
| 输出 | deepened-output | 深化输出 |
| 输出 | convergence-report | 收敛报告 |

### 证据类型

- `quality_score_report`（必需）— 质量评分报告
- `convergence_report`（必需）— 收敛检测报告
