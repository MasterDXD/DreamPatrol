# 深度拆解-质量保障与自演化闭环全链路

> 版本：2.73.4 | 更新时间：2026-06-02

---

## 概述

质量保障与自演化闭环是Harness框架的核心自改进引擎。它由10个紧密协作的模块组成，构建了一条从质量评分→自反思→对抗审查→可信度评估→债务追踪→漂移监控→演化治理的完整数据流，形成"观测→诊断→干预→验证"的闭环反馈机制。

该闭环的设计哲学是：**任何AI产出都必须经过多维度质量检验，任何质量退化都必须被自动检测并触发自愈流程，任何自改进都必须在治理约束下受控执行**。闭环的核心价值在于将"事后补救"转化为"事前预防+事中干预+事后复盘"的全生命周期质量保障。

### 核心设计原则

- **多维度评估**：质量不是单一指标，而是完整性/正确性/一致性/覆盖率/清晰度的加权综合
- **对抗性思维**：通过魔鬼代言人和证伪实验主动寻找缺陷，而非被动等待
- **信任追踪**：AI生成代码按来源追踪可信度，"似对非对"模式是最高风险信号
- **债务显性化**：理解债务从隐性变为显性，5种类型×4级严重度×4种状态精确量化
- **漂移感知**：长任务中约束漂移是质量退化的主因，5级漂移检测+否定约束识别
- **治理约束**：自演化不是无约束的自修改，提案生命周期+人工审批+证据验证三重保障

### 数据流说明

| 信号流向 | 触发条件 | 数据内容 |
|---------|---------|---------|
| QualityScorer → SelfReflection | `scored`事件，质量分低于阈值 | total, dimensions, grade |
| SelfReflection → AdversarialReview | 质量趋势为`degrading` | 证伪提示、反谄媚检查 |
| AdversarialReview → AiCodeTrustScorer | 对抗审查发现风险 | 攻击清单、证伪信号 |

| ComprehensionDebtTracker → ContextDriftMonitor | 债务升级为`escalated` | debtId, severity, type |
| ContextDriftMonitor → DocFreshnessGuard | 漂移等级≥`high` | driftScore, violatedConstraints |
| DocFreshnessGuard → FeedbackCredibility | 文档验证完成 | docPath, stale状态 |
| FeedbackCredibility → SelfEvolutionGovernor | 加权反馈低于0.5 | weightedFeedback值 |
| SelfEvolutionGovernor → QualityScorer | 提案执行完成 | 重新评分触发闭环迭代 |

## 各模块详解

### 1. QualityScorer — 质量评分器

#### 概述

QualityScorer是闭环的入口模块，对任务产出进行五维加权评估，输出0-1总分与等级判定。它是所有后续模块的数据源——自反思依赖其评分趋势，可信度评估器参考其维度分数，治理器监听其`scored`事件。

#### 核心API

| 方法 | 签名 | 说明 |
|------|------|------|
| `score` | `score(result, task?)` | 对任务产出进行五维加权质量评分 |
| `getHistory` | `getHistory(limit?)` | 获取评分历史记录 |
| `getStats` | `getStats()` | 获取评分统计摘要 |
| `attachSignalPersistence` | `attachSignalPersistence(sp)` | 附加信号持久化实例 |

#### 评分维度与权重

| 维度 | 权重 | 评分策略 |
|------|------|---------|
| completeness（完整性） | 0.25 | 基础分0.3 + 键数量加分(上限0.3) + 需求匹配度(0.3+0.7×匹配率) |
| correctness（正确性） | 0.30 | 基础分0.4 + success/valid/passed加分 - error/errors/failures扣分 + 期望输出匹配度 |
| consistency（一致性） | 0.15 | 基础分0.5 + 类型一致性(0.2) + status字段(0.15) + metadata/context(0.15) |
| coverage（覆盖率） | 0.15 | 基础分0.3 + coverage字段直接取值 / tests通过率 / 键数量加分(上限0.4) + scope加分(0.1) |
| clarity（清晰度） | 0.15 | 基础分0.4 + 多句加分(0.2) + 长度适中加分(0.2) + 大写开头(0.1) + 描述性键(0.15-0.2) |

#### 等级判定阈值

| 等级 | 分数范围 | 含义 |
|------|---------|------|
| excellent | ≥0.9 | 卓越，无需改进 |
| good | ≥0.75 | 良好，可接受 |
| acceptable | ≥0.6 | 可接受，有改进空间 |
| poor | ≥0.4 | 较差，需改进 |
| failing | <0.4 | 不合格，必须重做 |

#### 配置参数

```javascript
{
  weights: { completeness: 0.25, correctness: 0.30, consistency: 0.15, coverage: 0.15, clarity: 0.15 },
  thresholds: { excellent: 0.9, good: 0.75, acceptable: 0.6, poor: 0.4 },
  maxHistory: 300
}
```

#### 事件

| 事件名 | 载荷 | 触发时机 |
|--------|------|---------|
| `scored` | `{total, dimensions, grade, taskId, timestamp}` | 每次评分完成 |

#### 使用示例

```javascript
const QualityScorer = require('./src/runtime/quality/quality-scorer');
const scorer = new QualityScorer({ maxHistory: 500 });
scorer.attachSignalPersistence(signalPersistence);

const result = scorer.score(
  { success: true, data: { items: [1, 2, 3] }, coverage: 0.85 },
  { id: 'task-001', requirements: ['items', 'coverage'], expectedOutput: null }
);
console.log(result.grade);
console.log(result.dimensions);
```

### 2. SelfReflection — 自反思引擎

#### 概述

SelfReflection是闭环的"意识层"，负责输出质量自评与改进建议生成。它对比前后质量分数判定趋势（improving/stable/degrading），推荐动作（continue/deepen-analysis/rollback-and-revise），并内置证伪维度反思和反谄媚检查。

#### 核心API

| 方法 | 签名 | 说明 |
|------|------|------|
| `reflect` | `reflect(context)` | 执行自反思，生成反思问题、趋势判定与建议动作 |
| `falsificationReflection` | `falsificationReflection(output?, context?)` | 证伪维度反思，生成5条证伪提示 |
| `recordImprovement` | `recordImprovement(reflectionId, improvement)` | 记录改进条目 |
| `shouldTriggerReflection` | `shouldTriggerReflection(context)` | 判断是否应触发反思 |
| `getReflection` | `getReflection(reflectionId)` | 获取反思记录 |
| `getAgentReflections` | `getAgentReflections(agentId)` | 获取Agent的所有反思 |
| `getStats` | `getStats()` | 获取反思统计 |

#### 反思模板

| 产出类型 | 反思问题数 | 特殊维度 |
|---------|-----------|---------|
| code | 5 | 边界条件/一致性/安全性/性能/完整性 |
| design | 5 | 需求覆盖/过度设计/依赖关系/可扩展性/审查风险 |
| test | 5 | 关键路径/依赖风险/误判风险/数据代表性/审查风险 |
| documentation | 5 | 实现准确性/示例充分性/术语一致性/已知限制/审查风险 |
| decision | 5 | 证伪性/假设有效性/反谄媚/证据强度/替代覆盖 |

#### 质量趋势判定算法

```
delta = currentQuality - previousQuality
if delta < -improvementThreshold → trend: 'degrading', action: 'rollback-and-revise'
if delta > +improvementThreshold → trend: 'improving', action: 'continue'
else → trend: 'stable', action: 'deepen-analysis'
```

#### 配置参数

```javascript
{
  maxReflections: 3,
  improvementThreshold: 0.05,
  qualityWeights: { completeness: 0.25, correctness: 0.30, consistency: 0.15, security: 0.15, clarity: 0.15 },
  autoTriggerOnQualityDrop: true,
  persistResults: true,
  maxHistory: 500
}
```

#### 事件

| 事件名 | 载荷 | 触发时机 |
|--------|------|---------|
| `reflection-created` | `{reflectionId, agentId, qualityTrend, recommendedAction}` | 反思创建时 |
| `improvement-recorded` | `{reflectionId, dimension}` | 改进记录时 |

### 3. AdversarialReview — 对抗审查器

#### 概述

AdversarialReview采用"魔鬼代言人"角色，故意寻找缺陷和漏洞。它提供三种审查模式：双审查者多轮对抗（`review`）、决策对抗（`decisionAdversarial`）和证伪检验（`falsificationCheck`）。

#### 核心API

| 方法 | 签名 | 说明 |
|------|------|------|
| `review` | `async review(subject, reviewerA, reviewerB)` | 双审查者多轮对抗审查 |
| `decisionAdversarial` | `async decisionAdversarial(proposal?, options?)` | 决策对抗审查，多角色攻击 |
| `falsificationCheck` | `falsificationCheck(conclusion?, context?)` | 证伪检验 |

#### 对抗角色定义

| 角色键 | 角色名 | 审查焦点 |
|--------|--------|---------|
| cfo | 冷静的CFO | 成本、ROI、现金流风险 |
| investor | 挑剔的投资人 | 市场规模、竞争壁垒、退出路径 |
| veteran | 行业老手 | 行业潜规则、隐性成本、监管风险 |
| engineer | 悲观工程师 | 技术可行性、复杂度、维护成本 |
| ux_fanatic | 用户体验偏执狂 | 用户学习成本、使用障碍、流失风险 |

#### 多轮对抗算法

```
for round = 1 to maxRounds:
  reviewA = await reviewerA(subject, context)  // 含超时保护(30s)
  reviewB = await reviewerB(subject, context)
  if reviewA.approved AND reviewB.approved → consensus = true, break
  else → 合并反馈进入下一轮
return { consensus, rounds, details, finalFeedback }
```

#### 配置参数

```javascript
{
  maxRounds: 3,
  reviewTimeout: 30000  // 每个审查者超时时间(ms)
}
```

#### 事件

| 事件名 | 载荷 | 触发时机 |
|--------|------|---------|
| `round-complete` | `{round, reviewerA, reviewerB}` | 每轮审查完成 |
| `review-complete` | `{consensus, rounds, details, finalFeedback}` | 审查结束 |

### 4. AiCodeTrustScorer — AI代码可信度评估器

#### 概述

AiCodeTrustScorer基于7项风险指标检测AI生成代码的可信度，按来源追踪可信度趋势，支持指数衰减的时间衰减机制。其中`ALMOST_CORRECT`（似对非对）模式是最具特色的风险指标——代码看起来正确但包含微妙Bug。

#### 核心API

| 方法 | 签名 | 说明 |
|------|------|------|
| `assess` | `assess(codeContext)` | 评估代码上下文的可信度 |
| `assessWithSource` | `assessWithSource(sourceId, codeContext)` | 评估并关联来源追踪 |
| `getSourceTrustScore` | `getSourceTrustScore(sourceId)` | 获取来源可信度评分 |
| `getSourceStats` | `getSourceStats(sourceId)` | 获取来源统计信息 |
| `decaySourceScores` | `decaySourceScores()` | 执行时间衰减 |
| `getAverageScore` | `getAverageScore()` | 历史平均评分 |
| `getRiskDistribution` | `getRiskDistribution()` | 风险指标分布 |

#### 7项风险指标

| 指标 | 权重 | 严重度 | 检测条件 |
|------|------|--------|---------|
| NO_TESTS | 0.13 | 1.0 | `hasTests===false` 或测试列表为空 |
| UNHANDLED_EDGE | 0.17 | 0.8 | `edgeCasesHandled===false` |
| IMPLICIT_DEPS | 0.10 | 0.7 | `implicitDependencies===true` 或未列出依赖 |
| MAGIC_VALUES | 0.08 | 0.6 | `magicValues===true` 或硬编码值>3 |
| MISSING_ERROR_HANDLING | 0.16 | 0.9 | `errorHandlingComplete===false` |
| SPEC_VIOLATION | 0.13 | 0.8 | `specCompliant===false` |
| CONTEXT_DRIFT | 0.09 | 0.7 | `contextDrift===true` 或 `driftScore>0.3` |
| ALMOST_CORRECT | 0.14 | 0.6-0.9 | `almostCorrect===true` 或 `subtleBugCount>0` 或通过基本测试但缺边界+错误处理 |

#### 信任等级与建议

| 等级 | 分数范围 | 建议 |
|------|---------|------|
| high | ≥0.8 | accept |
| medium | ≥0.6 | review-carefully |
| low | ≥0.4 | reject |
| unreliable | <0.4 | reject-and-revise（若有severity≥0.9的风险） |

#### 时间衰减算法

```
每日衰减: score = 0.5 + (score - 0.5) × decayFactor^daysSinceUpdate
衰减因子: 0.95（默认）
清理规则: |score - 0.5| < 0.01 且 超过7天未更新 → 移除来源
```

#### 配置参数

```javascript
{
  thresholds: { high: 0.8, medium: 0.6, low: 0.4 },
  riskIndicators: { /* 可自定义权重 */ },
  maxHistory: 500,
  decayFactor: 0.95
}
```

#### 事件

| 事件名 | 载荷 | 触发时机 |
|--------|------|---------|
| `assessed` | `{score, level, risks, riskCount, recommendation, assessedAt}` | 每次评估完成 |

### 5. ComprehensionDebtTracker — 理解债务追踪器

#### 概述

ComprehensionDebtTracker将AI执行过程中的理解偏差显性化为可追踪的"债务"，支持5种债务类型×4级严重度×4种解决状态的精确量化。债务评分基于未解决债务的严重度加权平均。

#### 核心API

| 方法 | 签名 | 说明 |
|------|------|------|
| `recordDebt` | `recordDebt(debtInfo)` | 记录新的理解债务 |
| `resolveDebt` | `resolveDebt(debtId, resolutionNote?)` | 标记债务为已解决 |
| `escalateDebt` | `escalateDebt(debtId, reason?)` | 升级债务为escalated |
| `getDebt` | `getDebt(debtId)` | 获取债务对象 |
| `getOpenDebts` | `getOpenDebts()` | 获取未解决债务 |
| `getDebtsByType` | `getDebtsByType(type)` | 按类型筛选 |
| `getDebtsByTask` | `getDebtsByTask(taskId)` | 按任务筛选 |
| `calculateDebtScore` | `calculateDebtScore()` | 计算债务评分 |
| `getDebtDistribution` | `getDebtDistribution()` | 类型分布 |
| `getResolutionRate` | `getResolutionRate()` | 解决率 |
| `getAverageResolutionTimeMs` | `getAverageResolutionTimeMs()` | 平均解决时间 |

#### 债务类型

| 类型 | 含义 | 典型场景 |
|------|------|---------|
| requirement-ambiguity | 需求模糊 | 需求描述存在歧义，AI理解与意图不一致 |
| context-mismatch | 上下文不匹配 | AI使用了过时或不相关的上下文信息 |
| implicit-assumption | 隐式假设 | AI基于未验证的假设做出决策 |
| spec-gap | 规格缺口 | 实现偏离了规格说明 |
| domain-knowledge-gap | 领域知识缺口 | AI缺乏必要的领域专业知识 |

#### 严重度与评分

| 严重度 | 评分 | 阈值 |
|--------|------|------|
| critical | 1.0 | 债务评分≥0.7 |
| high | 0.75 | 债务评分≥0.5 |
| medium | 0.5 | — |
| low | 0.25 | — |

#### 解决状态流转

```
open → in-progress → resolved
  │                    ↑
  └→ escalated ────────┘
```

#### 容量管理

- 最大债务数：1000
- 淘汰策略：优先淘汰已解决的旧债务，其次淘汰最老的债务

#### 事件

| 事件名 | 载荷 | 触发时机 |
|--------|------|---------|
| `debt-recorded` | 完整debt对象 | 新债务记录 |
| `debt-resolved` | `{id, resolutionNote}` | 债务解决 |
| `debt-escalated` | `{id, reason}` | 债务升级 |

### 6. DeliveryEfficiencyMeter — 交付效率度量器

DeliveryEfficiencyMeter追踪6阶段时间分布、编码占比、AI加速比、审查瓶颈评分，提供反馈循环时长度量和管道瓶颈检测。它是闭环中"效率感知"的模块，帮助识别交付流程中的瓶颈和失衡。

| `endCycle` | `endCycle(cycleResult?)` | 结束当前周期 |
| `recordPhaseTime` | `recordPhaseTime(phase, durationMs, meta?)` | 记录阶段耗时 |
| `recordReviewCycle` | `recordReviewCycle(_meta?)` | 记录审查循环 |
| `recordCodeGeneration` | `recordCodeGeneration(durationMs, meta?)` | 记录代码生成 |

| `startFeedbackLoop` | `startFeedbackLoop()` | 开始反馈循环计时 |
| `endFeedbackLoop` | `endFeedbackLoop()` | 结束反馈循环计时 |
| `getTimeDistribution` | `getTimeDistribution()` | 各阶段时间占比 |
| `getCodingRatio` | `getCodingRatio()` | 编码占比 |
| `getAiAccelerationRatio` | `getAiAccelerationRatio()` | AI加速比 |
| `getReviewBottleneckScore` | `getReviewBottleneckScore()` | 审查瓶颈评分 |
| `getReviewThroughputImbalance` | `getReviewThroughputImbalance()` | 吞吐量失衡 |
| `getPipelineBottleneck` | `getPipelineBottleneck()` | 管道瓶颈检测 |
| `getFeedbackLoopDuration` | `getFeedbackLoopDuration()` | 反馈循环时长统计 |
| `getEfficiencyMetrics` | `getEfficiencyMetrics()` | 综合效率指标 |

#### 6阶段模型

| 阶段 | 标识 | 期望占比 |
|------|------|---------|
| 需求/方案 | requirements | 15% |
| 需求分析 | analysis | 15% |
| 架构设计 | architecture | 10% |
| 编码开发 | development | 20% |
| 测试/改Bug | testing | 25% |
| 部署上线 | deployment | 15% |

#### 关键度量算法

**审查瓶颈评分**：
```
bottleneckScore = reviewRatio × 0.5 + reworkRatio × 0.5
reviewRatio = totalReviewCycles / cycleCount
reworkRatio = totalReworkTime / totalDevTime
```

**吞吐量失衡**：
```
codeGenRate = codeGenCount / (codeGenTime / 60000)  // 每分钟生成数
reviewRate = reviewCount / (reviewTime / 60000)      // 每分钟审查数
ratio = codeGenRate / reviewRate
ratio ≥ 4.0 → critical | ≥ 2.0 → high | ≥ 1.0 → moderate | < 1.0 → balanced
```

**管道瓶颈检测**：
```
对每个阶段: overrun = actualRatio - expectedRatio
overrun > 0.3 → 标记为瓶颈
按overrun降序排列，返回首要瓶颈
```

**反馈循环趋势**：
```
前后半段平均值比较:
secondHalfAvg > firstHalfAvg × 1.2 → increasing
secondHalfAvg < firstHalfAvg × 0.8 → decreasing
else → stable
```

  maxCycles: 200
}
```

### 7. ContextDriftMonitor — 上下文漂移监控器

#### 概述

ContextDriftMonitor追踪长任务执行过程中的约束漂移。它通过注册约束、周期性检查约束是否仍在当前上下文中被遵守，识别5级漂移（none/low/medium/high/critical），并支持否定约束的模糊匹配。

#### 核心API

| `getDriftTrend` | `getDriftTrend()` | 漂移趋势 |
| `getStats` | `getStats()` | 统计信息 |

#### 漂移等级与阈值

| 等级 | 阈值 | 含义 |
|------|------|------|
| none | <0.2 | 无漂移 |
| low | ≥0.2 | 轻微漂移，需关注 |
| medium | ≥0.4 | 中度漂移，需干预 |
| high | ≥0.6 | 高度漂移，需立即处理 |
| critical | ≥0.8 | 严重漂移，任务可能偏离 |

#### 漂移评分算法

```
driftScore = Σ(priorityWeight) / totalConstraints
priorityWeight: critical=1.0, high=0.8, medium=0.5, low=0.3
违反次数≥3 → 标记为lostConstraint（约束丢失）
违反次数<3 → 标记为violatedConstraint（约束违反）
```

#### 否定约束识别

内置否定词集合：`no, not, never, without, must-not, don't, dont, cannot, cant, can't, avoid, forbidden, prohibited`

当约束文本包含否定词时，采用精确匹配；否则采用模糊匹配（显著词70%匹配率）。

#### 漂移趋势判定

```
取最近5个快照，计算违反率
前后半段比较:
secondAvg > firstAvg × 1.3 → worsening
secondAvg < firstAvg × 0.7 → improving
else → stable
```

}
```

### 9. FeedbackCredibility — 反馈可信度评估器

#### 概述

FeedbackCredibility基于反馈源的历史准确率，动态计算各反馈源的可信度评分，并提供加权聚合能力。高可信度源的反馈在决策中占据更大权重，支持时间衰减防止过时评分影响决策。

#### 核心API

| 方法 | 签名 | 说明 |
|------|------|------|
| `recordFeedback` | `recordFeedback(sourceId, feedback, actualOutcome)` | 记录反馈及结果 |
| `getTrustScore` | `getTrustScore(sourceId)` | 获取来源信任评分 |
| `getWeightedFeedback` | `getWeightedFeedback(feedbacks)` | 加权聚合多条反馈 |
| `decayTrustScores` | `decayTrustScores()` | 执行时间衰减 |

#### 信任评分算法

```
新来源: score = 0.5（默认值）
更新: score = correctCount / samples
衰减: score = 0.5 + (score - 0.5) × decayFactor^daysSinceUpdate
清理: |score - 0.5| < 0.01 且 超过7天 → 移除
```

#### 加权聚合算法

```
weightedSum = Σ(value_i × trustScore_i)
weightSum = Σ(trustScore_i)
result = weightedSum / weightSum
未知来源使用默认信任评分0.5作为权重
```

#### 配置参数

```javascript
{
  decayFactor: 0.95  // 每日衰减因子
}
```

| 事件名 | 载荷 | 触发时机 |
|--------|------|---------|
| `feedback-recorded` | `{sourceId, correct, score}` | 反馈记录时 |

## 闭环流程

### 完整执行流程

```
阶段1: 质量评分触发
  QualityScorer.score(result, task)
  → 输出: {total, dimensions, grade}
  → 事件: 'scored'
  → 若grade为poor/failing → 进入阶段2

阶段2: 自反思诊断
  SelfReflection.reflect({agentId, skillId, previousQuality, currentQuality})
  → 输出: {qualityTrend, recommendedAction, questions, selfCheckPrompt}
  → 若trend为degrading → 进入阶段3

阶段3: 对抗审查
  AdversarialReview.decisionAdversarial(proposal, {roles})
  → 输出: {attacks, falsification, antiSycophancyCheck}
  → 同时: SelfReflection.falsificationReflection(output)
  → 若发现高风险 → 进入阶段4

阶段4: 可信度评估
  AiCodeTrustScorer.assess(codeContext)
  → 输出: {score, level, risks, recommendation}
  → 若recommendation为reject/reject-and-revise → 进入阶段5

阶段5: 债务追踪
  ComprehensionDebtTracker.recordDebt({type, severity, description})
  → 输出: debt对象
  → 若severity为critical/high → 进入阶段6

阶段6: 漂移监控
  ContextDriftMonitor.checkDrift(currentContext)
  → 输出: {driftScore, level, violatedConstraints, lostConstraints}
  → 若level为high/critical → 进入阶段7

阶段7: 文档新鲜度检查
  DocFreshnessGuard.validateFreshness()
  → 输出: {valid, newlyStale, totalStale}
  → 若spec文档stale → triggerReverification

阶段8: 反馈可信度聚合
  FeedbackCredibility.getWeightedFeedback(feedbacks)
  → 输出: weightedValue
  → 若加权值低于0.5 → 进入阶段9

阶段9: 自演化治理
  SelfEvolutionGovernor心跳收集所有信号
  → 议程聚合 → 成熟检查 → 提案生成
  → 人工审批 → 执行 → 证据验证
  → 若执行成功 → 回到阶段1重新评分（闭环迭代）
```

### 闭环收敛条件

闭环在以下条件满足时停止迭代：

1. QualityScorer评分达到`good`及以上（≥0.75）
2. SelfReflection趋势为`improving`或`stable`
3. AiCodeTrustScorer信任等级为`high`（≥0.8）
4. ComprehensionDebtTracker债务评分为`manageable`
5. ContextDriftMonitor漂移等级为`none`或`low`
6. DocFreshnessGuard所有文档为fresh
7. SelfEvolutionGovernor无待审批提案

### 闭环执行示例

```javascript
async function executeQualityLoop(taskResult, task, codeContext, agentId, skillId) {
  const previousQuality = scorer.getHistory(1)[0]?.total ?? 0;

  const scoreResult = scorer.score(taskResult, task);

  if (scoreResult.grade === 'poor' || scoreResult.grade === 'failing') {
    const reflection = reflector.reflect({
      agentId,
      skillId,
      artifactType: 'code',
      previousQuality,
      currentQuality: scoreResult.total,
    });

    if (reflection.qualityTrend === 'degrading') {
      const adversarialResult = await adversarial.decisionAdversarial(
        JSON.stringify(taskResult),
        { roles: ['engineer', 'veteran'] }
      );

      const trustResult = trustScorer.assessWithSource(agentId, codeContext);

      if (trustResult.recommendation === 'reject-and-revise') {
        debtTracker.recordDebt({
          type: 'implicit-assumption',
          severity: 'high',
          description: 'AI产出可信度不足: ' + trustResult.risks.map(r => r.label).join(', '),
          source: agentId,
          taskId: task.id,
        });
      }
    }
  }

  const driftResult = driftMonitor.checkDrift(JSON.stringify(taskResult));
  if (driftResult.level === 'high' || driftResult.level === 'critical') {
    governor.triggerEventHeartbeat('quality-regression', {
      driftScore: driftResult.driftScore,
      violatedConstraints: driftResult.violatedConstraints.length,
    });
  }

  const freshness = freshnessGuard.validateFreshness();
  if (!freshness.valid) {
    const staleSpecs = freshnessGuard.getReverificationQueue();
    for (const spec of staleSpecs) {
      freshnessGuard.triggerReverification(spec.path);
    }
  }

  feedbackCred.recordFeedback(agentId, scoreResult.total, scoreResult.grade !== 'failing');

  return scoreResult;
}
```
