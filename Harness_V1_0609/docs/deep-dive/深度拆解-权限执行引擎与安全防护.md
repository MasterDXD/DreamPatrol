# 深度拆解-权限执行引擎与安全防护

> 版本：2.73.4 | 更新时间：2026-06-02

---

## 概述

Harness 框架的权限执行引擎（src/permission/）实现了从角色定义到运行时强制的完整安全链路，包含 RBAC 访问控制、文件操作守卫和审计日志三大子系统。本文深入拆解这一全链路。

## RBACEnforcer — 基于角色的访问控制

### canExecute 执行流程

1. 验证Agent ID格式（`AGENT_ID_PATTERN`）
2. 查找Agent定义（agents目录中的.md文件）
3. 查找Skill定义（skills目录中的.md文件）
4. 检查Agent的`available_skills`是否包含该Skill
5. 检查Skill的`enforcement`级别与Agent权限是否匹配

### 三级执行策略

| 策略 | 说明 | available_skills包含 | available_skills不包含 |
|------|------|---------------------|---------------------|
| `strict` | 严格模式，所有 Skill 执行必须按顺序 | ✅ 允许执行 | ❌ 阻止执行 |
| `recommended` | 推荐模式，仅关键 Skill 强制顺序 | ✅ 允许执行 | ⚠️ 警告但允许 |
| `optional` | 可选模式，顺序仅作建议 | ✅ 允许执行 | ✅ 允许执行 |

### 角色定义格式

```json
{
  "team-lead": {
    "level": 1,
    "allowedSkills": ["brainstorming", "requirement-analysis", "*"],
    "deniedSkills": [],
    "skillOrder": ["brainstorming", "requirement-analysis", "architecture-design"]
  },
  "task-worker": {
    "level": 3,
    "allowedSkills": ["tdd-implement", "module-development", "bug-fix"],
    "deniedSkills": ["architecture-design", "deployment"],
    "skillOrder": ["tdd-implement", "module-development"]
  }
}
```

### Skill 执行顺序验证

```javascript
canExecute(agentId, skillId) {
  const agent = this.agents[agentId];
  if (!agent) return false;
  if (agent.deniedSkills.includes(skillId)) return false;
  if (agent.allowedSkills.includes('*')) return true;
  if (!agent.allowedSkills.includes(skillId)) return false;
  return true;
}

validateSkillOrder(agentId, skillId, completedSkills) {
  const agent = this.agents[agentId];
  if (!agent || !agent.skillOrder) return true;
  const idx = agent.skillOrder.indexOf(skillId);
  if (idx === -1) return true;
  for (let i = 0; i < idx; i++) {
    if (!completedSkills.includes(agent.skillOrder[i])) {
      return false;
    }
  }
  return true;
}
```

### 热重载机制

RBACEnforcer支持配置文件变更时的自动热重载：
- 使用`fs.watch`监听agents和skills目录
- `_hotReload`方法带限流和冷却机制
- 重载失败时保持旧状态不变

## PermissionGuard — 文件操作权限守卫

### 路径遍历防护

所有文件操作经过规范化路径检查，防止 `../` 穿越：

```javascript
_normalizePath(filePath) {
  const resolved = path.resolve(this._projectRoot, filePath);
  if (!resolved.startsWith(this._projectRoot)) {
    throw new PermissionError('PATH_TRAVERSAL', 'Path traversal detected: ' + filePath);
  }
  return resolved;
}
```

### 文件写入检查（checkFileWrite）

```
1. _validatePath(filePath) → 路径验证
   ├── 类型检查：必须是非空字符串
   ├── 路径解析：path.resolve
   └── 项目边界检查：_isWithinProject
2. 系统文件保护：.harness/目录下的系统文件只读
3. 文件锁检查：同一文件不能被多个Agent同时写入
4. 锁超时处理：超过DEFAULT_LOCK_TIMEOUT_MS自动释放
```

### 文件删除检查（checkFileDelete）

```
1. _validatePath(filePath) → 路径验证
2. 系统文件保护：禁止删除.harness系统文件
3. 确认机制：需要用户确认或之前确认未过期
```

### 文件级锁

通过内存锁机制防止多 Agent 同时修改同一文件：

```javascript
acquireLock(filePath, agentId) {
  const normalized = this._normalizePath(filePath);
  if (this._locks.has(normalized)) {
    return { acquired: false, heldBy: this._locks.get(normalized) };
  }
  this._locks.set(normalized, agentId);
  return { acquired: true };
}
```

### 危险命令检测

检测并拦截潜在危险的系统命令（30+个危险命令模式匹配）：

```javascript
isDangerousCommand(cmd) {
  const DANGEROUS_PATTERNS = [
    /rm\s+-rf\s+\//, /del\s+\/[sS]/,
    /format\s+[cC]:/, /mkfs/,
    /dd\s+if=/, /:\(\)\{.*;\};/,
  ];
  return DANGEROUS_PATTERNS.some(p => p.test(cmd));
}
```

需要用户确认或之前确认未过期。

### 确认过期机制

用户确认操作有时效性，默认 5 分钟过期：

```javascript
requestConfirmation(agentId, operation, target) {
  const id = Date.now().toString(36) + '_' + crypto.randomBytes(4).toString('hex');
  this._confirmations.set(id, {
    agentId, operation, target,
    createdAt: Date.now(),
    expiresAt: Date.now() + this._confirmationExpiryMs,
  });
  return { confirmationId: id, expiresAt: this._confirmations.get(id).expiresAt };
}
```

- 确认有效期：DEFAULT_CONFIRMATION_EXPIRY_MS
- 确认键：`agentId + '\0' + action + '\0' + target`
- 过期确认自动清理

## AuditLogger — 审计日志

### 日志记录流程

```
1. log(event) → 构建审计条目
   ├── 计算哈希：_computeEntryHash(entry, index)
   │   └── 链式哈希：SHA256(前一条哈希 + 当前条目数据)
   ├── 添加到BoundedArray
   └── 触发持久化：_schedulePersist
2. _persistNow() → 写入磁盘
   └── DebouncedPersister防抖写入
```

### 链式哈希完整性验证

每条日志记录包含前一条记录的哈希值，形成不可篡改的链式结构：

```javascript
log(entry) {
  const prevHash = this._entries.length > 0
    ? this._entries[this._entries.length - 1].hash
    : '0000000000000000000000000000000000000000';
  const record = {
    ...entry,
    id: this._entries.length + 1,
    timestamp: new Date().toISOString(),
    prevHash: prevHash,
  };
  record.hash = crypto.createHash('sha256')
    .update(JSON.stringify(record))
    .digest('hex');
  this._entries.push(record);
}
```

### 完整性验证（verifyIntegrity）

- 从第一条到最后一条重新计算哈希链
- 检测篡改：计算哈希 ≠ 存储哈希 → 标记为篡改
- 返回篡改位置索引

### 篡改恢复（_restoreIntegrity）

- 截断到第一个篡改条目之前
- 保留未篡改部分的完整性

### 防抖持久化

日志通过 DebouncedPersister 实现防抖写入磁盘，避免高频操作导致 I/O 瓶颈：

- 写入间隔：500ms
- 最大缓冲：100 条
- 序列化：JSON 格式

### 查询过滤

支持按时间范围、agent、action 等维度过滤审计日志：

```javascript
query(filters) {
  let results = this._entries;
  if (filters.agent) results = results.filter(e => e.agent === filters.agent);
  if (filters.action) results = results.filter(e => e.action === filters.action);
  if (filters.since) results = results.filter(e => new Date(e.timestamp) >= new Date(filters.since));
  if (filters.until) results = results.filter(e => new Date(e.timestamp) <= new Date(filters.until));
  return results;
}
```

## 安全防护总结

| 防护层 | 机制 | 防护目标 |
|--------|------|---------|
| RBAC | Agent-Skill权限矩阵 + Skill顺序验证 | 未授权Skill执行/越权执行 |
| 路径守卫 | _validatePath + _isWithinProject | 路径遍历攻击 |
| 系统文件 | SYSTEM_FILES集合 | 系统配置篡改 |
| 文件锁 | acquireLock/releaseLock | 并发写入冲突 |
| 危险命令 | DANGEROUS_COMMAND_PATTERNS | 恶意命令执行 |
| 原型污染 | _sanitizeProto + _createSafeObject | __proto__注入 |
| 原型污染(R28) | DANGEROUS_KEYS过滤 + safeAssign替代Object.assign | URL查询参数/配置对象原型污染 |
| ReDoS(R28) | REDOS_DANGEROUS_RE检测 + 模式长度限制 | 恶意正则表达式灾难性回溯 |
| 安全日志(R28) | debug()记录认证/URL解析/Token验证失败 | 攻击检测与审计能力 |
| 审计链 | SHA256链式哈希 | 日志篡改 |
| 敏感操作 | 确认过期机制 + 人工审批门 | 未确认的危险操作 |

## Round 28 安全修复记录

> 本轮修复涉及3类安全漏洞：ReDoS（正则表达式拒绝服务）、原型污染、安全关键路径错误日志缺失。

### ReDoS防护 — deepening-notifier.js

**漏洞**：`_getCompiledPattern()` 将用户提供的 `pattern` 字符串直接编译为正则表达式，仅做了200字符长度限制，未检测嵌套量词等ReDoS危险模式。同项目的 `deepening-validator.js` 已实现 `REDOS_DANGEROUS_RE` 检测，但此处未复用。

**修复**：添加 `REDOS_DANGEROUS_RE` 检测，拒绝包含嵌套量词的危险模式。

### ReDoS防护 — context-compression-engine.js

**漏洞**：`compressToolOutput()` 的 `filterPatterns` 选项接受正则表达式字符串数组，直接通过 `new RegExp(pattern)` 编译，无任何ReDoS防护（无长度限制、无危险模式检测）。编译后的正则对输出的每一行执行 `regex.test(l)`，灾难性回溯的影响被行数放大。

**修复**：添加类型检查、200字符长度限制和 `REDOS_DANGEROUS_RE` 检测，拒绝危险模式。

### 原型污染防护 — server.js _sanitizeSearchParams

**漏洞**：URL查询参数键未检查 `__proto__`/`constructor`/`prototype` 等危险键名。`sanitized[key] = value` 可设置 `constructor` 等属性。项目已有 `DANGEROUS_KEYS` 常量但未在此处使用。

**修复**：添加 `DANGEROUS_KEYS.has(key)` 过滤。

### 原型污染防护 — skill-tree-dag.js

**漏洞**：`addNode()` 中 `Object.assign(existing, metadata ?? {}, ...)` 未过滤危险键。项目已有 `safeAssign` 工具但未使用。

**修复**：`Object.assign` → `safeAssign`。

### 安全日志缺失 — websocket-handler.js / server.js

**漏洞**：3处安全关键路径的catch块完全不记录错误原因：
- WebSocket URL解析失败（可能掩盖注入攻击）
- HTTP Token验证失败（丧失攻击检测能力）
- HTTP URL解析失败（可能掩盖路径遍历尝试）

**修复**：添加 `debug()` 日志记录错误信息。

### 原型污染防护 — config-validator.js maskConfigForLogging（Round 29）

**漏洞**：`maskConfigForLogging()`函数在遍历配置对象键值时，未过滤`__proto__`/`constructor`/`prototype`等危险键名。通过精心构造的配置对象，攻击者可在日志掩码处理过程中触发原型污染，向`Object.prototype`注入属性。

**影响行**：`maskConfigForLogging()`函数的键遍历逻辑。

**修复**：添加`DANGEROUS_KEYS`过滤，遍历时跳过危险键名，与项目已有的`DANGEROUS_KEYS`常量保持一致。

**影响**：堵住配置日志掩码处理中的原型污染入口，与项目其他位置的防护策略统一。

### 原型污染防护 — server.js _sanitizeConfig（Round 29）

**漏洞**：`_sanitizeConfig()`函数在遍历配置对象时，未过滤`__proto__`/`constructor`/`prototype`等危险键名。配置对象可通过外部输入（如API请求或配置文件）注入危险键，在消毒处理过程中触发原型污染。

**影响行**：`_sanitizeConfig()`函数的键遍历逻辑。

**修复**：添加`DANGEROUS_KEYS`过滤，遍历时跳过危险键名，与项目已有的`DANGEROUS_KEYS`常量保持一致。

**影响**：堵住服务端配置消毒中的原型污染入口，与`_sanitizeSearchParams`等已有防护形成完整覆盖。

### RBACEnforcer — watcher错误处理器资源泄漏（Round 29）

**缺陷**：`RBACEnforcer`的文件监视器（FSWatcher）`'error'`事件处理器在捕获错误后未从`_watchers`数组中移除失败的watcher，也未调用`.close()`释放资源。失败的watcher残留在数组中成为僵尸对象，既无法正常监视文件变更，又占用系统文件描述符资源，且在后续`close()`批量关闭时可能因已失效的watcher而抛出异常。

**影响行**：RBACEnforcer的watcher `'error'`事件回调及`_watchers`数组管理。

**修复**：在error回调中先调用失败watcher的`.close()`方法释放系统资源，再从`_watchers`数组中移除该watcher引用，确保错误场景下数组仅包含有效的watcher实例。

**影响**：消除僵尸watcher导致的文件描述符泄漏，确保RBAC配置监视器在异常场景下正确清理并维持有效监视能力。

### timingSafeEqual失败无日志 — security.js（Round 31）

**漏洞**：`timingSafeEqual`比较失败时，catch块为空，未记录任何失败原因。在安全认证场景下，时序安全比较的失败可能意味着令牌不匹配或输入格式异常，缺少日志导致安全事件无法追溯和排查。

**影响行**：`timingSafeEqual`调用的catch块。

**修复**：添加`debug()`日志记录比较失败的错误信息，便于安全审计和故障排查。

**影响**：时序安全比较失败时不再静默吞掉错误，debug日志提供可追溯的安全事件信息。
