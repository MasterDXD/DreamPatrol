# 深度拆解-事件驱动架构与消息流转

## 概述

Harness 框架采用事件驱动架构作为核心通信机制，通过 EventBus 实现模块间解耦通信，支持中间件拦截、事件转发、审计日志和结构化日志等横切关注点。

## 事件架构层次

```
┌──────────────────────────────────────────────┐
│              外部事件消费者                      │
│  (WebSocketHandler, DashboardServer)          │
├──────────────────────────────────────────────┤
│              EventBus 核心层                    │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐     │
│  │ 中间件链  │ │ 历史记录  │ │ 事件转发  │     │
│  └──────────┘ └──────────┘ └──────────┘     │
├──────────────────────────────────────────────┤
│              事件生产者层                       │
│  ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐  │
│  │Agent│ │Session│ │Deep.│ │Collab│ │Skill│  │
│  └─────┘ └─────┘ └─────┘ └─────┘ └─────┘  │
└──────────────────────────────────────────────┘
```

## EventBus 核心实现

### 中间件机制

EventBus 支持最多 50 个中间件，按注册顺序执行：

```javascript
eventBus.use(function auditMiddleware(event, data) {
  if (event.startsWith('agent:')) {
    auditLogger.log({ agent: data.agentId, action: event, target: data.target });
  }
});
```

中间件执行出错时，错误被捕获并通过 `middleware-error` 事件报告，不影响主事件流。

### 事件历史

EventBus 维护一个 BoundedArray（默认容量 1000）记录所有事件，用于调试和审计查询。

## 事件命名规范

事件名采用 `模块:动作` 的两级命名规范：

| 前缀 | 模块 | 示例事件 |
|------|------|---------|
| `agent:` | Agent 系统 | `agent:state-change`, `agent:critical-alert` |
| `session:` | 会话管理 | `session:created`, `session:phase-change` |
| `permission:` | 权限系统 | `permission:confirmation-recorded` |
| `deepening:` | 深化推理 | `deepening:converged`, `deepening:iteration` |
| `collaboration-mode:` | 协作模式 | `collaboration-mode:selected` |
| `subagent:` | 子 Agent | `subagent:spawned`, `subagent:completed` |
| `skill-reducer:` | Skill 缩减 | `skill-reducer:discovered` |
| `memory:` | 记忆系统 | `memory:invalidated-by-code-change` |
| `goal:` | 目标执行 | `goal:created`, `goal:completed` |
| `governor:` | 自演化 | `governor:proposal-generated` |
| `patch:` | 补丁审批 | `patch:submitted`, `patch:approved` |
| `signal:` | 信号持久化 | `signal:recorded` |

## 事件转发映射

### 标准转发（EVENT_FORWARD_MAP）

源模块的内部事件自动转发为标准化事件名：

```
源: agentRuntime.emit('agent-state-change', data)
→ EventBus.emit('agent:state-change', data)
```

共 30+ 个源模块、80+ 个事件映射。

### 条件转发（CONDITIONAL_EVENT_FORWARD_MAP）

某些模块的事件仅在模块存在时转发：

```
源: deepeningOrchestrator.emit('execution-complete', data)
→ EventBus.emit('deepening:orchestrated', data)
```

### 延迟转发（LAZY_DEEPENING_EVENT_MAP）

深化子模块采用延迟加载策略，仅在模块首次使用时注册事件转发：

```javascript
const instance = registry.getOrLoad('deepening-circuit-breaker');
if (instance) {
  instance.on('circuit-state-change', (e) => eventBus.emit('deepening:circuit-state-change', e));
}
```

## 性能考虑

1. **中间件数量限制**：最多 50 个，超出抛出 `CAPACITY_EXCEEDED` 错误
2. **事件历史容量**：BoundedArray 默认 1000，超出自动淘汰旧事件
3. **转发错误隔离**：转发过程中的错误通过 try/catch 隔离，不影响源模块

## 事件生命周期详解

一个事件从生产者 `emit` 到消费者 `on` 的完整路径包含五个阶段：

```
生产者 emit(event, data)
  │
  ▼
① 历史记录 — BoundedArray 浅拷贝后推入，超容量自动淘汰
  │
  ▼
② 中间件链 — 按 use() 注册顺序依次执行，单个中间件异常不阻断链
  │
  ▼
③ 监听器分发 — listeners(event) 获取已注册监听器，逐个同步调用
  │
  ▼
④ 错误报告 — 监听器异常触发 listener-error，中间件异常触发 middleware-error
  │
  ▼
⑤ 返回值 — 有任何监听器被调用（含出错）则返回 true，否则 false
```

### 历史记录阶段

`emit()` 首先将事件推入 `_history`（BoundedArray，默认容量 1000）。对象类型数据执行浅拷贝（数组用展开运算符，普通对象用 `{ ...data }`），原始值直接存储。每条记录包含 `event`、`data`、`timestamp` 三个字段。超容量时 BoundedArray 自动淘汰最早的事件。

### 中间件链执行顺序

中间件按 `use()` 注册顺序同步执行，签名为 `(event, data) => void`。单个中间件抛出异常时，错误被 `try/catch` 捕获并通过 `middleware-error` 事件报告（附带 `originalEvent`、`error`、`middleware` 字段），不影响后续中间件和主事件流。中间件数量上限为 50，超出时抛出 `CAPACITY_EXCEEDED` 错误。

### 监听器分发阶段

中间件执行完毕后，通过 `listeners(event)` 获取该事件的所有监听器，逐个同步调用。单个监听器异常同样被捕获，通过 `listener-error` 事件报告（附带 `originalEvent`、`error`、`listener` 字段），不影响后续监听器。为避免 `listener-error` 事件自身死循环，当 `event === 'listener-error'` 时不重复发射。

### onceAsync 异步等待

`onceAsync(event, timeoutMs)` 提供基于 Promise 的异步等待机制。超时默认使用 `DEFAULT_REQUEST_TIMEOUT_MS`，可通过参数覆盖。超时后若系统已关闭则 resolve `{ timedOut: true }`，否则 reject 抛出超时错误。内部使用 `timer.unref()` 避免阻止进程退出。

### 命名空间隔离

`createNamespace(prefix)` 返回代理对象，所有方法自动为事件名添加 `prefix:` 前缀。支持 `emit`、`on`、`once`、`off`、`onceAsync`、`removeAllListeners` 六个方法。`removeAllListeners` 不传参时仅移除该前缀下的所有事件监听器，通过 `eventNames().filter()` 实现。

## EventRegistrar 自动发现机制

EventRegistrar 是事件系统的"布线中枢"，负责将分散在各子模块中的事件统一桥接到全局 EventBus。其核心设计原则是**声明式映射 + 自动发现**，通过三张映射表覆盖所有事件转发场景。

### 三层映射表

| 映射表 | 常量名 | 适用场景 | 加载时机 |
|--------|--------|---------|---------|
| 标准转发 | `EVENT_FORWARD_MAP` | Agent、Session、深化推理等核心模块 | 启动时立即注册 |
| 条件转发 | `CONDITIONAL_EVENT_FORWARD_MAP` | 深化编排器/管道等延迟初始化模块 | 启动时注册，源模块不存在时静默跳过 |
| 懒加载转发 | `LAZY_DEEPENING_EVENT_MAP` | 深化子模块（熔断器/限流器/快照等） | 首次使用时通过 registry.getOrLoad() 加载 |

### 自动发现流程

```
_registerEventForwarding(ctx)
  │
  ├─ _forwardMappedEvents(ctx, EVENT_FORWARD_MAP)      ← 标准转发
  │    遍历映射表，ctx[group.src] 存在则注册转发
  │
  ├─ _forwardMappedEvents(ctx, CONDITIONAL_EVENT_FORWARD_MAP) ← 条件转发
  │    同上，源模块不存在时静默跳过
  │
  ├─ _wireLazyDeepeningEvents(registry, eventBus)      ← 懒加载转发
  │    registry.getOrLoad(moduleId) 获取或加载模块
  │    模块支持 on() 方法则注册转发
  │
  ├─ 协作模式双向关联
  │    collaborationModeRouter ← subagentExecutor/agentChannel
  │    subagentExecutor ← session/modelSelector/enforcer/contextManager
  │
  ├─ GoalExecutor 初始化与依赖注入
  │
  ├─ 因果子系统初始化 (_initCausalModules)
  │    PhaseContextInjector / CausalDataBus / CausalBufferManager /
  │    CausalMemoryStore / ConfigCausalValidator / DocFreshnessGuard /
  │    HumanApprovalGate
  │
  ├─ 因果连接与蒸馏 (_wireCausalAttachments + _wireCausalDistillation)
  │
  ├─ 自演化子系统初始化 (_initEvolutionModules)
  │    SignalPersistence / SelfEvolutionGovernor / SkillPatchApproval /
  │    CausalVectorIndex
  │
  ├─ 模块级事件转发 (_forwardModuleEvents)
  │    Governor / SkillPatch / Signal / Goal / SkillCreation
  │
  ├─ 子代理完成处理 (_wireSubagentCompletionHandlers)
  │    亲和力学习器 + 技能改进循环
  │
  └─ 链式对话事件注册 (_wireChatChainEvents)
```

### 监听器生命周期管理

所有通过 EventRegistrar 注册的监听器都记录在 `_registeredListeners` 数组中（包含 `emitter`、`event`、`handler` 三元组）。`shutdown()` 时遍历该数组，逐个调用 `emitter.removeListener()` 移除监听器，每次移除通过 `safeCall` 包裹防止异常中断清理流程，最后清空数组。这确保了系统关闭时不遗留悬空监听器导致内存泄漏。

### 审计中间件自动注册

`_registerAuditMiddleware()` 向 EventBus 注册一个中间件，检查每个事件名是否以 `AUDIT_PREFIXES` 中的前缀开头（共 16 个前缀），匹配则自动写入 AuditLogger，记录 `agent`、`action`、`target`、`result`、`details` 五个字段。

### 会话生命周期事件

`_registerSessionEvents()` 注册六类会话事件：

| 源事件 | 转发事件 | 附加处理 |
|--------|---------|---------|
| `session-created` | `session:created` | 无 |
| `phase-change` | `session:phase-change` | 自动创建 Checkpoint |
| `skill-complete` | `session:skill-complete` | 获取技能改进建议 |
| `budget-warning` | `session:budget-warning` | 无 |
| `shutdown` | `session:shutdown` | 持久化所有活跃会话摘要到 SQLite 和内存存储 |
| `logger.shutdown` | `audit:shutdown` | 无 |

## 跨子系统事件流

以下展示关键业务流程中事件的完整传播链路，从源模块发射到最终消费者处理。

### Agent 部署流程

```
AgentDeployment.emit('deployment-completed')
  → EventRegistrar 转发 → EventBus.emit('agent:deployed')
    → 审计中间件 → AuditLogger.log({ action: 'agent:deployed' })
    → Server._bridgeStateEvents → WebSocket.broadcast('data-update', { key: 'agents' })
    → 结构化日志（如为 critical-alert）
```

### 子代理任务执行流程

```
SubagentExecutor.emit('subagent-spawned')
  → EventBus.emit('subagent:spawned')
  → AuditLogger + WebSocket.broadcast('data-update', { key: 'subagentStats' })

SubagentExecutor.emit('subagent-completed')
  → EventBus.emit('subagent:completed')
  → AffinityLearner.recordExecution()    ← 质量评分计算
  → SkillImprovementLoop.recordLearning() ← 成功/失败经验记录
  → AuditLogger + WebSocket.broadcast('data-update', { key: 'subagentStats' })
```

### 会话阶段转换流程

```
SessionManager.emit('phase-change', { from, to, sessionId })
  → EventBus.emit('session:phase-change')
  → CheckpointManager.create(sessionId, { phase, completedSkills, tokensUsed })
  → AuditLogger.log({ action: 'session:phase-change' })
  → StructuredLogger.info('Phase transition', { from, to, sessionId })
  → Server 缓存失效 → cache.delete('sessions', 'workflow', 'overview')
  → WebSocket.broadcast('data-update', { key: 'sessions' })
```

### 因果蒸馏流程

```
CausalDataBus.emit('output-published', { skillId, causalId })
  → EventRegistrar._wireCausalDistillation handler
  → CausalDataBus.getCausalChainForSkill(skillId)
  → 检查 invariantPassed（未通过则跳过）
  → 提取 cause/effect 关键字段
  → CausalMemoryStore.addCausalMemory({ cause, effect, confidence, category })
     confidence: invariantPassed ? 0.85 : 0.5
```

### 自演化治理流程

```
SelfEvolutionGovernor.emit('proposal-generated')
  → EventBus.emit('governor:proposal-generated')
  → AuditLogger.log({ action: 'governor:proposal-generated' })

  → EventBus.emit('governor:heartbeat-complete')
```

## WebSocket 事件推送

EventBus 事件通过 DashboardServer 的桥接机制实时推送到前端 Dashboard，实现运行时状态的可视化监控。

### 桥接架构

```
EventBus.emit('agent:state-change', data)
  │
  ▼
Server._bridgeStateEvents() 注册的 handler
  │
  ▼
WebSocketHandler.broadcast('data-update', { key, value, event })
  │
  ▼
JSON.stringify({ event: 'data-update', data: {...}, timestamp })
  │
  ▼
WebSocket Frame → 所有已连接客户端
```

### 事件到状态键映射（_EVENT_STATE_KEY_MAP）

Server 维护一张事件名到前端状态键的映射表，共 50+ 条映射规则：

| 事件前缀 | 状态键 | 说明 |
|----------|--------|------|
| `subagent:*` | `subagentStats` | 子代理统计 |
| `session:*` | `sessions` | 会话列表 |
| `agent:*` | `agents` / `agentMonitor` | Agent 状态/监控 |
| `collaboration-mode:*` | `collaborationMode` | 协作模式 |
| `skill-reducer:*` | `skillLayerStats` | Skill 层级统计 |
| `pair-chat:*` | `pairChatStats` | 配对对话统计 |
| `chat-chain:*` | `chatChainStats` | 链式对话统计 |
| `deepening:*` | 按 `_DEEPENING_EVENT_RULES` 映射 | 深化推理各子模块 |

### 深化推理事件规则（_DEEPENING_EVENT_RULES）

深化推理事件采用动态映射，事件名格式为 `deepening:{suffix}`，通过 suffix 匹配到对应的前端状态键：

| suffix | 状态键 | 来源模块 |
|--------|--------|---------|
| `pipeline-complete` | `deepeningPipeline` | DeepeningPipeline |
| `cache-hit` / `cache-stored` | `deepeningCache` | DeepeningCache |
| `circuit-state-change` / `rate-limited` | `deepeningCircuitBreaker` | CircuitBreaker / RateLimiter |
| `state-transition` | `deepeningStateManager` | StateManager |
| `orchestrated` | `deepeningDashboard` | DeepeningOrchestrator |
| `convergence` | `deepeningConvergence` | ConvergenceDetector |
| `metric` | `deepeningMetricsAggregator` | MetricsCollector |
| `health-checked` | `deepeningHealthMonitor` | HealthMonitor |
| `event-recorded` / `snapshot-created` / `audit-recorded` | `deepeningEventReplay` | EventStore/Replay |

### 缓存失效联动

除了推送数据更新，Server 还注册了缓存失效监听器。当特定事件触发时，自动清除对应的 API 缓存键，确保后续 HTTP 请求返回最新数据：

| 事件 | 失效缓存键 |
|------|-----------|
| `session:created` | `sessions`, `overview` |
| `session:phase-change` | `sessions`, `workflow`, `overview` |
| `session:skill-complete` | `sessions`, `overview` |
| `session:budget-warning` | `sessions` |
| `agent:state-change` | `agents`, `overview` |
| `agent:registered` | `agents`, `overview` |
| `skills-reloaded` | `skills`, `overview` |

### 广播实现细节

`WebSocketHandler.broadcast(event, data)` 将消息序列化为 JSON（包含 `event`、`data`、`timestamp`），构造 WebSocket 文本帧（opcode 0x01），遍历所有存活客户端写入。写入失败的客户端标记为 dead，从连接池中移除并销毁 socket。广播过程通过 `safeCall` 包裹，确保单个客户端异常不影响其他客户端。

### 桥接生命周期

桥接监听器注册时同步将清理函数推入 `_wsBridgeCleanup` 数组。Server 重新初始化桥接时，先遍历该数组执行所有清理函数（调用 `eventBus.off()` 移除旧监听器），再注册新监听器，确保不会重复注册。

## 事件持久化与回放

Harness 提供两层事件持久化机制：EventBus 的内存历史记录和 DeepeningEventStore/DeepeningEventReplay 的结构化存储与回放。

### EventBus 历史记录

EventBus 内置 `BoundedArray`（默认容量 1000）记录所有经过总线的事件。每条记录包含 `event`（事件名）、`data`（浅拷贝的事件数据）、`timestamp`（毫秒时间戳）。通过 `getHistory(eventFilter?)` 查询，支持按事件名过滤。`clearHistory()` 可清空历史。历史记录仅存在于内存中，不持久化到磁盘。

### DeepeningEventStore — 追加写入存储

DeepeningEventStore 是深化管道的专用事件存储，支持六种标准事件类型：

| 事件类型 | 常量 | 快捷方法 |
|---------|------|---------|
| 执行启动 | `EXECUTION_START` | `recordExecutionStart(executionId, task)` |
| 执行完成 | `EXECUTION_COMPLETE` | `recordExecutionComplete(executionId, result)` |
| 迭代完成 | `ITERATION_COMPLETE` | `recordIterationComplete(executionId, iteration, score)` |
| 收敛检测 | `CONVERGENCE_DETECTED` | `recordConvergence(executionId, reason, iteration)` |
| 缓存命中 | `CACHE_HIT` | `recordCacheHit(taskId, score)` |
| 缓存未命中 | `CACHE_MISS` | `recordCacheMiss(taskId)` |

#### 存储结构

- **主存储**：`RingBuffer`（默认容量 `DEFAULT_MAX_ENTRIES`），追加写入，超容量自动淘汰最早事件
- **类型索引**：`_byType` 对象，记录每种类型的事件计数
- **执行 ID 索引**：`_byExecution` 对象 + `_executionIds` Set，支持按执行 ID 快速查询
- **序列号**：`_sequenceNumber`，全局递增，确保事件顺序

#### 查询能力

| 方法 | 说明 |
|------|------|
| `getByType(type)` | 按事件类型过滤 |
| `getByExecution(executionId)` | 按执行 ID 过滤 |
| `getExecutionTimeline(executionId)` | 获取执行时间线（同 getByExecution） |
| `query({ type, executionId, since, until })` | 多条件组合查询 |
| `getDashboard()` | 仪表盘数据（统计 + 最近 10 条 + 执行摘要） |

#### 磁盘持久化

启用 `persistToDisk: true` 后，EventStore 支持磁盘持久化：

- **写入**：`writeAtomic()` 原子写入，路径为 `{persistPath}/deepening-events.json`，内容为 `{ events, sequenceNumber }`
- **加载**：启动时 `_loadFromDisk()` 恢复事件列表、序列号和索引
- **自动刷盘**：`_autoFlushInterval` 定时刷盘 + `_autoFlushThreshold`（默认 50）计数触发
- **关闭保护**：`_onShutdown()` 先刷盘再清空，确保数据不丢失
- **错误处理**：写入/加载失败通过 `persist-error` / `restore-error` 事件报告

### DeepeningEventReplay — 事件回放

DeepeningEventReplay 提供更灵活的事件记录与回放能力，支持自定义过滤器和速度控制。

#### 核心能力

| 能力 | 方法 | 说明 |
|------|------|------|
| 事件记录 | `record(eventType, data, metadata)` | 自动分配 ID 和时间戳，维护类型计数索引 |
| 同步回放 | `replay({ type, filters, callback })` | 逐个触发 `replay` 事件 |
| 异步回放 | `startReplay({ type, filters, callback, speed })` | 支持速度控制（毫秒/事件），可中断 |
| 停止回放 | `stopReplay()` | 中断异步回放 |
| 自定义过滤器 | `registerFilter(name, filterFn)` | 注册可复用的过滤函数 |
| 按 ID 查询 | `getEvent(id)` | 通过 `_eventById` Map 快速查找 |

#### 回放流程

```
startReplay({ type: 'iteration', speed: 100 })
  │
  ├─ _applyFilters(events, { type })
  │    按 type 过滤（含子类型匹配，如 'iteration.round1'）
  │    应用所有已注册的自定义过滤器
  │
  └─ 逐个事件循环
       ├─ callback(event)     ← 用户回调
       ├─ emit('replay', event) ← 回放事件
       ├─ await setTimeout(speed) ← 速度控制
       └─ 检查 _playing 标志 ← 支持中断
```

#### 与 EventBus 的关系

DeepeningEventStore 通过 EventRegistrar 注册到全局事件总线：

```
DeepeningEventStore.emit('event-recorded')
  → EventRegistrar 转发 → EventBus.emit('deepening:event-recorded')
  → Server._bridgeStateEvents → WebSocket.broadcast('data-update', { key: 'deepeningEventReplay' })
```

这使得前端 Dashboard 可以实时监控深化推理的事件记录状态。
