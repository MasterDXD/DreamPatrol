# 深度拆解-错误处理与异常恢复体系

## 概述

Harness 框架的错误处理体系采用分层错误类 + 错误码映射 + 自动恢复策略的三层架构，确保在多 Agent 协作环境中错误可追踪、可分类、可恢复。

## 错误类层次结构

```
Error
└── HarnessError (基类)
    ├── SessionError        — 会话生命周期错误
    ├── PermissionError     — 权限与访问控制错误
    ├── TDDGateError        — TDD 门禁违规错误
    ├── AgentError          — Agent 运行时错误
    ├── DeepeningError      — 深化推理模块错误
    ├── CausalViolationError — 因果一致性违规错误
    ├── PipelineError       — 流水线执行错误
    └── HookError           — 可编程钩子错误
```

### HarnessError 基类字段

| 字段 | 类型 | 说明 |
|------|------|------|
| `code` | string | 错误码，如 `AGENT_TIMEOUT` |
| `errorId` | string | 唯一错误标识，格式 `err_<timestamp>_<random>` |
| `severity` | string | 严重级别：`critical`/`error`/`warn`/`info` |
| `httpStatus` | number | 映射的 HTTP 状态码 |
| `timestamp` | string | ISO 格式时间戳 |
| `context` | object | 附加上下文数据 |

### 关键方法

- `toJSON()` — 结构化序列化，包含所有字段
- `isRetryable()` — 基于 RETRYABLE_CODES 集合判断是否可重试

## 错误码体系

框架定义了 88 个错误码，每个错误码映射到特定的 severity 和 httpStatus：

| 错误码 | severity | httpStatus | 说明 |
|--------|----------|------------|------|
| `INIT_FAILED` | critical | 500 | 框架初始化失败 |
| `CONFIG_INVALID` | critical | 500 | 配置校验失败 |
| `AGENT_TIMEOUT` | error | 504 | Agent 执行超时 |
| `AGENT_NOT_FOUND` | warn | 404 | Agent 未注册 |
| `SESSION_NOT_FOUND` | warn | 404 | 会话不存在 |
| `SESSION_EXPIRED` | warn | 410 | 会话已过期 |
| `PERMISSION_DENIED` | error | 403 | 权限拒绝 |
| `TDD_VIOLATION` | error | 409 | TDD 门禁违规 |
| `DEEPENING_CIRCUIT_OPEN` | warn | 503 | 深化熔断器开启 |
| `CAPACITY_EXCEEDED` | warn | 503 | 容量超限 |
| `INVALID_INPUT` | warn | 400 | 输入校验失败 |

## 错误处理策略

### 1. 初始化阶段

初始化阶段采用**快速失败**策略：

```javascript
// module-initializer.js
try {
  router = new SkillRouter(projectRoot);
  router.discover();
} catch (err) {
  throw new HarnessError('INIT_FAILED', 'SkillRouter initialization failed: ' + err.message);
}
```

关键模块（SkillRouter、SessionManager、RBACEnforcer）初始化失败时，会清理已创建的模块并抛出 `INIT_FAILED` 错误。

### 2. 运行时阶段

运行时错误采用**降级容错**策略：

- **可恢复错误**：通过 RetryEngine 自动重试（指数退避，最多3次）
- **不可恢复错误**：通过 EventBus 发送错误事件，由上层处理
- **熔断保护**：DeepeningCircuitBreaker 在连续失败达到阈值后自动开启熔断

> **v2.32.2 修复说明**：
> - **RetryEngine 关闭中断检测**：原实现中 `isShuttingDown` 为布尔值，在 `sleep()` 休眠期间无法感知关闭信号变化，导致进程关闭时重试循环无法及时退出。现已改为 getter 函数（`get isShuttingDown()`），每次读取时实时获取关闭状态，确保休眠唤醒后能立即检测到关闭信号并中断重试。
> - **DeepeningPipeline 关闭清理**：原 `shutdown()` 方法未逐一关闭子模块（调度器、控制器、缓存、熔断器等21个子模块），导致子模块持有的定时器、连接池等资源泄漏。现已修正为按依赖逆序逐一关闭所有子模块，并添加 `isShuttingDown` 守卫防止关闭期间新任务进入管道。
> - **AgentWorkflowIntegration 异步任务超时保护**：原实现中异步任务执行无超时保护，若任务永远不 resolve/reject，则反馈永远不会提交，导致工作流停滞。现已通过 `setTimeout` 配合 `settled` 守卫标志实现超时保护，超时后自动提交失败反馈，防止双重提交；超时时长取自任务记录的 `task.timeout`；定时器调用 `.unref()` 不阻止进程退出。
> - **MCPClient 待处理请求计数下溢**：原实现中 `_pendingRequestCount` 在并发清理路径下可能递减为负数（如超时清理与正常响应同时触发），导致后续计数逻辑异常。现已将递减操作改为 `Math.max(0, ...)` 约束，确保计数永不为负。
> - **AuditLogger 完整性验证栈溢出**：原实现中 `verifyIntegrity()` 使用 `Math.min(...tamperedIndices)` 计算首个篡改索引，当篡改索引数组过大时，展开运算符会导致调用栈溢出（RangeError）。现已替换为 `reduce()` 模式逐项比较，消除栈溢出风险。
> - **RBACEnforcer 加载错误限制绕过**：原实现中 `_loadDefinitionsFromDir()` 部分错误路径直接使用 `this._loadErrors.push()` 添加错误记录，绕过了 `_addLoadError()` 方法中的 `MAX_LOAD_ERRORS` 上限检查，导致大量损坏定义文件时错误数组无限增长。现已统一使用 `_addLoadError()`，确保错误数量限制始终生效。
> - **DeepeningReportGenerator 质量趋势栈溢出**：原实现中 `_qualityTrend()` 使用 `Math.max(...scores)` 计算最高质量分数，当 scores 数组过大时，展开运算符会导致调用栈溢出（RangeError）。现已替换为 `reduce()` 模式逐项比较，消除栈溢出风险。
> - **DeepeningEventStore 磁盘加载索引丢失**：原实现中 `_loadFromDisk()` 和 `_loadFromDiskAsync()` 从磁盘加载事件后未重建 `_byType` 和 `_byExecution` 索引，导致进程重启后索引过期或不完整，按类型或执行ID查询返回空结果。现已修正为加载事件后自动重建索引。

### 3. 关闭阶段

关闭阶段采用**尽力而为**策略：

```javascript
// shutdown-mixin.js
try {
  this.emit('shutdown');
} catch (err) {
  debug('ShutdownMixin', 'emit-shutdown', err);
}
```

关闭过程中的错误通过 debug 日志记录，不抛出，确保其他模块能继续关闭。

## 错误传播路径

```
Agent 执行错误
    ↓
SubagentExecutor 捕获
    ↓ emit('subagent-failed')
EventBus 转发 → 'subagent:failed'
    ↓
AuditLogger 记录
    ↓
HealthChecker 更新状态
    ↓
StructuredLogger 输出
```

## 最佳实践

1. **始终使用自定义错误类**：`throw new DeepeningError(ERROR_CODES.INVALID_INPUT, 'message')` 而非 `throw new Error('message')`
2. **错误码优先分类**：DeepeningErrorHandler 优先通过 `error.code` 分类，仅在非 HarnessError 时回退到消息匹配
3. **裸 catch 必须记录日志**：`catch (err) { debug('Module', 'context', err); }` 而非 `catch (_) {}`
4. **使用 `fromError()` 工厂函数**：将原生 Error 转换为 HarnessError 以保留错误码和 severity 信息

### 三、修复原理

**`||` vs `??`**：`||`运算符对所有假值（`0`、`""`、`false`、`null`、`undefined`）都会触发回退，而`??`（空值合并运算符）仅在值为`null`或`undefined`时才回退。对于数值型字段（`priority=0`、`timestamp=0`、`pageSize=0`）和字符串型字段（空版本号、空策略名），`||`会错误地替换合法值。

**`err.message`防护**：当catch块中的`err`不是Error实例时（如`throw "string"`或`Promise.reject({code:500})`），直接访问`err.message`会产生`undefined`或TypeError。防护表达式`err && err.message ? err.message : String(err)`确保任何类型的错误值都能安全转为字符串。

function ensureArray(val) {

[goal-executor.js](file:///e:/Harness_V1_0429/src/runtime/workflow/goal-executor.js#L906) 的 `resume(goalId, executeFn, options)` 方法存在逻辑缺陷：当调用者未传入`executeFn`或传入非函数值时，目标状态已被修改为`GOAL_STATUS.ITERATING`，`_executingGoals`集合已添加goalId，`AbortController`已创建——但没有任何执行逻辑启动，目标永远停留在`ITERATING`状态，形成**目标卡死**。

原始代码流程（修复前）：

```
resume(goalId, undefined)
  → goal.status = ITERATING          // 状态已改
  → _executingGoals.add(goalId)      // 占位已加
  → new AbortController()            // 信号已创建
  → emit('goal-resumed')             // 事件已发
  → typeof executeFn !== 'function'  // 无执行函数
  → （无任何处理）                     // 目标卡死在ITERATING
```

**卡死后果**：
- 目标无法再次执行（`_validateExecution`检测到`ITERATING`状态会拒绝）
- 目标无法再次暂停（`pause()`检测到非`EXECUTING`/`ITERATING`状态会拒绝）
- 并发槽位被永久占用（`_executingGoals`不会自动清理）
- `AbortController`泄漏（`_cancelSignals`不会自动清理）

#### 修复方案

添加`else`分支，当`executeFn`无效时执行回退处理：

```javascript
if (typeof executeFn === 'function') {
  // ... 正常执行逻辑 ...
} else {
  debug('GoalExecutor', 'resumeGoalNoExecuteFn', { goalId });
  goal.status = GOAL_STATUS.PAUSED;       // 回退到暂停状态
  goal.updatedAt = Date.now();
  this._executingGoals.delete(goalId);     // 释放并发槽位
  this._cancelSignals.delete(goalId);      // 清理信号
  this._persistGoal(goalId);
  this.emit('goal-paused', { goalId, reason: 'no-execute-fn' });
}
```

**修复要点**：
1. **状态回退**：将目标状态恢复为`PAUSED`，而非停留在`ITERATING`，使目标可被后续`resume()`调用恢复
2. **资源释放**：清理`_executingGoals`和`_cancelSignals`，防止并发槽位和信号泄漏
3. **事件通知**：发射`goal-paused`事件（附带`reason: 'no-execute-fn'`），使上层监听器感知到回退
4. **调试可追踪**：通过`debug`日志记录回退事件，便于排查调用链路问题

### catch块中的二次异常预防

`err.message`无防护不仅是日志质量问题，更可能引发**二次异常**——在catch块中抛出新异常，导致原始错误信息完全丢失：

```javascript

  riskyOperation();
} catch (err) {
  this.emit('error', { message: err.message });  // 二次异常！
}

// 安全：任何err类型都能安全转为字符串
try {
  riskyOperation();
} catch (err) {
  this.emit('error', { message: err && err.message ? err.message : String(err) });
}
```

**二次异常的连锁效应**：
1. 原始错误信息丢失（被TypeError覆盖）
2. catch块内的清理逻辑被跳过（资源泄漏）
3. 上层catch可能再次触发二次异常（错误雪崩）
4. 最终表现为无关的TypeError，排查困难

## SQLite null安全体系

### 概述

[sqlite-store.js](file:///e:/Harness_V1_0429/src/runtime/infrastructure/sqlite-store.js) 作为框架的持久化核心，直接与better-sqlite3交互。SQLite查询结果可能返回`null`/`undefined`（表为空、行不存在、列为NULL），若不加防护直接访问属性，会引发TypeError或逻辑错误。框架建立了两层null安全防护体系。

### 第一层：`.get()?.cnt ?? 0` 模式 — 查询结果null安全

**问题场景**：`SELECT COUNT(*) as cnt FROM table` 在表为空时，better-sqlite3的`.get()`仍返回`{ cnt: 0 }`，但其他查询（如`SELECT * FROM table WHERE id = ?`）在行不存在时返回`undefined`。若直接访问`result.cnt`，当`result`为`undefined`时抛出TypeError。

**防护模式**：

```javascript
this._db.prepare('SELECT COUNT(*) as cnt FROM knowledge').get()?.cnt ?? 0
```

分解为三步：
1. `.get()` — 执行查询，返回行对象或`undefined`
2. `?.cnt` — 可选链访问`cnt`属性，`undefined`时安全返回`undefined`而非TypeError
3. `?? 0` — 空值合并，`undefined`或`null`时回退为`0`

**使用统计**：sqlite-store.js中共**14处**使用此模式：

| 位置 | 查询目标 | 回退值 |
|------|---------|--------|
| `_migrateFromJson()` | knowledge表计数 | `0` |
| `_migrateFromJson()` | skill_learnings表计数 | `0` |
| `getMemoryVerificationStats()` | memory_entries总数 | `0` |
| `getMemoryUsage()` | knowledge表计数 | `0` |
| `getMemoryUsage()` | skill_learnings计数 | `0` |
| `getMemoryUsage()` | causal_chain计数 | `0` |
| `getMemoryUsage()` | shared_learnings计数 | `0` |
| `getStats()` | knowledge计数 | `0` |
| `getStats()` | session_summaries计数 | `0` |
| `getStats()` | skill_learnings计数 | `0` |
| `getStats()` | shared_learnings计数 | `0` |
| `getStats()` | memory_entries计数 | `0` |
| `getStats()` | user_profile计数 | `0` |
| `getStats()` | affinity_records计数 | `0` |

### 第二层：`!this._db` 守卫模式 — 关闭后操作防护

**问题场景**：SqliteStore关闭后`this._db`被置为`null`，若此时有异步操作尝试访问数据库，会抛出TypeError。在多Agent并发环境中，关闭信号与待处理操作之间存在竞态窗口。

**防护模式**：

```javascript
getKnowledge(category) {
  if (!this._db) return [];    // 关闭后安全降级
  return this._stmts.getKnowledge.all(category ?? 'general');
}
```

每个公开方法入口处添加`!this._db`守卫，根据方法语义返回类型安全的默认值：

| 返回类型 | 默认值 | 方法示例 |
|----------|--------|---------|
| 数组 | `[]` | `getKnowledge()`、`getSessions()`、`getSkillLearnings()` |
| 对象/单行 | `null` | `getSession()`、`getUserPreference()`、`getAffinity()` |
| 布尔 | `false` | `addKnowledge()`、`updateSession()`、`addMemory()` |
| 数值 | `0` | `getMemoryCharCount()`、`invalidateMemoriesByPattern()` |
| 统计对象 | `{ total: 0, ... }` | `getStats()`、`getMemoryVerificationStats()` |
| void | （直接return） | `decayMemoryImportance()` |

**使用统计**：sqlite-store.js中共**32处**`!this._db`守卫，覆盖所有公开方法。

### 两层防护的协同关系

```
调用者 → 公开方法
         ↓
    [!this._db 守卫]  ← 第一道防线：关闭后安全降级
         ↓ (通过)
    [SQL查询执行]
         ↓
    [?.cnt ?? 0]      ← 第二道防线：查询结果null安全
         ↓
    返回安全值
```

- **第一层**防止"数据库已关闭"的TypeError（`null.all()` / `null.prepare()`）
- **第二层**防止"查询结果为空"的TypeError（`undefined.cnt`）
- 两层独立生效，即使第一层通过，第二层仍提供保护

### 与_ensureActive()的区别

SqliteStore还提供了`_ensureActive()`方法，在**内部关键操作**中抛出`DeepeningError('STORE_SHUTDOWN')`：

```javascript
_ensureActive() {
  if (!this._db) {
    throw new DeepeningError('STORE_SHUTDOWN', 'SqliteStore has been shut down');
  }
}
```

| 防护方式 | 行为 | 适用场景 |
|----------|------|---------|
| `!this._db` + 安全降级 | 静默返回默认值 | 公开查询方法（getKnowledge等） |
| `_ensureActive()` + 抛出异常 | 中断调用链 | 内部写操作（需确保数据一致性） |

**设计决策**：查询方法采用安全降级（返回空结果优于崩溃），写操作采用快速失败（静默丢弃写入比报错更危险）。

      if (!res.headersSent) send({ error: 'Internal server error' }, 500);
      else if (!res.writableEnded) safeCall(function() { res.end(); }, 'Dashboard', 'postEndFallback');

  });
});

`_executeHandle()`中`Promise.race([executePromise, timeoutPromise])`，当executePromise先完成时，timeoutPromise中的`setTimeout`仍在运行。虽然`settled`检查会阻止reject，但定时器资源未释放，阻止Node.js事件循环退出。修复：在try/catch中添加`clearTimeout(handle._timeoutId)`。

### 三、Promise无settled保护（6处HIGH→MEDIUM）

多个Promise构造函数中，多个异步回调（timeout/error/response）可能竞态调用resolve/reject，缺少`settled`标志保护导致双重结算：

| 文件 | 方法 | 竞态路径 |
|------|------|----------|
| mcp-client.js | `_sendStdioRequest` | timeout / write error / catch 三路竞态 |
| retry-engine.js | `_sleep` | setTimeout / setInterval shutdown 两路竞态 |
| mem0-adapter.js | `_makeRequest` | res.error / res.end reject / req.error 三路竞态 |
| honcho-adapter.js | `_makeRequest` | 同上 |
| hindsight-adapter.js | `_makeRequest` | 同上 |
| deepening-resource-manager.js | `acquire` | timeout / waiter.resolve 两路竞态 |

修复模式：添加`settled`标志 + `safeResolve`/`safeReject`包装函数。

### 四、Map迭代中删除元素（5处严重）

`for...of`迭代Map时直接调用`map.delete(key)`，ECAScript规范虽不抛异常，但可能导致跳过条目，清理不完整：

| 文件 | 方法 | 影响 |
|------|------|------|
| sqlite-store.js | `cleanupOrphanedInstances` | 多孤立实例时跳过条目 |
| context-compression-engine.js | `_checkCausalUpstream` | 过期缓存清理不完整 |
| structured-intent.js | `clearSession` | 会话参数清理不完整 |
| deepening-task-scheduler.js | `_evictCompleted` | 任务淘汰跳过条目 |
| collaboration-mode-router.js | cleanupTimer | 过期覆盖清理不完整 |

修复模式：先收集keys到数组`toDelete`，再在独立循环中删除。

## R38 修复记录 — async/await逻辑缺陷 + JSON.parse安全加固 + ReDoS防护 + 原型污染纵深防御

### 一、async方法未await导致功能完全失效（1处HIGH）

**HIGH: graph-rag.js _queryWithGraphify()**

`_queryWithGraphify()`是同步方法，但调用的`graphifyCompiler.query()`是async方法（返回Promise）。`nameResult`是Promise对象而非实际查询结果，`nameResult.results`始终为undefined，Graphify查询结果永远不被使用。修复：将`query()`和`_queryWithGraphify()`改为async，正确await。

### 二、ReDoS动态正则注入（1处HIGH）

**HIGH: iron-rule-engine.js _generateCheckFromPattern()**

`addPatternRule()`接受任意字符串pattern参数，直接编译为RegExp，未进行嵌套量词检测或长度限制。恶意pattern（如`(a+)+`）可导致灾难性回溯。同项目中`deepening-validator.js`等已有`REDOS_DANGEROUS_RE`检测，但iron-rule-engine未采用。修复：添加ReDoS检测+200字符长度限制+try-catch。

### 三、JSON.parse无try-catch（1处MEDIUM）

**MEDIUM: browser-use-adapter.js extractByTemplate() MCP模式**

MCP模式分支中`JSON.parse(content)`解析网络返回数据，content可能不是有效JSON。同方法DIRECT模式分支已有try-catch保护，MCP模式遗漏。修复：展开三元表达式为if-else + try-catch。

### 四、展开运算符原型污染纵深防御（6处MEDIUM）

4个文件的构造函数中使用`{...defaults, ...options}`模式合并构造参数，展开运算符虽不触发`__proto__`原型链修改，但仍会将`constructor`/`prototype`作为普通属性复制。修复：替换为`safeAssign()`统一安全策略。

| 文件 | 修复处数 |
|------|----------|
| quality-scorer.js | 2处（weights + thresholds） |
| ai-code-trust-scorer.js | 2处（thresholds + riskIndicators） |
| delivery-efficiency-meter.js | 1处（expectedDistribution） |
| deepening-service-registry.js | 1处（register cfg） |

### 五、shutdown路径Promise未处理（1处LOW）

**LOW: memory-sync-coordinator.js _onShutdown()**

shutdown路径中`targetStore.writeFn(item.data)`可能返回Promise（外部记忆提供商的write方法是async），但_onShutdown是同步方法无法await。修复：检测返回值是否为Promise，若是则附加`.catch()`防止unhandled rejection。
