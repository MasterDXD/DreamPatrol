## 模块群概述

深化调度与执行模块群是Harness多Agent框架深化子系统的核心执行层，涵盖任务调度、优先级排队、数据管道、部署管理、特性标志、服务注册、模块生命周期、插件系统、通知分发、工作流模板、配置管理、数据验证、重试策略、优雅关闭和安全防护等16个模块。这些模块共同构成了从"任务提交"到"安全执行"再到"优雅退出"的完整运行时链路，为上层深化推理编排器（DeepeningOrchestrator）和深化管道（DeepeningPipeline）提供可靠的底层调度与执行能力。

该模块群的设计理念是：**分层解耦、策略驱动、安全可控**。通过优先级队列和任务调度器实现任务的有序调度；通过数据管道和重试策略实现可靠执行；通过配置管理、特性标志和服务注册实现运行时弹性；通过安全守卫和优雅关闭实现安全可控的生命周期管理。

## 共同设计模式

### 1. DeepeningBase继承

所有16个模块均继承自`DeepeningBase`，自动获得：
- EventEmitter事件能力
- ShutdownMixin关闭生命周期
- attach*依赖注入方法
- `isHealthy()`/`getStats()`标准接口

### 2. 策略模式

- **DeepeningRetryPolicy**：四种退避策略（fixed/linear/exponential/exponential_jitter）
- **DeepeningFeatureFlags**：四种标志状态（on/off/percentage/variants）
- **DeepeningValidator**：三级验证严格度（strict/moderate/permissive）

### 3. 观察者模式

- **DeepeningConfigManager**：Watcher回调监听配置变更
- **DeepeningNotifier**：通道订阅模式匹配事件分发
- **DeepeningServiceRegistry**：心跳状态变更事件

### 4. 容量保护

- **DeepeningTaskQueue**：maxSize容量限制
- **DeepeningPriorityQueue**：maxSize + overflow事件
- **DeepeningTaskScheduler**：maxCompletedTasks + 自动淘汰
- **DeepeningRetryPolicy**：maxPolicies + 最旧淘汰
- **DeepeningSecurityGuard**：maxExecutions + maxAgentCallsPerExecution

### 5. 废弃迁移

部分模块已标记为废弃，推荐使用基础设施子系统的对应模块：

| 废弃模块 | 推荐替代 |
|---------|---------|
| DeepeningPriorityQueue | PriorityQueue（runtime/infrastructure/priority-queue） |
| DeepeningPluginSystem | PluginManager（runtime/infrastructure/plugin-manager） |
| DeepeningWorkflowTemplate | WorkflowTemplate（runtime/workflow/workflow-template） |

## DeepeningTaskScheduler详解

### 职责概述

DeepeningTaskScheduler提供任务调度能力，支持一次性任务、周期性任务和延迟执行，内置重试机制、并发控制和状态管理。任务在调度后自动执行，支持按名称批量取消，已完成任务自动淘汰防止内存泄漏。

### 构造函数参数

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `options.maxCompletedTasks` | number | 200 | 已完成任务最大保留数，超出自动淘汰 |
| `options.maxConcurrent` | number | 10 | 最大并发执行数 |

### 静态常量

| 常量 | 值 |
|------|-----|
| `TASK_STATES` | `{ PENDING, RUNNING, COMPLETED, FAILED, CANCELLED }` |
| `SCHEDULE_TYPES` | `{ ONCE, RECURRING, CRON }` |

### 核心API

| 方法 | 参数 | 返回值 | 说明 |
|------|------|--------|------|
| `schedule(name, handler, options)` | name: string, handler: Function, options: object | string | 调度任务，返回任务ID |
| `cancel(id)` | id: string | boolean | 按ID取消任务 |
| `cancelByName(name)` | name: string | number | 按名称取消所有pending任务，返回取消数量 |
| `getTask(id)` | id: string | Object\|null | 获取任务信息（不含handler） |
| `getPending()` | — | Object[] | 获取所有pending状态任务 |
| `getRunning()` | — | Object[] | 获取所有running状态任务 |
| `getByName(name)` | name: string | Object[] | 按名称获取任务列表 |
| `getStats()` | — | Object | 统计信息 |

#### schedule选项

| 选项 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `scheduleType` | string | 'once' | 调度类型：once/recurring |
| `delay` | number | — | 延迟执行时间（ms） |
| `interval` | number | — | 周期执行间隔（ms），recurring模式必填 |
| `retries` | number | 0 | 最大重试次数 |

### 事件列表

| 事件名 | 触发时机 | 数据 |
|--------|---------|------|
| `scheduled` | 任务调度成功 | `{ name, scheduleType }` |
| `started` | 任务开始执行 | `{ id, name }` |
| `completed` | 任务执行成功 | `{ id, name }` |
| `failed` | 任务执行失败（含重试耗尽） | `{ id, name, error }` |
| `retrying` | 任务重试中 | `{ name, retryCount }` |
| `cancelled` | 任务取消 | `{ name }` |

### 使用示例

```javascript
const DeepeningTaskScheduler = require('./src/runtime/deepening/deepening-task-scheduler');

const scheduler = new DeepeningTaskScheduler({ maxConcurrent: 5, maxCompletedTasks: 100 });

scheduler.on('completed', ({ id, name }) => {
  console.log(`任务完成: ${name} (${id})`);
});
scheduler.on('failed', ({ id, name, error }) => {
  console.error(`任务失败: ${name} - ${error}`);
});

const taskId = scheduler.schedule('data-sync', async () => {
  await syncDataFromRemote();
}, { retries: 3, delay: 5000 });

const recurringId = scheduler.schedule('health-check', async () => {
  await checkServiceHealth();
}, { scheduleType: 'recurring', interval: 30000 });

scheduler.cancel(taskId);
scheduler.cancelByName('health-check');

console.log(scheduler.getStats());
```

### 与其他模块的交互关系

- 被`DeepeningModuleRegistry`定义为infrastructure层级模块，可懒加载
- 通过`DeepeningBase.attachScheduler()`注入到其他深化模块
- 与`DeepeningRetryPolicy`互补：Scheduler提供任务级重试，RetryPolicy提供策略级重试

## DeepeningTaskQueue详解

### 职责概述

DeepeningTaskQueue提供基于最小堆的优先级任务队列，支持三级优先级（高/普通/低）、容量限制和任务取消。出队时自动跳过已取消的任务。

### 构造函数参数

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `options.concurrency` | number | 1 | 并发数（预留） |
| `options.maxSize` | number | 1000 | 队列最大容量 |

### 核心API

| 方法 | 参数 | 返回值 | 说明 |
|------|------|--------|------|
| `enqueueHigh(data)` | data: any | string | 高优先级入队（priority=1） |
| `enqueueNormal(data)` | data: any | string | 普通优先级入队（priority=2） |
| `enqueueLow(data)` | data: any | string | 低优先级入队（priority=3） |
| `dequeue()` | — | Object\|null | 出队最高优先级任务，自动跳过已取消 |
| `cancelTask(id)` | id: string | boolean | 取消任务（惰性删除） |
| `getTask(id)` | id: string | Object\|null | 获取任务 |
| `getQueueSize()` | — | number | 当前队列大小 |
| `getStats()` | — | Object | 统计信息 |

### 事件列表

继承DeepeningBase事件，无自定义事件。

### 使用示例

```javascript
const DeepeningTaskQueue = require('./src/runtime/deepening/deepening-task-queue');

const queue = new DeepeningTaskQueue({ maxSize: 500, concurrency: 3 });

const id1 = queue.enqueueHigh({ type: 'urgent', payload: 'critical-data' });
const id2 = queue.enqueueNormal({ type: 'regular', payload: 'normal-data' });
const id3 = queue.enqueueLow({ type: 'background', payload: 'cleanup-data' });

queue.cancelTask(id3);

const task = queue.dequeue();
console.log('出队任务:', task.data, '优先级:', task.priority);

console.log(queue.getStats());
```

### 与其他模块的交互关系

- 内部使用`MinHeap`（utils/min-heap）实现优先级排序
- 与`DeepeningPriorityQueue`功能重叠，但API更简洁（三级固定优先级）
- 被`DeepeningModuleRegistry`定义为infrastructure层级模块

## DeepeningPriorityQueue详解

### 职责概述

DeepeningPriorityQueue提供更丰富的堆优先级队列实现，支持五级优先级（CRITICAL/HIGH/NORMAL/LOW/IDLE）、延迟出队、暂停/恢复、按优先级查询和容量溢出保护。

> **⚠️ 已废弃**：推荐使用`PriorityQueue`（runtime/infrastructure/priority-queue）替代。

### 构造函数参数

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `options.maxSize` | number | DEFAULT_MAX_ENTRIES | 队列最大容量 |
| `options.concurrency` | number | 1 | 并发数（预留） |

### 静态常量

| 常量 | 值 |
|------|-----|
| `PRIORITY_LEVELS` | `{ CRITICAL: 0, HIGH: 1, NORMAL: 2, LOW: 3, IDLE: 4 }` |

### 核心API

| 方法 | 参数 | 返回值 | 说明 |
|------|------|--------|------|
| `enqueue(task, options)` | task: Object, options: object | string\|null | 入队，溢出返回null |
| `dequeue()` | — | Object\|null | 出队，跳过已取消和未到延迟时间的任务 |
| `peek()` | — | Object\|null | 查看队首（不移除） |
| `cancel(id)` | id: string | boolean | 取消任务 |
| `pause()` | — | true | 暂停出队 |
| `resume()` | — | true | 恢复出队 |
| `isPaused()` | — | boolean | 是否暂停 |
| `getPendingCount()` | — | number | 待处理任务数 |
| `getByPriority(level)` | level: number | Object[] | 按优先级查询任务 |
| `clear()` | — | true | 清空队列 |
| `getSize()` | — | number | 等同getPendingCount |
| `getStats()` | — | Object | 统计信息 |

#### enqueue选项

| 选项 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `priority` | number | 2 | 优先级（0-4） |
| `delay` | number | 0 | 延迟出队时间（ms） |

### 事件列表

| 事件名 | 触发时机 | 数据 |
|--------|---------|------|
| `enqueued` | 任务入队 | `{ id, name, priority }` |
| `overflow` | 队列溢出 | `{ task }` |
| `cancelled` | 任务取消 | `{ id }` |
| `paused` | 队列暂停 | — |
| `resumed` | 队列恢复 | — |
| `cleared` | 队列清空 | — |

### 使用示例

```javascript
const DeepeningPriorityQueue = require('./src/runtime/deepening/deepening-priority-queue');

const pq = new DeepeningPriorityQueue({ maxSize: 200 });

pq.enqueue({ name: 'critical-alert', data: 'server-down' }, { priority: DeepeningPriorityQueue.PRIORITY_LEVELS.CRITICAL });
pq.enqueue({ name: 'normal-task', data: 'process-data' }, { priority: DeepeningPriorityQueue.PRIORITY_LEVELS.NORMAL });
pq.enqueue({ name: 'delayed-task', data: 'report' }, { priority: DeepeningPriorityQueue.PRIORITY_LEVELS.LOW, delay: 60000 });

pq.pause();
pq.resume();

const task = pq.dequeue();
console.log('任务:', task.name, '优先级:', task.priority);

console.log(pq.getByPriority(0));
console.log(pq.getStats());
```

### 与其他模块的交互关系

- 内部使用`MinHeap`和`DEFAULT_MAX_ENTRIES`常量
- 与`DeepeningTaskQueue`功能重叠，但提供更细粒度的优先级控制
- 废弃后推荐迁移至`PriorityQueue`（runtime/infrastructure/priority-queue）

## DeepeningDataPipeline详解

### 职责概述

DeepeningDataPipeline提供多阶段数据处理管道，支持命名管道创建、阶段添加/移除、可选阶段、阶段超时和错误处理器注册。数据按阶段顺序流经各处理器，任一阶段失败可选择跳过（optional）或终止管道。

### 构造函数参数

无特殊参数，继承DeepeningBase默认构造。

### 核心API

| 方法 | 参数 | 返回值 | 说明 |
|------|------|--------|------|
| `create(name)` | name: string | this | 创建命名管道（幂等） |
| `remove(name)` | name: string | boolean | 删除管道 |
| `addStage(pipelineName, stageName, handler, options)` | pipelineName: string\|null, stageName: string, handler: Function, options: object | boolean | 添加阶段，pipelineName为null时使用默认管道 |
| `removeStage(pipelineName, stageName)` | pipelineName: string\|null, stageName: string | boolean | 移除阶段 |
| `addErrorHandler(pipelineName, handler)` | pipelineName: string\|null, handler: Function | boolean | 添加错误处理器 |
| `process(pipelineName, data)` | pipelineName: string\|null, data: any | Promise\<any\> | 执行管道，返回最终结果 |
| `getPipelineInfo(name)` | name: string | Object\|null | 获取管道信息 |

#### addStage选项

| 选项 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `optional` | boolean | false | 可选阶段，失败时跳过 |
| `timeout` | number | 0 | 阶段超时时间（ms），0为不限 |

### 事件列表

| 事件名 | 触发时机 | 数据 |
|--------|---------|------|
| `stepAdded` | 阶段添加 | `{ pipeline, name }` |
| `stage-skipped` | 可选阶段跳过 | `{ pipeline, stage, error }` |
| `stage-error` | 阶段错误 | Error + `{ pipeline, stage }` |
| `error-handler-error` | 错误处理器异常 | Error + `{ stage }` |

### 使用示例

```javascript
const DeepeningDataPipeline = require('./src/runtime/deepening/deepening-data-pipeline');

const pipeline = new DeepeningDataPipeline();

pipeline.create('etl');
pipeline.addStage('etl', 'extract', async (data) => {
  return await fetchDataFromSource(data);
}, { timeout: 5000 });
pipeline.addStage('etl', 'transform', async (data) => {
  return transformData(data);
});
pipeline.addStage('etl', 'enrich', async (data) => {
  return await enrichWithMetadata(data);
}, { optional: true });
pipeline.addStage('etl', 'load', async (data) => {
  return await loadToDatabase(data);
});
pipeline.addErrorHandler('etl', (err, stageName) => {
  console.error(`管道错误 [${stageName}]:`, err.message);
});

const result = await pipeline.process('etl', { source: 'api-endpoint' });
console.log(result);

console.log(pipeline.getPipelineInfo('etl'));
console.log(pipeline.getStats());
```

### 与其他模块的交互关系

- 被`DeepeningWorkflowTemplate`用于创建管道配置
- 被`DeepeningModuleRegistry`定义为infrastructure层级模块
- 与`DeepeningRetryPolicy`互补：Pipeline处理数据流，RetryPolicy处理执行重试

## DeepeningDeployment详解

### 职责概述

DeepeningDeployment提供模块部署管理，支持配置验证、版本化部署和部署历史查询。部署时自动添加时间戳和版本号。

> **@internal**：无外部消费者，仅供内部使用。

### 构造函数参数

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `options.deployPath` | string | './deploy' | 部署路径 |
| `options.backupPath` | string | './backup' | 备份路径 |

### 核心API

| 方法 | 参数 | 返回值 | 说明 |
|------|------|--------|------|
| `deploy(config)` | config: Object | Object | 执行部署，自动添加deployedAt和version |
| `listDeployments()` | — | Object[] | 列出所有部署记录 |
| `getCurrentDeployment()` | — | Object\|null | 获取当前部署 |
| `validateConfig(config)` | config: Object | true | 验证配置（必须包含非空agents数组） |
| `createDeploymentTemplate()` | — | Object | 创建部署模板 |

#### 部署模板结构

```javascript
{
  agents: [],           // Agent列表（必填）
  maxIterations: 4,     // 最大迭代次数
  config: {}            // 扩展配置
}
```

## DeepeningRetryPolicy详解

### 职责概述

DeepeningRetryPolicy提供策略化的重试机制，支持四种退避策略（固定/线性/指数/指数抖动）、可重试错误过滤、策略定义和执行。策略定义后通过`execute()`方法自动执行重试逻辑。

### 构造函数参数

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `options.maxPolicies` | number | 50 | 最大策略数，超出淘汰最旧 |
| `options.defaultMaxRetries` | number | 3 | 默认最大重试次数 |
| `options.defaultBaseDelay` | number | 100 | 默认基础延迟（ms） |
| `options.defaultMaxDelay` | number | DEFAULT_RETRY_MAX_DELAY_MS | 默认最大延迟（ms） |

### 静态常量

| 常量 | 值 |
|------|-----|
| `BACKOFF_STRATEGIES` | `{ FIXED, LINEAR, EXPONENTIAL, EXPONENTIAL_JITTER }` |

### 退避策略计算

| 策略 | 公式 |
|------|------|
| fixed | base |
| linear | base × attempt |
| exponential | min(base × 2^(attempt-1), maxDelay) |
| exponential_jitter | min(base × 2^(attempt-1) × (0.5 + random×0.5), maxDelay) |

### 核心API

| 方法 | 参数 | 返回值 | 说明 |
|------|------|--------|------|
| `definePolicy(name, options)` | name: string, options: object | true | 定义重试策略 |
| `getPolicyNames()` | — | string[] | 获取所有策略名 |
| `getPolicy(name)` | name: string | Object\|null | 获取策略定义 |
| `computeDelay(name, attempt)` | name: string, attempt: number | number | 计算退避延迟 |
| `execute(name, fn)` | name: string, fn: Function | Promise\<any\> | 执行带重试的函数 |
| `removePolicy(name)` | name: string | boolean | 移除策略 |
| `resetPolicy(name)` | name: string | boolean | 重置策略统计 |
| `getStats()` | — | Object | 统计信息 |

#### definePolicy选项

| 选项 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `maxRetries` | number | defaultMaxRetries | 最大重试次数 |
| `baseDelay` | number | defaultBaseDelay | 基础延迟（ms） |
| `maxDelay` | number | defaultMaxDelay | 最大延迟（ms） |
| `backoffStrategy` | string | 'exponential' | 退避策略 |
| `retryableErrors` | string[] | [] | 可重试错误消息关键字 |

### 事件列表

| 事件名 | 触发时机 | 数据 |
|--------|---------|------|
| `policyDefined` | 策略定义 | `{ name, maxRetries }` |
| `policyRemoved` | 策略移除 | `{ name }` |
| `policyReset` | 策略重置 | `{ name }` |
| `retrying` | 重试中 | `{ policy, attempt }` |
| `retrySucceeded` | 重试成功 | `{ attempt }` |
| `nonRetryable` | 不可重试错误 | `{ policy }` |
| `retriesExhausted` | 重试耗尽 | `{ maxRetries }` |

### 使用示例

```javascript
const DeepeningRetryPolicy = require('./src/runtime/deepening/deepening-retry-policy');

const retry = new DeepeningRetryPolicy({
  defaultMaxRetries: 3,
  defaultBaseDelay: 200,
  defaultMaxDelay: 10000
});

retry.definePolicy('api-call', {
  maxRetries: 5,
  baseDelay: 500,
  maxDelay: 30000,
  backoffStrategy: 'exponential_jitter',
  retryableErrors: ['ECONNRESET', 'ETIMEDOUT', '503']
});

retry.on('retrying', ({ policy, attempt }) => {
  console.log(`重试策略 ${policy}: 第${attempt}次`);
});
retry.on('retriesExhausted', ({ maxRetries }) => {
  console.log(`重试耗尽，最大重试次数: ${maxRetries}`);
});

try {
  const result = await retry.execute('api-call', async () => {
    return await callExternalAPI();
  });
  console.log('结果:', result);
} catch (e) {
  console.error('最终失败:', e.message);
}

console.log(retry.computeDelay('api-call', 1));
console.log(retry.computeDelay('api-call', 2));
console.log(retry.computeDelay('api-call', 3));

console.log(retry.getStats());
```

- 被`DeepeningModuleRegistry`定义为infrastructure层级模块
- 与`DeepeningTaskScheduler`互补：Scheduler提供任务级简单重试，RetryPolicy提供策略级精细重试
- 与`RetryEngine`（runtime/infrastructure/retry-engine）功能重叠，但RetryPolicy更轻量
- 使用`ensurePositiveNumber`（utils/param-validator）确保延迟参数有效

## DeepeningGracefulShutdown详解

### 职责概述

DeepeningGracefulShutdown提供优雅关闭协调能力，支持三阶段关闭流程（drain→stop→cleanup）、步骤依赖排序、超时保护和进度追踪。关闭时按阶段和顺序依次执行所有注册的关闭步骤。

### 构造函数参数

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `options.timeout` | number | DEFAULT_SHUTDOWN_TIMEOUT_MS | 单步骤超时时间（ms） |

### 静态常量

| 常量 | 值 |
|------|-----|
| `SHUTDOWN_PHASES` | `{ DRAIN, STOP, CLEANUP, DONE }` |

### 三阶段关闭流程

```
shutdown()
  │
  ├── Phase 1: DRAIN（排空）
  │     └── 停止接收新任务，等待进行中任务完成
  │
  ├── Phase 2: STOP（停止）
  │     └── 停止所有服务，断开连接
  │
  ├── Phase 3: CLEANUP（清理）
  │     └── 释放资源，持久化状态
  │
  └── Phase 4: DONE（完成）
        └── 发出shutdownCompleted事件
```

### 核心API

| 方法 | 参数 | 返回值 | 说明 |
|------|------|--------|------|
| `addStep(name, handler, options)` | name: string, handler: Function, options: object | boolean | 添加关闭步骤 |
| `removeStep(name)` | name: string | boolean | 移除关闭步骤 |
| `getSteps()` | — | Object[] | 获取所有步骤 |
| `shutdown()` | — | Promise\<void\> | 执行优雅关闭 |
| `shutdownManager()` | — | Promise\<void\> | 清空步骤后关闭 |
| `getProgress()` | — | Object | 获取关闭进度 |
| `isShuttingDown()` | — | boolean | 是否正在关闭 |
| `getPhase()` | — | string\|null | 当前阶段 |
| `reset()` | — | true | 重置关闭状态（恢复监听器） |
| `getStats()` | — | Object | 统计信息 |

#### addStep选项

| 选项 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `phase` | string | 'cleanup' | 关闭阶段：drain/stop/cleanup |
| `order` | number | 0 | 同阶段内排序 |
| `dependsOn` | string[] | [] | 依赖的其他步骤名 |

### 事件列表

| 事件名 | 触发时机 | 数据 |
|--------|---------|------|
| `stepAdded` | 步骤添加 | `{ name, phase }` |
| `shutdownStarted` | 关闭开始 | `{ steps }` |
| `phaseStarted` | 阶段开始 | `{ phase }` |
| `phaseCompleted` | 阶段完成 | `{ phase }` |
| `stepStarted` | 步骤开始 | `{ name }` |
| `stepCompleted` | 步骤完成 | `{ name, duration }` |
| `stepFailed` | 步骤失败 | `{ name, error }` |
| `shutdownCompleted` | 关闭完成 | `{ completed, failed, duration }` |
| `shutdownManager` | 管理器关闭 | — |
| `reset` | 状态重置 | — |

### 使用示例

```javascript
const DeepeningGracefulShutdown = require('./src/runtime/deepening/deepening-graceful-shutdown');

const shutdown = new DeepeningGracefulShutdown({ timeout: 10000 });

shutdown.addStep('stop-accepting', async () => {
  server.stopAcceptingNewConnections();
}, { phase: 'drain', order: 1 });

shutdown.addStep('wait-requests', async () => {
  await server.waitForPendingRequests(5000);
}, { phase: 'drain', order: 2, dependsOn: ['stop-accepting'] });

shutdown.addStep('close-connections', async () => {
  await connectionPool.closeAll();
}, { phase: 'stop', order: 1 });

shutdown.addStep('flush-cache', async () => {
  await cache.flush();
}, { phase: 'cleanup', order: 1 });

shutdown.addStep('save-state', async () => {
  await stateManager.persist();
}, { phase: 'cleanup', order: 2, dependsOn: ['flush-cache'] });

shutdown.on('stepCompleted', ({ name, duration }) => {
  console.log(`步骤完成: ${name} (${duration}ms)`);
});
shutdown.on('shutdownCompleted', ({ completed, failed, duration }) => {
  console.log(`关闭完成: ${completed}成功, ${failed}失败, 总耗时${duration}ms`);
});

process.on('SIGTERM', () => shutdown.shutdown());

console.log(shutdown.getProgress());
console.log(shutdown.getStats());
```

- 被`DeepeningModuleRegistry`定义为infrastructure层级模块
- 与`DeepeningBase`的ShutdownMixin互补：ShutdownMixin提供简单的关闭标记，GracefulShutdown提供协调式关闭
- 关闭时保存事件监听器，`reset()`时恢复
- 使用`safeExecute`确保关闭过程中emit不抛异常

## DeepeningSecurityGuard详解

### 职责概述

DeepeningSecurityGuard提供安全防护能力，内置Aho-Corasick多模式匹配算法检测禁止模式，支持Agent白名单、执行调用限制和管道配置验证。Aho-Corasick算法实现O(n+m+z)时间复杂度的多模式搜索，适用于大量禁止模式的实时检测。

### 构造函数参数

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `options.maxExecutions` | number | 200 | 最大跟踪执行数 |
| `options.maxAgentCallsPerExecution` | number | 100 | 每次执行最大Agent调用数 |

### Aho-Corasick算法

内部实现`_AhoCorasick`类，提供高效的多模式字符串匹配：

```
addPattern(pattern) → 构建Trie树
_build()            → 构建失败指针（BFS）
search(text)        → O(n)时间搜索所有匹配模式
```

### 核心API

| 方法 | 参数 | 返回值 | 说明 |
|------|------|--------|------|
| `validatePipelineConfig(config)` | config: Object | true | 验证管道配置（必须包含非空agents数组） |
| `validateAgentExecution(agentId, context)` | agentId: string, context: any | true | 验证Agent执行权限 |
| `addAllowedAgent(agentId)` | agentId: string | boolean | 添加允许的Agent |
| `addForbiddenPattern(pattern)` | pattern: string | boolean | 添加禁止模式（最长256字符） |
| `checkForbiddenPatterns(data)` | data: string\|Object | boolean | 检查数据是否包含禁止模式，检测到抛出HarnessError |
| `startExecution(executionId)` | executionId: string | boolean | 开始执行跟踪 |
| `updateExecution(executionId)` | executionId: string | boolean | 更新执行调用计数，超限返回false |
| `recordAgentCall(executionId)` | executionId: string | boolean | 记录Agent调用（等同updateExecution） |
| `endExecution(executionId)` | executionId: string | true | 结束执行跟踪 |
| `getExecutionStats(executionId)` | executionId: string | Object\|undefined | 获取执行统计 |
| `startPeriodicCheck()` | — | true | 启动周期检查（预留） |
| `stopPeriodicCheck()` | — | true | 停止周期检查（预留） |
| `getStats()` | — | Object | 统计信息 |

### 事件列表

| 事件名 | 触发时机 | 数据 |
|--------|---------|------|
| `execution-limit-exceeded` | Agent调用超限 | `{ executionId, agentCalls }` |

### 使用示例

```javascript

const guard = new DeepeningSecurityGuard({
  maxExecutions: 100,
  maxAgentCallsPerExecution: 50
});

guard.addAllowedAgent('analyst');
guard.addAllowedAgent('worker');
guard.addAllowedAgent('qa');

guard.addForbiddenPattern('rm -rf');
guard.addForbiddenPattern('DROP TABLE');
guard.addForbiddenPattern('eval(');
guard.addForbiddenPattern('__proto__');

  guard.validateAgentExecution('analyst');
} catch (e) {
  console.log('Agent未授权:', e.message);
}

try {
  guard.checkForbiddenPatterns({ query: 'DROP TABLE users;' });
} catch (e) {
  console.log('禁止模式:', e.message);
}

guard.startExecution('exec-001');
for (let i = 0; i < 10; i++) {
  guard.recordAgentCall('exec-001');
}
console.log(guard.getExecutionStats('exec-001'));
guard.endExecution('exec-001');

console.log(guard.getStats());
```

- 与`DeepeningDeployment.validateConfig()`配合验证部署配置

## Round 5 缺陷修复记录

> 本轮修复涉及深化子系统中4个模块的关键缺陷，涵盖缓存语义、限流泄漏、熔断器边界和状态机守卫条件。

### DeepeningCache — 缓存falsy值拒绝修复

**缺陷**：`store()` 方法使用 `!task || !result` 条件校验，导致合法的 falsy 值（`0`、`""`、`false`）被错误拒绝，无法作为缓存条目存储。

**修复**：条件从 `!task || !result` 改为 `task == null || result == null`，仅拒绝 `null` 和 `undefined`，允许 `0`、`""`、`false` 等合法 falsy 值通过。

**影响范围**：缓存结果为数值零、空字符串或布尔 false 的深化推理结果现在可以正确缓存和命中。

### DeepeningRateLimiter — 分钟计数器泄漏修复

**缺陷**：`acquire()` 方法先检查分钟速率再检查小时速率，当小时速率拒绝请求时，分钟计数器已被递增但请求实际未通过，导致分钟计数器虚高（泄漏）。

**修复**：调整检查顺序，先检查小时速率再检查分钟速率。小时速率拒绝时直接返回，不再递增分钟计数器。

**影响范围**：限流统计更准确，避免分钟计数器因小时级拒绝而虚高，确保限流决策基于真实请求量。

### DeepeningCircuitBreaker — 熔断器边界修复

**缺陷1**：未强制执行 `maxCircuits` 限制，熔断器实例数可能无限增长导致内存泄漏。

**修复1**：新增 `maxCircuits` 限制强制执行，超出时采用回退淘汰（fallback eviction）策略移除最旧的熔断器实例。

**缺陷2**：`halfOpenCalls` 计数器在所有状态下均递增，而非仅在 `half_open` 状态下递增，导致计数不准确。

**修复2**：`halfOpenCalls` 仅在 `half_open` 状态下递增，确保半开探测计数的准确性。

**影响范围**：熔断器实例数受控，内存使用可预测；半开状态探测逻辑更精确，避免误判。

### DeepeningStateManager — 状态转换守卫条件增强

**缺陷**：`transitionByEvent` 方法的守卫条件（guard condition）无法访问转换上下文信息，限制了基于上下文的状态转换决策能力。

**修复**：`transitionByEvent` 新增 `context` 参数，在调用守卫条件函数时将上下文透传，使守卫条件可以基于转换上下文做出更精细的决策。

**签名变更**：

```javascript
// 修复前
transitionByEvent(eventName)

// 修复后
transitionByEvent(eventName, context)
```

## Round 7 缺陷修复记录

> 本轮修复涉及深化子系统中6个模块的关键缺陷，涵盖运算符优先级、部分失败回滚、异步回调、事件丢失、空参数防护和负数安全验证。

### DeepeningOrchestrator — 运算符优先级修复与空agents数组验证

**缺陷1**：`execute()` 方法中解析 `depthLevel` 时使用 `options.depthLevel || defaultDepthLevel || 'standard'`，由于 `||` 运算符的 falsy 语义，当 `options.depthLevel` 为合法的 `0` 或空字符串 `""` 时，会被错误地跳过，回退到默认值。

**修复1**：改用 nullish coalescing 运算符 `??`，条件改为 `options.depthLevel ?? defaultDepthLevel ?? 'standard'`，仅当值为 `null` 或 `undefined` 时才回退，允许 `0` 和 `""` 等合法 falsy 值通过。

**缺陷2**：`execute()` 方法未验证 `agents` 参数，传入空数组 `[]` 时仍会进入迭代循环，导致零次 Agent 执行但返回 `success: true` 的误导性结果。

**修复2**：新增 `agents` 数组非空验证，空数组时抛出 `HarnessError`，明确拒绝无效输入。

**影响范围**：depthLevel 为数值零或空字符串的场景现在可以正确传递；空 agents 输入不再静默通过，避免误导性执行结果。

### DeepeningPipeline — initialize() 部分失败回滚清理

**缺陷**：`initialize()` 方法在组装模块时，若某个模块创建或 attach 失败，已成功创建的模块实例不会被清理，导致管道处于半初始化状态，后续调用可能使用不完整的模块集合。

**修复**：`initialize()` 新增部分失败回滚逻辑，在初始化失败时遍历并清理已创建的模块实例（调用 `shutdown()` 并移除引用），确保管道要么完全初始化成功，要么干净地回退到未初始化状态。

**影响范围**：管道初始化失败后不再残留半初始化模块，避免后续操作使用不完整的模块集合导致不可预测的行为。

### DeepeningStateManager — transition() await异步回调与context参数传递

**缺陷1**：`transition()` 方法在调用状态转换回调（onEnter/onExit）时未使用 `await`，异步回调中的错误不会被捕获，且回调内的异步操作（如持久化）可能在状态转换完成后才执行，导致状态不一致。

**修复1**：`transition()` 中对回调的调用改为 `await`，确保异步回调完成后再继续状态转换流程，回调中的错误也能被正确捕获和处理。

**缺陷2**：`transitionByEvent()` 方法的守卫条件（guard condition）无法访问转换上下文信息（Round 5 已部分修复签名），但 `transition()` 方法的 onEnter/onExit 回调同样缺少 context 参数透传。

**修复2**：`transition()` 的 onEnter/onExit 回调新增 `context` 参数透传，使回调函数可以基于转换上下文做出更精细的决策。

**影响范围**：异步回调现在被正确等待，状态转换的时序一致性得到保障；回调函数可访问转换上下文，支持更复杂的状态转换逻辑。

### DeepeningTaskScheduler — 并发限制时deferred事件修复

**缺陷**：`schedule()` 方法在并发任务数达到 `maxConcurrent` 限制时，新任务被静默丢弃（仅返回任务ID但不加入执行队列），调用方无法感知任务被延迟。

**修复**：并发限制触发时，新增 `deferred` 事件发射，携带 `{ id, name, reason: 'concurrency-limit' }` 数据，通知调用方任务因并发限制被延迟执行。任务仍会被调度，但调用方可以据此调整策略或记录日志。

**影响范围**：调用方现在可以监听 `deferred` 事件感知并发限制，避免因任务静默延迟而误判执行状态。

### DeepeningCache — invalidateByPattern({}) 空pattern防护

**缺陷**：`invalidateByPattern()` 方法接受 pattern 对象进行模式匹配失效，当传入空对象 `{}` 时，所有缓存条目均匹配成功，导致全量缓存被意外清空。

**修复**：新增空 pattern 防护，当 pattern 为空对象（`Object.keys(pattern).length === 0`）时抛出 `HarnessError`，明确拒绝可能导致全量失效的模糊操作。若需清空全部缓存，应使用 `clear()` 方法。

**影响范围**：防止因传入空 pattern 对象导致全量缓存意外失效，确保缓存失效操作具有明确的意图。

### DeepeningRateLimiter — tryConsume 负数计数安全验证

**缺陷**：`tryConsume()` 方法未验证 `count` 参数，传入负数时会导致计数器递减（而非递增），使限流统计失真，攻击者可通过传入负数绕过限流。

**修复**：新增 `count` 参数安全验证，当 `count` 为负数或非有限数值时抛出 `HarnessError`，明确拒绝无效输入。

**影响范围**：限流计数器不再受负数输入影响，防止限流机制被绕过。

## Round 8 缺陷修复记录

> 本轮修复涉及深化子系统中8个模块的关键缺陷，涵盖自动重新调度、默认拒绝安全策略、资源释放、除零防护、状态检查、数据刷写、空值处理和策略回退。

### DeepeningTaskScheduler — _scheduleNext方法自动重新调度pending任务

**缺陷**：`_scheduleNext()` 方法在任务执行完成后，未自动检查并调度队列中等待的pending任务。当并发槽位释放时，pending状态的任务不会被自动拾取执行，导致任务在并发限制场景下被永久搁置。

**修复**：`_scheduleNext()` 新增自动重新调度逻辑，在任务完成（成功或失败）后检查pending任务队列，若当前并发数未达上限，自动调度下一个pending任务执行。

**影响范围**：并发限制场景下，pending任务不再被永久搁置，并发槽位释放后自动触发后续任务执行，确保任务调度的连续性。

### DeepeningSecurityGuard — 空allowlist默认拒绝（deny by default）

**缺陷**：`validateAgentExecution()` 方法在Agent白名单（allowlist）为空时，允许所有Agent执行（默认开放模式），违反最小权限原则。未配置白名单的系统默认放行所有Agent，存在安全风险。

**修复**：空allowlist时改为默认拒绝（deny by default），白名单为空时所有Agent执行请求均被拒绝。同时，非字符串输入仍执行模式检查（`checkForbiddenPatterns`），确保即使Agent ID类型异常，禁止模式检测仍然生效。

**影响范围**：未显式配置白名单的系统现在默认拒绝所有Agent执行请求，符合最小权限原则；非字符串输入不会绕过禁止模式检测。

### DeepeningBase — _onShutdown资源释放

**缺陷**：`_onShutdown()` 方法仅设置关闭标志，未释放attach依赖（`_attachedDeps`）、模块依赖（`_deps`）和EventEmitter监听器，导致关闭后对象仍持有外部引用，可能阻止垃圾回收并引发内存泄漏。

**修复**：`_onShutdown()` 新增资源释放逻辑：清空`_attachedDeps`映射、清空`_deps`映射、调用`removeAllListeners()`移除所有事件监听器，确保关闭后对象不持有任何外部引用。

**影响范围**：所有继承DeepeningBase的模块在关闭后不再残留外部引用，避免内存泄漏和重复事件触发。

### AdaptiveDepthController — _calcComplexityScore除零/NaN防护

**缺陷**：`_calcComplexityScore()` 方法在计算复杂度分数时，当分母为零或计算结果为NaN时，未进行防护处理，导致后续逻辑使用NaN值进行决策，可能引发无限深化或提前终止。

**修复**：新增除零和NaN防护，分母为零时返回默认复杂度分数，计算结果为NaN时回退到安全默认值，确保复杂度评估始终返回有效数值。

**影响范围**：复杂度评估在边界条件下（如零任务、零因子）不再产生NaN，深化深度决策基于有效数值，避免无限深化或异常终止。

### ConvergenceDetector — shutdown状态检查、_safeNum辅助方法、_ensureHistory类型验证

**缺陷1**：`detect()` 和相关方法未检查shutdown状态，关闭后仍可能被调用，导致对已释放资源的访问。

**修复1**：新增shutdown状态检查，关闭后调用立即返回安全默认值（已收敛），避免对已释放资源的访问。

**缺陷2**：历史记录数组可能被外部代码替换为非数组类型，导致`push()`等操作抛出异常。

**修复2**：新增`_ensureHistory()`类型验证方法，确保历史记录始终为数组类型，非数组时自动重置为空数组。新增`_safeNum()`辅助方法，统一处理数值参数的NaN/Infinity防护。

**影响范围**：ConvergenceDetector在shutdown后不再访问已释放资源；历史记录类型异常时自动恢复，数值参数始终有效。

### DeepeningMetricsCollector — 新增flush方法与_onShutdown调用flush

**缺陷**：模块关闭时，已采集但未持久化的指标数据丢失，无法在关闭前获取最终统计快照。

**修复**：新增`flush()`方法，执行"快照→清空→事件"三步操作：先获取当前指标快照，再清空内部计数器，最后发射`flushed`事件携带快照数据。`_onShutdown()`中调用`flush()`确保关闭前指标数据不丢失。

**影响范围**：模块关闭时指标数据不再丢失，调用方可通过`flush()`方法或`flushed`事件获取最终统计快照。

### DeepeningReportGenerator — 空metrics处理、_tokenEfficiency除零守卫、bestScore NaN校验

**缺陷1**：`generate()` 方法未处理空metrics输入，当指标数据为空或undefined时，报告生成过程中访问属性抛出异常。

**修复1**：新增空metrics处理，metrics为空时返回包含默认值的空报告，而非抛出异常。

**缺陷2**：`_tokenEfficiency()` 方法在totalTokens为零时触发除零错误，导致报告生成失败。

**修复2**：新增除零守卫，totalTokens为零时返回0作为效率值。

**缺陷3**：`bestScore` 可能为NaN（如所有迭代均未产生有效分数），NaN值写入报告后影响下游消费方的判断逻辑。

**修复3**：新增NaN校验，bestScore为NaN时替换为0，确保报告中的分数值始终有效。

**影响范围**：报告生成在空数据、零Token和无效分数场景下不再失败，始终返回有效报告。

### DeepeningStrategyPlugin — 无效策略名回退到fixed-depth

**缺陷**：`execute()` 方法在遇到无效策略名时，不执行任何策略也不报错，导致深化推理无限继续（无收敛判定），消耗大量Token。

**修复**：无效策略名时自动回退到`fixed-depth`策略（而非无限继续），确保深化推理始终有明确的终止条件。同时发射`strategy-fallback`事件通知调用方策略被降级。

**影响范围**：无效策略名不再导致无限深化，自动回退到安全的固定深度策略，避免Token浪费。

## Round 9 缺陷修复记录

> 本轮修复涉及深化子系统中9个模块的关键缺陷，涵盖过期锁清理、关闭引用修复、驱逐失败拒绝、基准测试错误处理、配置深拷贝与不可变检查、通配符计数更新、延迟任务出队、容量上限检查和重复事件修复。

### DeepeningLockManager — acquire()过期锁自动清理

**缺陷**：`acquire()` 方法在获取锁时，仅检查锁是否已被持有，未检查已持有锁是否已过期。当锁的持有者超时未释放时，新请求者无法获取已过期但仍被占用的锁，导致锁永久死锁。

**修复**：`acquire()` 新增过期锁自动清理逻辑，在获取锁前检查当前持有者的锁是否已超时。若锁已过期，自动释放旧锁并允许新所有者获取，避免过期锁导致的死锁。

**影响范围**：锁持有者异常退出或超时未释放时，锁不再永久阻塞，新请求者可在锁过期后自动获取。

### DeepeningTaskQueue — _onShutdown引用修复

**缺陷**：`_onShutdown()` 方法在关闭时仅清空了堆（`heap`），未清空条目映射（`entries`），导致关闭后条目映射仍持有对已出队任务的引用，阻止垃圾回收，造成内存泄漏。

**修复**：`_onShutdown()` 同时清空 `heap` 和 `entries`，确保关闭后不残留任何任务引用。

**影响范围**：TaskQueue关闭后不再残留任务引用，内存可被正确回收。

### DeepeningBackpressureManager — 驱逐失败时拒绝注册新流

**缺陷**：`registerStream()` 方法在背压管理器已达到容量上限时，尝试驱逐最旧流以腾出空间。但若驱逐操作失败（如流不可中断），新流仍被注册，导致实际流数超过容量限制。

**修复**：驱逐失败时，`registerStream()` 返回失败结果，拒绝注册新流，确保实际流数始终不超过配置的容量上限。

**影响范围**：背压管理器的流数始终受容量限制约束，驱逐失败不再静默放行。

### DeepeningBenchmark — runThroughput添加try-catch错误处理

**缺陷**：`runThroughput()` 方法在执行基准测试时，若某个测试任务抛出异常，整个基准测试立即中断，已完成的测试结果丢失，无法获取部分性能数据。

**修复**：`runThroughput()` 为每个测试任务添加 try-catch 错误处理，单个任务失败时记录错误并继续执行后续任务，确保基准测试可完整运行并返回所有可用结果。

**影响范围**：基准测试在单个任务异常时不再整体中断，可获取部分性能数据用于分析。

### DeepeningConfigManager — reset()引用类型深拷贝，import()不可变检查

**缺陷1**：`reset()` 方法在重置配置项为初始值时，直接引用初始值对象（浅拷贝），导致后续对重置后配置的修改会影响初始值定义，多次reset后初始值被污染。

**修复1**：`reset()` 对引用类型的初始值执行深拷贝（`JSON.parse(JSON.stringify())`），确保重置后的配置与初始值定义互不影响。

**缺陷2**：`import()` 方法未检查导入数据中是否包含不可变配置项，允许通过导入覆盖不可变配置，违反不可变语义。

**修复2**：`import()` 新增不可变检查，遇到不可变配置项时跳过覆盖并记录警告，确保不可变配置无法通过导入被篡改。

**影响范围**：reset操作不再污染初始值定义，多次reset结果一致；不可变配置无法通过导入绕过，配置安全性得到保障。

### DeepeningEventBus — 驱逐订阅时更新通配符计数

**缺陷**：`unsubscribe()` 方法在移除订阅时，未更新通配符订阅计数（`_wildcardCount`）。当通配符订阅被驱逐或手动取消后，计数器仍保持旧值，导致事件分发时误判是否存在通配符订阅，产生不必要的匹配开销或遗漏分发。

**修复**：`unsubscribe()` 在移除订阅时检查被移除订阅是否为通配符模式，若是则递减 `_wildcardCount`，确保通配符计数与实际订阅数一致。

**影响范围**：事件分发的通配符判断更准确，避免不必要的模式匹配开销和分发遗漏。

### DeepeningPriorityQueue — 延迟任务不再阻塞队列出队

**缺陷**：`dequeue()` 方法在遇到延迟时间未到的任务时，直接返回 `null`（队列为空），而非跳过该任务继续检查下一个。当队首存在延迟任务时，所有优先级更高的非延迟任务被阻塞，无法出队执行。

**修复**：`dequeue()` 遇到延迟未到的任务时跳过该任务，继续检查堆中下一个任务，确保非延迟任务可正常出队。延迟任务留在堆中等待其延迟时间到达后被正常出队。

**影响范围**：延迟任务不再阻塞其他任务的出队，优先级队列的调度公平性得到保障。

### DeepeningResourceManager — reserve()容量上限检查

**缺陷**：`reserve()` 方法在预留资源时，未检查预留量是否超过总容量上限。当预留量超过配置的最大容量时，资源管理器的已用计数变为负数或溢出，导致后续资源分配逻辑混乱。

**修复**：`reserve()` 新增容量上限检查，当预留量超过剩余可用容量时，拒绝预留并返回失败结果，确保已用资源量始终不超过总容量。

**影响范围**：资源预留不再超过容量上限，资源管理器的计数始终有效，避免超分配。

### DeepeningValidator — 修复重复发出validation事件

**缺陷**：`validate()` 和 `validateWithSchema()` 方法在验证完成后均会发射 `validation` 事件，但 `validate()` 内部调用 `validateWithSchema()`，导致同一验证操作触发两次 `validation` 事件，造成事件监听器重复处理。

**修复**：`validate()` 不再独立发射 `validation` 事件，由 `validateWithSchema()` 统一发射，确保每次验证仅触发一次事件。

**影响范围**：验证事件不再重复触发，事件监听器无需去重处理。

## Round 10 缺陷修复记录

> 本轮修复涉及深化子系统中8个模块的关键缺陷，涵盖深克隆保护、管道中断、自环检测、超时映射、淘汰计数、状态机转换、时间窗口计算和事件过滤。

### DeepeningSnapshotManager — create/restore深克隆保护

**缺陷**：`create()` 和 `restore()` 方法在创建和恢复快照时，直接引用原始对象（浅拷贝），导致快照与原始状态共享引用。对快照的修改会影响原始状态，对原始状态的修改也会影响已保存的快照，破坏快照的不可变语义。

**修复**：`create()` 和 `restore()` 对快照数据执行深克隆（`JSON.parse(JSON.stringify())`），确保快照与原始状态完全隔离，快照的不可变语义得到保障。

**影响范围**：快照数据不再与原始状态共享引用，快照恢复后原始状态不受影响，多次恢复结果一致。

### DeepeningDataPipeline — abortOnError选项，阶段失败中断管道

**缺陷**：`process()` 方法在某个阶段执行失败时，无论阶段是否为可选（optional），都继续执行后续阶段。非可选阶段失败后继续执行可能导致下游阶段接收到不完整或无效的中间数据，产生级联错误。

**修复**：`addStage()` 新增 `abortOnError` 选项（默认 `true`），当非可选阶段失败且 `abortOnError` 为 `true` 时，立即中断管道执行并抛出错误，不再继续后续阶段。可选阶段（`optional: true`）失败时仍跳过并继续。

**影响范围**：非可选阶段失败后管道不再静默继续执行，避免级联错误和数据污染；可选阶段行为不变。

### DeepeningDependencyResolver — 自环检测与深度超限标记已访问

**缺陷1**：`resolve()` 方法未检测自环依赖（模块依赖自身），自环导致无限递归解析，最终栈溢出崩溃。

**修复1**：新增自环检测，当模块依赖自身时抛出 `SELF_DEPENDENCY` 错误，明确拒绝自环依赖。

**缺陷2**：`resolve()` 在依赖深度超限时，未标记已访问节点，导致同一节点被重复访问，依赖图较大时产生指数级冗余遍历。

**修复2**：深度超限时标记已访问节点，避免重复遍历，确保依赖解析的时间复杂度为线性。

**影响范围**：自环依赖不再导致栈溢出；依赖图较大时解析性能显著提升，不再产生指数级冗余遍历。

### DeepeningErrorHandler — timeout类型映射修复

**缺陷**：`handleError()` 方法在映射错误类型时，未将 `ETIMEDOUT`、`ESOCKETTIMEDOUT` 等超时相关错误码映射为 `timeout` 类型，而是统一归为 `unknown` 类型。超时错误无法被正确分类，导致重试策略和错误处理逻辑无法针对超时场景做出专门决策。

**修复**：新增超时错误码到 `timeout` 类型的映射，`ETIMEDOUT`、`ESOCKETTIMEDOUT`、`ERR_HTTP2_SESSION_TIMEOUT` 等错误码统一映射为 `timeout` 类型。

**影响范围**：超时错误现在可被正确分类，重试策略和错误处理逻辑可针对超时场景做出专门决策（如指数退避重试）。

### DeepeningEventStorage — RingBuffer淘汰计数递减与自动刷盘机制

**缺陷1**：`store()` 方法在RingBuffer淘汰旧事件时，未递减内部事件计数器，导致计数器持续递增，与实际存储的事件数不一致，统计信息失真。

**修复1**：RingBuffer淘汰旧事件时同步递减内部事件计数器，确保计数器与实际存储事件数一致。

**缺陷2**：事件存储依赖手动调用 `flush()` 持久化，进程异常退出时未刷盘的事件数据丢失。

**修复2**：新增自动刷盘机制，基于事件数量阈值和时间间隔自动触发刷盘，减少数据丢失风险。

**影响范围**：事件存储统计信息准确；进程异常退出时事件数据丢失风险降低。

### DeepeningStateMachine — 移除idle→cancelled无效转换，reset不存在时返回错误

**缺陷1**：状态机定义中包含 `idle → cancelled` 的转换路径，但 `idle` 状态下取消操作无实际语义（任务尚未开始，无需取消），该转换路径的存在增加了状态空间的复杂度，且可能被误触发。

**修复1**：移除 `idle → cancelled` 无效转换路径，`idle` 状态下不再允许转换到 `cancelled` 状态。

**缺陷2**：`reset()` 方法在目标状态不存在时，静默返回成功（`true`），调用方无法感知重置失败。

**修复2**：`reset()` 在目标状态不存在时返回错误对象（`{ ok: false, error: 'STATE_NOT_FOUND' }`），明确告知调用方重置失败原因。

**影响范围**：状态机转换图更精简，无效转换不再存在；`reset()` 失败时可被调用方感知和处理。

### DeepeningThrottle — 时间窗口计算修复

**缺陷**：`acquire()` 方法在计算时间窗口时，使用硬编码的 `MS_PER_MINUTE` 常量计算窗口边界，而非使用构造函数参数 `_interval`。当配置了非标准间隔（如30秒、5分钟）时，窗口计算错误，导致限流判断不准确。

**修复**：时间窗口计算改用 `_interval` 替代硬编码的 `MS_PER_MINUTE`，确保窗口边界与配置的限流间隔一致。

**影响范围**：非标准限流间隔下限流判断准确，限流行为与配置一致。

### DeepeningVisualization — 事件类型过滤修复与timestamp判断修复

**缺陷1**：`render()` 方法在按事件类型过滤可视化数据时，使用严格相等比较事件类型字符串，但事件类型可能带有命名空间前缀（如 `deepening.stage.completed`），导致带前缀的事件无法匹配过滤条件，被错误排除。

**修复1**：事件类型过滤改用 `startsWith()` 匹配，支持带命名空间前缀的事件类型过滤。

**缺陷2**：时间线渲染中，timestamp比较使用 `>` 运算符，导致相同时间戳的事件被错误排序（后到达的事件排在前面）。

**修复2**：timestamp比较改用 `>=` 运算符，相同时间戳的事件按到达顺序排列，确保排序稳定性。

**影响范围**：带命名空间前缀的事件类型可被正确过滤；时间线排序在相同时间戳场景下稳定。

## Round 11 缺陷修复记录

> 本轮修复涉及深化子系统中10个模块的关键缺陷，含3个回归修复（Round 7修复不完整）和7个新发现缺陷，涵盖时序安全、缓存防护、异步回调、限流计算、特性标志、快照索引、模块生命周期、通知安全、服务注册和优雅关闭。

### DeepeningCache — invalidateByPattern null/undefined防护（回归修复）

**缺陷**：Round 7修复了`invalidateByPattern({})`空对象防护，但遗漏了`null`和`undefined`参数。传入`null`或`undefined`时，`Object.keys(null)`抛出`TypeError`，导致缓存操作异常中断。

**修复**：新增`null`/`undefined`参数防护，`pattern`为`null`、`undefined`或非对象类型时直接返回0（无条目失效）。

**影响范围**：`invalidateByPattern`对所有非法参数均安全返回，不再抛出异常。

### DeepeningStateManager — transition() Promise返回值检测（回归修复）

**缺陷**：Round 7为`transition()`的回调调用添加了`await`关键字，但调用模式`fromStateObj.onExit(context)`仍不处理回调返回Promise的情况。当`onExit`返回Promise时，Promise被创建但未被await（因为调用本身未检测thenable返回值），异步操作在状态转换完成后才执行，导致状态不一致。

**修复**：改为先调用回调获取返回值，再检测返回值是否为Promise（`typeof result.then === 'function'`），若是则await：

```javascript
const result = fromStateObj.onExit(context ?? null);
if (result && typeof result.then === 'function') await result;
```

**影响范围**：异步回调现在被正确等待，无论回调函数是同步还是异步，状态转换的时序一致性得到保障。

### DeepeningRateLimiter — utilization负值防护

**缺陷**：`getBucketInfo()`中利用率计算`(bucket.tokens / bucket.maxTokens) * 100`在`tokens`为负数时（如并发扣减导致），利用率返回负值，误导监控和告警系统。

**修复**：利用率计算包裹`Math.max(0, ...)`，确保返回值始终为非负数。

**影响范围**：限流利用率指标始终为有效非负值，监控和告警系统不再受负值干扰。

### DeepeningFeatureFlags — 百分比评估确定性与默认拒绝策略

**缺陷1**：`evaluate()`在PERCENTAGE类型标志无context时，使用`Math.random() * 100`决定是否启用。这导致同一标志在无context场景下每次评估结果不同，违反特性标志的确定性原则（同一标志对同一输入应返回相同结果）。

**修复1**：无context时使用`this._hash(name)`替代`Math.random() * 100`，基于标志名计算确定性哈希值作为百分比判定依据，确保同一标志名始终返回相同结果。

**缺陷2**：`evaluate()`在遇到未知标志状态（非ON/OFF/PERCENTAGE/VARIANTS）时，默认返回`true`（允许），违反最小权限原则。未知状态应默认拒绝。

**修复2**：未知标志状态fallthrough改为`return false`（deny-by-default），确保未明确配置的标志不会意外启用。

**影响范围**：特性标志评估在无context场景下结果确定且一致；未知状态标志默认拒绝，安全性提升。

### DeepeningSnapshotStore — BoundedMap onEvict同步_versions索引

**缺陷**：`DeepeningSnapshotStore`使用`BoundedMap`存储快照，`_versions` Map作为按名称索引的二级索引。当`BoundedMap`因容量限制驱逐条目时，`onEvict`回调仅递减`_totalSizeBytes`，未同步清理`_versions`中对应的版本ID引用。被驱逐快照的版本ID仍残留在`_versions`中，导致`restoreLatest()`可能返回已被驱逐的快照ID，访问时得到`null`。

**修复**：`onEvict`回调新增`_versions`索引同步逻辑——从`_versions`中查找并移除被驱逐快照的版本ID，若版本列表变空则删除整个名称条目。

**影响范围**：快照驱逐后`_versions`索引与实际存储一致，`restoreLatest()`不再返回已驱逐快照的ID。

### DeepeningModuleRegistry — _onShutdown异步检测与unload()调用shutdown

**缺陷1**：`_onShutdown()`遍历所有已加载模块实例调用`inst.shutdown()`，但未检测shutdown方法是否返回Promise。异步shutdown的Promise未被await，其rejection也不会被捕获，可能导致关闭过程中的异步错误被静默吞没。

**修复1**：检测shutdown返回值是否为Promise，若是则附加`.catch()`捕获rejection并记录错误。

**缺陷2**：`unload()`方法从`_instances`中删除模块实例前，未调用`inst.shutdown()`释放模块资源。直接删除引用导致模块持有的定时器、连接等资源泄漏。

**修复2**：`unload()`在删除实例前先调用`inst.shutdown()`（若存在），确保资源被正确释放。

**影响范围**：模块关闭过程中的异步错误不再被静默吞没；模块卸载前资源被正确释放。

### DeepeningNotifier — 订阅对象id、ReDoS防护、不存在订阅操作和关闭重置

**缺陷1**：`subscribe()`返回的订阅ID未存储在订阅对象自身，导致通过`getSubscriptionStats()`等途径获取的订阅对象缺少`id`属性，无法追踪订阅ID。

**修复1**：订阅对象新增`id`属性，值为生成的订阅ID。

**缺陷2**：`_getCompiledPattern()`对正则表达式模式长度无限制，恶意构造的超长模式（如数万个字符的交替模式）可导致正则编译耗时过长（ReDoS攻击）。

**修复2**：新增模式长度限制（200字符），超长模式抛出错误拒绝编译。

**缺陷3**：`enableSubscription()`和`disableSubscription()`对不存在的订阅ID返回`true`，调用方无法感知操作失败。

**修复3**：不存在订阅时返回`false`，明确告知操作失败。

**缺陷4**：`_onShutdown()`未重置`_enabledCount`和`_disabledCount`计数器，关闭后统计信息残留。

**修复4**：`_onShutdown()`新增`_enabledCount = 0; _disabledCount = 0`重置。

**影响范围**：订阅对象可追踪ID；ReDoS攻击被拦截；订阅操作结果更准确；关闭后统计信息干净。

### DeepeningServiceRegistry — _onShutdown清空二级索引

**缺陷**：`_onShutdown()`清空了`_services`主存储，但未清空`_byState`和`_byTag`二级索引映射。关闭后通过`getServicesByState()`或`getServicesByTag()`仍可获取已不存在的服务引用。

**修复**：`_onShutdown()`新增`this._byState = {}; this._byTag = {}`清空二级索引。

**影响范围**：服务注册关闭后所有索引均被清空，不再残留过期引用。

### DeepeningGracefulShutdown — 依赖检查使用completedSteps与超时race清理timer

**缺陷1**：步骤依赖检查使用`this._steps.find(s => s.name === depName)`判断依赖步骤是否存在，但未检查依赖步骤是否已完成。即使依赖步骤尚未执行，当前步骤也会被允许执行，违反依赖排序语义。
