# 模块详解-技能生命周期模块群

> 版本：2.73.4 | 目录：src/runtime/skill/ | 文件数：6

---

## 1. 模块群概述

技能生命周期模块群是Harness多Agent框架技能子系统的核心运维层，涵盖技能从创建到演化、灰度发布、运行监控、审计追踪和持续改进的完整生命周期管理。6个模块协同工作，形成"创建→演化→灰度→监控→审计→改进"的闭环：

| 模块 | 文件 | 核心职责 |
|------|------|---------|
| SkillTreeDAG | skill-tree-dag.js | 技能依赖DAG图、拓扑排序执行、种子技能自生长、循环依赖检测 |
| SkillEvolver | skill-evolver.js | LLM驱动的三阶段演化（摘要→聚合→执行）、补丁审批、Token预算保护 |
| SkillCanary | skill-canary.js | 金丝雀灰度发布、流量百分比控制、成功率与延迟评估、自动晋升/回滚 |
| SkillObservability | skill-observability.js | 统一可观察性、跨模块指标聚合、执行链路追踪、健康仪表盘、告警规则引擎 |
| SkillAuditTrail | skill-audit-trail.js | 变更审计轨迹、历史查询、影响分析、风险评级、审计报告生成 |
| SkillImprovementLoop | skill-improvement-loop.js | 飞轮三道门验证（成功率→回测→AB测试）、学习经验记录、补丁审批与应用 |

设计哲学：**技能即生命体**。每个Skill不是静态的文档，而是持续演化的活知识。模块群通过自动化的灰度发布、实时监控、审计追溯和飞轮改进机制，确保技能库随项目演进而持续进化，同时保障变更的安全性和可追溯性。

## 3. SkillTreeDAG详解

**文件**：[skill-tree-dag.js](file:///e:/Harness_V1_0429/src/runtime/skill/skill-tree-dag.js) | **核心类**：`SkillTreeDAG extends EventEmitter`

SkillTreeDAG以有向无环图建模技能间的依赖关系，支持拓扑排序执行、种子技能自生长和循环依赖检测。与SkillGraph的关系建模定位不同，SkillTreeDAG专注于执行顺序和演化树结构。

### 3.1 节点与边

**节点结构**（`addNode(skillId, metadata)` 创建）：

```javascript
{
  id: skillId,
  category: metadata.category ?? 'general',
  level: metadata.level ?? 0,
  status: metadata.status ?? 'active',
  seed: metadata.seed ?? false,
  createdAt: Date.now(),
  updatedAt: Date.now(),
}
```

边存储在 `_edges` Map中，key为技能ID，value为该技能所依赖的目标ID数组。

### 3.2 拓扑排序

`getExecutionOrder()` 使用DFS后序遍历实现拓扑排序，返回结构化结果：

```javascript
{
  order: string[],       // 合法拓扑序列
  cyclicNodes: string[], // 参与循环的节点ID列表
  hasCycle: boolean,     // 是否存在循环
}
```

### 3.3 循环依赖检测

`_wouldCreateCycle(skillId, dependsOnId)` 在添加边时实时检测：

1. 从 `dependsOnId` 开始BFS遍历
2. 如果遍历到 `skillId`，说明添加该边会形成环
3. 拒绝添加并返回 `false`，同时发出 `cycle-detected` 事件

### 3.4 层级传播

`addDependency()` 成功后调用 `_propagateLevel(skillId)` 递归传播层级增量：

```javascript
addDependency(skillId, dependsOnId) {
  node.level = Math.max(node.level, depNode.level + 1);
  this._propagateLevel(skillId);
}
```

### 3.5 种子技能自生长

`evolveFromSeed(seedId, newSkillId, metadata)` 从种子技能派生新技能：

- 自动建立依赖关系（新技能依赖种子技能）
- 新技能level = seed.level + 1
- 非种子技能调用返回 `null`

### 3.6 核心方法

| 方法 | 签名 | 说明 |
|------|------|------|
| `addNode` | `(skillId, metadata?) → Node \| boolean` | 添加节点，已存在则更新metadata，节点数达上限返回false |
| `addDependency` | `(skillId, dependsOnId) → boolean` | 添加依赖边，自动检测循环依赖并传播层级 |
| `getDependencies` | `(skillId) → string[]` | 获取直接依赖（前驱节点） |
| `getDependents` | `(skillId) → string[]` | 获取直接被依赖（后继节点） |
| `getExecutionOrder` | `() → { order, cyclicNodes, hasCycle }` | 拓扑排序，返回合法执行顺序和循环节点信息 |
| `getRoots` | `() → string[]` | 获取无依赖的根节点 |
| `getLeaves` | `() → string[]` | 获取无后继的叶节点 |
| `getSubtree` | `(skillId) → string[]` | 获取以某节点为根的完整子树 |
| `getSeedSkills` | `() → Node[]` | 获取所有标记为seed的节点 |
| `evolveFromSeed` | `(seedId, newSkillId, metadata?) → Node \| boolean \| null` | 从种子技能演化出新节点 |
| `getNode` | `(skillId) → Node \| null` | 获取节点数据 |
| `getNodeCount` | `() → number` | 获取节点总数 |
| `getEdgeCount` | `() → number` | 获取边总数 |
| `getDepth` | `() → number` | 获取DAG最大深度 |
| `removeNode` | `(skillId) → void` | 移除节点及其所有关联边 |

### 3.7 配置项

| 选项 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `maxDepth` | number | 10 | DAG最大允许深度 |
| `maxChildren` | number | 20 | 每个节点最大子节点数 |
| `maxNodes` | number | 200 | 最大节点数 |
| `maxEdges` | number | 1000 | 最大边数 |

### 3.8 事件

| 事件名 | 载荷 | 说明 |
|--------|------|------|
| `node-added` | `{ skillId }` | 节点添加成功 |
| `cycle-detected` | `{ skillId, dependsOnId }` | 检测到循环依赖 |

### 3.9 依赖关系

- **内部依赖**：`safeAssign`（安全属性赋值）
- **混入**：`withShutdown`（关闭生命周期）
- **被依赖**：SkillAuditTrail（`attachSkillGraph` 挂载后用于影响分析中的依赖者查询）

## 4. SkillEvolver详解

**文件**：[skill-evolver.js](file:///e:/Harness_V1_0429/src/runtime/skill/skill-evolver.js) | **核心类**：`SkillEvolver extends EventEmitter`

SkillEvolver是技能子系统的演化引擎，通过LLM驱动的三阶段流程（摘要→聚合→执行）实现技能的自我改进。与SkillImprovementLoop基于经验统计的优化不同，SkillEvolver利用大语言模型进行深度分析和内容生成。

### 4.1 三阶段演化流程

`evolve(skillId, sessionTraces)` 执行完整的演化流水线：

```
evolve() 执行流程：
  1. 前置检查
     ├── 关闭状态检查
     ├── LLM客户端检查
     ├── SkillRouter检查
     ├── 演化健康检查（evolutions < 10000）
     └── Token预算检查（remaining/total >= 0.3）

  2. _summarize(skillId, traces)
     ├── 构建LLM Prompt：分析session traces提取成功/失败模式
     └── 返回 { patterns, failures }

  3. _aggregate(skillId, summary)
     ├── 构建LLM Prompt：识别不变量和修改目标
     └── 返回 { invariants, modificationTargets }

  4. _execute(skillId, aggregation)
     ├── 构建LLM Prompt：基于聚合结果生成改进指令
     └── 返回 { refinedBody, newSkills }

  5. 补丁处理
     ├── 有 patchApproval → 提交审批流
     └── 无 patchApproval → 暂存到 _pendingEvolvedPatches
```

### 4.2 补丁应用

`applyEvolvedPatch(skillId, options)` 将演化结果写入技能文件：

1. 解析补丁来源（审批通过 / 待处理）
2. 解析技能文件路径
3. `_backupSkill()` → 备份原文件
4. 读取技能Markdown文件
5. `_splitFrontmatter()` → 分离Frontmatter和Body
6. 查找 `EVOLUTION_MARKER`（`<!-- evolution-section -->`）
7. `_buildEvolutionSection()` → 构建演化内容
8. `writeAtomicTextAsync()` → 原子写入
9. `skillRouter.discoverAsync()` → 重新发现
10. 发出 `evolution-applied` 事件

### 4.3 演化内容格式

`_buildEvolutionSection(patch)` 生成的演化内容：

```markdown
> Evolved based on LLM analysis (2026-05-31)

[refinedBody内容]

### Invariants
- 保持TDD门禁的强制性
- 不修改核心触发条件

### Modification Targets
- 优化错误恢复步骤的描述
- 增加边界情况处理指引
```

### 4.4 Token预算保护

- 最低预算比例：`MIN_TOKEN_BUDGET_RATIO = 0.3`
- 剩余预算低于30%时跳过演化，返回 `{ skipped: true }`
- 演化上限：`MAX_EVOLUTIONS = 10000`

### 4.5 核心方法

| 方法 | 签名 | 说明 |
|------|------|------|
| `evolve` | `(skillId, sessionTraces) → Promise<{success, skillId?, summary?, aggregation?, execution?, error?, skipped?}>` | 执行三阶段演化流水线 |
| `applyEvolvedPatch` | `(skillId, options?) → Promise<{success, skillId?, error?}>` | 将已审批的演化补丁应用到技能文件 |
| `getPendingEvolvedPatches` | `() → Object` | 获取所有待审批的演化补丁 |
| `getStats` | `() → { evolutions, pendingPatches, appliedPatches, errors }` | 获取演化器统计信息 |
| `isHealthy` | `() → boolean` | 检查是否健康（未关闭且演化次数未达上限） |
| `attachLlmClient` | `(client) → SkillEvolver` | 挂载LLM客户端实例 |
| `attachTokenManager` | `(tm) → SkillEvolver` | 挂载Token管理器实例 |
| `attachPatchApproval` | `(pa) → SkillEvolver` | 挂载补丁审批器实例 |
| `attachSqliteStore` | `(store) → SkillEvolver` | 挂载SQLite存储实例 |
| `attachSkillRouter` | `(router) → SkillEvolver` | 挂载SkillRouter实例 |

### 4.6 配置项

| 选项 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `llmClient` | Object | null | LLM客户端，需提供 `chat(prompt)` 方法 |
| `tokenManager` | TokenManager | null | Token预算管理器 |
| `patchApproval` | SkillPatchApproval | null | 补丁审批流 |
| `sqliteStore` | SqliteStore | null | 持久化存储 |
| `skillRouter` | SkillRouter | null | 技能路由器 |
| `projectRoot` | string | '' | 项目根目录 |

### 4.7 事件

| 事件名 | 载荷 | 说明 |
|--------|------|------|
| `evolution-completed` | `{ skillId, hasRefinedBody }` | 演化流程完成 |
| `evolution-applied` | `{ skillId }` | 演化补丁已应用到技能文件 |
| `patch-pending-approval` | `{ skillId, patchData, reason }` | 补丁等待审批 |

### 4.8 依赖关系

- **内部依赖**：`safeJsonParse`（安全JSON解析）、`writeAtomicTextAsync`（原子写入）、`emitError`（错误事件发射）

## 5. SkillCanary详解

**文件**：[skill-canary.js](file:///e:/Harness_V1_0429/src/runtime/skill/skill-canary.js) | **核心类**：`SkillCanary extends EventEmitter`

SkillCanary实现技能的金丝雀灰度发布机制，新技能或变更技能按比例放量发布，收集成功率与延迟指标，自动评估并决定全量晋升或回滚。

### 5.1 金丝雀阶段

技能启用金丝雀模式后经历以下阶段：

```
initializing → warming → evaluating → promoted / rolled_back
```

| 阶段 | 进入条件 | 说明 |
|------|---------|------|
| `initializing` | `enableCanary()` 调用 | 初始阶段，开始收集样本 |
| `warming` | 样本数 ≥ `warmupSamples` | 预热完成，继续积累样本 |
| `evaluating` | 样本数 ≥ `minSamples` | 样本充足，可进行评估 |
| `promoted` | `evaluateCanary()` 通过 | 全量发布 |
| `rolled_back` | 评估失败 ≥ `MAX_EVAL_FAILURES(3)` 次 | 自动回滚 |

### 5.2 流量控制

`shouldActivate(skillId)` 基于流量百分比决定当前请求是否激活金丝雀版本：

```javascript
const activated = Math.random() * 100 < canary.trafficPercent;
```

### 5.3 评估逻辑

`evaluateCanary(skillId)` 评估金丝雀是否通过：

| 条件 | 计算 | 通过标准 |
|------|------|---------|
| 成功率 | `successes / totalSamples` | ≥ `successRateThreshold`（默认0.8） |
| 延迟 | `avgLatency` | ≤ `baseline.avgLatency × latencyMultiplier`（默认1.5） |

评估失败累计达 `MAX_EVAL_FAILURES(3)` 次时自动回滚。

### 5.4 自动评估

`startAutoEvaluation(interval)` 启动定时自动评估，遍历所有处于 `evaluating` 阶段的金丝雀：

- 评估通过 → 自动 `promote()`
- 评估失败次数 ≥ 3 → 自动 `rollback()`
- 使用 `setInterval` + `unref()` 避免阻止进程退出

### 5.5 延迟百分位数

`getCanaryMetrics()` 返回P50和P95延迟：

```javascript
{
  successRate: number,
  avgLatency: number,
  sampleCount: number,
  p50Latency: number | null,
  p95Latency: number | null,
}
```

### 5.6 核心方法

| 方法 | 签名 | 说明 |
|------|------|------|
| `enableCanary` | `(skillId, options?) → boolean` | 为技能启用金丝雀模式 |
| `disableCanary` | `(skillId) → boolean` | 禁用金丝雀模式 |
| `isCanaryEnabled` | `(skillId) → boolean` | 查询是否启用金丝雀模式 |
| `shouldActivate` | `(skillId) → boolean` | 判断当前请求是否应激活金丝雀版本 |
| `promote` | `(skillId) → boolean` | 金丝雀通过验证，全量发布 |
| `rollback` | `(skillId) → boolean` | 金丝雀验证失败，回滚 |
| `recordResult` | `(skillId, result) → void` | 记录金丝雀执行结果（success/latency） |
| `getCanaryMetrics` | `(skillId) → Object \| null` | 获取金丝雀指标（成功率/延迟/百分位） |
| `getCanaryStatus` | `(skillId) → Object \| null` | 获取金丝雀状态（阶段/流量/评估信息） |
| `evaluateCanary` | `(skillId) → { passed, reason, metrics } \| null` | 评估金丝雀是否通过 |
| `startAutoEvaluation` | `(interval) → void` | 启动定时自动评估 |
| `stopAutoEvaluation` | `() → void` | 停止自动评估 |
| `isHealthy` | `() → boolean` | 检查是否健康（未关闭且无评估失败超限的金丝雀） |

### 5.7 配置项

| 选项 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `trafficPercent` | number | 10 | 流量百分比（0-100） |
| `minSamples` | number | 20 | 最小样本数（进入评估阶段） |
| `successRateThreshold` | number | 0.8 | 成功率阈值 |
| `latencyMultiplier` | number | 1.5 | 延迟倍数阈值（相对基线） |
| `warmupSamples` | number | 10 | 预热样本数（进入预热阶段） |
| `baseline.successRate` | number | 1 | 基线成功率 |
| `baseline.avgLatency` | number | 0 | 基线平均延迟（0表示不检查延迟） |

**容量常量**：

| 常量 | 值 | 说明 |
|------|---|------|
| `MAX_CANARIES` | 50 | 最大同时运行的金丝雀数 |
| `MAX_LATENCIES` | 100 | 每个金丝雀最多保留的延迟记录数 |
| `MAX_EVAL_FAILURES` | 3 | 最大连续评估失败次数（超过自动回滚） |

### 5.8 事件

| 事件名 | 载荷 | 说明 |
|--------|------|------|
| `canary-enabled` | `{ skillId, trafficPercent }` | 金丝雀模式启用 |
| `canary-disabled` | `{ skillId }` | 金丝雀模式禁用 |
| `canary-activated` | `{ skillId, activated }` | 请求激活判断结果 |
| `canary-promoted` | `{ skillId }` | 金丝雀全量发布 |
| `canary-rolled-back` | `{ skillId }` | 金丝雀回滚 |
| `canary-evaluation-passed` | `{ skillId, successRate, avgLatency }` | 评估通过 |
| `canary-evaluation-failed` | `{ skillId, reasons, successRate, avgLatency }` | 评估失败 |

### 5.9 依赖关系

- **内部依赖**：`safeExecute`（安全执行）
- **混入**：`withShutdown`（关闭生命周期）
- **被依赖**：SkillObservability（`attachModule('canary', canary)` 挂载后用于指标收集）

## 6. SkillObservability详解

**文件**：[skill-observability.js](file:///e:/Harness_V1_0429/src/runtime/skill/skill-observability.js) | **核心类**：`SkillObservability extends EventEmitter`

SkillObservability聚合技能子系统各模块的运行指标，提供执行链路追踪、健康仪表盘和告警规则引擎，是技能子系统的统一监控中心。

### 6.1 模块挂载

`attachModule(name, module)` 挂载技能子系统模块，用于后续指标收集。支持8个模块名称：

| 名称 | 对应模块 | 要求 |
|------|---------|------|
| `router` | SkillRouter | 提供 `getStats()` 方法 |
| `curator` | SkillCurator | 提供 `getStats()` 方法 |
| `improver` | SkillImprover | 提供 `getStats()` 方法 |
| `evolver` | SkillEvolver | 提供 `getStats()` 方法 |
| `creationEngine` | SkillCreationEngine | 提供 `getStats()` 方法 |
| `improvementLoop` | SkillImprovementLoop | 提供 `getStats()` 方法 |
| `graph` | SkillGraph | 提供 `getStats()` 方法 |
| `canary` | SkillCanary | 提供 `getStats()` 方法 |

### 6.2 指标收集

`collectMetrics()` 从所有挂载模块调用 `getStats()` 方法，返回按模块名称索引的指标快照。每个模块的调用使用 `safeExecute` 包裹，单个模块异常不影响整体收集。

### 6.3 执行链路追踪

```javascript
const traceId = observability.startTrace('tdd-implement', { agent: 'task-worker' });
// ... 技能执行 ...
observability.endTrace(traceId, { error: null, duration: 5000 });
```

- 活跃追踪容量：`MAX_ACTIVE_TRACES = 200`，超出时最旧追踪自动完成
- 完成追踪容量：`MAX_COMPLETED_TRACES = 500`，超出时FIFO淘汰

### 6.4 健康仪表盘

`getHealthDashboard()` 返回综合健康数据：

```javascript
{
  healthy: boolean,
  moduleHealth: { [name]: boolean },     // 各模块健康状态
  skills: { total, active, stale },      // 技能统计
  cacheHitRate: number,                  // 缓存命中率
  flywheel: { patches, learnings, ... }, // 飞轮统计
  canary: Object,                        // 金丝雀状态
  recentErrors: Array,                   // 最近10条错误
  activeTraces: number,
  completedTraces: number,
  alertRules: number,
  activeAlerts: number,
}
```

### 6.5 告警规则引擎

`addAlertRule(rule)` 添加告警规则：

```javascript
observability.addAlertRule({
  name: 'low-cache-hit-rate',
  condition: (metrics) => metrics.router?.cacheHitRate < 0.3,
  severity: 'warning',
});
```

`evaluateAlerts()` 基于当前指标快照评估所有规则，新触发的告警发出 `alert-triggered` 事件，恢复的告警发出 `alert-cleared` 事件。

### 6.6 核心方法

| 方法 | 签名 | 说明 |
|------|------|------|
| `attachModule` | `(name, module) → SkillObservability` | 挂载技能子系统模块 |
| `collectMetrics` | `() → Object` | 从所有挂载模块收集指标快照 |
| `getAggregatedMetrics` | `() → Object \| null` | 获取上次收集的指标快照 |
| `startTrace` | `(skillId, context?) → string` | 开始追踪技能执行，返回traceId |
| `endTrace` | `(traceId, result?) → void` | 结束追踪，记录执行结果 |
| `getTrace` | `(traceId) → Object \| null` | 获取单条追踪记录 |
| `getActiveTraces` | `() → Object[]` | 获取所有活跃追踪 |
| `getRecentTraces` | `(limit?) → Object[]` | 获取最近完成的追踪 |
| `getHealthDashboard` | `() → Object` | 返回综合健康仪表盘数据 |
| `addAlertRule` | `(rule) → void` | 添加告警规则 |
| `removeAlertRule` | `(name) → void` | 移除告警规则 |
| `evaluateAlerts` | `() → Object[]` | 评估所有告警规则 |
| `getActiveAlerts` | `() → Object[]` | 获取当前活跃告警 |
| `isHealthy` | `() → boolean` | 检查是否健康（未关闭且活跃追踪未超限） |
| `getStats` | `() → { modulesAttached, activeTraces, completedTraces, alertRules, activeAlerts }` | 获取可观察性统计信息 |

### 6.7 事件

| 事件名 | 载荷 | 说明 |
|--------|------|------|
| `metrics-collected` | `{ snapshot, moduleCount }` | 指标收集完成 |
| `trace-started` | `{ traceId, skillId }` | 追踪开始 |
| `trace-completed` | `{ traceId, skillId, duration }` | 追踪完成 |
| `alert-triggered` | `{ name, severity }` | 告警触发 |
| `alert-cleared` | `{ name }` | 告警清除 |

### 6.8 依赖关系

- **内部依赖**：`safeExecute`（安全执行）、`shortId`（追踪ID生成）
- **混入**：`withShutdown`（关闭生命周期）
- **外部依赖**：各技能子系统模块（通过 `attachModule` 挂载，需提供 `getStats()` 和可选的 `isHealthy()` 方法）

## 7. SkillAuditTrail详解

**文件**：[skill-audit-trail.js](file:///e:/Harness_V1_0429/src/runtime/skill/skill-audit-trail.js) | **核心类**：`SkillAuditTrail extends EventEmitter`

SkillAuditTrail记录技能文件的所有变更操作，提供变更历史查询、影响分析、风险评级和审计报告生成能力。支持防抖持久化到磁盘，启动时自动恢复。

### 7.1 变更动作类型

| 动作 | 说明 |
|------|------|
| `created` | 技能创建 |
| `modified` | 技能修改 |
| `deleted` | 技能删除 |
| `classified` | 技能分类变更 |
| `pinned` | 技能钉住 |
| `unpinned` | 技能取消钉住 |
| `evolved` | 技能演化 |
| `improved` | 技能改进 |
| `promoted` | 技能晋升（金丝雀通过） |
| `rolled_back` | 技能回滚 |
| `canary_enabled` | 金丝雀启用 |
| `canary_disabled` | 金丝雀禁用 |

### 7.2 操作者类型

| 操作者 | 说明 |
|--------|------|
| `system` | 系统自动操作 |
| `user` | 用户手动操作 |
| `agent` | Agent操作 |
| `evolver` | SkillEvolver演化操作 |
| `improver` | SkillImprover改进操作 |
| `curator` | SkillCurator策展操作 |
| `canary` | SkillCanary灰度操作 |

### 7.3 影响分析

`getImpactAnalysis(skillId)` 分析技能变更的影响范围：

```javascript
{
  skillId: string,
  changeCount: number,
  lastChange: Object | null,
  dependents: string[],   // 依赖该技能的技能列表（通过SkillGraph查询）
  riskLevel: 'low' | 'medium' | 'high',
}
```

**风险评级规则**：

| 条件 | 风险级别 |
|------|---------|
| 最近7天变更 > 10次 | high |
| 核心技能且最近7天变更 > 5次 | high |
| 最近7天变更 > 5次 | medium |
| 核心技能且最近7天有变更 | medium |
| 其他 | low |

核心技能判定：技能的 `phase` 为 `brainstorming`、`requirement-analysis` 或 `architecture-design`。

### 7.4 审计报告

`generateAuditReport(options)` 生成结构化审计报告：

```javascript
{
  period: { since, until },
  totalChanges: number,
  byAction: { [action]: count },
  byActor: { [actor]: count },
  topChangedSkills: [{ skillId, changeCount }],  // Top 10
  highRiskSkills: [{ skillId, riskLevel, changeCount }],
  impactSummaries: [{ skillId, changeCount, lastChange, dependents, riskLevel }],
}
```

### 7.5 持久化

- 存储路径：`.harness/skills/.audit/audit-trail.json`
- 使用 `DebouncedPersister` 防抖持久化
- 启动时通过 `JsonStoreRestorer` 恢复数据
- 最大条目数：`MAX_ENTRIES = 5000`，超出时FIFO淘汰
- 健康检查上限：`HEALTH_MAX_ENTRIES = 10000`

### 7.6 核心方法

| 方法 | 签名 | 说明 |
|------|------|------|
| `recordChange` | `(entry) → Object \| null` | 记录变更条目 |
| `getHistory` | `(skillId, options?) → Object[]` | 查询技能变更历史，支持多维度过滤 |
| `getRecentChanges` | `(limit?) → Object[]` | 获取最近的所有变更 |
| `getChangesByActor` | `(actor, limit?) → Object[]` | 按操作者查询变更 |
| `getChangesByAction` | `(action, limit?) → Object[]` | 按动作类型查询变更 |
| `getChangeCount` | `(skillId?) → number` | 获取变更计数 |
| `getImpactAnalysis` | `(skillId) → Object` | 分析技能变更的影响范围和风险级别 |
| `generateAuditReport` | `(options?) → Object` | 生成审计报告 |
| `attachSkillGraph` | `(graph) → SkillAuditTrail` | 挂载SkillGraph实例，用于影响分析 |
| `attachSkillRouter` | `(router) → SkillAuditTrail` | 挂载SkillRouter实例，用于核心技能判定 |
| `getStats` | `() → { totalEntries, byAction, byActor, oldestEntry, newestEntry }` | 获取审计轨迹统计信息 |
| `isHealthy` | `() → boolean` | 检查是否健康（未关闭且条目数未超限） |

### 7.7 配置项

| 选项 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `projectRoot` | string | '' | 项目根目录（为空时不持久化） |
| `maxEntries` | number | 5000 | 最大条目数 |
| `debounceMs` | number | - | 防抖持久化延迟毫秒数 |

### 7.8 事件

| 事件名 | 载荷 | 说明 |
|--------|------|------|
| `change-recorded` | `record` | 变更条目已记录 |
| `audit-report-generated` | `report` | 审计报告已生成 |

### 7.9 依赖关系

- **内部依赖**：`DebouncedPersister`（防抖持久化）、`JsonStoreRestorer`（数据恢复）、`timestampId`（条目ID生成）、`safeExecute`/`safeCall`（安全执行）
- **混入**：`withShutdown`（关闭生命周期）
- **外部依赖**：SkillGraph（`attachSkillGraph`，用于影响分析中的依赖者查询）、SkillRouter（`attachSkillRouter`，用于核心技能判定）

## 8. SkillImprovementLoop详解

**文件**：[skill-improvement-loop.js](file:///e:/Harness_V1_0429/src/runtime/skill/skill-improvement-loop.js) | **核心类**：`SkillImprovementLoop extends EventEmitter`

SkillImprovementLoop实现"学习→积累→审批→应用"的完整闭环，将学习经验自动写入技能Markdown文件。核心机制是飞轮三道门验证，只有全部通过的技能改进才会被提升到正式技能文件中。

### 8.1 自动改进触发

`_checkAutoImprove(skillId)` 在每次记录学习后检查：

- 学习记录数 ≥ `AUTO_IMPROVE_THRESHOLD(3)` 时触发
- 提取所有tips和avoidances
- 若有 `SkillPatchApproval`，提交审批流程；否则暂存到 `_pendingPatches`
- 待审批补丁容量：`MAX_PENDING_PATCHES = 100`，超出时淘汰最旧

### 8.2 飞轮三道门

```
Gate 1: 成功率阈值 → Gate 2: 回测 → Gate 3: AB测试 → promoted / failed
```

| 门禁 | 阈值 | 说明 |
|------|------|------|
| Gate 1 | `FLYWHEEL_SUCCESS_THRESHOLD = 5` | 学习记录数≥5条且存在技巧或避坑数据 |
| Gate 2 | `FLYWHEEL_BACKTEST_MIN_RATE = 0.6` | 近10条学习中含whatWorked的比例≥60% |
| Gate 3 | `FLYWHEEL_AB_TEST_ROUNDS = 10`，`FLYWHEEL_AB_MIN_IMPROVEMENT = 0.1` | AB测试至少10轮，改进比例≥10% |

**门禁状态流转**：

```
none → backtest (Gate1通过) → ab-test (Gate2通过) → promoted (Gate3通过) / failed (Gate3未通过)
```

### 8.3 补丁应用流程

`applyPatch(skillId, options)` 执行完整的补丁应用流程：

```
1. 获取已审批/待处理的补丁
2. _backupSkill() → 备份原文件到 .harness/skills/.backups/
3. 读取技能Markdown文件
4. _splitFrontmatter() → 分离Frontmatter和Body
5. 查找 IMPROVEMENT_MARKER ('<!-- auto-improvement-section -->')
6. _buildImprovementSection() → 构建改进内容
7. 替换/追加改进内容到Body
8. writeAtomicTextAsync() → 原子写入
9. skillRouter.discoverAsync() → 重新发现
10. 发出 'improvement-applied' 事件
```

### 8.4 改进内容格式

`_buildImprovementSection(patch)` 生成的改进内容：

```markdown
> 基于7次执行经验自动生成 (2026-05-31)

### 成功技巧
- 先写失败测试再实现
- 始终确认RED状态

### 避坑指南
- 跳过RED阶段导致返工
- 不要在GREEN阶段过度设计
```

### 8.5 因果数据总线集成

当 `causalBus` 可用时，学习记录会发布到因果数据总线：

```javascript
this._causalBus.publish('skill:learning-recorded', {
  skillId, agentId, tips, avoidances,
});
```

### 8.6 共享学习

`getSharedTipsForContext(skillId)` 合并本地学习和共享学习（来自SqliteStore），提供更全面的经验参考。

### 8.7 核心方法

| 方法 | 签名 | 说明 |
|------|------|------|

## 9. 模块间协作流程

### 9.1 技能生命周期闭环

```
┌──────────────────────────────────────────────────────────────────────────┐
│                        技能生命周期完整闭环                                │

│  1. 创建阶段                                                             │

│                                                                          │
│  2. 演化阶段                                                             │
│     SkillEvolver.evolve(skillId, traces) → 三阶段LLM分析                 │
│     SkillAuditTrail.recordChange({ action: 'evolved', actor: 'evolver'})│
│                                                                          │
│  3. 灰度阶段                                                             │

│     ├── 通过 → SkillCanary.promote(skillId)                             │

│     └── 失败 → SkillCanary.rollback(skillId)                            │
│               SkillAuditTrail.recordChange({ action: 'rolled_back' })    │
│                                                                          │
│  5. 监控阶段                                                             │
│     SkillObservability.collectMetrics() → 聚合各模块指标                  │
│     SkillObservability.startTrace() / endTrace() → 链路追踪              │

```

## 10. 与其他子系统的交互

### 10.1 与技能路由子系统的交互

- **SkillRouter** → SkillTreeDAG：路由发现后注册技能节点和依赖关系
- **SkillRouter** → SkillObservability：作为被监控模块提供 `getStats()` 数据
- **SkillRouter** → SkillAuditTrail：技能发现变更时记录审计条目
- **SkillEvolver** → SkillRouter：演化补丁应用后调用 `discoverAsync()` 重新发现
- **SkillImprovementLoop** → SkillRouter：改进补丁应用后调用 `discoverAsync()` 重新发现

### 10.2 与因果子系统的交互

- **SkillImprovementLoop** → CausalDataBus：学习记录发布到 `skill:learning-recorded` 主题
- **CausalDataBus** → SkillEvolver：因果事件可触发演化流程

### 10.3 与模型子系统的交互

- **SkillEvolver** → TokenManager：演化前检查Token预算（`remaining/total >= 0.3`）
- **SkillEvolver** → LLM客户端：三阶段演化流程调用 `chat()` 方法

### 10.4 与思维子系统的交互

- **DreamEngine** → SkillTreeDAG：梦境模式可触发种子技能自生长
- **DreamEngine** → SkillImprovementLoop：离线经验提炼后注入学习记录

### 10.5 与基础设施子系统的交互

- **SqliteStore** → SkillImprovementLoop：学习记录持久化存储
- **DebouncedPersister** → SkillAuditTrail：审计数据防抖持久化
- **JsonStoreRestorer** → SkillAuditTrail：启动时恢复审计数据

### 10.6 与权限子系统的交互

- **SkillPatchApproval** → SkillEvolver / SkillImprovementLoop：补丁审批流程管控
- **RBACEnforcer** → SkillCanary：金丝雀操作权限控制
