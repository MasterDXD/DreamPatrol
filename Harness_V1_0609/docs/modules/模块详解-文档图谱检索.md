# 模块详解-文档图谱检索

> 版本：2.73.4 | 文件：src/runtime/workflow/graph-rag.js | 行数：~895行

---

## 模块概述

GraphRAG模块实现了基于知识图谱的检索增强生成（Graph-based Retrieval-Augmented Generation）系统。模块从文档内容中自动提取四类实体（PERSON/ORG/TECH/CONCEPT），通过段落级共现分析和关键词检测建立三种关系（DEPENDS_ON/PART_OF/RELATED_TO），基于连通分量算法构建实体聚类，支持多跳子图扩展查询。核心价值在于将非结构化文档转化为结构化的实体-关系图谱，使Agent能够通过图谱遍历发现隐含的知识关联。

## 融合来源

融合自知识图谱（Knowledge Graph）和信息检索领域的GraphRAG技术。传统RAG仅依赖向量相似度检索，GraphRAG通过构建实体-关系图谱，支持多跳推理和关联发现，弥补了纯向量检索在关联推理上的不足。实体提取融合了命名实体识别（NER）的正则表达式方法，关系检测借鉴了开放信息抽取（OpenIE）的共现分析策略。

## 使用示例

```javascript
const GraphRAG = require('./src/runtime/workflow/graph-rag');

const graphRag = new GraphRAG({ maxEntities: 3000, maxRelations: 5000 });
graphRag.attachEmbeddingService(embeddingService);

graphRag.ingestDocument('arch-overview', `
  SkillRouter负责Skill的自动发现和匹配。
  PhaseOrchestrator依赖SkillRouter来确定阶段转换。
  SessionManager与PhaseOrchestrator协作管理会话状态。
  框架采用分层架构，Interaction层依赖Business层。
`);

graphRag.buildClusters();

const result = graphRag.query('SkillRouter和PhaseOrchestrator的关系', {
  topK: 5,
  maxHops: 2,
  minRelevance: 0.3,
});

console.log('Results:', result.results.length);
console.log('Paths:', result.paths.length);

const entityGraph = graphRag.getEntityGraph('ent_1', 2);
console.log('Subgraph entities:', entityGraph.entities.length);
```

## 核心算法详解

### ingestDocument() 文档摄入管线

文档摄入采用四阶段管线架构，每阶段独立处理、逐级传递：

```
文本分段 → 实体提取(NER正则) → 关系检测(共现分析+关键词) → 图谱写入
```

**阶段一：文本分段**

文档内容按 `\n\s*\n` 正则分割为段落（`PARAGRAPH_SPLIT`），段落作为后续共现分析的基本窗口单元。分段结果传递给实体提取和关系检测两个阶段。

**阶段二：实体提取**

调用 `_extractEntities(content, docId)` 执行NER正则提取。详见下方"实体提取算法"小节。

**阶段三：关系检测**

调用 `_extractRelations(content, entities, docId)` 基于提取出的实体执行共现分析。详见下方"关系检测算法"小节。

**阶段四：图谱写入**

实体和关系直接写入内存Map（`_entities`、`_relations`），同时维护键索引（`_entityKeyIndex`、`_relationKeyIndex`）用于去重和快速查找。写入完成后更新统计计数器并发射 `document-inguted` 事件。

**容量保护机制**：

- 文档数达到 `maxDocuments`（默认500）时，淘汰最早导入的文档（Map插入序保证FIFO）
- 重复导入同一docId时，先调用 `_removeDocumentEntities()` 清除旧实体和关系，再重新摄入
- 实体数达到 `maxEntities` 时停止实体提取循环
- 关系数达到 `maxRelations` 时停止关系创建循环

### 实体提取算法

实体提取由 `_extractEntities(content, docId)` 方法实现，采用四类正则模式并行扫描：

**四类实体正则模式**：

| 实体类型 | 正则特征 | 匹配示例 |
|---------|---------|---------|
| PERSON | 称谓+姓名 / 名+中间名首字母+姓 | `Dr. Alice Smith`, `John Q. Public` |
| ORG | 大写词组+组织后缀（Inc/Corp/Ltd/LLC/Company/Group/Foundation/Institute/University/Team/Lab等） | `OpenAI Inc`, `MIT University` |
| TECH | 点分驼峰（`a.b.C`）、连字符JS/TS文件名（`xxx-yyy.js`）、技术缩写词（`xxxJS/API/SDK/CLI/ORM/DB/SQL/HTTP/REST/RPC/ML/AI/LLM`）、驼峰命名 | `Node.js`, `express-router.js`, `TypeScriptSDK`, `WebSocket` |
| CONCEPT | 中文2-8字+领域后缀（模型/架构/系统/引擎/框架/平台/模块/组件/服务/流程/策略/规则/协议/接口/数据/缓存/队列/任务/调度/监控/安全/权限/认证/授权） | `知识图谱引擎`, `权限认证` |

**上下文窗口消歧**：

提取过程通过 `_entityKeyIndex`（键格式：`TYPE:normalizedName`）实现去重和合并：

1. 每个正则匹配结果先通过 `_normalizeEntityName()` 标准化（trim + 多空格压缩为单空格）
2. 构建键 `type:normalizedName`，在 `seen` 集合中检查本次提取是否已出现同名同类型实体
3. 若 `_entityKeyIndex` 中已存在该键，说明图谱中已有该实体，仅追加mention记录 `{docId, position}`
4. 若不存在，创建新实体对象并写入 `_entities` Map 和 `_entityKeyIndex`

这种设计确保跨文档的同一实体被合并而非重复创建，mention数组记录了实体在所有文档中的出现位置，为后续段落级共现分析提供位置索引。

### 关系检测算法

关系检测由 `_extractRelations(content, entities, docId)` 方法实现，采用段落级共现统计 + 预定义关系关键词匹配的双策略：

**策略一：段落级共现统计（cooccurrenceWindow）**

1. 文档按 `PARAGRAPH_SPLIT`（`\n\s*\n`）分割为段落
2. 对每个段落，通过 `_findParagraphEntities()` 找出段落内出现的实体：遍历每个实体的mentions，检查position是否落在段落范围 `[paraStart, paraEnd)` 内
3. 段落内实体两两配对（`_createCooccurrenceRelations()`），创建共现关系

**策略二：预定义关系关键词匹配**

对每个共现实体对，调用 `_detectRelationType(paragraph, source, target)` 检测关系类型：

| 关系类型 | 关键词模式 | 判定逻辑 |
|---------|-----------|---------|
| DEPENDS_ON | `depends? on / relies? on / requires? / needs? / uses? / 依赖 / 需要 / 引用 / 调用` | 段落匹配关键词 **且** source实体在文本中出现在target实体之前 |
| PART_OF | `part of / belongs? to / contained? in / member of / submodule of / 包含 / 属于 / 组成 / 一部分` | 段落匹配关键词即判定 |
| RELATED_TO | `related to / associated with / connected to / links? to / references? / 相关 / 关联 / 连接 / 涉及` | 段落匹配关键词即判定 |
| RELATED_TO（默认） | 无匹配 | 所有关键词均不匹配时，默认为RELATED_TO |

**权重计算公式**：

```
初始权重：W₀ = 0.3
重复共现增强：Wₙ = min(Wₙ₋₁ + 0.1, 1.0)
剪枝阈值：W < minRelationWeight（默认0.1）→ 移除
有效权重范围：[minRelationWeight, 1.0]
```

- 新建关系初始权重0.3，evidence字段保存段落前200字符作为关系证据
- 若同一实体对（正向或反向）已存在同类型关系，权重递增0.1，上限1.0
- 关系创建完成后，`_pruneWeakRelations()` 移除权重低于 `minRelationWeight` 的弱关系

### buildClusters() 连通分量聚类

聚类构建由 `buildClusters()` 方法实现，采用基于邻接表的连通分量检测算法：

**步骤一：构建邻接表（`_buildAdjacency`）**

遍历所有关系，为每个实体构建无向邻居集合。关系视为无向边——source和target互为邻居：

```
adjacency[entityId] = Set<neighborEntityId>
```

**步骤二：查找连通分量（`_findConnectedComponents`）**

采用DFS（栈实现）遍历所有实体节点：

1. 初始化 `visited` 空集合和 `communities` 空数组
2. 遍历 `_entities` Map中每个实体ID
3. 若实体未被访问，以该实体为起点执行DFS：压栈 → 弹出 → 标记已访问 → 加入当前community → 将未访问邻居压栈
4. DFS完成后，community即为一个连通分量
5. 所有连通分量按实体数量降序排列

**步骤三：孤立实体过滤**

单元素连通分量（仅含一个无关系实体）也会被保留在聚类中，但其聚类摘要仅包含实体名和类型统计，无关系信息。超过 `maxClusters`（默认100）时按实体数降序截断，小聚类优先淘汰。

**步骤四：聚类标签生成（`_generateClusterSummary`）**

对每个连通分量调用 `_buildClusterFromCommunity()` 构建聚类对象，摘要包含：
- 前10个实体名称（`Entities: ...`）
- 实体类型统计（`Types: 3 PERSON, 2 TECH, 1 CONCEPT`）
- 关系类型统计（`Relations: 2 DEPENDS_ON, 1 RELATED_TO`）

### query() 多跳查询算法

查询由 `query(question, options)` 方法实现，采用四阶段管线：

```
实体识别 → 子图扩展(maxHops限制) → 路径评分 → 结果排序(topK截断)
```

**阶段一：实体识别**

调用 `_extractQueryEntities(question)` 从问题中提取查询实体：

1. 使用四类实体正则（PERSON/ORG/TECH/CONCEPT）扫描问题文本
2. 额外匹配大写词组（`\b[A-Z][a-z]+(?:\s+[A-Z][a-z]+)*\b`）作为CONCEPT类型补充
3. 去重后返回查询实体列表

调用 `_matchEntities(queryEntities)` 匹配图谱中已有实体：

- 精确匹配：`_entityKeyIndex` 中查找 `TYPE:normalizedName`，匹配分数 = 1.0
- 模糊匹配：遍历 `_entities`，比较小写名称的包含关系，匹配分数 = 0.8
- 模糊匹配条件：`eLower === qLower || eLower.indexOf(qLower) >= 0 || qLower.indexOf(eLower) >= 0`

**阶段二：子图扩展（`_expandSubGraph`）**

BFS从匹配实体集合出发，逐层扩展邻居节点：

1. 构建全局邻接表（从 `_relations` 构建，每条关系双向添加）
2. 将所有匹配实体入队，初始跳数 hops = 0
3. BFS循环：弹出队首实体，若未访问则加入子图；若 hops < maxHops，将其未访问邻居入队（hops + 1）
4. 收集子图内关系（source和target均在子图中的关系）
5. 去重关系（通过 `seenRelIds` 集合）

**maxHops参数**控制扩展深度，默认值为2。v2.7.139增加了深度限制防止组合爆炸（详见R58修复记录）。

**阶段三：路径评分（`_scoreSubGraph`）**

对子图中每个实体计算相关性评分：

```
匹配实体：score = matchScore（1.0 或 0.8）
非匹配实体：score = 0.5 / max(distance, 1)
关系权重加成：score += relationWeight(entityId, subGraphRelations) × 0.2
最终分数：score = min(score, 1.0)
```

其中 `relationWeight` 为该实体在子图中所有关联关系的权重之和。

**阶段四：结果排序**

1. 过滤：移除 score < minRelevance（默认0.3）的实体
2. 排序：按score降序排列
3. 截断：取前topK（默认5）个结果
4. 路径提取：调用 `_extractPaths()` 从结果实体回溯到匹配实体，生成关联路径（最多10条）

## 图谱数据结构

### _entities Map

主实体存储，键为实体ID（`ent_1`, `ent_2`, ...），值为实体对象：

```javascript
{
  id: string,           // 实体ID，格式 ent_N
  name: string,         // 标准化实体名（trim + 多空格压缩）
  type: string,         // PERSON | ORG | TECH | CONCEPT
  mentions: [           // 出现记录数组
    {
      docId: string,    // 所属文档ID
      position: number  // 在文档内容中的字符偏移量
    }
  ]
}
```

### _entityKeyIndex Map

实体键索引，用于O(1)精确查找和跨文档实体合并。键格式为 `TYPE:normalizedName`，值为实体ID。例如 `"TECH:Node.js" → "ent_3"`。

### _relations Map

主关系存储，键为关系ID（`rel_1`, `rel_2`, ...），值为关系对象：

```javascript
{
  id: string,           // 关系ID，格式 rel_N
  source: string,       // 源实体ID
  target: string,       // 目标实体ID
  type: string,         // DEPENDS_ON | PART_OF | RELATED_TO
  weight: number,       // 关系权重 [minRelationWeight, 1.0]
  evidence: string      // 关系证据文本（段落前200字符）
}
```

### _relationKeyIndex Map

关系键索引，用于关系去重。键格式为 `sourceId->targetId:relType`，值为关系ID。创建关系时同时检查正向键和反向键，避免重复创建。

### _clusters Map

聚类存储，键为聚类ID（`cluster_1`, `cluster_2`, ...），值为聚类对象：

```javascript
{
  id: string,           // 聚类ID，格式 cluster_N
  entities: Array,      // 聚类内实体对象数组
  relations: Array,     // 聚类内关系对象数组（source和target均在聚类内）
  summary: string,      // 聚类摘要（实体名 + 类型统计 + 关系统计）
  documentIds: [string] // 关联文档ID列表
}
```

### _documents Map

文档索引，键为文档ID，值为文档对象：

```javascript
{
  id: string,           // 文档ID
  content: string,      // 文档原始内容
  metadata: Object,     // 文档元数据（用户自定义）
  ingestedAt: string    // 摄入时间（ISO 8601格式）
}
```

Map的插入序保证FIFO语义，文档数达到上限时淘汰最早导入的文档。

## 查询优化策略

### 实体缓存

`_entityKeyIndex` 提供O(1)精确查找能力。查询时先通过键索引定位实体，避免遍历全量 `_entities` Map。模糊匹配仅在精确匹配失败时触发，作为降级策略使用。

### 子图剪枝

BFS扩展子图时采用两层剪枝：

1. **visited集合**：已访问实体不再入队，避免环路导致的无限扩展
2. **maxHops深度限制**：当 hops ≥ maxHops 时，当前实体不再扩展其邻居，从源头限制子图规模
3. **关系去重**：子图关系收集时通过 `seenRelIds` 集合去重，且仅保留两端实体均在子图中的关系

### 早期终止

多处设置容量上限检查实现早期终止：

- `_extractEntities()`：实体数达到 `maxEntities` 时break退出循环
- `_createCooccurrenceRelations()`：关系数达到 `maxRelations` 时break退出双层循环
- `_extractRelations()`：段落遍历中关系数达到上限时break

### relevance阈值过滤

`minRelevance`（默认0.3）作为最终过滤门槛，移除评分低于阈值的实体。这确保了查询结果仅包含与查询实体有足够关联度的节点，减少无效结果噪音。阈值可通过 `query()` 的options参数调整。

## R58修复记录

| 字段 | 内容 |
|------|------|
| 编号 | R58 |
| 版本 | v2.7.139 |
| 类型 | 性能优化 |
| 模块 | graph-rag.js |
| 问题 | 图谱查询在高度连通的知识图谱上执行多跳扩展时，BFS扩展的节点数随跳数呈指数增长（O(b^d)，b为平均度数，d为跳数），导致查询响应时间急剧上升甚至超时 |
| 修复 | `query()` 方法的 `_expandSubGraph()` 增加maxHops深度限制（默认值2），BFS扩展时当 hops ≥ maxHops 即停止该方向的邻居扩展；同时增加visited集合防止环路重复访问 |
| 影响 | 查询性能提升显著，2跳扩展在平均度数10的图谱上将最大访问节点数从无限制降至约100个；查询结果精度基本不受影响，因为2跳已覆盖绝大多数有意义的关联路径 |
| 回归测试 | 通过5000+测试用例，图谱查询相关用例全部通过 |
