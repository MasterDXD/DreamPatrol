# 模块详解-基础设施核心模块群

> 源码路径：`src/runtime/infrastructure/`
> 模块数量：6
> 核心职责：基础设施核心服务——重试/并发/健康/构建/插件/存储

---

## 模块群概述

基础设施核心模块群是运行时引擎（`src/runtime/infrastructure/`）的核心服务层，负责从**任务重试与升级**、**并发控制**、**健康检查**、**实例构建与销毁**、**插件生命周期管理**和**持久化存储**六个维度为整个框架提供底层支撑能力。该模块群包含6个核心模块，其中5个继承自 `EventEmitter`，1个为纯函数模块（InstanceBuilder），是所有上层子系统（Agent、工作流、门禁、深化推理等）的运行时依赖。

基础设施核心模块群的设计理念是：**为上层子系统提供可靠、可控、可观测的基础设施原语，使上层模块无需关心重试策略、并发限制、健康探测、实例组装、插件扩展和数据持久化等横切关注点**。通过 `RetryEngine` 提供三级升级重试，通过 `ConcurrencyController` 提供信号量式并发限制，通过 `HealthChecker` 提供分层健康检查与探针，通过 `InstanceBuilder` 提供框架实例构建与优雅销毁，通过 `PluginManager` 提供插件注册与钩子执行，通过 `SqliteStore` 提供多表持久化与全文检索，共同构成框架的"六大基石"。

## 模块清单

| 模块 | 源文件 | 说明 |
|------|--------|------|
| RetryEngine | retry-engine.js | 重试引擎：指数退避、三级升级策略（retry→replan→decompose）、关闭中断休眠 |
| ConcurrencyController | concurrency-controller.js | 并发控制器：信号量式并发限制、acquire/release手动控制、run自动管理、租约超时 |
| HealthChecker | health-checker.js | 健康检查器：分层检查项（critical/warning/info）、liveness/readiness探针、因果数据总线集成 |
| InstanceBuilder | instance-builder.js | 实例构建器：属性映射、分组API构建、管道执行绑定、优雅销毁 |
| PluginManager | plugin-manager.js | 插件管理器：插件注册/注销、钩子链式执行、危险键过滤、初始化失败回滚 |
| SqliteStore | sqlite-store.js | SQLite存储：多表管理、FTS5全文检索、WAL模式、容量淘汰、JSON迁移 |

## 共同设计模式

### 1. EventEmitter继承

6个模块中有5个继承自 `EventEmitter`（InstanceBuilder为纯函数模块），可直接 `emit`/`on` 进行事件通知：

| 模块 | 事件机制 |
|------|---------|
| RetryEngine | `task-completed`、`task-retry`、`retry-exhausted`、`escalation` |
| ConcurrencyController | `acquired`、`released`、`queued`、`rejected`、`timeout`、`lease-expired`、`run-rejected` |
| HealthChecker | `initialized`（由SqliteStore发射） |
| PluginManager | 继承EventEmitter，无自定义事件 |
| SqliteStore | `initialized`、`migrated`、`knowledge-added`、`knowledge-updated`、`knowledge-removed`、`session-summary-saved`、`skill-learning-added`、`shared-learning-added`、`memory-added`、`memory-removed`、`memory-verified`、`memories-invalidated`、`user-preference-set`、`affinity-upserted`、`evicted` |

### 2. withShutdown混入

5个类模块均通过 `withShutdown` 混入支持优雅关闭：

| 模块 | 关闭行为 |
|------|---------|
| RetryEngine | 清空尝试记录、批量清理休眠定时器、移除所有事件监听 |
| ConcurrencyController | 清空等待队列和运行中任务、清除租约定时器 |
| HealthChecker | 清空检查项/层级/超时/状态缓存、移除所有事件监听 |
| PluginManager | 销毁所有已注册插件、清空钩子注册表 |
| SqliteStore | WAL检查点、关闭数据库连接、清理全局实例注册表 |

### 3. 容量保护

所有带容量限制的模块在达到上限时执行淘汰策略：

| 模块 | 容量限制 | 淘汰策略 |
|------|---------|---------|
| RetryEngine | `_maxAttemptsEntries`（1000） | FIFO淘汰最旧尝试记录 |
| ConcurrencyController | `_maxQueue`（默认100） | 队列满时拒绝新请求 |
| HealthChecker | `_maxChecks`（100） | 超过时拒绝注册 |
| PluginManager | `MAX_PLUGINS`（100）、`MAX_HOOKS_PER_NAME`（50） | 超过时拒绝注册 |
| SqliteStore | knowledge（500）、skill_learnings（200）、shared_learnings（200）、causal_chain（2000） | 淘汰最旧10%记录 |

## RetryEngine详解

### 职责概述

重试引擎提供带指数退避的任务重试和三级升级策略（retry→replan→decompose）。重试耗尽后自动升级：先尝试重新规划任务（replan），再尝试分解为子任务递归执行（decompose）。支持关闭检测中断休眠、任务尝试追踪和事件通知。

### 构造函数参数

```javascript
new RetryEngine(options)
```

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `options.maxRetries` | number | 3 | 最大重试次数，上限为100 |
| `options.backoffBaseMs` | number | 1000 | 退避基础时间（毫秒），实际退避为 `backoffBaseMs * 2^(attempt-1)` |

### 核心方法

#### `execute(task, _depth)`

执行带重试和升级策略的任务。重试耗尽后依次尝试重新规划（replan）和分解（decompose）。

- **参数**：
  - `task` (`Object`) — 任务对象
    - `task.execute` (`Function`, 必需) — 任务执行函数，签名为 `(context: Object) => Promise<*>`
    - `task.id` (`string`, 可选) — 任务标识符
    - `task.replan` (`Function`, 可选) — 重新规划函数，签名为 `(errors: Array) => Promise<Object|null>`
    - `task.decompose` (`Function`, 可选) — 分解函数，签名为 `(errors: Array) => Promise<Object[]>`
  - `_depth` (`number`, 可选, 默认0) — 当前递归深度，超过 `MAX_DECOMPOSE_DEPTH`（3）时终止
- **返回值**：`Promise<{ success: boolean, result?: *, attempts: number, escalatedTo?: string, errors?: Array, partialResults?: Array }>`
- **说明**：每次重试间使用指数退避，退避上限为 `MAX_BACKOFF_MS`；关闭时自动中断休眠

#### `getAttempt(taskId)`

获取指定任务的尝试上下文信息。

- **参数**：`taskId` (`string`) — 任务标识符
- **返回值**：`Object | null` — 任务尝试上下文，包含 `taskId`、`level`、`attempt`、`maxRetries`、`errors` 等字段

### 事件列表

| 事件名 | 触发条件 | 数据 |
|--------|---------|------|
| `task-completed` | 任务执行成功 | `{ taskId, attempt, result?, level? }` |
| `task-retry` | 任务执行失败，即将重试 | `{ taskId, attempt, error }` |
| `retry-exhausted` | 重试次数耗尽 | `{ taskId, errors }` |
| `escalation` | 升级到replan或decompose | `{ taskId, level }` |

### 配置常量

| 常量 | 值 | 说明 |
|------|-----|------|
| `ESCALATION_LEVELS.RETRY` | `'retry'` | 重试级别 |
| `ESCALATION_LEVELS.REPLAN` | `'replan'` | 重新规划级别 |
| `ESCALATION_LEVELS.DECOMPOSE` | `'decompose'` | 分解级别 |
| `DEFAULT_MAX_RETRIES` | 3 | 默认最大重试次数 |
| `ABSOLUTE_MAX_RETRIES` | 100 | 绝对最大重试次数上限 |
| `MAX_DECOMPOSE_DEPTH` | 3 | 最大分解递归深度 |

### 使用示例

```javascript
const RetryEngine = require('./src/runtime/infrastructure/retry-engine');

const engine = new RetryEngine({ maxRetries: 3, backoffBaseMs: 500 });

engine.on('task-retry', ({ taskId, attempt, error }) => {
  console.log(`任务 ${taskId} 第${attempt}次重试: ${error}`);
});

engine.on('escalation', ({ taskId, level }) => {
  console.log(`任务 ${taskId} 升级到 ${level}`);
});

const result = await engine.execute({
  id: 'task-001',
  execute: async (ctx) => { return doWork(ctx); },
  replan: async (errors) => { return { execute: async (ctx) => { return alternativeWork(ctx); } }; },
  decompose: async (errors) => {
    return [
      { id: 'sub-1', execute: async (ctx) => { return subTask1(ctx); } },
      { id: 'sub-2', execute: async (ctx) => { return subTask2(ctx); } },
    ];
  },
});

console.log('成功:', result.success, '尝试次数:', result.attempts);
```

### 与其他模块的交互关系

| 模块 | 交互方式 |
|------|---------|
| ConcurrencyController | RetryEngine的重试任务可通过ConcurrencyController.run()控制并发 |
| HealthChecker | RetryEngine注册为HealthChecker的检查项，报告重试引擎健康状态 |
| InstanceBuilder | InstanceBuilder在销毁流程中调用RetryEngine.shutdown() |
| PhaseOrchestrator | 阶段编排器通过RetryEngine执行阶段任务，失败时自动重试和升级 |

## ConcurrencyController详解

### 职责概述

并发控制器是信号量式并发限制器，控制同时执行的任务数量。提供 `acquire`/`release` 手动控制和 `run` 自动管理模式，支持等待队列、超时自动释放、任务元数据追踪和统计信息。

### 构造函数参数

```javascript
new ConcurrencyController(maxConcurrent, maxQueue, options)
```

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `maxConcurrent` | number | 6 | 最大并发任务数 |
| `maxQueue` | number | 100 | 最大等待队列长度 |
| `options.leaseTimeoutMs` | number | 300000 | 任务租约超时时间（毫秒），超时后自动释放 |

### 核心方法

#### `acquire(taskId, metadata)`

获取并发槽位。有空闲槽位时立即获取，否则进入等待队列。

- **参数**：
  - `taskId` (`string | number`) — 任务标识符
  - `metadata` (`Object`, 可选) — 任务元数据
- **返回值**：`Promise<boolean>` — 获取成功返回 `true`，失败返回 `false`
- **失败原因**：关闭中、无效ID、队列满、超时

#### `release(taskId)`

释放并发槽位。释放后自动从等待队列中取出下一个任务分配槽位。

- **参数**：`taskId` (`string | number`) — 要释放的任务标识符
- **返回值**：`boolean` — 释放成功返回 `true`，任务不存在时返回 `false`

#### `run(taskId, fn, metadata)`

在并发控制下执行异步函数。自动获取和释放槽位。

- **参数**：
  - `taskId` (`string | number`) — 任务标识符
  - `fn` (`Function`) — 要执行的异步函数
  - `metadata` (`Object`, 可选) — 任务元数据
- **返回值**：`Promise<*>` — `fn` 的返回值
- **异常**：获取槽位失败时抛出 `HarnessError('ACQUIRE_FAILED')`

#### `isRunning(taskId)`

检查指定任务是否正在运行。

- **参数**：`taskId` (`string | number`) — 任务标识符
- **返回值**：`boolean`

#### `getRunningTasks()`

获取所有正在运行的任务信息列表。

- **返回值**：`Array<{ taskId: string, startedAt: number, duration: number, metadata: Object }>`

#### `getStats()`

获取并发控制器的运行统计数据。

- **返回值**：`{ maxConcurrent: number, runningCount: number, queuedCount: number, availableSlots: number }`

#### `clear()`

清空所有等待队列和运行中的任务。

- **返回值**：`void`

#### `isHealthy()`

检查并发控制器是否健康。

- **返回值**：`boolean` — 运行数未达上限或等待队列为空时返回 `true`

### 只读属性

| 属性 | 类型 | 说明 |
|------|------|------|
| `maxConcurrent` | number | 最大并发数 |
| `runningCount` | number | 当前正在运行的任务数 |
| `queuedCount` | number | 等待队列中的任务数 |
| `availableSlots` | number | 当前可用的并发槽位数 |

### 事件列表

| 事件名 | 触发条件 | 数据 |
|--------|---------|------|
| `acquired` | 成功获取槽位 | `{ taskId, runningCount, fromQueue? }` |
| `released` | 释放槽位 | `{ taskId, duration, runningCount }` |
| `queued` | 任务进入等待队列 | `{ taskId, queuedCount }` |
| `rejected` | 请求被拒绝 | `{ taskId, reason }` |
| `timeout` | 等待获取超时 | `{ taskId, reason }` |
| `lease-expired` | 租约超时自动释放 | `{ taskId, reason }` |
| `run-rejected` | run()获取槽位失败 | `{ taskId, reason }` |

### 配置常量

| 常量 | 值 | 说明 |
|------|-----|------|
| `DEFAULT_MAX_CONCURRENT` | 6 | 默认最大并发数 |
| `DEFAULT_MAX_QUEUE` | 100 | 默认最大等待队列长度 |
| `DEFAULT_LEASE_TIMEOUT_MS` | 300000 | 默认租约超时时间（5分钟） |

### 使用示例

```javascript
const ConcurrencyController = require('./src/runtime/infrastructure/concurrency-controller');

const cc = new ConcurrencyController(4, 50, { leaseTimeoutMs: 60000 });

cc.on('acquired', ({ taskId, runningCount }) => {
  console.log(`任务 ${taskId} 获取槽位，当前运行: ${runningCount}`);
});

cc.on('lease-expired', ({ taskId }) => {
  console.log(`任务 ${taskId} 租约超时，自动释放`);
});

const result = await cc.run('task-001', async () => {
  return await doExpensiveWork();
});

console.log(cc.getStats());
console.log(cc.isHealthy());
```

### 与其他模块的交互关系

| 模块 | 交互方式 |
|------|---------|
| RetryEngine | RetryEngine的重试任务可通过ConcurrencyController.run()控制并发 |
| HealthChecker | ConcurrencyController注册为HealthChecker的检查项 |
| InstanceBuilder | InstanceBuilder在销毁流程中调用ConcurrencyController.clear()和shutdown() |
| AgentRuntime | AgentRuntime通过ConcurrencyController限制同时运行的Agent数量 |
| MultiAgentRouter | 多Agent路由器通过ConcurrencyController控制并发调度 |

## HealthChecker详解

### 职责概述

健康检查器注册和管理分层健康检查项（critical/warning/info），提供单项检查、全量检查、按层级检查和聚合报告。支持 liveness/readiness 探针、超时保护、因果数据总线状态变更通知和检查统计。

### 构造函数参数

```javascript
new HealthChecker()
```

无构造函数参数，所有配置通过方法调用完成。

### 核心方法

#### `attachCausalDataBus(cdb)`

附加CausalDataBus实例，用于在健康状态变更时发布因果事件。

- **参数**：`cdb` (`CausalDataBus`) — 因果数据总线实例
- **返回值**：`HealthChecker` — this（链式调用）

#### `register(name, checkFn, tier, options)`

注册健康检查项。

- **参数**：
  - `name` (`string`, 必需) — 检查项名称（非空字符串，唯一标识）
  - `checkFn` (`Function`, 必需) — 检查函数，返回 `{ status, message }` 或抛出异常
  - `tier` (`string`, 可选, 默认 `'warning'`) — 严重层级（critical/warning/info）
  - `options.timeoutMs` (`number`, 可选) — 超时时间（毫秒）
- **返回值**：`HealthChecker` — this（链式调用）
- **异常**：名称无效、检查函数非函数、或超过最大检查数量（100）时抛出 `HarnessError`

#### `unregister(name)`

注销健康检查项。

- **参数**：`name` (`string`) — 检查项名称
- **返回值**：`boolean` — 注销成功返回 `true`，检查项不存在时返回 `false`

#### `check(name)`

执行指定名称的健康检查。

- **参数**：`name` (`string`) — 检查项名称
- **返回值**：`Promise<{ name, status, message, details, tier, timestamp, timedOut? }>` — 检查结果

#### `checkAll()`

执行所有已注册的健康检查。按批次并发执行，状态变更时通过因果数据总线发布事件。

- **返回值**：`Promise<{ status, checks, timestamp }>` — 全量检查结果

#### `checkByTier(tier)`

按严重层级执行健康检查。

- **参数**：`tier` (`string`) — 严重层级（critical/warning/info）
- **返回值**：`Promise<{ tier, checks, timestamp }>` — 按层级检查结果

#### `checkCritical()`

执行所有critical级别的健康检查。

- **返回值**：`Promise<{ tier, checks, timestamp }>` — critical层级检查结果

#### `getAggregatedReport()`

获取聚合健康报告。按层级分组汇总所有检查结果，计算整体状态和统计信息。

- **返回值**：`Promise<{ status, summary, tiers, timestamp, error? }>` — 聚合健康报告
- **整体状态判定**：critical层级有不健康项 → `'critical'`；warning层级有不健康项 → `'degraded'`；全部健康 → `'healthy'`

#### `liveness()`

存活探针。返回进程存活状态和运行时间。

- **返回值**：`Promise<{ alive: boolean, uptimeMs: number, timestamp: string }>`

#### `readiness()`

就绪探针。检查所有critical级别检查项是否健康，决定服务是否可接收流量。

- **返回值**：`Promise<{ ready: boolean, criticalChecks: number, unhealthyCritical: number, timestamp: string, error? }>`

#### `getCheckTier(name)`

获取指定检查项的严重层级。

- **参数**：`name` (`string`) — 检查项名称
- **返回值**：`string | null` — 严重层级

#### `listChecks()`

获取所有已注册检查项的名称列表。

- **返回值**：`string[]`

#### `getStats()`

获取健康检查器的运行统计数据。

- **返回值**：`{ totalChecks, checkCount, startTime, uptimeMs, lastCheckTime, lastCheckResult, tiers }`

### 事件列表

| 事件名 | 触发条件 | 数据 |
|--------|---------|------|
| （通过CausalDataBus） | 健康状态变更 | `{ checkName, previousStatus, currentStatus, tier, message }` |

### 配置常量

| 常量 | 值 | 说明 |
|------|-----|------|
| `_maxChecks` | 100 | 最大检查项数量 |

| `CHECK_TIMEOUT_MS` | `DEFAULT_REQUEST_TIMEOUT_MS` | 默认检查超时时间 |

### 使用示例

## InstanceBuilder详解

### 职责概述

实例构建器是从运行时上下文中构建框架实例对象的纯函数模块。提供属性映射、分组API构建、实例销毁等核心能力，将分散的运行时组件聚合为统一的实例接口，支持管道执行和优雅关闭。InstanceBuilder不继承EventEmitter，导出4个函数。

### 导出函数

#### `buildInstance(ctx, executePipeline)`

构建框架实例对象，将扁平属性映射、分组API、管道执行和销毁方法合并为统一实例。

- **参数**：
  - `ctx` (`Object`) — 运行时上下文对象，包含所有已初始化的组件实例
  - `executePipeline` (`Function`) — 管道执行函数，签名为 `(ctx, userMessage, options) => Promise<*>`
- **返回值**：`Object` — 框架实例对象，包含：
  - 所有 `_buildPropertyMap` 产出的扁平属性
  - 所有 `_buildGroupedAPI` 产出的分组API（core/agents/gate/collaboration/store）
  - `executePipeline(userMessage, options)` 异步方法
  - `destroy()` 异步方法

#### `_buildPropertyMap(ctx)`

从运行时上下文中构建扁平属性映射表。将上下文中所有运行时组件提取为键值对映射。

- **参数**：`ctx` (`Object`) — 运行时上下文对象
- **返回值**：`Object.<string, Object>` — 包含所有运行时组件的扁平属性映射表
- **映射字段**：router、session、orchestrator、enforcer、guard、logger、tddGate、verifier、eventBus、pluginManager、healthChecker、priorityQueue、retryEngine、concurrencyController、agentRuntime、deepeningOrchestrator、sqliteStore、causalDataBus 等140+个组件

#### `_buildGroupedAPI(ctx)`

从运行时上下文中构建分组API映射表。将组件按功能域划分为五个分组。

- **参数**：`ctx` (`Object`) — 运行时上下文对象
- **返回值**：`{ core, agents, gate, collaboration, store }` — 按功能域分组的组件映射表

| 分组 | 包含组件 |
|------|---------|
| `core` | router、session、orchestrator、enforcer、guard、logger、tddGate、verifier、eventBus、healthChecker、priorityQueue、tokenManager、commandRouter、programmableHookExecutor、contextCompressionEngine |
| `agents` | runtime、lifecycle、sandbox、monitor、deployment、stateManager、workflowIntegration、packManager |
| `gate` | tddGate、verifier、complianceChecker、deviationApproval、codeReviewCheck、designSkillEngine、generatorVerifier |
| `collaboration` | modeRouter、structuredIntent、subagentExecutor、pairChat、chatChain |
| `store` | sqlite、memory、improvementLoop、nudge、creationEngine、curator、userModelManager、mcpClient |

#### `_destroyInstance(ctx)`

异步销毁框架实例，执行优雅关闭流程。

- **参数**：`ctx` (`Object`) — 运行时上下文对象
- **返回值**：`Promise<void>`
- **关闭流程**：
  1. 设置 `_destroying` 标志防止重入
  2. 通过结构化日志和事件总线记录关闭开始
  3. 优先关闭 `deepeningRegistry`
  4. 按预定义顺序对60+组件执行 `flush` → `shutdown` → `removeAllListeners`
  5. 每个组件异步shutdown最多等待 `GRACEFUL_RESULT_WAIT_MS`（2000ms）
  6. 整体关闭流程最多等待 `SHUTDOWN_TIMEOUT_MS`（15000ms）
  7. 清理 `concurrencyController` 和 `agentChannel`
  8. 移除全局异常处理器
  9. 通过事件总线和结构化日志记录关闭完成

### 配置常量

| 常量 | 值 | 说明 |
|------|-----|------|
| `SHUTDOWN_TIMEOUT_MS` | 15000 | 框架关闭超时时间（毫秒） |
| `GRACEFUL_RESULT_WAIT_MS` | 2000 | 单个组件异步关闭结果等待时间（毫秒） |

### 使用示例

```javascript
const { buildInstance } = require('./src/runtime/infrastructure/instance-builder');

const instance = buildInstance(ctx, executePipeline);

const result = await instance.executePipeline('用户消息', { sessionId: 's-001' });

console.log(instance.core.router);
console.log(instance.agents.runtime);
console.log(instance.gate.tddGate);
console.log(instance.collaboration.modeRouter);
console.log(instance.store.sqlite);

await instance.destroy();
```

| 模块 | 交互方式 |
|------|---------|
| 所有运行时组件 | InstanceBuilder将所有组件聚合为统一实例接口 |
| RetryEngine | InstanceBuilder在销毁流程中调用RetryEngine.shutdown() |
| ConcurrencyController | InstanceBuilder在销毁流程中调用ConcurrencyController.clear()和shutdown() |

## PluginManager详解

### 职责概述

插件管理器管理插件的生命周期（注册、初始化、销毁）和钩子（hook）执行。插件通过 `init` 函数接收上下文并注册钩子处理器，钩子按注册顺序链式执行。支持危险键过滤、初始化失败回滚和插件查询。

### 构造函数参数

```javascript
new PluginManager(eventBus)
```

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `eventBus` | EventBus | `null` | 事件总线实例，将传递给插件的初始化上下文 |

### 核心方法

#### `register(plugin)`

注册插件。插件通过 `init` 函数接收上下文并注册钩子处理器，初始化失败时自动回滚已注册的钩子。

- **参数**：`plugin` (`Object`)
  - `plugin.id` (`string`, 必需) — 插件唯一标识符
  - `plugin.init` (`Function`, 可选) — 初始化函数，签名为 `(ctx: Object) => void`
  - `plugin.destroy` (`Function`, 可选) — 销毁函数，签名为 `(ctx: Object) => void`
- **返回值**：`PluginManager` — this（链式调用）
- **异常**：插件缺少id、id重复或初始化失败时抛出 `HarnessError`
- **说明**：`init` 接收的上下文包含 `eventBus`、`hooks` 和 `registerHook(hookName, fn)` 方法

#### `unregister(pluginId)`

注销插件。调用插件的 `destroy` 方法并移除其注册的所有钩子处理器。

- **参数**：`pluginId` (`string`) — 要注销的插件标识符
- **返回值**：`boolean` — 注销成功返回 `true`，插件不存在时返回 `false`

#### `executeHook(hookName, data)`

执行指定钩子，按注册顺序链式调用所有处理器。处理器返回值不为 `undefined` 时覆盖传入数据。

- **参数**：
  - `hookName` (`string`) — 钩子名称
  - `data` (`*`) — 钩子数据，将依次传递给每个处理器
- **返回值**：`*` — 经过所有处理器处理后的最终数据

#### `getPlugin(pluginId)`

根据标识符获取插件对象。

- **参数**：`pluginId` (`string`) — 插件标识符
- **返回值**：`Object | null` — 插件对象，不存在时返回 `null`

#### `listPlugins()`

获取所有已注册插件的标识符列表。

- **返回值**：`string[]`

#### `getHooks(hookName)`

获取钩子注册信息。

- **参数**：`hookName` (`string`, 可选) — 钩子名称，省略时返回所有钩子信息
- **返回值**：不指定名称时返回 `Object<string, string[]>`（所有钩子的插件ID映射）；指定名称时返回 `string[]`（该钩子的插件ID数组）

#### `destroy()`

销毁所有已注册插件。依次调用每个插件的 `destroy` 方法并清空钩子注册表。

- **返回值**：`void`

#### `isHealthy()`

检查插件管理器是否健康。

- **返回值**：`boolean` — 有插件注册或有钩子处理器时返回 `true`

### 钩子注册上下文

插件 `init` 函数接收的上下文对象结构：

```javascript
{
  eventBus: EventBus,
  hooks: Object,
  registerHook: (hookName: string, fn: Function) => void
}
```

`registerHook` 的安全限制：
- 钩子名称必须为非空字符串
- 危险键（`DANGEROUS_KEYS`集合中的名称）被过滤
- 每个钩子名称最多注册50个处理器

### 配置常量

| 常量 | 值 | 说明 |
|------|-----|------|
| `MAX_PLUGINS` | 100 | 最大插件数量 |
| `MAX_HOOKS_PER_NAME` | 50 | 每个钩子名称的最大处理器数量 |

### 使用示例

```javascript
const PluginManager = require('./src/runtime/infrastructure/plugin-manager');

const pm = new PluginManager(eventBus);

pm.register({
  id: 'logger-plugin',
  init(ctx) {
    ctx.registerHook('before-execute', (data) => {
      console.log('执行前:', data.taskId);
      return data;
    });
    ctx.registerHook('after-execute', (data) => {
      console.log('执行后:', data.taskId);
      return data;
    });
  },
  destroy(ctx) {
    console.log('日志插件已销毁');
  },
});

const result = pm.executeHook('before-execute', { taskId: 't-001' });
console.log(pm.listPlugins());
console.log(pm.getHooks());

pm.unregister('logger-plugin');
```

### 与其他模块的交互关系

| 模块 | 交互方式 |
|------|---------|
| EventBus | PluginManager构造时接收EventBus实例，传递给插件初始化上下文 |
| InstanceBuilder | InstanceBuilder在销毁流程中调用PluginManager.shutdown() |
| ProgrammableHookExecutor | 两者互补：PluginManager管理插件级钩子，ProgrammableHookExecutor管理框架级钩子 |
| HealthChecker | PluginManager注册为HealthChecker的检查项 |

健康检查。判断数据库连接是否存活。

- **返回值**：`boolean`

## 模块间协作流程

### 任务执行与重试流程

```
任务提交
  │
  ├── 1. ConcurrencyController.acquire(taskId)
  │     获取并发槽位，队列满时等待
  │
  ├── 2. RetryEngine.execute(task)
  │     ├── 首次执行 task.execute(context)
  │     ├── 失败 → 指数退避休眠 → 重试
  │     ├── 重试耗尽 → 升级到 replan
  │     │     ├── task.replan(errors) → 重新执行
  │     │     └── replan耗尽 → 升级到 decompose
  │     │           ├── task.decompose(errors) → 子任务列表
  │     │           └── 递归执行子任务（深度+1）
  │     └── 全部耗尽 → 返回 { success: false }
  │
  ├── 3. ConcurrencyController.release(taskId)
  │     释放槽位，自动分配给等待队列中的下一个任务
  │
  └── 4. 返回结果
```

### 健康检查与就绪探针流程

```
定时/按需触发
  │
  ├── 1. HealthChecker.checkAll()
  │     按批次并发执行所有已注册检查项
  │     ├── SqliteStore.isHealthy() → 数据库连接状态
  │     ├── ConcurrencyController.isHealthy() → 并发负载状态
  │     ├── PluginManager.isHealthy() → 插件注册状态
  │     └── 其他自定义检查项
  │
  ├── 2. 状态变更检测
  │     对比前次检查结果，状态变更时通过CausalDataBus发布事件
  │
  ├── 3. HealthChecker.getAggregatedReport()
  │     按层级分组汇总，计算整体状态
  │     ├── critical层级有不健康项 → 'critical'
  │     ├── warning层级有不健康项 → 'degraded'
  │     └── 全部健康 → 'healthy'
  │
  └── 4. 探针响应
        ├── liveness() → 进程存活状态
        └── readiness() → critical检查全部通过则就绪
```

### 框架实例构建与销毁流程

```
框架启动
  │
  ├── 1. 初始化所有运行时组件
  │     ├── new SqliteStore(projectRoot).init()
  │     ├── new ConcurrencyController(max, queue)
  │     ├── new RetryEngine(options)
  │     ├── new HealthChecker()
  │     ├── new PluginManager(eventBus)
  │     └── ...其他60+组件
  │
  ├── 2. buildInstance(ctx, executePipeline)
  │     ├── _buildPropertyMap(ctx) → 140+扁平属性
  │     ├── _buildGroupedAPI(ctx) → 5个分组API
  │     └── 合并 executePipeline + destroy 方法
  │
  └── 3. 返回统一实例对象

框架关闭
  │
  ├── 1. instance.destroy()
  │     ├── 设置 _destroying 标志
  │     ├── 优先关闭 deepeningRegistry
  │     ├── 按顺序对60+组件执行 flush → shutdown → removeAllListeners
  │     ├── 每组件异步shutdown最多等待2秒
  │     ├── 整体关闭最多等待15秒
  │     ├── 清理 concurrencyController 和 agentChannel
  │     └── 移除全局异常处理器
  │
  └── 2. SqliteStore.shutdown()
        ├── WAL检查点（TRUNCATE）
        └── 关闭数据库连接
```

### 插件注册与钩子执行流程

```
插件注册
  │
  ├── 1. PluginManager.register(plugin)
  │     ├── 验证plugin.id（非空、不重复、未超限）
  │     ├── 构建初始化上下文 { eventBus, hooks, registerHook }
  │     ├── 调用 plugin.init(ctx)
  │     │     └── 插件通过 ctx.registerHook(name, fn) 注册钩子
  │     │           ├── 验证钩子名称（非空、非危险键、未超限）
  │     │           └── 追加到 _hooks[name] 数组
  │     └── 初始化失败 → 回滚已注册的钩子
  │
  └── 钩子执行
        │
        ├── 2. PluginManager.executeHook(hookName, data)
        │     ├── 获取钩子处理器列表
        │     ├── 按注册顺序链式调用
        │     ├── 处理器返回非undefined → 覆盖data
        │     └── 处理器异常 → 静默跳过，记录调试日志
        │
        └── 3. 返回最终处理结果
```
