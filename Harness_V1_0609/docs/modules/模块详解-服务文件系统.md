## 模块概述

ServiceFS模块实现了统一的服务文件系统抽象层，将多个异构服务适配为统一的文件系统接口。模块采用FUSE-like的挂载模型，每个服务通过实现标准适配器接口（list/read/write/remove/exists）挂载到统一路径空间（默认`/services/`），Agent可通过类Unix文件操作（ls/cat/write/rm/exists/tree）透明访问不同服务的资源。内置MemoryAdapter提供内存存储实现，支持路径遍历防护和挂载容量限制。

## 融合来源

融合自操作系统的虚拟文件系统（VFS）思想和Plan 9的"一切皆文件"（Everything is a File）哲学。模块将不同类型的服务（数据库、API、缓存等）统一抽象为文件系统语义，使Agent无需了解服务细节即可通过标准文件操作访问资源。挂载模型借鉴了Unix的mount机制，路径解析借鉴了VFS的路径查找算法。

## 使用示例

```javascript
const ServiceFS = require('./src/runtime/infrastructure/service-fs');

const sfs = new ServiceFS({ mountPrefix: '/services/', maxMounts: 10 });

const memoryAdapter = new ServiceFS.MemoryAdapter();
memoryAdapter.write('config.json', '{"theme": "dark"}');
memoryAdapter.write('cache/entry-1.json', '{"key": "value"}');

sfs.mount('memory', memoryAdapter);

const sqliteAdapter = {
  list: (path) => sqliteStore.query('list', { path }),
  read: (path) => sqliteStore.query('read', { path }),
  write: (path, content) => sqliteStore.upsert('data', path, content),
  remove: (path) => sqliteStore.delete('data', path),
  exists: (path) => sqliteStore.query('exists', { path }),
};
sfs.mount('db', sqliteAdapter);

const entries = sfs.ls('/services/memory/');
console.log('Entries:', entries);

const content = sfs.cat('/services/memory/config.json');
console.log('Content:', content);

const treeView = sfs.tree();
console.log(treeView);
```

## 核心算法详解

### `resolve()` 路径解析算法

`resolve()` 是整个ServiceFS的核心路由函数，负责将虚拟路径拆解为服务名和适配器内部路径，同时执行多层安全校验。算法流程如下：

```
输入: path (如 "/services/memory/cache/entry-1.json")
  │
  ├─ Step 1: 空值/类型校验
  │   └─ path 必须为非空字符串，否则抛出 INVALID_INPUT
  │
  ├─ Step 2: 路径长度校验
  │   └─ path.length > pathMaxLength(512) 时抛出 INVALID_INPUT
  │
  ├─ Step 3: mountPrefix 剥离
  │   └─ 检查 path 是否以 mountPrefix("/services/") 开头
  │   └─ 不匹配则抛出 INVALID_INPUT: "Path must start with /services/"
  │   └─ 截取前缀之后的部分 → withoutPrefix
  │
  ├─ Step 4: serviceName 提取
  │   └─ withoutPrefix 为空则抛出 INVALID_INPUT: "Path must include a service name"
  │   └─ 定位 withoutPrefix 中首个 '/' 的位置
  │   └─ 无 '/' → serviceName = withoutPrefix, adapterPath = ''
  │   └─ 有 '/' → serviceName = beforeSlash, adapterPath = afterSlash
  │
  ├─ Step 5: 路径遍历防护
  │   └─ adapterPath 包含 ".." → 抛出 INVALID_INPUT: "Path traversal detected"
  │
  └─ 输出: { serviceName, adapterPath }
```

**解析示例**：

| 输入路径 | serviceName | adapterPath |
|----------|-------------|-------------|
| `/services/memory/config.json` | `memory` | `config.json` |
| `/services/db/` | `db` | `` (空字符串) |
| `/services/cache` | `cache` | `` (空字符串) |
| `/services/store/a/b/c.json` | `store` | `a/b/c.json` |

**边界条件处理**：
- 路径仅到服务根目录（如 `/services/memory`）：adapterPath 为空字符串，操作时由各方法决定是否允许
- 路径尾部斜杠（如 `/services/db/`）：adapterPath 为空字符串（`slice(slashIdx + 1)` 在尾部斜杠后截取为空）
- 路径中包含 `..`：直接拒绝，不尝试规范化，采用零容忍策略

### `mount()/unmount()` 挂载管理

#### `mount()` 流程

```
输入: serviceName, adapter
  │
  ├─ Step 1: 关闭状态守卫
  │   └─ guardShutdown() — 系统正在关闭时拒绝操作
  │
  ├─ Step 2: serviceName 校验
  │   └─ 非空字符串检查 → INVALID_INPUT
  │
  ├─ Step 3: adapter 对象校验
  │   └─ 非空对象检查 → INVALID_INPUT
  │
  ├─ Step 4: 适配器接口校验（Duck Typing）
  │   └─ 遍历 VALID_ADAPTER_METHODS = ['list','read','write','remove','exists']
  │   └─ 逐一检查 adapter[method] 是否为 function
  │   └─ 缺少任何方法 → INVALID_INPUT: "adapter missing required method: xxx"
  │
  ├─ Step 5: 重复挂载检查
  │   └─ this._mounts.has(serviceName) → INVALID_STATE: "Service already mounted: xxx"
  │
  ├─ Step 6: 容量限制检查
  │   └─ this._mounts.size >= maxMounts → CAPACITY_EXCEEDED: "Max mounts reached (N)"
  │
  ├─ Step 7: 注册
  │   └─ this._mounts.set(serviceName, adapter)
  │   └─ this._tree[serviceName] = { type: 'dir', name: serviceName }
  │   └─ this._stats.mounts++
  │
  ├─ Step 8: 事件发射
  │   └─ this.emit('mounted', { serviceName })
  │
  └─ Step 9: 返回 this（支持链式调用）
```

**Duck Typing 校验设计**：不要求适配器继承特定基类，而是检查是否实现了 `VALID_ADAPTER_METHODS` 中定义的全部5个方法。这种设计允许任何对象（包括纯字面量对象）作为适配器，只要它提供了正确的接口，体现了"如果它走起来像鸭子，叫起来像鸭子，那它就是鸭子"的鸭子类型哲学。

#### `unmount()` 流程

```
输入: serviceName
  │
  ├─ Step 1: 关闭状态守卫
  │
  ├─ Step 2: 存在性检查
  │   └─ 不存在 → 返回 false（非异常，幂等设计）
  │
  ├─ Step 3: 清理
  │   └─ this._mounts.delete(serviceName)
  │   └─ delete this._tree[serviceName]
  │   └─ this._stats.unmounts++
  │
  ├─ Step 4: 事件发射
  │   └─ this.emit('unmounted', { serviceName })
  │
  └─ Step 5: 返回 true
```

**设计决策**：`unmount()` 对不存在的服务返回 `false` 而非抛出异常，这是幂等设计——多次卸载同一服务不会导致错误，便于清理代码编写。

### `ls/cat/write/rm/exists` 操作转发

五个文件操作方法遵循统一的转发模式，将虚拟路径操作委托给对应的服务适配器：

```
通用转发流程:
  │
  ├─ Step 1: guardShutdown() — 关闭状态守卫
  ├─ Step 2: resolve(path) — 路径解析 + 安全校验
  ├─ Step 3: this._mounts.get(serviceName) — 获取适配器
  ├─ Step 4: 适配器存在性检查（exists除外，返回false）
  ├─ Step 5: 方法特定校验（cat/write/rm要求adapterPath非空）
  ├─ Step 6: adapter.method(adapterPath, ...) — 委托适配器执行
  ├─ Step 7: this._stats.xxx++ — 更新操作统计
  └─ Step 8: this.emit(event, data) — 发射事件
```

**各方法差异点**：

| 方法 | 适配器不存在时 | adapterPath为空时 | 统计字段 | 事件名 |
|------|---------------|-------------------|---------|--------|
| `ls` | 抛出 RESOURCE_NOT_FOUND | 允许（列出根目录） | `lists` | `listed` |
| `cat` | 抛出 RESOURCE_NOT_FOUND | 抛出 INVALID_INPUT | `reads` | `read` |
| `write` | 抛出 RESOURCE_NOT_FOUND | 抛出 INVALID_INPUT | `writes` | `written` |
| `rm` | 抛出 RESOURCE_NOT_FOUND | 抛出 INVALID_INPUT | `deletes` | `removed` |
| `exists` | 返回 `false` | 返回 `true`（服务根存在） | 无 | 无 |

**`exists()` 的特殊设计**：
- 适配器不存在时返回 `false` 而非抛出异常——存在性检查不应因服务未挂载而中断
- adapterPath 为空时返回 `true`——路径仅指向服务根目录，而服务已挂载，故视为存在
- 不更新统计、不发射事件——存在性检查是轻量级操作，避免高频查询产生事件风暴

**错误包装策略**：所有方法通过 `resolve()` 统一校验路径合法性，适配器层抛出的错误（如 `RESOURCE_NOT_FOUND`）直接向上传播，ServiceFS 不做二次包装，保持错误栈的清晰性。

### `tree()` 树形视图生成

`tree()` 方法生成类Unix `tree` 命令的输出格式，支持全量视图和指定路径的子树视图：

```
tree(path?, depth?)
  │
  ├─ 计算最大深度: maxDepth = depth != null ? max(0, floor(depth)) : 10
  │
  ├─ 分支A: 指定路径
  │   └─ resolve(path) → 获取适配器 → _buildTree(adapter, adapterPath, serviceName, maxDepth, 0)
  │
  └─ 分支B: 全量视图
      └─ 输出 mountPrefix 行（如 "/services/"）
      └─ 按 serviceName 排序遍历所有挂载
      └─ 每个服务: ├──/└── + name + '/'
      └─ 递归展开子树，缩进使用 │   /    前缀
```

**`_buildTree()` 递归算法**：

```
_buildTree(adapter, adapterPath, serviceName, maxDepth, currentDepth)
  │
  ├─ 终止条件: currentDepth >= maxDepth → 返回 ''
  │
  ├─ 获取条目: adapter.list(adapterPath)
  │   └─ 空条目 → 返回 ''
  │
  ├─ 排序规则:
  │   └─ 目录优先（dir 排在 file 前面）
  │   └─ 同类型按名称 localeCompare 排序
  │
  └─ 遍历条目:
      ├─ 前缀: 最后一个条目用 └──，其余用 ├──
      ├─ 后缀: 目录类型加 '/'
      └─ 目录递归:
          ├─ 拼接子路径: adapterPath ? adapterPath + '/' + name : name
          ├─ 递归调用 _buildTree(..., currentDepth + 1)
          └─ 缩进前缀: 最后一个条目用 '    '，其余用 '│   '
```

**输出示例**：

```
/services/
├── db/
│   ├── config/
│   │   └── settings.json
│   └── users.json
└── memory/
    ├── cache/
    │   └── entry-1.json
    └── config.json
```

**depth 限制的作用**：防止适配器返回过深的目录结构导致递归栈溢出或输出过长。默认值10层足以覆盖绝大多数场景，同时可通过参数调整。`depth` 参数经过 `Math.max(0, Math.floor(depth))` 规范化，确保为非负整数。

## 安全防护机制

### 路径遍历攻击防护

ServiceFS 在 `resolve()` 方法中实现了严格的路径遍历防护：

- **`..` 检测**：adapterPath 中包含 `..` 时立即抛出 `INVALID_INPUT` 错误，采用零容忍策略，不尝试路径规范化或消除
- **设计理由**：路径规范化（如将 `/services/x/../../etc/passwd` 规范化为 `/etc/passwd`）虽然技术上可行，但增加了攻击面。零容忍策略更安全——任何包含 `..` 的路径一律拒绝
- **`~` 处理**：由于 mountPrefix 强制要求路径以 `/services/` 开头，`~` 开头的路径自然无法通过前缀校验，无需额外检测

**防护覆盖范围**：

| 攻击向量 | 防护层 | 效果 |
|----------|--------|------|
| `/services/x/../../etc/passwd` | `..` 检测 | 拒绝 |
| `/services/x/../y` | `..` 检测 | 拒绝 |
| `~/etc/passwd` | mountPrefix 前缀校验 | 拒绝 |
| `/etc/passwd` | mountPrefix 前缀校验 | 拒绝 |
| 超长路径（>512字符） | pathMaxLength 校验 | 拒绝 |

### 挂载容量限制

- **maxMounts 限制**：默认值20，通过 `this._mounts.size >= this._config.maxMounts` 检查
- **防护目的**：防止无限挂载导致内存泄漏或资源耗尽
- **配置方式**：构造时传入 `{ maxMounts: N }` 调整限制
- **超限行为**：抛出 `CAPACITY_EXCEEDED` 错误，携带当前限制值信息

### 路径长度限制

- **pathMaxLength 限制**：默认值512字符
- **防护目的**：防止超长路径导致的缓冲区问题或DoS攻击
- **检查时机**：在 `resolve()` 中最先执行（在所有解析逻辑之前），避免对超长路径进行无意义的字符串操作
- **超限行为**：抛出 `INVALID_INPUT` 错误，携带当前限制值信息

### 操作审计日志

ServiceFS 通过以下机制实现操作可审计性：

- **事件发射**：每次挂载、卸载、读写、删除、列表操作均触发对应事件，外部监听器可记录审计日志
- **debug 日志**：mount/unmount/write/rm 操作通过 `debug('ServiceFS', action, detail)` 记录调试日志
- **操作统计**：`getStats()` 返回完整的操作计数，包含 mounts/unmounts/reads/writes/deletes/lists 六项指标
- **关闭状态守卫**：所有操作入口调用 `guardShutdown()`，系统关闭期间拒绝一切操作，防止关闭过程中的未授权访问

## MemoryAdapter内存存储实现

### 内部Map结构

MemoryAdapter 使用单一 `Map<string, string>` 作为存储结构，键为文件路径，值为字符串内容：

```
_store: Map {
  "config.json"          → '{"theme": "dark"}'
  "cache/entry-1.json"   → '{"key": "value"}'
  "cache/entry-2.json"   → '{"key": "value2"}'
  "data/users.json"      → '[]'
}
```

**目录的虚拟化**：Map 中不存储目录条目，目录由文件路径中的 `/` 分隔符隐式推导。例如 `cache/entry-1.json` 的存在意味着 `cache/` 目录存在。这种设计避免了目录和文件之间的同步问题。

### `list()` 目录推导算法

```
输入: path = "cache"
  │
  ├─ 构建 prefix: "cache/"
  │
  ├─ 遍历 _store.keys():
  │   ├─ 跳过不以 prefix 开头的键
  │   ├─ 截取 remaining = key.slice(prefix.length)
  │   │   例: "cache/entry-1.json" → remaining = "entry-1.json"
  │   │
  │   ├─ remaining 中无 '/' → 文件条目
  │   │   └─ entries.set(name, { name, type: 'file', size, modified })
  │   │
  │   └─ remaining 中有 '/' → 目录条目
  │       └─ dirName = remaining.slice(0, slashIdx)
  │       └─ entries.set(dirName, { name: dirName, type: 'dir' })
  │       └─ 同一目录名仅记录一次（Map去重）
  │
  └─ 返回 Array.from(entries.values())
```

**根目录列出**（path 为空时）：
- prefix 为空字符串，所有键参与匹配
- 仅包含 `/` 的键被识别为子目录的直接子条目
- 不包含 `/` 的键被识别为根级文件

### `remove()` 递归删除

```
输入: path = "cache"
  │
  ├─ 精确匹配删除: _store.has("cache") → _store.delete("cache")
  │
  ├─ 前缀匹配收集: prefix = "cache/"
  │   └─ 遍历所有键，收集以 prefix 开头的键到 keysToDelete 数组
  │   └─ 注意: 先收集再删除，避免遍历中修改Map导致未定义行为
  │
  ├─ 批量删除: 遍历 keysToDelete，逐一 _store.delete(key)
  │
  └─ 返回: 有任何条目被删除则 true，否则 false
```

**两阶段删除设计**：先收集待删除键到临时数组，再批量删除。这是Map遍历安全的标准模式——在遍历Map.keys()时直接调用delete会导致未定义行为（ECMAScript规范中，在迭代过程中修改Map的键集合是不安全的）。

### 原子操作保证

MemoryAdapter 的操作在单线程Node.js环境中具有天然的原子性：

- **`write()`**：单次 `Map.set()` 操作，不可中断
- **`read()`**：单次 `Map.get()` 操作，不可中断
- **`remove()`**：虽然涉及多次 `Map.delete()`，但在单线程环境中不会被其他操作穿插。不过需注意：在删除过程中如果同一适配器的其他操作被同步调用（理论上不会在单线程中发生），可能看到部分删除的中间状态
- **`list()`**：基于快照的遍历（`Map.keys()` 返回迭代器），在遍历期间Map的修改可能导致条目遗漏，但不会导致崩溃

**局限性**：MemoryAdapter 不提供跨操作的事务保证。例如"先exists再read"的组合不是原子的，中间可能被其他操作修改。需要事务保证的场景应使用SqliteStore适配器。
