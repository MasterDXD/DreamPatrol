# 模块详解-会话与上下文子系统

> 版本：2.73.4 | 文件：src/runtime/session/ + src/runtime/context/

---

## 1. 概述

会话与上下文子系统是Harness多Agent框架的基础运行时组件，由两个紧密协作的子模块群构成——**会话子系统**（`src/runtime/session/`，2个模块）和**上下文子系统**（`src/runtime/context/`，5个模块），共计7个核心组件。

### 1.1 子系统定位

会话与上下文子系统解决的核心问题是：**在Token预算有限的前提下，如何确保每个Agent在正确的时机获得正确的上下文信息，同时保证会话状态的持久化与可恢复性**。

它通过五层机制实现这一目标：

| 层次 | 核心组件 | 功能 |
|------|---------|------|
| **会话管理层** | SessionManager | 会话全生命周期管理：创建、阶段转换、Token预算管控、防抖持久化、TTL过期清理 |
| **检查点层** | CheckpointManager | 状态快照创建与恢复，因果WAL回滚协调，进程崩溃后恢复 |
| **压缩层** | ContextCompressionEngine | Token预算达到阈值时，根据技能类别和因果关联智能压缩上下文 |
| **隔离层** | IsolatedContextManager | 为每个Agent任务创建独立执行上下文，控制Agent间上下文共享边界 |
| **注入层** | PhaseContextInjector + LTIContextInjector + AutoregressiveContextSchema | 按阶段注入规则/Agent定义、按迭代深度注入原始目标、自回归上下文传递 |

### 1.2 设计原则

- **防抖持久化**：内存即时更新、磁盘延迟写入，合并高频操作为单次IO
- **阶段感知**：上下文注入和压缩策略均与六阶段执行流程深度绑定
- **因果一致性**：检查点恢复时协调因果WAL回滚，保证因果链完整性
- **隔离安全**：Agent间上下文隔离，访问控制列表防止跨任务泄漏
- **增量优化**：状态哈希去重、计划缓存、增量跳过避免重复计算

### 3.1 SessionManager — 会话状态管理器

#### 职责与定位

SessionManager是会话子系统的核心组件，负责管理会话的全生命周期。它跟踪当前执行阶段、已完成Skill列表、Token使用量、深化推理状态和熵状态，通过防抖持久化机制将会话状态写入`.harness/sessions/`目录，支持进程重启后从磁盘恢复会话。

核心能力：
- 会话创建与ID验证（正则校验 + 最大长度限制）
- 六阶段合法转换验证（`PHASE_TRANSITIONS_SET`白名单）
- Token预算管控（80%预警 / 95%危险 / 100%耗尽三级告警）
- 防抖持久化（`KeyedDebouncer`，默认300ms合并写入）
- TTL过期清理（默认24小时，5分钟扫描间隔）
- 配置热重载（`fs.watch` + 指数退避重试，最多10次）
- 深化推理状态追踪（迭代计数、质量分数、收敛历史）
- 熵状态追踪（先验丰富度、收敛轮次）
- 会话恢复（进程重启后从磁盘加载未过期会话）

#### 构造函数

```javascript
new SessionManager(projectRoot)
```

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `projectRoot` | string | 是 | 项目根目录的绝对路径，必须通过`validateProjectRoot`校验 |

#### 公共方法

| 方法 | 参数 | 返回值 | 说明 |
|------|------|--------|------|
| `create(sessionId, options?)` | `sessionId: string`（匹配`[a-zA-Z0-9_-]`，最长64字符），`options?: { agent?: string }` | `Session` | 创建新会话，ID格式校验+容量检查+驱逐最旧 |
| `get(sessionId)` | `sessionId: string` | `Session \| null` | 获取会话快照（深拷贝，不含`_arContext`） |
| `advancePhase(sessionId, newPhase)` | `sessionId: string`, `newPhase: string` | `Session` | 推进到新阶段，校验转换合法性，触发`phase-change`事件和AR注入 |
| `completeSkill(sessionId, skillId)` | `sessionId: string`, `skillId: string` | `Session` | 记录已完成Skill，触发`skill-complete`事件和因果输出发布 |

| `recordDeepeningConvergence(sessionId, data?)` | `sessionId: string`, `data?: { converged?, reason?, qualityScore?, iterations? }` | `void` | 记录深化推理收敛事件 |
| `getStats()` | — | `{ activeSessions, totalTokensUsed, phases }` | 获取统计信息（1秒缓存） |
| `getPreviousSessionContext()` | — | `Promise<Object \| null>` | 获取最近会话上下文摘要，用于会话恢复 |

| `registerShutdownHooks()` | — | `this` | 注册SIGINT/SIGTERM信号处理器 |

| 字段 | 类型 | 说明 |

#### 配置项

配置文件路径：`.harness/config.json`

| 配置项 | 类型 | 默认值 | 说明 |
|--------|------|--------|------|

#### 使用示例

```javascript
const SessionManager = require('./src/runtime/session/session-manager');

// 创建会话管理器
const mgr = new SessionManager('/path/to/project');

// 监听事件
mgr.on('phase-change', (evt) => {
  console.log(`阶段转换: ${evt.from} → ${evt.to}`);
});
mgr.on('budget-warning', (evt) => {
  console.log(`预算警告: 已用${evt.tokensUsed} tokens, 比例${evt.budget.ratio}`);
});

// 创建会话
const session = mgr.create('my-session', { agent: 'domain-analyst' });

// 推进阶段
mgr.advancePhase('my-session', 'requirement-analysis');

// 完成技能
mgr.completeSkill('my-session', 'brainstorming');

// 记录Token使用
mgr.addTokenUsage('my-session', 1500);

// 检查预算
const budget = mgr.checkBudget('my-session');
console.log(`预算使用: ${budget.ratio * 100}%`);

// 记录深化迭代
mgr.recordDeepeningIteration('my-session', { qualityScore: 0.85 });

// 更新熵状态
mgr.updateEntropyState('my-session', {
  score: 0.7,
  level: 'high-entropy',
  signals: ['rich-vocabulary', 'multiple-intents'],
});

// 获取统计信息
console.log(mgr.getStats());

// 优雅关机
mgr.registerShutdownHooks();
```

### 3.2 CheckpointManager — 检查点管理器

#### 职责与定位

CheckpointManager负责会话检查点的创建、恢复和删除，支持因果WAL回滚协调。它通过单调时间戳强制（防止时钟回拨导致检查点乱序）和因果WAL序列号追踪，确保检查点恢复时的因果一致性。

核心能力：
- 同步/异步双模式检查点创建
- 单调时间戳强制（`_lastTimestamp`单调递增）
- 因果WAL序列号追踪与回滚协调
- 最大检查点数限制（50个，超限驱逐最旧）
- 持久化到`.harness/checkpoints/`目录
- 进程重启后自动恢复检查点

#### 构造函数

```javascript
new CheckpointManager(projectRoot)
```

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `projectRoot` | string | 是 | 项目根目录的绝对路径 |

#### 公共方法

| 方法 | 参数 | 返回值 | 说明 |
|------|------|--------|------|
| `create(sessionId, data)` | `sessionId: string`（匹配`[a-zA-Z0-9_-]`，最长128字符），`data: CheckpointData` | `Object \| null` | 同步创建检查点 |
| `createAsync(sessionId, data)` | 同上 | `Promise<Object \| null>` | 异步创建检查点 |
| `get(checkpointId)` | `checkpointId: string` | `Object \| null` | 获取检查点快照 |

### 3.3 ContextCompressionEngine — 上下文压缩引擎

#### 职责与定位

ContextCompressionEngine负责在Token预算达到阈值时，根据技能类别和因果关联智能压缩上下文。它将技能分为`current_phase`、`completed_phase`、`future_phase`、`specification_asset`和因果关联类别，对每类技能应用不同的压缩策略（`full`/`summary`/`discard`）。

核心能力：
- 智能技能分类（阶段感知 + 因果覆盖 + 规格资产保留）
- 三级压缩策略（full保留 / summary摘要 / discard丢弃）
- Token估算（ASCII字符÷4，非ASCII字符÷2）
- 增量跳过（状态哈希未变时复用上次结果）
- 压缩计划缓存（最大50条）
- 因果上游检测（CausalValidator集成）
- 因果压缩策略（CausalBufferManager集成）
- 文本输出压缩（填充词去除、冗余注释过滤、智能截断）
- 工具调用输出压缩（行去重、正则过滤、对象截断）

#### 构造函数

```javascript
new ContextCompressionEngine(options?)
```

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `options.threshold` | number | 否 | 压缩触发阈值（默认0.8，即80%预算时触发） |
| `options.retainCurrentPhase` | boolean | 否 | 是否保留当前阶段上下文（默认true） |
| `options.retainKeyDecisions` | boolean | 否 | 是否保留关键决策（默认true） |
| `options.retainSessionState` | boolean | 否 | 是否保留会话状态（默认true） |
| `options.tokenCharsRatio` | number | 否 | Token字符比（默认4，即4字符≈1 token） |
| `options.maxSummaryLength` | number | 否 | 摘要最大长度（默认200） |
| `options.strategies` | Object | 否 | 各类别压缩策略映射 |
| `options.strategies.completed_phase` | string | 否 | 已完成阶段策略（默认'summary'） |
| `options.strategies.future_phase` | string | 否 | 未来阶段策略（默认'summary'） |

| 分类 | 条件 | 默认策略 | 说明 |
|------|------|----------|------|
| `current_phase` | 技能阶段 === 当前阶段 | `full` | 当前阶段技能完整保留 |
| `completed_phase` | 技能已完成 | `summary` | 已完成技能压缩为摘要 |
| `future_phase` | 技能阶段 > 当前阶段索引 | `summary` | 未来阶段技能压缩为摘要 |
| `specification_asset` | 技能输出含'specification' | `full`（不可更改） | 规格产出技能始终完整保留 |
| `causal_relevance_high` | 因果缓冲管理器判定高关联 | `full` | 因果高关联技能完整保留 |
| `causal_relevance_medium` | 因果缓冲管理器判定中关联 | `summary` | 因果中关联技能压缩为摘要 |
| `causal_relevance_low` | 因果缓冲管理器判定低关联 | `discard` | 因果低关联技能直接丢弃 |
| `causal_upstream` | 因果验证器判定为上游 | `full` | 因果上游技能完整保留 |
| `unclassified` | 不属于以上任何类别 | `full` | 未分类技能完整保留 |

#### 使用示例

```javascript

const engine = new ContextCompressionEngine({
  threshold: 0.7,

    future_phase: 'discard',
    current_phase: 'full',
    unclassified: 'full',
    specification_asset: 'full',
  },
});

// 判断是否需要压缩
const shouldCompress = engine.shouldCompress({
  tokensUsed: 75000,
  tokenBudget: 100000,
});
// true (75% > 70%)

// 压缩上下文
const result = engine.compress({
  currentPhase: 'module-development',
  skills: [
    { skill_id: 'brainstorming', phase: 'brainstorming', instruction: '...', summary: '...' },
    { skill_id: 'tdd-implement', phase: 'module-development', instruction: '...', summary: '...' },
  ],
  completedSkills: ['brainstorming'],
  keyDecisions: [{ id: 'd1', decision: 'Use SQLite for persistence' }],
  specificationAssets: [{ assetId: 'spec-1', assetType: 'requirement' }],
});

console.log(result.compressionRatio);  // 压缩比
console.log(result.tokenSavings);       // 节省Token数

// 获取压缩计划
const plan = engine.getCompressionPlan({ currentPhase: 'module-development', skills: [...] });
console.log(plan.retain);    // 保留的技能
console.log(plan.compress);  // 压缩的技能

// 压缩文本输出
const compressed = engine.compressOutput(longText, {
  maxLength: 1000,
  preserveCodeBlocks: true,
  stripFiller: true,
  stripRedundant: true,
});

// 动态修改策略
engine.setStrategy('completed_phase', 'discard');

// 附加因果验证器
engine.attachConfigCausalValidator(causalValidator);
engine.attachCausalBufferManager(causalBufferManager);
```

### 3.4 IsolatedContextManager — 隔离上下文管理器

#### 职责与定位

IsolatedContextManager为每个Agent任务创建隔离的执行上下文，控制Agent间的上下文共享边界。它按Agent角色分配工具集，管理上下文大小限制、访问控制策略和上下文生命周期，防止跨任务上下文泄漏。

核心能力：
- Agent角色工具集分配（5种预定义角色 + 自定义扩展）
- 访问控制列表（ACL）：每个上下文有owner和allowedAgents集合
- 上下文容量管理（最大20个，超限LRU驱逐）
- 注入上下文大小限制（最大50000字符）
- 结果提交与置信度追踪
- 操作历史记录（RingBuffer，最大200条）

#### 构造函数

```javascript
new IsolatedContextManager(options?)
```

#### 驱逐策略

当上下文数量达到上限时，按以下优先级驱逐：

1. **已完成上下文**：优先驱逐`lastAccessedAt`最早的已完成上下文
2. **过期上下文**：驱逐状态为`released`或`failed`的上下文
3. **LRU驱逐**：驱逐`lastAccessedAt`最早的活跃上下文（触发`active-context-evicted`事件）

#### 使用示例

```javascript
  agentId: 'task-worker',
  parentSessionId: 'session-42',
  constraints: ['Must follow TDD', 'No external dependencies'],
  successCriteria: ['All tests pass', 'No security vulnerabilities'],
});

console.log(ctx.contextId);    // 'ictx-xxxxx'
console.log(ctx.toolSet);      // ['read', 'write', 'search', 'run']
console.log(ctx.systemPrompt); // 自动生成的系统提示

// 授予其他Agent访问权限
icm.grantContextAccess(ctx.contextId, 'domain-analyst');

// 获取上下文（需通过ACL检查）
const ctxCopy = icm.getContext(ctx.contextId, 'domain-analyst');

// 提交执行结果
icm.submitResult(ctx.contextId, {
  output: { files: ['auth.js', 'auth.test.js'] },
  summary: 'Authentication module implemented with TDD',
  confidence: 0.92,
  evidence: [{ type: 'test-result', passed: true }],
});

// 释放上下文
icm.releaseContext(ctx.contextId);

// 获取统计信息
console.log(icm.getStats());
```

### 3.6 LTIContextInjector — LTI上下文注入器

#### 职责与定位

LTIContextInjector实现学习工具互操作（LTI）上下文注入，将原始任务上下文与当前任务状态融合，支持按迭代深度渐进式注入。它维护原始上下文注册表和注入历史，用于跨迭代的上下文一致性保持。

核心能力：
- 原始上下文注册表（最大200个任务）
- 注入历史追踪（RingBuffer，每任务最大10条，总最大500条）
- 目标信号计算（Jaccard相似度 / 字符bigram重叠度）
- 渐进式注入（按迭代深度注入原始目标和约束）
- LTI模式：当原始目标与当前目标重叠度低于50%时注入原始目标

#### 构造函数

```javascript
new LTIContextInjector(options?)
```

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `options.mode` | string | 否 | 注入模式（默认'lti'） |
| `options.maxHistory` | number | 否 | 每任务注入历史最大条数（默认10） |

#### 公共方法

| 方法 | 参数 | 返回值 | 说明 |
|------|------|--------|------|
| `registerOriginalContext(taskId, context)` | `taskId: string`, `context: Object` | `void` | 注册原始任务上下文 |
| `inject(taskId, currentTask, iteration?)` | `taskId: string`, `currentTask: Object`, `iteration?: number` | `Object` | 注入原始上下文到当前任务 |
| `getOriginalContext(taskId)` | `taskId: string` | `Object \| null` | 获取原始注册上下文 |
| `getInjectionHistory(taskId)` | `taskId: string` | `InjectionHistoryEntry[]` | 获取注入历史 |
| `unregisterContext(taskId)` | `taskId: string` | `boolean` | 取消注册上下文 |
| `getStats()` | — | `LTIStats` | 获取统计信息 |

#### 注入结果结构

注入后的任务对象会新增`_ltiContext`字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `_ltiContext.originalGoal` | string | 原始目标 |

| `_ltiContext.iteration` | number | 当前迭代深度 |
| `_ltiContext.mode` | string | 注入模式 |
| `_ltiContext.injectedAt` | string | 注入时间（ISO格式） |
| `_ltiContext.goalSignal` | string \| null | 目标信号（仅LTI模式，重叠度<0.5时为原始目标） |
| `_ltiContext.originalRequirements` | Array | 原始需求列表 |

#### InjectionHistoryEntry结构

| 字段 | 类型 | 说明 |
|------|------|------|
| `iteration` | number | 迭代序号 |
| `timestamp` | string | 时间戳（ISO格式） |
| `hasGoalSignal` | boolean | 是否包含目标信号 |

#### LTIStats结构

| 字段 | 类型 | 说明 |
|------|------|------|

| `totalInjections` | number | 总注入次数 |

#### 事件

| 事件名 | 载荷 | 触发时机 |

### 3.7 AutoregressiveContextSchema — 自回归上下文模式

#### 职责与定位

AutoregressiveContextSchema是上下文子系统的底层基础设施模块，提供自回归上下文字段的注入、提取、合并、验证和兼容性检查功能。它在迭代深化推理中，将前驱结果、质量分数和反馈注入上下文，实现自回归式上下文传递。

该模块以纯函数集合形式导出（非类），所有函数均为无副作用的工具函数。

核心能力：
- 字段注入（过滤危险键、截断超长字符串和大数组、限制最大字段数）
- 字段提取（排除版本号和更新时间戳等元数据）
- 字段合并（提取现有上下文 + 覆盖字段 + 重新注入）
- 字段验证（数值范围、数组类型、字符串类型）
- 版本兼容性检查（字段缺失检测、新版本不兼容警告）

#### 导出常量

| 常量 | 值 | 说明 |
|------|-----|------|
| `AR_CONTEXT_KEY` | `'_ar'` | 上下文存储键名 |
| `VERSION` | `1` | 当前版本号 |
| `FIELDS` | Object | 字段名常量映射 |
| `VERSION_FIELD_MAP` | `{ 0: [], 1: [所有字段] }` | 版本→字段映射 |
| `SOURCE_IDS` | Object | 来源标识常量 |

#### FIELDS字段常量

| 字段名 | 常量 | 说明 |
|--------|------|------|
| `previousResult` | `FIELDS.PREVIOUS_RESULT` | 前驱结果 |
| `previousScore` | `FIELDS.PREVIOUS_SCORE` | 前驱质量分数（0-1） |
| `qualityHistory` | `FIELDS.QUALITY_HISTORY` | 质量历史（数组） |
| `feedback` | `FIELDS.FEEDBACK` | 反馈信息 |
| `previousOutput` | `FIELDS.PREVIOUS_OUTPUT` | 前驱输出 |
| `focusAreas` | `FIELDS.FOCUS_AREAS` | 聚焦区域（数组） |
| `originalGoal` | `FIELDS.ORIGINAL_GOAL` | 原始目标 |
| `iteration` | `FIELDS.ITERATION` | 当前迭代序号（≥0） |
| `maxIterations` | `FIELDS.MAX_ITERATIONS` | 最大迭代次数（1-100） |
| `iterationSummary` | `FIELDS.ITERATION_SUMMARY` | 迭代摘要 |
| `source` | `FIELDS.SOURCE` | 来源标识 |

#### SOURCE_IDS来源标识

| 常量 | 值 | 说明 |
|------|-----|------|
| `SOURCE_IDS.ORCHESTRATOR` | `'deepening-orchestrator'` | 深化编排器 |
| `SOURCE_IDS.REFINEMENT` | `'iterative-refinement'` | 迭代精化器 |
| `SOURCE_IDS.RECURRENT` | `'recurrent-deepening-scheduler'` | 循环深化调度器 |
| `SOURCE_IDS.SKILL_COMPLETE` | `'skill-complete'` | 技能完成 |
| `SOURCE_IDS.PHASE_ADVANCE` | `'phase-advance'` | 阶段推进 |

#### 导出函数

| 函数 | 参数 | 返回值 | 说明 |
|------|------|--------|------|
| `inject(target, fields)` | `target: Object`, `fields: Object` | `Object` | 向目标对象注入自回归上下文字段 |
| `extract(target)` | `target: Object` | `Object \| null` | 从目标对象提取上下文数据 |
| `merge(target, overrides)` | `target: Object`, `overrides: Object` | `Object` | 合并上下文（提取+覆盖+注入） |
| `validate(target)` | `target: Object` | `{ valid, warnings }` | 验证上下文数据 |
| `compatibilityCheck(target, requiredVersion?)` | `target: Object`, `requiredVersion?: number` | `CompatibilityResult` | 版本兼容性检查 |
| `strip(target)` | `target: Object` | `Object` | 移除`_ar`属性 |

#### 注入规则

1. **危险键过滤**：`DANGEROUS_KEYS`中的键名被拒绝注入
2. **已知字段检查**：非`FIELDS`中定义的字段被拒绝注入
3. **最大字段数**：最多20个字段（不含`_version`和`updatedAt`）
4. **字符串截断**：超过2000字符的字符串被截断
5. **数组截断**：超过100元素的数组被截断
6. **版本标记**：自动添加`_version`和`updatedAt`

#### 验证规则

| 字段 | 类型约束 | 范围约束 |
|------|---------|---------|
| `previousScore` | number | 0 ≤ value ≤ 1.0 |
| `iteration` | number | value ≥ 0 |
| `maxIterations` | number | 1 ≤ value ≤ 100 |
| `qualityHistory` | Array | — |
| `focusAreas` | Array | — |
| `previousResult` | string | — |
| `previousOutput` | string | — |
| `originalGoal` | string | — |
| `feedback` | string | — |
| `iterationSummary` | string | — |
| `source` | string | — |

#### CompatibilityResult结构

| 字段 | 类型 | 说明 |
|------|------|------|
| `compatible` | boolean | 是否兼容 |
| `reason` | string | 原因描述 |
| `contextVersion` | number | 上下文版本号 |
| `requiredVersion` | number | 所需版本号 |
| `missingFields` | string[] | 缺失字段列表 |
| `warning` | string | 警告信息 |

#### 使用示例

```javascript
const AR = require('./src/runtime/context/autoregressive-context-schema');

// 注入自回归上下文
const session = { id: 'session-1', currentPhase: 'module-development' };
AR.inject(session, {
  [AR.FIELDS.PREVIOUS_RESULT]: 'brainstorming',
  [AR.FIELDS.PREVIOUS_SCORE]: 0.85,
  [AR.FIELDS.ITERATION]: 3,
  [AR.FIELDS.MAX_ITERATIONS]: 10,
  [AR.FIELDS.SOURCE]: AR.SOURCE_IDS.SKILL_COMPLETE,
});
// session._ar = { previousResult: 'brainstorming', previousScore: 0.85, ... }

// 提取上下文
const ctx = AR.extract(session);
console.log(ctx.previousResult);  // 'brainstorming'

// 合并上下文
AR.merge(session, {
  [AR.FIELDS.QUALITY_HISTORY]: [0.7, 0.8, 0.85],
  [AR.FIELDS.FEEDBACK]: 'Improve test coverage',
});

// 验证上下文
const validation = AR.validate(session);
console.log(validation.valid);      // true
console.log(validation.warnings);   // []

// 兼容性检查
const compat = AR.compatibilityCheck(session, 1);
console.log(compat.compatible);  // true
console.log(compat.reason);      // 'version_match'

// 移除上下文
AR.strip(session);
// session._ar === undefined
```

## 4. 端到端示例

以下展示一个完整的会话生命周期，演示所有7个组件如何协同工作：

```javascript
const SessionManager = require('./src/runtime/session/session-manager');
const CheckpointManager = require('./src/runtime/session/checkpoint-manager');
const ContextCompressionEngine = require('./src/runtime/context/context-compression-engine');
const IsolatedContextManager = require('./src/runtime/context/isolated-context-manager');
const PhaseContextInjector = require('./src/runtime/context/phase-context-injector');
const LTIContextInjector = require('./src/runtime/context/lti-context-injector');
const AR = require('./src/runtime/context/autoregressive-context-schema');

const projectRoot = '/path/to/project';

// ===== 1. 初始化所有组件 =====
const sessionManager = new SessionManager(projectRoot);
const checkpointManager = new CheckpointManager(projectRoot);
const compressionEngine = new ContextCompressionEngine({ threshold: 0.75 });
const isolatedCtx = new IsolatedContextManager({ maxContexts: 20 });
const phaseInjector = new PhaseContextInjector(projectRoot);
const ltiInjector = new LTIContextInjector({ mode: 'lti' });

// 组件挂载
sessionManager.attachPhaseContextInjector(phaseInjector);
sessionManager.attachCausalDataBus(causalDataBus); // 假设已初始化
compressionEngine.attachConfigCausalValidator(causalValidator);
compressionEngine.attachCausalBufferManager(causalBufferManager);

// ===== 2. 创建会话 =====
const session = sessionManager.create('project-alpha', { agent: 'team-lead' });
// 事件: session-created

// ===== 3. 注册原始任务上下文（LTI） =====
ltiInjector.registerOriginalContext('project-alpha', {
  goal: 'Build a secure REST API with user authentication',
  constraints: ['No plaintext passwords', 'Rate limiting required'],
  requirements: ['JWT tokens', 'OAuth2 support'],
});
// 事件: context-registered

// ===== 4. 阶段推进：brainstorming → requirement-analysis =====
sessionManager.advancePhase('project-alpha', 'requirement-analysis');
// 内部流程:
//   1. 验证阶段转换合法性 (PHASE_TRANSITIONS_SET)
//   2. 更新 session.currentPhase
//   3. 触发 phase-change 事件
//   4. AR.inject() 注入自回归上下文
//   5. phaseInjector.injectForPhase('requirement-analysis') 注入阶段上下文

// ===== 5. 创建隔离上下文执行任务 =====
const taskCtx = isolatedCtx.createIsolatedContext({
  taskDescription: 'Analyze authentication requirements',
  agentId: 'domain-analyst',
  parentSessionId: 'project-alpha',
  constraints: ['Follow OWASP guidelines'],
});
// 事件: context-created

// ===== 6. LTI上下文注入（迭代深化推理中） =====
const currentTask = {
  goal: 'Design auth token flow',
  description: 'Working on JWT refresh mechanism',
};
const injectedTask = ltiInjector.inject('project-alpha', currentTask, 2);
// injectedTask._ltiContext 包含原始目标、约束和目标信号
// 事件: context-injected

// ===== 7. 完成技能 =====
sessionManager.completeSkill('project-alpha', 'brainstorming');
sessionManager.completeSkill('project-alpha', 'requirement-analysis');
// 内部流程:
//   1. 更新 completedSkills 列表
//   2. 触发 skill-complete 事件
//   3. AR.inject() 注入技能完成上下文
//   4. causalDataBus.publishOutput() 发布因果输出

// ===== 8. 记录Token使用并检查预算 =====
sessionManager.addTokenUsage('project-alpha', 50000);
const budget = sessionManager.checkBudget('project-alpha');
// 如果 ratio >= 0.8, 触发 budget-warning 事件

// ===== 9. 上下文压缩 =====
if (compressionEngine.shouldCompress({
  tokensUsed: session.tokensUsed,
  tokenBudget: 100000,
})) {

    currentPhase: session.currentPhase,
    skills: allSkills,
    completedSkills: session.completedSkills,
    keyDecisions: [{ id: 'd1', decision: 'Use JWT' }],
    specificationAssets: [{ assetId: 'req-spec', assetType: 'requirement' }],

}

// ===== 10. 创建检查点 =====

  phase: session.currentPhase,
  completedSkills: session.completedSkills,
  tokensUsed: session.tokensUsed,
  causalWalSequence: 42,

```

## 5. 最佳实践与注意事项

### 5.1 会话管理

| 实践 | 说明 |
|------|------|
| **始终调用`registerShutdownHooks()`** | 确保进程退出前会话状态刷盘到磁盘，避免数据丢失 |
| **使用`flush()`在关键操作后强制刷盘** | 在创建重要检查点或完成关键技能后，调用`flush()`确保数据持久化 |
| **监听`budget-warning`事件** | 在Token使用达到80%时主动触发上下文压缩，而非等到100%耗尽 |
| **避免频繁`addTokenUsage`调用** | 批量累积Token使用量后一次性调用，减少防抖持久化压力 |
| **会话ID使用`generateSessionId()`** | 自动生成的ID保证格式合规，避免手动构造ID导致校验失败 |

### 5.2 检查点管理

| 实践 | 说明 |
|------|------|
| **在关键决策前创建检查点** | 如架构变更、大规模重构前创建检查点，便于回滚 |
| **使用`createAsync`而非`create`** | 在生产环境中优先使用异步版本，避免阻塞事件循环 |
| **检查点包含`causalWalSequence`** | 与CausalDataBus协调时，确保检查点记录WAL序列号，恢复时才能正确回滚 |
| **定期清理旧检查点** | 检查点最大50个，超限自动驱逐最旧；重要检查点应导出备份 |

### 5.3 上下文压缩

| 实践 | 说明 |
|------|------|
| **`specification_asset`策略不可更改** | 规格产出技能始终完整保留，这是设计约束而非bug |
| **附加因果组件后缓存自动清除** | `attachConfigCausalValidator`和`attachCausalBufferManager`会清除缓存和增量状态，附加后需重新压缩 |
| **`shouldCompress`先于`compress`调用** | 避免不必要的压缩计算，先检查阈值再执行压缩 |
| **`compressOutput`用于AI输出压缩** | 去除填充词（"Sure, let me explain..."）和冗余注释，显著减少Token消耗 |
| **`compressToolOutput`用于工具输出压缩** | 对长命令输出（如日志、文件列表）进行行去重和截断 |
| **正则过滤模式有安全限制** | `filterPatterns`中正则长度不超过200字符，量词密度不超过8，防止ReDoS攻击 |

### 5.4 隔离上下文

| 实践 | 说明 |
|------|------|
| **按角色分配工具集** | 使用默认工具集映射，避免给Agent分配不必要的工具 |
| **及时释放已完成上下文** | 调用`releaseContext`释放不再使用的上下文，避免容量耗尽 |
| **ACL最大20个Agent** | 单个上下文的`allowedAgents`集合不超过20个，避免权限膨胀 |
| **`getContext`返回深拷贝** | 修改返回值不影响内部状态，如需更新应使用`submitResult` |

### 5.5 阶段上下文注入

| 实践 | 说明 |
|------|------|
| **生产环境使用`injectForPhaseAsync`** | 同步版本在开发环境可用，生产环境应使用异步版本避免阻塞 |
| **缓存TTL为60秒** | 规则文件修改后最多60秒生效，紧急时可调用`clearCache()`强制刷新 |
| **`module-development`阶段加载最多规则** | 9个规则文件+5个Agent定义，Token消耗最大，需注意预算 |

### 5.6 LTI上下文注入

| 实践 | 说明 |
|------|------|
| **先注册再注入** | 未注册的taskId调用`inject`会原样返回currentTask，不执行注入 |
| **目标信号仅在LTI模式下计算** | 非LTI模式不计算`goalSignal`，无法检测目标漂移 |
| **中文文本使用字符bigram** | 目标重叠度计算对中文使用字符bigram，对英文使用词级Jaccard |
| **注入历史有容量限制** | 每任务最多10条历史，总最多500条，超限自动淘汰最早条目 |

### 5.7 自回归上下文

| 实践 | 说明 |
|------|------|
| **使用`FIELDS`常量而非字符串** | 避免拼写错误，`AR.FIELDS.PREVIOUS_RESULT`而非`'previousResult'` |
| **注入前检查兼容性** | 使用`compatibilityCheck`确保上下文版本与当前代码兼容 |
| **`strip`在持久化前调用** | `_ar`上下文为运行时状态，不应持久化到磁盘 |
| **最大20个字段** | 超过限制后新字段被拒绝注入，需合理规划字段使用 |

### 5.8 常见陷阱

| 陷阱 | 说明 | 解决方案 |
|------|------|----------|
| 会话ID格式错误 | `create`抛出`INVALID_SESSION_ID` | 使用`SessionManager.generateSessionId()`生成ID |
| 阶段转换不合法 | `advancePhase`抛出`INVALID_PHASE_TRANSITION` | 检查`PHASE_TRANSITIONS_SET`白名单 |
| 检查点恢复后因果链断裂 | 未协调WAL回滚 | 使用`restoreWithCausalRollback`而非`restore` |
| 压缩结果被意外修改 | `compress`返回对象被外部修改 | 返回值为深拷贝，但`_lastResult`缓存可能受影响 |
| 上下文泄漏 | Agent A可访问Agent B的上下文 | 使用`grantContextAccess`显式授权，默认仅owner可访问 |
| 配置热重载失败 | `fs.watch`在部分系统不可靠 | 指数退避重试最多10次，失败后需手动重启 |
