# 第一部分：架构概览

## 概述

因果子系统（Causal Subsystem）负责管理Agent间数据流动的因果关系追踪，确保多Agent协作时的数据一致性和可追溯性。该子系统包含6个核心模块，协同完成因果数据的发布订阅、缓冲管理、配置验证、内存存储、向量索引和一致性检查。

## 模块清单

| 模块 | 源文件 | 说明 |
|------|--------|------|
| CausalDataBus | causal-data-bus.js | 因果数据总线，事件发布/订阅、因果排序、版本追踪 |
| CausalConfigValidator | causal-config-validator.js | 因果配置验证器，模式校验、依赖检查、一致性验证 |
| CausalBufferManager | causal-buffer-manager.js | 因果缓冲管理器，写入缓冲、刷盘策略、溢出处理 |
| CausalMemoryStore | causal-memory-store.js | 因果内存存储，内存索引、快速查询、TTL过期 |
| CausalVectorIndex | causal-vector-index.js | 因果向量索引，向量相似度搜索、嵌入管理 |
| CausalConsistencyChecker | causal-consistency-checker.js | 因果一致性检查器，最终一致性验证、冲突检测 |

## 模块协作关系图

```
                    ┌─────────────────────┐
                    │  CausalConfigValidator  │
                    │  (静态依赖图+配置验证)   │
                    └──────┬──────────────┘
                           │ getDependencyGraph()

                           ↓
┌──────────────┐    ┌──────────────────┐    ┌─────────────────────┐
│ CausalBuffer │◄───│  CausalDataBus   │───►│ CausalConsistency   │
│  Manager     │    │  (核心总线)       │    │   Checker           │
│ (注意力权重)  │───►│                  │    │ (双层一致性检查)      │
└──────────────┘    └──┬───────────┬───┘    └────────┬────────────┘
                       │           │                  │
          publishOutput│           │getCausalChain    │
                       ↓           ↓                  │
              ┌──────────────┐  ┌────────────────┐   │
              │ CausalVector │  │ CausalMemory   │◄──┘
              │   Index      │  │   Store        │
              │ (向量搜索)    │  │ (因果记忆+TTL) │
              └──────────────┘  └────────────────┘
```

## 关键依赖关系

- **CausalDataBus** 是核心枢纽，所有模块围绕它运作
- **CausalBufferManager** 依赖 CausalDataBus + SkillRouter，为上下文压缩引擎提供注意力权重
- **CausalConsistencyChecker** 依赖 CausalDataBus + CausalMemoryStore + CausalConfigValidator，执行双层一致性检查
- **CausalMemoryStore** 可选依赖 SqliteStore 做持久化
- **CausalVectorIndex** 可选依赖 EmbeddingService 做语义向量搜索

# 第二部分：架构设计详解

## CausalDataBus 设计

### 核心职责

CausalDataBus是因果子系统的核心枢纽，负责：
- 管理SkillInterface定义（因果输入/输出/不变量/场景）
- 发布和消费因果输出数据
- 维护因果链（causalChain）和待处理输出（pendingOutputs）
- WAL（Write-Ahead Log）持久化与恢复
- 并行输出冲突检测与合并
- 因果链回滚

### SkillInterface定义规范

通过`defineSkillInterface(skillId, definition)`注册接口，definition结构如下：

```javascript
{
  causalInputs: [           // 因果输入列表
    {
      name: 'requirement-completed',   // 输入名称
      source: 'skill:requirement-analysis', // 来源Skill
      required: false                   // 是否必需（默认true）
    }
  ],
  causalOutputs: [          // 因果输出列表
    {
      name: 'architecture-completed'    // 输出名称
    }
  ],
  invariants: [             // 不变量列表
    'skills-must-complete-in-order',    // 字符串形式
    { field: 'coverage', required: true, type: 'number', min: 0.8 }  // 对象声明式
  ],
  scenarios: [              // 场景列表
    {
      name: 'normal-flow',
      given: { input: 'exists' },
      then: { output: 'exists' }
    }
  ],
  version: 1                // 接口版本号
}
```

### 不变量类型

| 类型 | 形式 | 说明 | 示例 |
|------|------|------|------|
| 字符串肯定 | `'fieldName'` | 字段必须为truthy值 | `'coverage'` → coverage必须存在且非零 |
| 字符串否定 | `'!fieldName'` | 字段必须为falsy值 | `'!errors'` → errors必须不存在或为零 |
| 对象声明式 | `{ field, required, type, min, max }` | 结构化约束 | `{ field: 'score', type: 'number', min: 0, max: 100 }` |

> **安全限制**：对象不变量中的`check`函数字段会被拒绝，触发`invariant-check-skipped`事件，原因：`function_check_not_allowed_for_security`。

### 并行输出合并策略

| 策略 | 常量 | 说明 |
|------|------|------|
| **last-wins** | `MERGE_STRATEGIES.LAST_WINS` | 默认策略，后写入的覆盖先写入的（safeAssign顺序遍历） |
| **first-wins** | `MERGE_STRATEGIES.FIRST_WINS` | 保留最先写入的值（反向safeAssign，后写入的被覆盖） |
| **deepest-wins** | `MERGE_STRATEGIES.DEEPEST_WINS` | 按时间戳排序，最新的覆盖旧的（含深层对象合并） |
| **union** | `MERGE_STRATEGIES.UNION` | 合并所有输出：数组拼接、对象合并、新键追加，跳过DANGEROUS_KEYS |

### WAL持久化机制

CausalDataBus使用WAL（Write-Ahead Log）确保数据持久性：

- **存储路径**：`.harness/causal-wal/`
- **状态文件**：`causal-state.json`（防抖持久化，默认间隔）
- **操作日志**：`wal-operations.jsonl`（每行一个JSON操作）
- **检查点间隔**：每50条操作执行一次即时持久化
- **日志轮转**：当日志文件超过`MAX_JSON_FILE_SIZE`时，归档为`.archived`文件并创建新日志
- **背压控制**：写入流不可写时触发`wal-backpressure`事件，等待drain事件
- **恢复流程**：启动时先恢复state文件，再重放WAL日志中seq > 当前序列号的操作

## CausalBufferManager 设计

### 核心职责

CausalBufferManager基于注意力权重机制，为上下文压缩引擎提供因果感知的压缩策略建议。

### 注意力权重计算

`computeAttentionWeights(currentSkillId)`方法计算当前Skill对所有其他Skill的注意力权重：

| 权重来源 | 权重值 | 说明 |
|---------|--------|------|
| 直接依赖 | **1.0** | 当前Skill的causal_inputs中source引用的Skill |
| 传播衰减 | `decay^distance` | 间接依赖，decay默认0.7，distance为因果距离 |
| 背景 | **0.1** | 因果链中存在但无直接/间接依赖关系的Skill |

**传播算法**：BFS遍历依赖图，从直接依赖开始，每层距离权重乘以decay因子，最大传播距离由`maxCausalDistance`控制（默认5）。

**示例**：
```
当前Skill: D
D → 依赖 A（直接，权重1.0）
A → 依赖 B（距离1，权重0.7^1=0.7）
B → 依赖 C（距离2，权重0.7^2=0.49）
E（因果链中但无依赖关系，权重0.1）
```

### 压缩策略映射

`getCompressionStrategy(skillId, currentSkillId)`根据注意力权重返回压缩策略：

| 注意力权重 | 策略 | 说明 |
|-----------|------|------|
| ≥ 0.7 | `full` | 高因果相关，保留原文 |
| 0.3 ~ 0.7 | `summary` | 中等因果相关，摘要压缩 |
| < 0.3 或不存在 | `discard` | 低因果相关，可丢弃 |

### 缓存机制

- 注意力权重缓存：`_attentionCache`（Map，最大100条），TTL为`DEFAULT_TTL_CACHE_MS`
- 缓存命中时直接返回，避免重复计算
- `invalidateAttentionCache()`手动清除缓存

## CausalConfigValidator 设计

### 核心职责

CausalConfigValidator负责静态配置的因果验证，构建依赖图、检测循环依赖、发现配置漂移、分析变更影响。

### 依赖图（6类节点）

`buildDependencyGraph()`构建包含6类节点的依赖图：

| 节点类型 | 键名 | 来源 | 属性 |
|---------|------|------|------|
| **skills** | `graph.skills` | config.skill_registry | id, phase, enforcement, dependsOn, dependsOnSet, blocks, applicableAgents, fileExists, specificationBindings |
| **agents** | `graph.agents` | config.agent_permissions | id, allowedTools, restrictedOps, fileExists |
| **rules** | `graph.rules` | .harness/rules/目录扫描 | id, fileExists |
| **hooks** | `graph.hooks` | config.hooks | id, handlers |
| **mcp** | `graph.mcp` | config.mcp_servers | id, enabled, type |
| **sourceCode** | `graph.sourceCode` | src/目录JS文件扫描 | id, exports, imports, dependsOnSet, specificationBindings, resolvedImports, dependedOnBy |

### 边构建与错误检测

`_buildEdges()`方法在构建边时检测以下错误类型：

| 错误类型 | 说明 |
|---------|------|
| `missing_dependency` | Skill依赖了不存在的Skill |
| `missing_agent_reference` | Skill引用了不存在的Agent |
| `missing_skill_file` | Skill无对应的.md文件 |
| `missing_agent_file` | Agent无对应的.md文件 |
| `missing_spec_binding` | Skill的specificationBinding指向不存在的源码文件 |

### 循环依赖检测

`detectCircularDependencies()`使用DFS算法检测Skill间的循环依赖：

```javascript
const cycles = validator.detectCircularDependencies();
// 返回: [['skill-a', 'skill-b', 'skill-a'], ...]
```

### 配置漂移检测

| 方法 | 说明 |
|------|------|
| `snapshotConfig()` | 对当前配置做快照（JSON序列化），重置driftDetected标记 |
| `detectConfigDrift()` | 比较当前配置与快照，返回`{ drifted, added, removed, reason }` |
| `isDriftDetected()` | 返回是否已检测到漂移 |

### 影响分析

`getImpactAnalysis(nodeId, nodeType)`分析指定节点的变更影响范围：

| nodeType | 检测范围 |
|----------|---------|
| `'skill'` | 依赖此Skill的其他Skill、使用此Agent的Skill |
| `'agent'` | 使用此Agent的Skill |
| `'sourceCode'` | 导入此源码的其他源码、spec_bound到此源码的Skill |

## CausalConsistencyChecker 设计

### 核心职责

CausalConsistencyChecker执行双层一致性检查，验证运行时因果数据与静态配置、内存存储之间的一致性。

### 双层一致性检查

| 检查层 | 方法 | 比较对象 | 检测内容 |
|--------|------|---------|---------|
| **运行时 vs 静态** | `checkRuntimeVsStatic()` | CausalDataBus接口 vs ConfigCausalValidator依赖图 | 有静态依赖但无运行时接口的Skill |
| **内存 vs 运行时** | `checkMemoryVsRuntime()` | CausalMemoryStore搜索结果 vs CausalDataBus因果链 | 低置信度（<0.3）的内存条目 |

### 问题严重度分级

| 严重度 | 说明 | 示例 |
|--------|------|------|
| **high** | 严重问题，可能导致数据丢失或不一致 | （预留，当前未产生） |
| **medium** | 中等问题，静态与运行时不一致 | Skill有静态依赖但无运行时接口 |
| **low** | 轻微问题，数据质量下降 | 输出在内存中置信度过低 |

### 完整一致性检查

`checkFullConsistency()`同时执行两层检查，汇总所有问题：

```javascript
const result = checker.checkFullConsistency();
// {
//   consistent: false,
//   totalIssues: 3,
//   highIssues: 0,
//   mediumIssues: 2,
//   lowIssues: 1,
//   issues: [...],
//   runtimeVsStatic: false,
//   memoryVsRuntime: false
// }
```

## CausalMemoryStore 设计

### 核心职责

CausalMemoryStore管理因果记忆的存储、检索和衰减，支持关键词搜索、语义向量搜索、语义分组、上下文链和因果链追踪。

### 搜索模式

| 模式 | 方法 | 说明 |
|------|------|------|
| **关键词搜索** | `searchByCausalSimilarity(query, {mode:'keyword'})` | 提取关键词→相似度索引匹配→Jaccard相似度排序 |
| **语义向量搜索** | `searchByCausalSimilarity(query, {mode:'semantic'})` | 需EmbeddingService。文本向量化→余弦相似度排序 |
| **自动选择** | `searchByCausalSimilarity(query, {mode:'auto'})` | 有EmbeddingService时用语义搜索，否则用关键词搜索 |
| **语义分组** | `searchBySemanticGroup(query, opts)` | 基础搜索+category/tags/confidence过滤+时间衰减加权 |
| **上下文链** | `searchByContextChain(query, completedSkills, opts)` | 语义分组+已完成Skill扩展查询，合并去重排序 |
| **因果链追踪** | `traceCausalChain(effectKeyword, opts)` | BFS沿cause字段反向追踪因果链（最大深度5，最大50条） |

### 时间衰减机制

`_applyTimeDecay(entry)`计算时间衰减后的置信度：

```
衰减置信度 = max(0.01, 原始置信度 × decayFactor^ageDays)
```

- `decayFactor`默认0.98（每天衰减2%）
- 30天后：0.98^30 ≈ 0.545（约45%衰减）
- 最小值0.01，防止完全归零

### 因果记忆条目结构

```javascript
{
  id: 'cm_xxxx',           // UUID前缀
  cause: string,            // 因
  effect: string,           // 果
  context: string,          // 上下文描述
  confidence: number,       // 置信度(0~1)
  temporalScope: string,    // 时间范围：'session'
  category: string,         // 分类
  tags: string[],           // 标签（最多20个）
  source: string,           // 来源
  createdAt: number,        // Unix时间戳（秒）
  updatedAt: number,
  verifiedAt: number|null,
}
```

### 因果冲突检测

`detectCausalConflicts()`检测相似原因但不同结果的记忆条目：

- 原因相似度 ≥ `conflictThreshold`（默认0.7）
- 结果相似度 < `similarityThreshold`（默认0.3）
- 使用Jaccard相似度（关键词集合交集/并集）

## CausalVectorIndex 设计

### 核心职责

CausalVectorIndex提供基于向量相似度的因果数据检索能力，支持EmbeddingService语义嵌入和词哈希降级方案。

### 降级机制

当EmbeddingService不可用或嵌入失败时，自动降级到词哈希向量：

| 参数 | 值 | 说明 |
|------|-----|------|
| 向量维度 | **128** | `VECTOR_DIMENSIONS = 128` |
| 最大向量数 | **5000** | `MAX_VECTORS = 5000`，超出时淘汰最旧向量 |
| 默认相似度阈值 | **0.3** | `DEFAULT_SIMILARITY_THRESHOLD` |

### 词哈希降级算法

`_generateFallbackVector(text)`将文本转换为128维向量：

1. 文本按空格分词
2. 对每个词计算hash值（djb2变体）
3. hash值对128取模确定维度索引
4. 该维度累加 `1.0 / (词位置 + 1)`（越靠前的词权重越高）
5. L2归一化

# 第三部分：API参考

## 1. CausalDataBus — 因果数据总线

**源文件**：[causal-data-bus.js](../../src/runtime/causal/causal-data-bus.js)

### 职责概述

因果数据总线是因果子系统的核心枢纽，负责事件发布/订阅、因果链维护、版本追踪、WAL持久化、回滚支持和并行输出合并。它继承自 `EventEmitter`，通过 `withShutdown` 混入提供优雅关闭能力。

### 构造函数参数

```javascript
new CausalDataBus(options)
```

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `options.projectRoot` | `string` | `null` | 项目根目录，设置后启用WAL持久化 |
| `options.maxHistory` | `number` | `200` | 因果链最大保留条目数 |
| `options.maxPendingOutputs` | `number` | `50` | 待处理输出最大数量 |
| `options.maxInterfaces` | `number` | `100` | Skill接口定义最大数量 |
| `options.maxConflictResolvers` | `number` | `20` | 冲突解决器最大数量 |

**静态工厂方法**：

```javascript
CausalDataBus.fromConfig(projectRoot)
```

从项目配置自动读取容量参数创建实例。

### 公共方法签名

| 方法 | 签名 | 返回值 | 说明 |
|------|------|--------|------|
| `attachProjectRoot` | `attachProjectRoot(projectRoot: string)` | `this` | 延迟附加项目根目录，触发WAL初始化 |
| `attachSqliteStore` | `attachSqliteStore(sqliteStore: object)` | `this` | 附加SQLite存储用于双重持久化 |
| `defineSkillInterface` | `async defineSkillInterface(skillId: string, definition: object)` | `iface` | 定义Skill因果接口 |
| `getSkillInterface` | `getSkillInterface(skillId: string)` | `iface \| null` | 获取指定Skill的因果接口 |
| `getDefinedInterfaces` | `getDefinedInterfaces()` | `Array<iface>` | 获取所有已定义接口列表 |
| `validateScenario` | `validateScenario(skillId: string, scenarioName: string, context: object)` | `{valid, reason, issues, scenarioName}` | 验证场景条件是否满足 |
| `checkScenarioCoverage` | `checkScenarioCoverage(skillId: string, testedScenarios: string[])` | `{coverage, untested, total, tested}` | 检查场景覆盖率 |
| `validateInputs` | `validateInputs(skillId: string, context: object)` | `{valid, missing, reason}` | 验证因果输入是否完整 |

## 2. CausalBufferManager — 因果缓冲管理器

### 职责概述

| `options.maxCausalDistance` | `number` | `5` | 最大因果传播距离（1-10） |

### 公共方法签名

| 方法 | 签名 | 返回值 | 说明 |

| `getBufferStats` | `getBufferStats()` | `object` | 获取缓冲区统计信息 |
| `invalidateAttentionCache` | `invalidateAttentionCache()` | `void` | 使注意力权重缓存失效 |

**静态属性**：`CausalBufferManager.VALID_STRATEGIES` = `Set(['full', 'summary', 'discard'])`

### 事件列表

本模块继承 `EventEmitter` 但未定义自定义事件。

### 使用示例

## R38 修复记录

### `??` vs `||` 运算符误用系统性修复

**缺陷**：多个模块的数值配置参数使用`??`（空值合并）运算符提供默认值。对于计数型/容量型参数，`0`作为配置值通常无意义且可能导致功能异常，应使用`||`运算符在`0`时也回退到默认值。

**修复**：将以下参数从`??`改为`||`运算符：

| 模块 | 参数 | 修复 |
|------|------|------|
| causal-memory-store.js | `limit ?? 10`（3处） | `limit \|\| 10` |
| causal-memory-store.js | `maxDepth ?? 5` | `maxDepth \|\| 5` |
| causal-vector-index.js | `topK ?? 5` | `topK \|\| 5` |

**影响范围**：数值配置参数为0时正确回退到默认值，避免功能异常。

## R20 修复记录

### _flushWALPending null安全修复

**缺陷**：`causal-data-bus.js`的`_flushWALPending`方法中，`this._walLogStream.write()`的返回值或内部状态可能为`null`，直接调用其方法或属性时导致`TypeError: Cannot read property of null`异常，WAL刷盘流程崩溃。

**修复**：在`this._walLogStream.write()`调用前添加null检查，`_walLogStream`为null时跳过写入操作。

**影响范围**：WAL刷盘流程在流未初始化或已关闭时不再崩溃，优雅跳过写入。
