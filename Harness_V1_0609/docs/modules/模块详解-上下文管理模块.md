## 概述
本文档描述上下文管理模块的具体实现（2.73.4），包括CLAUDE.md注入、Session生命周期管理、上下文压缩策略、Skill三层缓存按需加载、隔离上下文管理和思维检索循环。

## 核心功能
1. **CLAUDE.md自动注入**：扫描、解析、合并项目内所有规则文件（16个规则+28个Agent定义+84个Skill定义）
2. **Session管理**：创建、初始化、运行、压缩、持久化、恢复，防抖持久化（200ms），TTL过期（24h），最大100个会话
3. **上下文压缩**：ContextCompressionEngine智能压缩，保留当前阶段Skill完整指令，压缩已完成Skill为摘要，Token使用率80%时自动触发
4. **Skill三层缓存按需加载**：L1摘要（始终加载）→ L2指令体（按需加载）→ L3参考资源（按需加载），smartPreload智能预加载
5. **隔离上下文管理**（v2.7新增）：IsolatedContextManager为每个子Agent提供独立上下文，防止上下文污染
6. **思维检索循环**（v2.7新增）：ThoughtRetrieverCycle五步循环，三种检索模式（confidence/semantic/hybrid）
7. **阶段上下文注入**（v2.7新增）：PhaseContextInjector根据当前阶段自动注入相关上下文

## 实现原理

### CLAUDE.md注入流程
1. 递归扫描项目目录，发现所有`.md`文件
2. 解析Frontmatter元数据（parseFrontmatter工具函数）
3. 处理`@include`指令，递归加载引用文件
4. 按类型（规则、文档、配置）合并为统一提示词
5. 注入到所有Agent的系统上下文中

### Session生命周期（v2.7.148）
```
创建（generateSessionId: sess-{uuid前16位}）
  → 初始化（加载规则/记忆/工具/Skill路由/阶段上下文）
  → 运行（Skill按需加载/深化迭代记录/Agent操作记录）
  → Compact触发（Token使用率80%）
  → 持久化（DebouncedPersister 200ms防抖写入.harness/sessions/）
  → 恢复（进程重启后自动从磁盘恢复）
```

Session关键配置：
| 配置 | 值 | 说明 |
|------|---|------|
| MAX_SESSIONS | 100 | 最大会话数，超限驱逐最旧 |
| SESSION_TTL_MS | 86400000 | 会话TTL（24小时） |
| DEBOUNCE_MS | 200 | 持久化防抖延迟 |
| DEFAULT_TOKEN_BUDGET | 1000000000 | 默认Token预算 |

### Skill三层缓存策略（v2.7.148）
| 层级 | 内容 | 加载时机 | 估算Token |
|------|------|---------|----------|
| L1 | Frontmatter摘要（skill_id, name, phase, enforcement, depends_on） | 框架初始化时全部加载 | ~500/Skill |
| L2 | 完整指令体（Markdown内容） | match()时自动加载 | ~2000/Skill |
| L3 | 参考资源（示例、模板） | deepening时按需加载 | ~5000/Skill |

加载策略：
- **分层加载**：核心身份声明始终注入；Skill路由指令按需加载当前阶段相关的Skill
- **摘要替代**：非当前阶段的Skill仅注入名称和触发条件，不注入完整步骤
- **渐进展开**：当Skill被激活时，才加载其L2完整内容到上下文
- **压缩回收**：已完成Skill的L2详细步骤从上下文中移除，仅保留完成状态
- **智能预加载**：smartPreload根据上下文预加载匹配的Skill L2，smartPreloadByPhase按阶段预加载
- **去重索引**：内容去重索引避免重复加载相同内容

### 上下文压缩策略（v2.7.148）
```
触发条件：Token使用率达到80%阈值
   ↓
ContextCompressionEngine执行压缩
   ├── 保留：当前阶段Skill完整指令
   ├── 保留：关键决策和状态
   ├── 保留：最近N条操作记录
   ├── 压缩：已完成Skill → 仅保留完成状态
   ├── 压缩：历史上下文 → 摘要
   └── 丢弃：冗余内容和过期信息
   ↓
压缩后Token使用率应低于60%
```

### 隔离上下文管理（v2.7新增）
```
SubagentExecutor.spawn(task, agentConfig)
   ↓
IsolatedContextManager创建独立上下文
   ├── 上下文ID: ctx-{uuid}
   ├── 继承父上下文的基础规则
   ├── 不共享其他子Agent的中间结果
   ├── 独立的Token计数
   └── 任务完成后上下文自动清理
```

### 思维检索循环（v2.7新增）
```
ThoughtRetrieverCycle.execute(agentOutput, context)
   ↓
RETRIEVE: 检索相关思维
   ├── confidence模式：按置信度排序，minConfidence=0.7
   ├── semantic模式：语义检索（需embeddingService），minConfidence=0.5
   └── hybrid模式（默认）：confidence权重0.4 + semantic权重0.6，合并排序取Top10
   ↓
GENERATE: 基于检索结果生成输出
   ↓
DISTILL: 提炼思维，评估置信度
   ↓
DEDUPLICATE: 查重去冗余（ThoughtDeduplicator）
   ├── accepted: 新思维
   ├── duplicates: 重复思维
   └── merged: 合并思维
   ↓
STORE: 更新记忆（ThoughtMemoryStore）
```

### 阶段上下文注入（v2.7新增）

```
PhaseContextInjector
   ├── 根据当前phase字段注入阶段特定上下文
   ├── 包含该阶段的Skill摘要
   ├── 包含该阶段的完成条件
   └── 包含前序阶段的完成状态
```

## 使用示例
```
1. 项目启动时，系统自动扫描.harness/rules/和docs/guidelines/下的所有.md文件
2. 解析每个文件的Frontmatter元数据和@include指令
3. 合并为统一的系统提示词，注入到所有Agent上下文
4. SessionManager创建会话，PhaseContextInjector注入阶段上下文
5. SkillRouter按需加载L2指令体（smartPreload智能预加载）
6. SubagentExecutor为每个子Agent创建隔离上下文
7. ThoughtRetrieverCycle执行思维检索循环（hybrid模式）
8. Token使用率达到80%时，ContextCompressionEngine自动触发压缩
9. 任务完成后，Session状态防抖持久化到.harness/sessions/
10. 进程重启后，SessionManager自动从磁盘恢复会话
```

## 注意事项
- 压缩上下文时必须保留关键决策和状态
- Session恢复后需验证所有工具状态的一致性
- @include引用的文件不存在时需优雅降级
- 隔离上下文不共享子Agent中间结果，避免上下文污染
- 思维检索的hybrid模式需要EmbeddingService支持
- 防抖持久化200ms内合并多次写入，减少磁盘I/O
- 会话TTL 24小时后自动过期，需定期清理
- 最大100个会话，超限自动驱逐最旧会话

## R38 修复记录

### `??` vs `||` 运算符误用系统性修复

**缺陷**：多个模块的数值配置参数使用`??`（空值合并）运算符提供默认值。对于计数型/容量型参数，`0`作为配置值通常无意义且可能导致功能异常，应使用`||`运算符在`0`时也回退到默认值。

**修复**：将以下参数从`??`改为`||`运算符：

| 模块 | 参数 | 修复 |
|------|------|------|
| isolated-context-manager.js | `maxHistory ?? 200` | `maxHistory \|\| 200` |

**影响范围**：数值配置参数为0时正确回退到默认值，避免功能异常。

## 核心算法详解

### ContextCompressionEngine.compress() 压缩算法

`compress()`方法是上下文压缩引擎的核心入口，负责根据当前执行阶段和技能分类策略对技能列表进行智能压缩。完整算法流程如下：

#### 1. 增量跳过检测

```
输入context → 计算stateHash → 与_lastStateHash比较
   ├── 相同且_lastResult存在 → 增量跳过，返回deepClone(_lastResult)
   │    └── deepClone失败 → 降级到JSON.parse(JSON.stringify)
   │         └── JSON序列化失败 → 清空增量状态，递归重试compress()
   └── 不同 → 继续压缩流程
```

状态哈希计算（`_computeStateHash`）：将`currentPhase`、排序后的`skillId:phase`列表、排序后的`completedSkills`列表和排序后的`specAssetIds`拼接后，使用DJB2变体哈希算法（`h = ((h << 5) - h + charCode) | 0`）生成36进制字符串。

#### 2. 分类策略（keep/summarize/discard）

对每个Skill执行五层分类决策：

```
Skill → _determineSkillCategory()
   │
   ├── 第一层：规格资产检测
   │    └── _hasSpecificationOutput()：检查skill.causal_outputs中是否包含'specification'输出
   │         └── 是 → category = 'specification_asset'，强制strategy='full'
   │
   ├── 第二层：因果覆盖检测（因果缓冲管理器优先）
   │    └── _matchSkillPattern()
   │         ├── causalBufferManager存在 + skill已完成 + currentSkillId已设置
   │         │    └── causalBufferManager.getCompressionStrategy(skillId, currentSkillId)
   │         │         ├── 'full' → causal_relevance_high
   │         │         ├── 'summary' → causal_relevance_medium
   │         │         └── 其他 → causal_relevance_low (discard)
   │         │
   │         └── causalValidator存在 + skill已完成
   │              └── _isCausalUpstream()：检查skill是否为当前阶段技能的因果上游
   │                   └── 是 → causal_upstream，强制strategy='full'
   │
   ├── 第三层：阶段分类（无因果覆盖时）
   │    ├── skill.phase === currentPhase → current_phase
   │    ├── completedSkills.has(skill.skill_id) → completed_phase
   │    ├── PHASE_INDEX[skill.phase] > currentPhaseIdx → future_phase
   │    └── 以上均不匹配 → unclassified
   │
   └── 第四层：策略应用（_applyStrategy）
        ├── strategy='full' → compress=false，保留完整instruction
        ├── strategy='summary'
        │    ├── summaryTokens >= instructionTokens → 回退到full（避免压缩反增）
        │    └── summaryTokens < instructionTokens → compress=true，用summary替换instruction
        └── strategy='discard' → compress=true，compressedTokenEstimate=0
```

默认策略映射：

| 类别 | 默认策略 | 说明 |
|------|---------|------|
| current_phase | full | 当前阶段技能保留完整指令 |
| completed_phase | summary | 已完成技能压缩为摘要 |
| future_phase | summary | 未来阶段技能压缩为摘要 |
| unclassified | full | 未分类技能保留完整指令 |
| specification_asset | full（强制） | 规格资产始终保留，不允许修改 |

#### 3. Token估算

```javascript
// _estimateTokens算法
nonAscii = text.match(/[\x80-\uFFFF]/g).length  // CJK等双字节字符数
ascii = text.length - nonAscii                    // ASCII字符数
ratio = config.tokenCharsRatio ?? 4               // 默认4字符/Token
tokens = ceil((ascii + nonAscii * 2) / ratio)     // CJK字符权重×2
```

Token估算考虑CJK字符的双倍权重，更准确地反映中文上下文的Token消耗。

#### 4. 压缩计划生成（getCompressionPlan）

独立于`compress()`的计划查询接口，结果按上下文状态缓存（`_planCache`，最大50条）：

```
输入context → 计算cacheKey → 缓存命中？
   ├── 是 → 返回缓存计划，stats.cacheHits++
   └── 否 → 遍历skills → _classifySkillForPlan()
        ├── action='retain' → 加入retain列表
        └── action='compress' → 加入compress列表，累加savings
        → 返回 { retain, compress, estimatedSavings }
```

缓存键格式：`phase:sortedSkillIds:sortedCompletedIds`

#### 5. 上下文分类与结果组装

```
keyDecisions → retainKeyDecisions=true时保留，否则清空
sessionState → retainSessionState=true时保留，否则清空
specificationAssets → 过滤有效资产（assetId或assetType存在），标记retained=true
```

最终结果包含：`retainedSkills`、`compressedSkills`、`tokenSavings`、`compressionRatio`（保留2位小数）、`originalTokenEstimate`、`compressedTokenEstimate`、`keyDecisions`、`sessionState`、`retainedSpecAssets`。

#### 6. 因果上游缓存

`_isCausalUpstream()`使用带TTL的内存缓存（最大500条，过期时间`DEFAULT_PIPELINE_TIMEOUT_MS`），避免重复遍历依赖图。缓存满时先清理过期条目（超过5分钟），仍有空间才插入新条目。

#### 7. 输出压缩（compressOutput / compressToolOutput）

**compressOutput**：文本输出压缩，支持：
- 填充词去除（`Sure,`、`Great question!`、`Let me explain...`等AI常见填充语）
- 冗余注释过滤（代码块中仅保留TODO/FIXME/HACK/NOTE/IMPORTANT注释，过滤率>50%时生效）
- 按句子截断（保留前60%长度给文本，剩余空间给代码块）
- 最大长度硬截断（超出maxLength-3后追加`...`）

**compressToolOutput**：工具调用输出压缩，支持：
- 字符串行压缩：filterPatterns正则过滤（含ReDoS危险模式检测`/(?:\([^)]*[+*][^)]*\))[+*{]/`，模式长度限制200字符）、重复行合并（连续≥threshold行合并为`line (xN)`）、头尾保留截断（60%头部+30%尾部+省略行数提示）
- 对象输出压缩：数组>5项保留前3后2、字符串>500字符截断为前200字符+省略提示、大数组>10项保留前5后2

### IsolatedContextManager 隔离机制

#### 1. 共享边界控制（whitelist/blacklist）

IsolatedContextManager通过访问控制列表（ACL）实现Agent间的上下文共享边界：

```
创建上下文 → _accessControl.set(contextId, { owner, allowedAgents: Set([owner]) })
   │
   ├── grantContextAccess(contextId, agentId)
   │    └── allowedAgents.add(agentId)，上限20个Agent
   │
   ├── revokeContextAccess(contextId, agentId)
   │    └── 不允许撤销owner自身权限
   │
   └── getContext(contextId, requestingAgentId)
        ├── 无requestingAgentId → 跳过ACL检查
        ├── allowedAgents.has(agentId) === false → emit('access-denied')，返回null
        └── 通过ACL → 返回深拷贝副本
```

默认工具集按Agent角色分配（白名单模式）：

| Agent角色 | 默认工具集 |
|-----------|-----------|
| task-worker | read, write, search, run |
| domain-analyst | read, write, search, web |
| quality-assurance | read, search, run, web |
| devops-engineer | read, write, search, run |
| technical-writer | read, write, search |

#### 2. 上下文快照

`getContext()`返回的是深拷贝副本，修改不影响内部状态。快照包含以下字段的独立拷贝：

- `constraints`：`Array.slice()`浅拷贝
- `successCriteria`：`Array.slice()`浅拷贝
- `result.evidence`：`deepClone()`深拷贝（R8修复：防止子Agent修改evidence条目污染父上下文）
- `result`其他字段：直接引用（output/summary/confidence/completedAt为不可变或基本类型）

#### 3. 写时复制（COW）策略

IsolatedContextManager采用隐式COW策略：

- **读取时复制**：`getContext()`始终返回深拷贝，调用方修改不影响内部状态
- **写入时独立**：`createIsolatedContext()`为每个Agent创建独立的上下文对象，不共享引用
- **共享合并**：`_mergeShared(target, source, visited)`用于将共享上下文合并到目标上下文，使用`visited Set`防止循环引用，数组使用`slice()`创建独立副本
- **结果提交**：`submitResult()`直接写入内部上下文对象，不经过COW路径（仅owner可提交）

#### 4. 驱逐策略

上下文数量达到`maxContexts`（默认20）时触发三级驱逐：

```
_evictOldest()
   ├── 第一优先：驱逐最旧的completed状态上下文（lastAccessedAt最小）
   ├── 第二优先：驱逐released/failed状态的上下文（任意一个）
   └── 第三优先：驱逐LRU最久未访问的上下文（包括active状态）
        └── 驱逐active上下文时触发 'active-context-evicted' 事件
```

#### 5. 生命周期管理

```
active（创建时） → completed（submitResult时） → released（releaseContext时）
                                              → failed（异常时）
```

历史记录使用`RingBuffer`（默认容量200），记录创建和完成事件，用于审计和统计。

### AutoregressiveContextSchema 自回归模式

#### 上下文自回归生成与验证流程

AutoregressiveContextSchema为深化推理（Deepening）子系统提供自回归上下文管理，将前一轮迭代的输出作为下一轮的输入上下文，实现迭代精化的闭环。

#### 1. 注入流程（inject）

```
target对象 + fields键值对
   │
   ├── 目标校验：target非对象 → 返回null
   ├── 字段校验：fields非对象 → 返回target原样
   │
   ├── 初始化：target._ar = target._ar ?? {}
   │
   └── 逐字段注入：
        ├── 危险键过滤：DANGEROUS_KEYS中的键直接跳过
        ├── 未知字段过滤：不在FIELDS白名单中的键跳过并记录debug日志
        ├── 字段数限制：已有字段数 ≥ MAX_AR_FIELDS(20) 且新键不在已有字段中 → 跳过
        ├── 字符串截断：长度 > MAX_FIELD_LENGTH(2000) → 截断到2000字符
        ├── 数组截断：长度 > MAX_ARRAY_LENGTH(100) → 截断到100项
        └── 写入：target._ar[key] = value
        → 追加元数据：_version = 1, updatedAt = Date.now()
```

已知字段白名单（FIELDS）：

| 字段 | 类型 | 用途 |
|------|------|------|
| previousResult | string | 前一轮迭代结果 |
| previousScore | number | 前一轮质量评分（0-1） |
| qualityHistory | array | 质量评分历史序列 |
| feedback | string | 反馈信息 |
| previousOutput | string | 前一轮输出 |
| focusAreas | array | 关注领域列表 |
| originalGoal | string | 原始目标 |
| iteration | number | 当前迭代序号 |
| maxIterations | number | 最大迭代次数（1-100） |
| iterationSummary | string | 迭代摘要 |
| source | string | 来源标识 |

来源标识（SOURCE_IDS）：

| 标识 | 来源 |
|------|------|
| deepening-orchestrator | 深化推理编排器 |
| iterative-refinement | 迭代精化器 |
| recurrent-deepening-scheduler | 循环深化调度器 |
| skill-complete | 技能完成事件 |
| phase-advance | 阶段推进事件 |

#### 2. 提取流程（extract）

```
target对象 → target._ar存在？
   ├── 否 → 返回null
   └── 是 → 遍历_ar的所有键
        ├── 跳过元数据键：_version, updatedAt
        └── 收集业务字段到新对象ctx
        → 返回ctx
```

#### 3. 合并流程（merge）

```
target + overrides
   → extract(target) 获取现有上下文（可能为null）
   → { ...existing, ...overrides } 合并覆盖
   → inject(target, merged) 重新注入
```

合并操作等价于"提取现有→覆盖更新→重新注入"三步原子操作。

#### 4. 验证流程（validate）

```
target._ar → 逐字段校验
   ├── 数值范围校验：
   │    ├── previousScore ∈ [0, 1]
   │    ├── iteration ≥ 0
   │    └── maxIterations ∈ [1, 100]
   ├── 数组类型校验：qualityHistory, focusAreas 必须为Array
   ├── 字符串类型校验：previousResult, previousOutput, originalGoal, feedback, iterationSummary, source 必须为string
   └── 返回 { valid: warnings.length === 0, warnings }
```

#### 5. 兼容性检查（compatibilityCheck）

```
target._ar._version vs requiredVersion
   ├── 无_ar上下文 → compatible=true, reason='no_ar_context'
   ├── 版本匹配 → compatible=true, reason='version_match'
   ├── 上下文版本 > 所需版本 → compatible=false, reason='newer_version_not_guaranteed_compatible'
   └── 上下文版本 < 所需版本
        → VERSION_FIELD_MAP[ctxV] vs VERSION_FIELD_MAP[reqV]
        → 检查缺失字段
        → compatible = missing.length === 0
```

版本字段映射：

| 版本 | 支持字段 |
|------|---------|
| 0 | 无（空数组） |
| 1 | 全部11个FIELDS字段 |

#### 6. 清理流程（strip）

直接删除`target._ar`属性，返回target引用。用于迭代结束时清理自回归上下文。

## R59 修复记录

### safeStringify循环引用保护

**缺陷**：`ContextCompressionEngine.compressToolOutput()`的`filterPatterns`选项在处理包含循环引用的对象输出时，内部调用`JSON.stringify()`会抛出`TypeError: Converting circular structure to JSON`异常，导致工具输出压缩失败。

**根因**：`_compressObjectOutput()`方法处理对象类型输出时，未对循环引用场景做防护。当工具返回的对象包含双向引用（如父子节点互引）时，`JSON.stringify()`无法序列化。

**修复**：v2.7.148引入`safeStringify`（来自`src/utils/safe-execute.js`）替代`JSON.stringify()`。`safeStringify`使用`WeakSet`追踪已访问对象，遇到循环引用时输出`'[Circular]'`占位符而非抛出异常：

```javascript
// safeStringify实现（src/utils/safe-execute.js）
function safeStringify(obj, replacer, space) {
  try {
    const seen = new WeakSet();
    return JSON.stringify(obj, function(key, value) {
      if (typeof value === 'object' && value !== null) {
        if (seen.has(value)) return '[Circular]';
        seen.add(value);
      }
      return typeof replacer === 'function' ? replacer(key, value) : value;
    }, space);
  } catch (_e) {
    return String(obj);
  }
}
```

**影响范围**：`compressToolOutput()`的对象输出压缩路径现在能安全处理循环引用，不再因序列化失败而中断压缩流程。

**相关模块**：`safeStringify`已在以下模块中使用：
- `src/runtime/causal/causal-data-bus.js` — 因果事件序列化
- `src/runtime/infrastructure/signal-persistence.js` — 信号持久化
- `src/web/server.js` — HTTP响应序列化

## R62 修复记录

### ConversationContextStore预处理语句缓存

**缺陷**：`ConversationContextStore`的`_persistTurn()`、`_persistSessionMeta()`、`_deleteTurnsFromStore()`、`_restoreFromSqlite()`、`_loadSessionFromStore()`、`_deleteSessionFromStore()`等方法中，每次调用都执行`db.prepare(sql)`重新编译SQL语句。better-sqlite3的`db.prepare()`不要求手动`.finalize()`（与旧版sqlite3不同），但每次调用都重新编译SQL造成不必要的性能开销，在高频对话轮次持久化场景下影响更明显。

**根因**：与`SqliteStore`（`src/runtime/infrastructure/sqlite-store.js`）的`_prepareStatements()`模式不一致。`SqliteStore`在初始化时一次性`prepare`并缓存30+条预处理语句，而`ConversationContextStore`每次操作都重新编译。

**修复**：v2.7.148引入`_prepareStatements(db)`方法，在`_ensureTables()`成功后缓存9条预处理语句：

```javascript
_prepareStatements(db) {
  this._stmts = {
    insertTurn: db.prepare('INSERT OR REPLACE INTO conversation_turns ...'),
    insertSession: db.prepare('INSERT OR REPLACE INTO conversation_sessions ...'),
    deleteTurn: db.prepare('DELETE FROM conversation_turns WHERE turn_id = ?'),
    deleteTurnsBySession: db.prepare('DELETE FROM conversation_turns WHERE session_id = ?'),
    deleteSession: db.prepare('DELETE FROM conversation_sessions WHERE session_id = ?'),
    selectSessions: db.prepare('SELECT * FROM conversation_sessions ORDER BY ...'),
    selectTurnsBySession: db.prepare('SELECT * FROM conversation_turns WHERE ... ORDER BY sequence ASC'),
    selectSessionById: db.prepare('SELECT * FROM conversation_sessions WHERE session_id = ?'),
    selectTurnsBySessionDesc: db.prepare('SELECT * FROM conversation_turns WHERE ... ORDER BY sequence DESC LIMIT ?'),
  };
}
```

各方法优先使用`this._stmts`缓存的预处理语句，回退到`db.prepare()`以兼容`_stmts`未初始化的场景。`_onShutdown()`中清理`this._stmts = null`。

**影响范围**：对话轮次持久化、会话元数据持久化、会话恢复、会话删除等SQLite操作的性能显著提升，消除了每次操作的SQL编译开销。
