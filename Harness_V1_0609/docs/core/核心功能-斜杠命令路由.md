# 核心功能-斜杠命令路由

> 版本：2.73.4 | 模块：src/runtime/workflow/command-router.js

---

## 概述

CommandRouter负责斜杠命令的自动发现、解析和路由。支持别名、中文命令和模糊匹配，集成因果总线实现命令执行的因果追踪。

> 详细的API文档和命令定义格式请参见 [模块详解-CommandRouter模块](../modules/模块详解-CommandRouter模块.md)

## 核心能力

| 能力 | 说明 |
|------|------|
| **自动发现** | 扫描.harness/commands/目录，加载命令定义 |
| **别名支持** | 一个命令可有多个别名，通过_aliasMap映射到command_id |
| **中文命令** | 支持中文命令名和别名 |
| **模糊匹配** | 容忍拼写错误，提供最接近的命令建议 |
| **因果总线集成** | 通过setCausalBus接入因果数据总线，自动注册命令因果接口 |
| **执行历史** | RingBuffer记录最近100条命令执行记录 |
| **优雅关闭** | withShutdown混入，清理所有内部状态 |

## 命令发现机制详解

### discover() 同步扫描流程

`discover()`方法负责同步扫描`.harness/commands/`目录，加载所有命令定义文件并构建内部数据结构。完整流程如下：

```
discover()
  │
  ├─ 1. 守卫检查：guardShutdown()，若实例已关闭则抛出错误
  │
  ├─ 2. 重置状态：清空 commands[]、registry{}、_aliasMap{}
  │
  ├─ 3. 目录检查：fs.existsSync(commandsDir)
  │     └─ 目录不存在 → 返回空数组 []
  │
  ├─ 4. 文件扫描：scanMarkdownDirSync(commandsDir)
  │     └─ 使用 safeExecute 包裹，扫描失败时返回空数组
  │
  ├─ 5. 逐文件解析：
  │     for each file in files:
  │       ├─ parseMarkdownFile(filePath) → { frontmatter, body }
  │       ├─ 校验：frontmatter存在 且 command_id存在？否 → continue 跳过
  │       ├─ 构建命令对象：
  │       │   command = {
  │       │     command_id, name, description,
  │       │     skills: parseArray(fm.skills) ?? [],
  │       │     agent, phase,
  │       │     aliases: parseArray(fm.aliases) ?? [],
  │       │     enforcement: fm.enforcement || 'recommended',
  │       │     instruction: body,
  │       │     _filePath
  │       │   }
  │       ├─ 注册到 registry：registry[commandId] = command
  │       └─ 注册别名：aliases.forEach(alias => _aliasMap[alias] = commandId)
  │
  ├─ 6. 发射事件：emit('commands-discovered', { count })
  │
  └─ 7. 因果注册：_registerCausalInterfaces()
```

### discoverAsync() 异步扫描流程

`discoverAsync()`是`discover()`的异步版本，使用`fs.promises`和`parseMarkdownFileAsync`替代同步API。核心差异：

| 对比项 | discover() | discoverAsync() |
|--------|-----------|-----------------|
| 目录存在检查 | `fs.existsSync()` | `fs.promises.access()` + safeExecuteAsync |
| 文件扫描 | `scanMarkdownDirSync()` | `scanMarkdownDirAsync()` |
| 文件解析 | `parseMarkdownFile()` | `await parseMarkdownFileAsync()` |
| 错误处理 | `safeExecute()` | `safeExecuteAsync()` |
| 返回值 | `Command[]` | `Promise<Command[]>` |

两者在解析逻辑、命令对象构建、别名注册、事件发射和因果接口注册方面完全一致。

### registry 和 aliasMap 构建

命令发现完成后，两个核心数据结构被填充：

- **registry**：以`command_id`为键的命令对象映射表。`resolve()`的精确匹配直接查询此表。
- **_aliasMap**：以别名为键、`command_id`为值的映射表。`resolve()`的别名匹配查询此表后，再从registry获取命令对象。

```
示例（/plan 命令）：

registry = {
  '/plan': { command_id: '/plan', name: '实现规划', skills: [...], ... }
}

_aliasMap = {
  '/规划': '/plan',
  '/plan-project': '/plan'
}
```

当同一别名被多个命令定义时，后加载的命令会覆盖先前的映射。命令文件的加载顺序取决于操作系统的文件系统遍历顺序，因此应避免在不同命令中定义相同别名。

## resolve() 三级解析策略

`resolve(input)`方法按以下顺序尝试解析用户输入为命令对象：

```
输入字符串 → trim()
  ↓
1. 精确匹配 → registry[trimmed] 存在？→ 返回命令对象
  ↓ 否
2. 别名匹配 → _aliasMap[trimmed] 存在？→ 返回 registry[_aliasMap[trimmed]]
  ↓ 否
3. 斜杠前缀提取 → 正则 /(\/[\w-]+)/ 提取候选 → registry[candidate] 或 _aliasMap[candidate]
  ↓ 否
返回 null
```

| 级别 | 匹配方式 | 示例输入 | 匹配目标 |
|------|---------|---------|---------|
| 精确匹配 | 完全相等 | `/plan` | `registry['/plan']` |
| 别名匹配 | 别名映射 | `/规划` | `_aliasMap['/规划']` → `registry['/plan']` |
| 斜杠前缀提取 | 正则提取首个`/word`片段 | `/plan some args` | 提取`/plan` → `registry['/plan']` |

## fuzzyMatch() 模糊匹配算法

当`resolve()`无法精确解析时，`fuzzyMatch(input)`提供容错匹配。算法先调用`resolve()`，若返回非空则直接使用；否则进入模糊评分：

1. 输入和命令ID/名称均做归一化处理：`toLowerCase().replace(/[/\s-]/g, '')`
2. 对每个命令计算匹配分数，取最高分且≥0.5的命令返回

### 评分规则

| 匹配方式 | 分数 | 常量名 | 说明 |
|---------|------|--------|------|
| 命令ID包含输入 | **0.9** | `FUZZY_MATCH_ID_CONTAINS_SCORE` | 最高置信度，ID是最精确的标识 |
| 命令名称包含输入 | **0.7** | `FUZZY_MATCH_NAME_CONTAINS_SCORE` | 名称匹配次之 |
| 部分字符匹配 | `(匹配字符数/输入长度) × 0.5` | `FUZZY_MATCH_PARTIAL_MULTIPLIER` | 逐字符在ID中顺序查找，按比例×0.5倍率 |
| 最低阈值 | **0.5** | `FUZZY_MATCH_MIN_THRESHOLD` | 低于此分数的匹配被丢弃 |

### 示例

```
输入: "plan"（归一化后）
  /plan → ID包含"plan" → 0.9 ✓
  /deploy → 部分匹配(p,l,a) → 3/4×0.5=0.375 ✗ < 0.5
```

## Tab补全机制

`complete(partial)`方法为终端或UI提供Tab补全功能，根据用户输入的部分命令前缀返回匹配的命令列表。

### 实现原理

```
complete(partial)
  │
  ├─ 1. 输入校验：partial 非空且为字符串？否 → 返回 []
  │
  ├─ 2. 前缀检查：trimmed 以 '/' 开头？否 → 返回 []
  │     （仅对斜杠开头的输入提供补全）
  │
  ├─ 3. 前缀归一化：prefix = trimmed.toLowerCase()
  │
  ├─ 4. 命令ID前缀匹配：
  │     for each cmd in commands:
  │       cmd.command_id.toLowerCase().startsWith(prefix)?
  │         → matches.push({ command_id, name, description })
  │
  ├─ 5. 别名前缀匹配：
  │     for each alias in cmd.aliases:
  │       alias.toLowerCase().startsWith(prefix)?
  │         → matches.push({ command_id, name, alias, description })
  │
  └─ 6. 返回 matches[]
```

### 前缀匹配算法

补全采用**大小写不敏感的前缀匹配**。输入`/pl`可以匹配`/plan`；输入`/规划`可以匹配中文别名`/规划`。匹配结果包含两种类型：

| 匹配类型 | 返回字段 | 说明 |
|---------|---------|------|
| 命令ID匹配 | `{ command_id, name, description }` | 直接通过命令ID前缀匹配 |
| 别名匹配 | `{ command_id, name, alias, description }` | 通过别名前缀匹配，额外返回`alias`字段 |

### 补全示例

```
输入: "/pl"
  → [
      { command_id: "/plan", name: "实现规划", description: "..." },
    ]

输入: "/c"
  → [
      { command_id: "/code-review", name: "代码审查", description: "..." },
      { command_id: "/code-simplify", name: "代码简化", description: "..." },
      { command_id: "/cli", name: "软件操控", description: "..." },
    ]

输入: "/审"
  → [
      { command_id: "/code-review", name: "代码审查", alias: "/审查", description: "..." },
    ]
```

## 执行历史管理

CommandRouter使用[RingBuffer](../../src/utils/ring-buffer.js)记录命令执行历史，提供高效的固定容量FIFO队列。

### RingBuffer实现

RingBuffer（环形缓冲区）替代`Array + shift()`模式，避免O(n)的shift操作性能瓶颈。核心特性：

| 特性 | 说明 |
|------|------|
| **固定容量** | 构造时指定，CommandRouter使用`MAX_EXECUTION_HISTORY = 100` |
| **自动淘汰** | 容量满时push新元素，自动淘汰最旧元素 |
| **O(1)操作** | push/shift均为O(1)时间复杂度 |
| **迭代支持** | 实现Symbol.iterator协议，支持for...of遍历 |

### 执行记录结构

每次`executeCommand()`调用时，自动创建执行记录并推入RingBuffer：

```javascript
{
  commandId: '/plan',          // 命令标识
  name: '实现规划',             // 命令名称
  phase: 'brainstorming',     // 所属阶段
  skills: [...],              // 触发的技能链
  enforcement: 'recommended', // 执行级别
  timestamp: 1717000000000,   // 执行时间戳（Date.now()）
  context: {},                // 执行上下文
  status: 'dispatched'        // 状态：固定为'dispatched'
}
```

### getExecutionHistory(limit)

查询最近N条执行记录。参数处理逻辑：

- `limit`为有效正整数时，取`min(limit, historySize)`条最近记录
- `limit`未提供或无效时，默认返回最近100条
- 返回数组按时间从旧到新排列（`toArray().slice(-count)`）

### 历史记录生命周期

```
executeCommand() 被调用
  → 创建 executionRecord
  → _executionHistory.push(record)
  → 若超过100条，自动淘汰最早记录
  → getExecutionHistory() 查询时返回最近记录
  → _onShutdown() 时 clear() 清空全部历史
```

## 因果总线集成

### setCausalBus(bus)

注入因果数据总线实例。要求bus必须实现`publishOutput`方法，否则抛出`DeepeningError('INVALID_INPUT')`。设置后若已有命令，自动调用`_registerCausalInterfaces()`。

### _registerCausalInterfaces()

为每个已发现的命令在因果总线上注册SkillInterface：

- **接口ID**：`cmd:` + command_id（如`cmd:/plan`）
- **因果输入**：命令所属阶段之前的所有阶段的`{phase}-completed`信号（required: false）
- **因果输出**：`{phase}-completed` + `command-executed`
- **不变量**：`skills-must-complete-in-order`
- **版本**：1

若接口已存在（`getSkillInterface`返回非空）则跳过，避免重复注册。

### 因果输出发布

`executeCommand()`执行时，若因果总线已连接，自动通过`publishOutputSync()`发布命令执行数据：

```javascript
causalBus.publishOutputSync('cmd:/plan', {
  commandId: '/plan',
  phase: 'brainstorming',
  skills: ['brainstorming', 'requirement-analysis', 'architecture-design'],
  enforcement: 'recommended',
  timestamp: 1717000000000
});
```

## 与SkillRouter的协作

斜杠命令触发Skill链的执行是一个多组件协作流程，涉及CommandRouter、PipelineExecutor、SkillRouter、PhaseOrchestrator和RBACEnforcer。

### 命令触发Skill链的完整流程

```
用户输入 "/build 用户认证模块"
  │
  ├─ 1. CommandRouter.isCommand(input)
  │     判断输入是否为斜杠命令（以/开头且存在于registry或aliasMap）
  │
  ├─ 2. CommandRouter.resolve(input)
  │     三级解析：精确→别名→斜杠前缀提取 → 返回命令对象
  │
  ├─ 3. CommandRouter.executeCommand(commandId, context)
  │     ├─ 记录执行历史（RingBuffer.push）
  │     ├─ 发布因果输出（causalBus.publishOutputSync）
  │     ├─ 发射'command-executed'事件
  │     └─ 返回执行计划（skills、agent、phase、enforcement、instruction）
  │
  ├─ 4. PipelineExecutor.executePipeline(ctx, userMessage, options)
  │     │
  │     ├─ 4a. _resolveCommand(ctx, userMessage)
  │     │      调用 commandRouter.isCommand() + getExecutionPlan()
  │     │      → 返回 commandPlan（含skills列表）
  │     │
  │     ├─ 4b. _matchSkills(ctx, userMessage, opts, commandPlan)
  │     │      若 commandPlan 存在：
  │     │        → 直接从 commandPlan.skills 映射为 Skill 对象
  │     │        → 跳过 SkillRouter 的语义匹配，使用命令指定的技能链
  │     │      若 commandPlan 不存在：
  │     │        → 调用 SkillRouter.match() 进行语义匹配
  │     │
  │     ├─ 4c. SkillRouter.loadL2Async(matchedSkills[0])
  │     │      加载首个匹配Skill的L2指令层
  │     │
  │     ├─ 4d. ProgrammableHookExecutor.execute('pre_tool_call', context)
  │     │      执行前置钩子（含AI服务安全检查等）
  │     │
  │     ├─ 4e. TDD门禁检查（_runPreExecutionChecks）
  │     │      验证TDD合规性
  │     │
  │     ├─ 4f. CollaborationModeRouter 选择协作模式
  │     │
  │     └─ 4g. 执行 + 后置验证
  │            执行技能 → 证据验证 → 覆盖率检查
  │
  └─ 5. 返回执行结果
```

### PhaseOrchestrator阶段验证

PhaseOrchestrator管理六阶段执行流程，定义阶段序列和转换规则。命令的`phase`字段决定了其在流程中的位置：

1. **阶段序列**：brainstorming → requirement-analysis → architecture-design → module-development → integration-testing → deployment
2. **阶段完成条件**：当前阶段的所有必需Skill执行完毕
3. **TDD门禁**：进入module-development阶段前强制检查测试覆盖率

CommandRouter通过因果总线与PhaseOrchestrator协作：命令执行时发布`{phase}-completed`因果输出，PhaseOrchestrator订阅这些信号来追踪阶段进度。

### RBACEnforcer权限检查

RBACEnforcer基于角色访问控制，对Skill执行顺序进行验证：

- **strict**级别：强制验证Agent角色是否有权执行命令指定的Skill链
- **recommended**级别：推荐验证，不阻止执行但记录警告
- **optional**级别：不进行权限检查

在PipelineExecutor的`_checkApprovalGate()`阶段，RBACEnforcer会检查当前Agent是否被授权执行命令中的技能链。若权限不足，返回`approval-blocked`状态。

### 命令路由 vs Skill路由

| 对比项 | 命令路由 | Skill路由 |
|--------|---------|----------|
| 触发方式 | 用户显式输入`/command` | 根据上下文自动匹配 |
| 技能选择 | 命令定义中显式指定skills列表 | SkillRouter语义匹配算法选择 |
| 优先级 | 命令路由优先（PipelineExecutor先检查命令） | 命令不匹配时才进入Skill路由 |
| 灵活性 | 固定技能链，用户可预测 | 动态匹配，适应上下文变化 |
| 适用场景 | 明确的工作流（如/build、/deploy） | 模糊需求、探索性任务 |

## 完整API列表

| 方法 | 返回值 | 说明 |
|------|--------|------|
| `discover()` | `Command[]` | 同步扫描.harness/commands/，加载命令定义，重建registry和aliasMap |
| `discoverAsync()` | `Promise<Command[]>` | 异步版本，使用fs.promises和parseMarkdownFileAsync |
| `resolve(input)` | `Command \| null` | 三级解析：精确→别名→斜杠前缀提取 |
| `getCommand(commandId)` | `Command \| null` | 直接从registry获取，不做别名或模糊匹配 |
| `getExecutionPlan(commandId)` | `Object \| null` | 返回命令执行计划（含skills、agent、phase、enforcement、instruction） |
| `executeCommand(commandId, context)` | `Object \| null` | 解析命令→记录执行历史→发布因果输出→触发`command-executed`事件→返回执行计划 |
| `isCommand(input)` | `boolean` | 判断输入是否为有效斜杠命令（以`/`开头且存在于registry或aliasMap） |
| `complete(partial)` | `Object[]` | Tab补全：返回以partial为前缀的命令和别名列表 |
| `fuzzyMatch(input)` | `Command \| null` | 模糊匹配，先尝试resolve()再评分 |
| `listCommands()` | `Object[]` | 列出所有命令的摘要信息（不含instruction和_filePath） |
| `getHelpText(useColor)` | `string` | 格式化帮助文本，支持ANSI彩色输出（自动检测TTY） |
| `getExecutionHistory(limit)` | `Object[]` | 获取最近N条执行记录（默认100） |
| `setCausalBus(bus)` | `void` | 注入因果数据总线 |
| `getStats()` | `Object` | 返回统计信息：totalCommands、totalAliases、commandsByPhase、executionHistorySize、causalBusConnected |

### 事件

| 事件名 | 触发时机 | 数据 |
|--------|---------|------|
| `commands-discovered` | discover/discoverAsync完成 | `{ count }` |
| `command-executed` | executeCommand调用 | 执行记录对象 |

## 路由流程

```
用户输入 → isCommand()判断 → resolve()三级解析 → 精确匹配？→ 是 → executeCommand()
                              ↓ 否
                         fuzzyMatch()模糊匹配 → 找到？→ executeCommand()
                                                   ↓ 未找到
                                              建议最接近命令
```
