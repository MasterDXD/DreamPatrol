# 核心功能-性能调优指南

## 概述

Harness Engineering 框架在设计时已考虑性能因素，包括三层缓存、防抖持久化、RAF批量渲染等机制。本指南提供运行时性能调优策略和最佳实践。

## 缓存体系

### SkillRouter 三层缓存

| 层级 | 存储 | 内容 | 默认TTL | 默认容量 |
|------|------|------|---------|---------|
| L1 | 内存 | Skill摘要（frontmatter解析结果） | 永久 | 无限制 |
| L2 | 内存 | Skill指令体（完整Markdown内容） | 30分钟 | 50条 |
| L3 | 内存 | Skill资源文件（references/目录） | 30分钟 | 50条 |

**调优建议**：
- 高频场景增大 `cacheMax`：`new SkillRouter(root, { cacheMax: 200 })`
- 长会话增大 `cacheTTL`：`new SkillRouter(root, { cacheTTL: 60 * 60 * 1000 })`
- 使用 `smartPreload()` 预加载当前阶段所需Skill
- 使用 `smartPreloadByPhase('module-development')` 按阶段预加载

### match() 路由缓存

`match()` 方法内置路由结果缓存，相同查询参数（agent + messageLength + completedSkills）直接返回缓存结果。

**缓存失效条件**：
- `discover()` 被调用（Skill文件变更）
- `shutdown()` 被调用

### SessionManager getStats() 缓存

`getStats()` 内置1秒TTL缓存，避免高频调用时重复计算。

## 内存优化

### SessionManager 防抖持久化

- 写操作默认200ms防抖，合并多次写入为一次磁盘IO
- `create()` 使用立即写入（`immediate=true`）
- 其他操作（`completeSkill`、`addTokenUsage`等）使用防抖写入

**调优建议**：
- 进程退出前必须调用 `shutdown()` 或 `flush()` 确保数据落盘
- 使用 `registerShutdownHooks()` 自动注册SIGINT/SIGTERM处理

### Session 容量控制

| 参数 | 默认值 | 说明 |
|------|--------|------|
| MAX_SESSIONS | 100 | 最大活跃会话数 |
| SESSION_TTL_MS | 24h | 会话TTL |
| completedSkills上限 | 500 | 超出裁剪到400 |
| agentHistory上限 | 500 | 超出裁剪 |
| convergenceHistory上限 | 500 | 超出裁剪到400 |

### get() 返回值优化

`get()` 返回会话对象的直接引用（非深拷贝），减少GC压力。如需安全隔离，调用方应自行拷贝。

- 状态变更先收集到渲染队列
- 下一个动画帧统一执行DOM更新
- 避免频繁重排重绘

## 常见性能问题排查

### 1. match() 响应慢
- 检查是否调用了 `discover()` 导致缓存失效
- 检查 `completedSkills` 列表是否过长
- 考虑增大 `cacheMax`

### 2. SessionManager 写入频繁
- 检查是否有高频 `addTokenUsage()` 调用
- 防抖机制会自动合并，无需手动优化
- 确保进程退出前调用 `flush()`

### 3. 内存持续增长
- 检查会话数量是否超过 `MAX_SESSIONS`
- 检查 `agentHistory` 和 `convergenceHistory` 是否正常裁剪
- 使用 `getStats()` 监控活跃会话数

### 4. Dashboard 加载慢
- 检查API缓存TTL配置
- 确认RAF批量渲染正常工作
- 检查WebSocket连接是否正常建立

## 并发控制调优

### ConcurrencyController 配置参数

ConcurrencyController 采用信号量式并发限制，控制同时执行的任务数量。

| 参数 | 默认值 | 说明 |
|------|--------|------|
| maxConcurrent | 6 | 最大并发任务数 |
| maxQueue | 100 | 最大等待队列长度 |
| leaseTimeoutMs | 300000 (5分钟) | 任务租约超时，超时自动释放槽位 |
| acquireTimeout | 60000 (1分钟) | 等待队列中的获取超时 |

### 使用模式

**手动模式（acquire/release）**：适用于需要精细控制生命周期的场景。

```javascript
const cc = new ConcurrencyController(10, 200, { leaseTimeoutMs: 10 * 60 * 1000 });
const acquired = await cc.acquire('task-1', { priority: 'high' });
try {
  await doWork();
} finally {
  cc.release('task-1');
}
```

**自动模式（run）**：适用于一次性任务，自动获取和释放槽位。

```javascript
const cc = new ConcurrencyController(8);
const result = await cc.run('task-2', async () => {
  return await computeResult();
});
```

### 调优建议

| 场景 | maxConcurrent | maxQueue | leaseTimeoutMs | 说明 |
|------|---------------|----------|----------------|------|
| CPU密集型 | CPU核心数 | 50 | 10分钟 | 避免过度调度导致上下文切换 |
| IO密集型 | CPU核心数×2~4 | 200 | 5分钟 | IO等待时释放CPU给其他任务 |
| 混合负载 | CPU核心数×2 | 100 | 5分钟 | 平衡CPU和IO利用率 |
| 低延迟优先 | 4 | 20 | 2分钟 | 快速拒绝超载请求，避免队列堆积 |

- 监听 `rejected` 事件跟踪被拒绝的任务，调整 `maxQueue` 避免静默丢弃
- 监听 `lease-expired` 事件检测任务泄漏（忘记 release 的场景）
- 使用 `getStats()` 实时监控并发利用率：`availableSlots` 持续为 0 说明需要增大 `maxConcurrent`
- 使用 `getRunningTasks()` 检查长时间运行的任务，排查租约超时原因

### 健康检查

```javascript
const cc = new ConcurrencyController(6);
if (!cc.isHealthy()) {
  console.warn('并发控制器过载：运行数已达上限且队列非空');
}
```

## EventBus 性能优化

### EventBus 配置参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| maxListeners | 50 | 每个事件最大监听器数 |
| maxHistory | 1000 | 事件历史最大条目数（BoundedArray） |
| maxMiddleware | 50 | 最大中间件数量 |

### 事件处理流程

```
emit(event, data)
  → 存入历史（BoundedArray，FIFO淘汰）
  → 中间件链顺序执行（异常不中断）
  → 分发给所有监听器（异常不中断）
```

### 调优建议

**1. 控制历史容量**

事件历史使用 BoundedArray 存储，默认容量 1000。高频事件场景下应适当增大：

```javascript
const bus = new EventBus({ maxHistory: 5000 });
```

低频事件场景下可减小以节省内存：

```javascript
const bus = new EventBus({ maxHistory: 200 });
```

**2. 中间件性能**

中间件在每次 `emit()` 时同步执行，应保持轻量：

- 避免在中间件中执行IO操作
- 过滤无关事件时尽早返回
- 中间件异常不会阻断事件分发，但会产生 `middleware-error` 事件

```javascript
bus.use((event, data) => {
  if (!event.startsWith('agent:')) return;
  lightweightFilter(data);
});
```

**3. 命名空间隔离**

使用 `createNamespace()` 避免事件名冲突，同时便于按模块清理监听器：

```javascript
const ns = bus.createNamespace('deepening');
ns.emit('converged', { taskId: 't1' });
ns.removeAllListeners();
```

**4. 异步等待优化**

`onceAsync()` 支持超时机制，默认使用 `DEFAULT_REQUEST_TIMEOUT_MS`（30秒）：

```javascript
const { timedOut, data } = await bus.onceAsync('phase:complete', 5000);
if (timedOut) {
  console.warn('等待事件超时');
}
```

**5. 监听器泄漏检测**

设置合理的 `maxListeners`，超出时 Node.js 会发出警告。如果预期监听器数量较多，主动调大：

```javascript
const bus = new EventBus({ maxListeners: 100 });
```

## WebSocket 性能

### WebSocketHandler 配置参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| HEARTBEAT_INTERVAL | 30000 (30秒) | 心跳Ping间隔 |
| MAX_PAYLOAD_SIZE | 1MB (1048576) | 单帧最大负载 |
| MAX_FRAME_BUFFER_SIZE | 1MB | 帧缓冲区最大容量 |
| MAX_CLIENTS | 50 | 最大同时连接数 |
| MAX_FRAMES_PER_DATA | 1000 | 单次data事件最大帧数 |
| WS_MESSAGE_RATE_LIMIT | 30 | 消息速率限制（条/窗口） |
| WS_MESSAGE_RATE_WINDOW | 1000 (1秒) | 速率限制窗口 |

### 安全特性

- **认证**：SHA-256 Token + `timingSafeEqual` 防时序攻击
- **Origin校验**：生产环境强制校验，开发环境允许本地连接
- **速率限制**：30条/秒/客户端，超出断开连接
- **负载保护**：单帧超过 1MB 关闭连接（状态码 1009）
- **帧数保护**：单次 data 超过 1000 帧关闭连接（状态码 1002）

### 调优建议

**1. 心跳间隔**

| 场景 | 建议间隔 | 说明 |
|------|---------|------|
| 局域网/低延迟 | 15秒 | 快速检测断连 |
| 公网/一般场景 | 30秒（默认） | 平衡检测速度和开销 |
| 高延迟/移动端 | 60秒 | 减少误判断连 |

心跳超时判定：连续 5 次心跳未响应（`HEARTBEAT_INTERVAL × 5`）或帧缓冲区滞留超过 5 个心跳周期，判定为死连接。

**2. 连接数管理**

默认最大 50 个连接。生产环境根据并发用户数调整：

```javascript
const handler = new WebSocketHandler({
  authToken: process.env.WS_AUTH_TOKEN,
  allowedOrigins: ['https://dashboard.example.com'],
});
```

当连接数达到 `MAX_CLIENTS` 时，新连接收到 429 (Too Many Connections) 响应。

**3. 消息大小优化**

- 单条消息建议控制在 64KB 以内，避免触发帧缓冲区拼接
- 大数据分片发送，利用 JSON 结构的 `chunk` 字段
- `broadcast()` 发送前预序列化，所有客户端共享同一帧缓冲区

**4. 广播性能**

`broadcast()` 对所有活跃客户端写入同一帧数据，写入失败的客户端自动清理：

```javascript
handler.broadcast('agent-update', { agentId: 'lead', status: 'running' });
```

**5. 健康检查**

```javascript
if (!handler.isHealthy()) {
  console.warn('WebSocket连接数已达上限');
}
console.log('当前连接数:', handler.clientCount);
```

## 深化推理缓存

### DeepeningCache 配置参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| maxSize | 1000 | 缓存最大条目数（BoundedMap） |

### 质量感知缓存策略

DeepeningCache 与普通缓存的关键区别：**覆盖时优先保留高质量评分的条目**。

```
store(task, result, { qualityScore: 0.85 })
  → 键已存在且旧评分 ≥ 0.85 → 保留旧条目（返回 true）
  → 键已存在且旧评分 < 0.85 → 替换为新条目
  → 键不存在 → 直接存储
```

### 缓存键优化

缓存键使用 `WeakMap` 缓存已序列化的结果，避免对同一任务对象重复调用 `JSON.stringify()`：

```javascript
const task = { type: 'deepen', phase: 'refinement', depth: 3 };
cache.store(task, result, { qualityScore: 0.9 });
cache.retrieve(task);
```

**注意**：`WeakMap` 要求键为对象，原始类型（string/number）作为任务描述符时无法利用键缓存。

### 调优建议

| 场景 | maxSize | 说明 |
|------|---------|------|
| 少量深度任务 | 200 | 任务种类少，缓存命中率高 |
| 大量浅层任务 | 2000 | 任务种类多，需要更大容量 |
| 长时间运行 | 1000（默认） | 平衡内存和命中率 |

- 使用 `getStats()` 监控命中率，低于 30% 时考虑增大 `maxSize`
- 使用 `invalidateByPattern({ agentId })` 按Agent批量失效，避免全量清空
- 淘汰回调（BoundedMap `onEvict`）自动递增 `_evictions` 计数，无需手动追踪

```javascript
const cache = new DeepeningCache({ maxSize: 2000 });
const stats = cache.getStats();
console.log('命中率:', (stats.hitRate * 100).toFixed(1) + '%');
console.log('淘汰数:', stats.evictions);
console.log('当前条目:', stats.size);
```

## LRU/TTL 缓存调优

### 缓存组件选择指南

| 组件 | 淘汰策略 | TTL支持 | 容量限制 | 适用场景 |
|------|---------|---------|---------|---------|
| LRUCache | LRU（最近最少使用） | 无 | maxSize=50 | 无过期需求的固定容量缓存 |
| TTLCache | 最早过期优先 | 有（defaultTTL=60s） | maxSize=1000 | 需要自动过期的时效性缓存 |
| BoundedMap | FIFO（最早插入） | 无 | maxSize（必填） | 有界映射，需要淘汰回调 |
| BoundedArray | FIFO/LRU | 无 | maxSize（1~1000000） | 有界数组，事件历史等序列数据 |

### LRUCache 调优

```javascript
const cache = new LRUCache(200);
cache.set('skill:code-review', skillData);
const data = cache.get('skill:code-review');
```

| 参数 | 默认值 | 调优建议 |
|------|--------|---------|
| maxSize | 50 | 高频访问场景增大到 200~500；低频场景保持默认 |

- `get()` 操作自动将条目移至最近位置（Map插入序），O(1) 复杂度
- `set()` 容量满时淘汰 Map 中第一个键（最久未访问），O(1) 复杂度
- 不支持 TTL，需要手动 `delete()` 或 `clear()`

### TTLCache 调优

```javascript
const cache = new TTLCache({
  defaultTTL: 5 * 60 * 1000,
  maxSize: 500,
  cleanupInterval: 60 * 1000,
});
cache.set('api:overview', data);
cache.set('api:agents', data, 10 * 60 * 1000);
```

| 参数 | 默认值 | 调优建议 |
|------|--------|---------|
| defaultTTL | 60000 (1分钟) | API缓存 5~10分钟；配置缓存 30分钟 |
| maxSize | 1000 | 根据键空间大小调整 |
| cleanupInterval | 0（禁用） | 大量条目时设为 30~60秒，避免惰性删除堆积 |

**过期策略**：

- **惰性删除**（默认）：`get()`/`has()` 时检查过期，零开销但可能堆积过期条目
- **定时清理**（可选）：设置 `cleanupInterval` 后定期扫描，内存更紧凑但增加CPU开销
- **淘汰策略**：容量满时淘汰最早过期的条目（非LRU）

**统计监控**：

```javascript
const { hits, misses, expired, evicted, size } = cache.stats;
console.log('命中率:', (hits / (hits + misses) * 100).toFixed(1) + '%');
console.log('过期数:', expired);
console.log('淘汰数:', evicted);
```

**工具方法**：

```javascript
TTLCache.isEntryExpired(entry);
TTLCache.computeExpiresAt(60000);
TTLCache.isTimestampExpired(timestamp, 60000);
cache.getRemainingTTL('key');
cache.refresh('key');
cache.purgeExpired();
```

## 内存管理最佳实践

### BoundedMap 使用建议

BoundedMap 提供固定容量上限的 Map 封装，容量满时按 FIFO 淘汰最早插入的条目。

```javascript
const map = new BoundedMap(500, {
  onEvict: (key, value) => {
    debug('BoundedMap', 'evicted', { key });
  },
});
```

| 场景 | 建议容量 | 说明 |
|------|---------|------|
| Agent状态存储 | 100 | Agent数量有限 |
| 缓存条目索引 | 500~2000 | 根据键空间调整 |
| 事件元数据 | 1000（默认） | 平衡内存和覆盖率 |

- 利用 `onEvict` 回调记录淘汰事件，辅助容量规划
- `evictedCount` 属性追踪累计淘汰数，持续增长说明容量不足
- 不支持 TTL，需要过期的场景使用 TTLCache

### BoundedArray 使用建议

BoundedArray 提供固定容量的环形缓冲区，支持 FIFO 和 LRU 两种淘汰策略。

```javascript
const fifo = new BoundedArray(1000);
const lru = new BoundedArray(500, { strategy: 'lru', onEvict: (item) => {} });
```

| 策略 | 适用场景 | 性能特征 |
|------|---------|---------|
| FIFO（默认） | 事件历史、日志缓冲 | O(1) push，无额外内存 |
| LRU | 热点数据缓存、访问频率差异大 | push 需查找最久未访问，额外 Map 存储访问时间 |

- FIFO 策略下 `push()` 为 O(1)，LRU 策略下 `push()` 需遍历查找最久未访问元素
- LRU 策略使用 `touch(index)` 更新访问时间，支持手动标记热点
- 容量范围 1~1000000，超出抛出 `INVALID_INPUT` 错误
- `toArray()`/`slice()`/`filter()` 等方法会导出为普通数组，大数据量时注意内存峰值

### GC 优化建议

**1. 避免频繁创建临时对象**

```javascript
const cache = new LRUCache(100);
for (let i = 0; i < 10000; i++) {
  cache.set('key-' + i, { data: new ArrayBuffer(1024) });
}
```

上述代码在容量满后每次 `set()` 都会淘汰旧条目，产生GC压力。应预评估容量需求。

**2. 及时释放大对象**

```javascript
cache.shutdown();
map.shutdown();
arr.shutdown();
```

`shutdown()` 清空内部存储并释放引用，允许 GC 回收大对象。

**3. 使用 Bounded 容器替代无界数组**

```javascript
const history = new BoundedArray(1000);
history.push(event);
```

替代 `const history = []; history.push(event);`，避免数组无限增长导致内存泄漏。

**4. 监控淘汰率**

```javascript
const evictionRate = map.evictedCount / totalOperations;
if (evictionRate > 0.3) {
  console.warn('淘汰率过高，考虑增大容量');
}
```

### 缓存策略

静态文件服务根据文件类型自动设置 `Cache-Control`：

| 文件类型 | Cache-Control | 说明 |
|---------|---------------|------|
| HTML / sw.js | `max-age=0, no-cache` | 每次验证 freshness |
| 字体/图片（woff/woff2/png/svg/webp/ico） | `public, max-age=31536000, immutable` | 永久缓存（内容哈希） |
| 其他静态资源（生产环境） | `public, max-age=86400, stale-while-revalidate=60` | 缓存1天，后台重新验证 |
| 所有资源（开发环境） | `no-cache, no-store, must-revalidate` | 禁用缓存 |

### 条件缓存机制

- **ETag**：基于文件大小 + 修改时间的 SHA-256 哈希（前16字符）
- **If-None-Match**：匹配时返回 304 Not Modified
- **If-Modified-Since**：匹配时返回 304 Not Modified
- **Range请求**：支持 HTTP 206 Partial Content，适用于大文件断点续传

### 压缩策略

| 参数 | 默认值 | 说明 |
|------|--------|------|
| COMPRESSION_THRESHOLD_BYTES | 512 | 低于此值不压缩 |
| MAX_COMPRESS_SIZE | 1MB | 超过此值不压缩 |
| compressTimeoutMs | 3000 | 压缩超时回退为未压缩 |

**压缩优先级**：brotli > gzip > deflate

```javascript
compressResponse(req, res, body, headers, 200, 5000);
```

**同步压缩**（适用于小文件）：

```javascript
const result = compressBody(body, acceptEncoding);
if (result) {
  headers['Content-Encoding'] = result.encoding;
  headers['Content-Length'] = String(result.data.length);
  res.writeHead(200, headers);
  res.end(result.data);
}
```

### 调优建议

- **增大路径缓存**：文件数超过 100 时，修改 `_REALPATH_CACHE_MAX` 减少磁盘IO
- **压缩超时**：大响应体（接近 1MB）增大 `compressTimeoutMs` 到 5000ms
- **流式传输**：大文件自动使用 `createReadStream().pipe(res)`，避免一次性加载到内存
- **请求中断处理**：`req.on('close', () => stream.destroy())` 防止客户端断开后继续读取文件
