# 核心功能-团队编程模式实现方案

## 概述
本文档定义类似Claude Code的团队编程模式的具体实现方案（v2.7.122），涵盖协作流程设计、实时代码共享、多人同步编辑、代码审查流程、权限管理和版本控制六大核心模块。v2.7新增目标执行引擎、深化推理系统、5种协作模式路由、子Agent并行执行、生成器验证器等核心能力。

## 核心功能
1. **协作流程引擎**：Agent间结构化消息传递与任务自动流转（含Skill自动路由+5种协作模式）
2. **实时代码共享**：基于共享工作区的代码状态同步
3. **多人同步编辑**：基于操作转换(OT)的并发编辑与冲突解决
4. **代码审查流水线**：多级审查 + TDD门禁 + verification验证 + 生成器验证器 + 自动化质量门禁
5. **权限管理矩阵**：细粒度RBAC权限与动态授权 + 审计日志链式哈希
6. **版本控制策略**：代码快照、分支管理与自动回滚
7. **目标执行引擎**（v2.7新增）：长期目标自动分解、自主迭代收敛、暂停/恢复/取消
8. **深化推理系统**（v2.7新增）：多轮迭代深化、质量评分、收敛检测、21个深化子模块
9. **子Agent并行执行**（v2.7新增）：并行生成、隔离上下文、模型解析、搜索缓存

## 实现原理

### 1. 协作流程设计

#### 1.1 Agent间消息传递协议
```json
{
  "message_id": "msg-xxx",
  "timestamp": "2026-04-10T14:30:00Z",
  "from": "task-worker-1",
  "to": "domain-analyst-1",
  "type": "task_submit|review_request|review_result|status_update|alert",
  "priority": "critical|high|normal|low",
  "payload": {
    "task_id": "TASK-101",
    "content": "..."
  },
  "requires_ack": true,
  "ack_timeout": "5m"
}
```

#### 1.2 任务状态机（v2.0）
```
Created → Assigned → SkillMatched → InProgress(TDD) → Verifying → ReviewPending → Reviewing
    ↑                                                                          |
    |          Rejected ←──────────────────────────────────────────────────────┘
    |                                                                          |
    └──────────────────────────────────────────────────────────────────────────┘
                                                          ↓ Approved
                                                    Completed
```

**v2.0新增状态**：
- **SkillMatched**：Skill自动路由引擎匹配并激活相关Skill
- **InProgress(TDD)**：开发任务必须在TDD门禁下执行（RED→GREEN→REFACTOR）
- **Verifying**：执行verification-before-completion验证，提供完成证据

#### 1.3 消息总线架构
- **发布-订阅模式**：Agent通过消息总线发布状态变更，相关Agent自动订阅
- **点对点模式**：直接向指定Agent发送任务指令和审核请求
- **广播模式**：Team Lead向所有Agent广播全局决策和进度更新
- **消息持久化**：所有消息写入`.harness/sessions/`确保可追溯

#### 1.4 技术实现路径
| 组件 | 实现方式 | 说明 |
|------|----------|------|
| 消息总线 | 内存事件队列 + 文件持久化 | Agent间通过JSON消息通信 |
| 状态存储 | `.harness/sessions/` + `.harness/checkpoints/` | 任务状态和上下文持久化 |
| 调度器 | Team Lead Agent内置 | 任务分配、依赖解析、优先级排序 |

### 2. 实时代码共享机制

#### 2.1 共享工作区模型
```
.harness/workspace/
├── staging/              # 暂存区：Agent提交的待审核代码
│   ├── TASK-101/         # 按任务ID组织
│   │   ├── meta.json     # 提交元数据（Agent、时间、变更说明）
│   │   └── changes/      # 变更文件
│   │       ├── src/main.py
│   │       └── tests/test_main.py
├── shared/               # 共享区：已审核通过的代码
│   └── src/              # 项目源码最新状态
└── locks/                # 锁区：文件级编辑锁
    └── src/main.py.lock  # 锁文件（Agent ID + 过期时间）
```

#### 2.2 代码共享流程
1. **声明意图**：Worker向Team Lead声明要编辑的文件列表
2. **获取锁**：Team Lead检查文件锁状态，无冲突则授权
3. **本地编辑**：Worker在staging区编辑代码
4. **提交变更**：Worker将变更提交到staging区，附带变更说明
5. **审核合并**：Analyst审核通过后，从staging合并到shared
6. **广播通知**：合并后通知所有Agent更新本地缓存

#### 2.3 上下文同步策略
- **增量同步**：只传递变更的diff，不传递完整文件
- **变更日志**：`.harness/workspace/changelog.json` 记录所有变更
- **按需拉取**：Agent只在需要时拉取最新的shared代码
- **冲突检测**：合并前自动检测staging与shared的diff冲突

#### 2.4 技术实现路径
| 组件 | 实现方式 | 说明 |
|------|----------|------|
| 共享工作区 | 文件系统 + JSON元数据 | staging/shared/locks三区模型 |
| 变更追踪 | unified diff格式 | 记录每次变更的增删改 |
| 锁管理 | 文件锁 + 过期机制 | 防止并发编辑冲突 |

### 3. 多人同步编辑功能

#### 3.1 操作转换(OT)模型
```json
{
  "operation_id": "op-xxx",
  "agent": "task-worker-1",
  "file": "src/main.py",
  "type": "insert|delete|replace",
  "position": {"line": 10, "col": 5},
  "content": "def new_function():",
  "timestamp": "2026-04-10T14:30:00.123Z",
  "base_version": 3
}
```

#### 3.2 并发编辑冲突解决
```
场景：Worker-A 和 Worker-B 同时编辑 src/main.py

1. 预防策略（优先）：
   - 文件级锁：同一文件同一时间只允许一个Agent编辑
   - Team Lead调度：将编辑同一文件的任务串行化

2. 检测策略（备用）：
   - 版本号检测：提交时检查base_version是否与当前版本一致
   - 不一致 → 触发合并流程

3. 合并策略：
   - 非重叠变更：自动合并（不同区域修改）
   - 重叠变更：标记冲突，由Domain Analyst裁决
   - 冲突标记格式：
     <<<<<<< task-worker-1
     Worker-1的代码
     =======
     Worker-2的代码
     >>>>>>> task-worker-2
```

#### 3.3 编辑锁协议
```json
{
  "lock_id": "lock-xxx",
  "file": "src/main.py",
  "agent": "task-worker-1",
  "acquired_at": "2026-04-10T14:30:00Z",
  "expires_at": "2026-04-10T14:50:00Z",
  "task_id": "TASK-101",
  "auto_release": true
}
```

- 锁超时默认20分钟（与task_timeout一致）
- 锁超时后自动释放，其他Agent可获取
- 任务完成后自动释放锁
- Team Lead可强制释放锁

#### 3.4 技术实现路径
| 组件 | 实现方式 | 说明 |
|------|----------|------|
| 编辑锁 | `.harness/workspace/locks/` 文件 | 文件级互斥锁 |
| 冲突检测 | base_version比对 | 提交时检查版本一致性 |
| 自动合并 | diff3算法 | 非重叠变更自动合并 |
| 冲突裁决 | Domain Analyst人工处理 | 重叠变更标记后由分析师决定 |

### 4. 代码审查流程

#### 4.1 多级审查流水线（v2.0 — 含TDD门禁和verification验证）
```
Worker提交代码
    ↓
[TDD门禁检查] ─── 无失败测试先行 → 返回Worker重做TDD
    ↓ 通过
[自动检查门禁] ─── 不通过 → 返回Worker修改
    ↓ 通过
[verification-before-completion] ─── 无完成证据 → 返回Worker补充证据
    ↓ 通过
[Domain Analyst审核] ─── 不通过 → 返回Worker修改
    ↓ 通过
[QA测试验证] ─── 不通过 → 返回Worker修改
    ↓ 通过
[Team Lead终审] ─── 不通过 → 返回对应环节
    ↓ 通过
合并到shared工作区
```

**v2.0新增门禁**：
- **TDD门禁**：检查所有实现代码是否有对应的失败测试先行，无测试则拒绝
- **verification验证**：要求提供测试通过、Lint零错误、覆盖率≥80%等实际证据

#### 4.2 自动检查门禁（v2.0 — 含TDD检查）
```json
{
  "gate_id": "gate-auto",
  "checks": [
    {"name": "tdd_compliance", "pass": true, "details": "all implementation has failing test first"},
    {"name": "lint", "pass": true, "details": "0 errors, 2 warnings"},
    {"name": "type_check", "pass": true, "details": "all types valid"},
    {"name": "unit_test", "pass": true, "details": "12/12 passed"},
    {"name": "security_scan", "pass": true, "details": "no secrets found"},
    {"name": "coverage", "pass": true, "details": "85% (threshold: 80%)"},
    {"name": "verification_evidence", "pass": true, "details": "all evidence items provided"}
  ],
  "overall": "pass",
  "blocking_issues": 0
}
```

#### 4.3 审查报告格式
```json
{
  "review_id": "rev-xxx",
  "task_id": "TASK-101",
  "reviewer": "domain-analyst-1",
  "verdict": "approve|reject|request_changes",
  "items": [
    {
      "file": "src/main.py",
      "line": 42,
      "severity": "blocking|major|minor|suggestion",
      "comment": "缺少空指针检查",
      "suggestion": "添加 if data is None: return"
    }
  ],
  "summary": "整体逻辑正确，需补充边界检查"
}
```

#### 4.4 技术实现路径
| 组件 | 实现方式 | 说明 |
|------|----------|------|
| 自动门禁 | Hook机制 + lint/test工具 | pre_task_submit Hook触发 |
| 人工审核 | Domain Analyst Agent | 基于code-review Skill执行 |
| 审查报告 | JSON格式 + Markdown可读版 | 存储在staging区 |
| 合并操作 | 文件复制 + changelog更新 | 审核通过后自动执行 |

### 5. 权限管理系统

#### 5.1 RBAC权限矩阵
| 资源/操作 | Team Lead | Domain Analyst | Task Worker | QA | DevOps |
|-----------|-----------|----------------|-------------|-----|--------|
| 读取任意文件 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 写入src/ | ✅ | ✅ | ✅（仅staging） | ❌ | ✅ |
| 写入docs/ | ✅ | ✅ | ✅（仅staging） | ✅（仅测试报告） | ❌ |
| 删除文件 | ⚠️需确认 | ❌ | ❌ | ❌ | ⚠️需确认 |
| 修改.harness/ | ✅ | ❌ | ❌ | ❌ | ❌ |
| 合并到shared | ✅ | ✅ | ❌ | ❌ | ✅ |
| 生产部署 | ⚠️需确认 | ❌ | ❌ | ❌ | ⚠️需确认 |
| 预算调整 | ⚠️需确认 | ❌ | ❌ | ❌ | ❌ |
| 强制释放锁 | ✅ | ❌ | ❌ | ❌ | ❌ |

#### 5.2 动态授权流程
```
Agent请求操作
    ↓
权限检查（基于config.json agent_permissions）
    ↓
不在权限列表 → 拒绝 + 记录审计日志
    ↓
在权限列表但需确认 → 暂停 + 通知用户
    ↓
在权限列表且无需确认 → 执行 + 记录审计日志
```

#### 5.3 权限配置扩展
```json
{
  "resource_permissions": {
    "src/": {
      "read": ["all"],
      "write_staging": ["task-worker", "domain-analyst", "devops-engineer"],
      "write_shared": ["domain-analyst", "team-lead", "devops-engineer"],
      "delete": ["team-lead"]
    },
    "docs/": {
      "read": ["all"],
      "write": ["domain-analyst", "task-worker", "quality-assurance"],
      "delete": ["team-lead"]
    },
    ".harness/": {
      "read": ["team-lead"],
      "write": ["team-lead"],
      "sessions_write": ["all"],
      "checkpoints_write": ["all"]
    }
  }
}
```

#### 5.4 技术实现路径
| 组件 | 实现方式 | 说明 |
|------|----------|------|
| 权限存储 | config.json + 资源权限扩展 | 声明式权限配置 |
| 权限检查 | pre_tool_call Hook | 每次操作前自动校验 |
| 确认机制 | 用户交互Hook | 敏感操作暂停等待用户确认 |
| 审计追踪 | 审计日志JSON | 所有操作记录可追溯 |

### 6. 版本控制策略

#### 6.1 代码快照机制
```json
{
  "snapshot_id": "snap-xxx",
  "created_at": "2026-04-10T14:30:00Z",
  "trigger": "checkpoint|phase_complete|manual",
  "phase": "module-development",
  "files": {
    "src/main.py": "sha256:abc123...",
    "src/utils.py": "sha256:def456..."
  },
  "metadata": {
    "completed_tasks": ["TASK-101", "TASK-102"],
    "test_results": "all_passed",
    "token_usage": 150000
  }
}
```

#### 6.2 分支策略
```
main（shared工作区，始终可部署）
  ├── feature/TASK-101（Worker-1的开发分支）
  ├── feature/TASK-102（Worker-2的开发分支）
  └── hotfix/BUG-003（紧急修复分支）
```

- 每个任务创建一个feature分支（对应staging区）
- 开发完成后通过审查流水线合并到main
- 紧急修复走hotfix流程，优先审查
- 分支命名规范：`feature/TASK-XXX` 或 `hotfix/BUG-XXX`

#### 6.3 回滚策略
```
触发回滚条件：
1. 集成测试失败 → 回滚到最近通过的Checkpoint
2. 生产环境异常 → 回滚到上一个稳定快照
3. 用户手动触发 → 回滚到指定快照

回滚流程：
1. 停止所有正在进行的任务
2. 从目标快照恢复所有文件
3. 更新shared工作区
4. 通知所有Agent刷新上下文
5. 记录回滚原因和影响范围
```

#### 6.4 变更日志
```json
{
  "changelog": [
    {
      "version": 3,
      "timestamp": "2026-04-10T14:30:00Z",
      "agent": "task-worker-1",
      "task_id": "TASK-101",
      "action": "merge",
      "files_changed": ["src/main.py", "tests/test_main.py"],
      "review_id": "rev-xxx",
      "previous_version": 2
    }
  ]
}
```

#### 6.5 技术实现路径
| 组件 | 实现方式 | 说明 |
|------|----------|------|
| 快照 | 文件复制 + SHA256校验 | 每个Checkpoint包含完整快照 |
| 分支 | staging区子目录 | 每个任务独立staging目录 |
| 回滚 | 快照恢复 + 文件覆盖 | 从Checkpoint恢复全部文件 |
| 变更日志 | changelog.json | 线性版本历史 |

## 高效沟通与协作保障

### 信息同步机制
1. **消息总线**：所有Agent通过统一消息总线通信，确保信息不丢失
2. **状态广播**：关键状态变更（任务完成、代码合并、冲突发生）自动广播
3. **上下文共享**：通过CLAUDE.md注入和Session管理，所有Agent共享项目知识
4. **变更通知**：代码合并后自动通知相关Agent刷新本地缓存

### 代码质量保障
1. **自动门禁**：lint + 类型检查 + 单元测试 + 安全扫描，不通过不允许提交
2. **多级审查**：自动检查 → Analyst审核 → QA验证 → Lead终审
3. **测试覆盖**：要求80%以上测试覆盖率
4. **安全扫描**：检测硬编码密钥、注入风险、权限越界

### 开发效率保障
1. **并行开发**：不同Agent编辑不同文件时完全并行
2. **自动合并**：非冲突变更自动合并，减少人工干预
3. **快速回滚**：Checkpoint + 快照机制，5分钟内恢复到任意版本
4. **增量同步**：只传递diff，减少Token消耗和同步延迟

## 注意事项
- 文件级锁是并发安全的第一道防线，应优先使用预防策略
- 自动合并仅适用于非重叠变更，重叠变更必须人工裁决
- 权限检查必须在每次操作前执行，不可缓存权限结果
- 快照存储空间需定期清理，保留最近7天 + 每阶段一个里程碑快照
