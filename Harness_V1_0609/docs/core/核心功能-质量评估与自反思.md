## 概述

质量子系统是Harness多Agent框架的质量保障核心，由9个模块协同工作，形成"评分→反思→对抗→检测→演化→可信度→债务→效率"的完整质量闭环：

| 模块 | 职责 |
|------|------|
| **QualityScorer** | 多维度质量评分，加权计算总分与等级 |
| **SelfReflection** | 自反思机制，检测质量趋势并生成改进建议 |
| **AdversarialReview** | 对抗审查，双审查员故意寻找缺陷 |
| **DocFreshnessGuard** | 文档新鲜度守卫，检测过时文档与代码-文档不一致 |
| **SelfEvolutionGovernor** | 自演化治理器，速率受限的自我改进提案机制 |
| **FeedbackCredibility** | 反馈可信度评估器，评估反馈来源可靠性、加权聚合 |
| **AiCodeTrustScorer** | AI代码可信度评估器，7项风险指标检测，按来源追踪可信度趋势 |
| **ComprehensionDebtTracker** | 理解债务追踪器，5种债务类型×4级严重度×4种解决状态 |
| **DeliveryEfficiencyMeter** | 交付效率度量器，6阶段时间分布追踪，编码占比/AI加速比/审查瓶颈评分 |

### 协作流程

1. Agent执行任务产出结果 → **QualityScorer**对结果进行多维度评分
2. 评分结果与历史对比 → **SelfReflection**检测质量趋势，生成自反思提示
3. 关键产出需审查 → **AdversarialReview**双审查员对抗审查
4. 代码变更发生 → **DocFreshnessGuard**检测文档是否过时
5. 质量信号持续积累 → **SelfEvolutionGovernor**心跳采集→议程成熟→生成改进提案
6. AI代码产出 → **AiCodeTrustScorer**评估可信度，按来源追踪趋势
7. 理解不足被识别 → **ComprehensionDebtTracker**记录理解债务，追踪解决进度
8. 交付周期完成 → **DeliveryEfficiencyMeter**度量效率，识别瓶颈

## 核心概念

### 质量评分维度

QualityScorer定义5个评分维度，每个维度独立评分后加权汇总：

| 维度 | 权重 | 说明 |
|------|------|------|
| **completeness** | 0.25 | 完整性——结果是否覆盖需求、字段是否充分 |
| **correctness** | 0.30 | 正确性——结果是否成功、是否匹配预期输出 |
| **consistency** | 0.15 | 一致性——结果内部类型是否统一、结构是否规范 |
| **coverage** | 0.15 | 覆盖度——测试覆盖率或结果字段覆盖范围 |
| **clarity** | 0.15 | 清晰度——描述是否充分、格式是否规范 |

### 质量等级

总分经加权计算后，按阈值映射为5个等级：

| 等级 | 阈值范围 | 含义 |
|------|---------|------|
| **excellent** | ≥ 0.9 | 优秀 |
| **good** | ≥ 0.75 | 良好 |
| **acceptable** | ≥ 0.6 | 可接受 |
| **poor** | ≥ 0.4 | 较差 |
| **failing** | < 0.4 | 不合格 |

### 自反思趋势

SelfReflection通过对比前后质量分数，检测4种质量趋势：

| 趋势 | 判定条件 | 建议动作 |
|------|---------|---------|
| **improving** | delta > improvementThreshold | `continue` |
| **stable** | |delta| ≤ improvementThreshold | `deepen-analysis` |
| **degrading** | delta < -improvementThreshold | `rollback-and-revise` |
| **unknown** | 质量值为NaN或Infinity | `validate-quality-metrics` |
| **initial** | 无历史质量值 | `proceed-with-caution` |

### 文档新鲜度策略

DocFreshnessGuard对文档采用两种存活策略：

| 策略 | 适用文档 | 过期阈值 |
|------|---------|---------|
| **active** | 规格文档（specification） | 3天（SPEC_STALE_THRESHOLD_MS） |
| **passive** | 普通文档 | 7天（STALE_THRESHOLD_MS） |

## QualityScorer详解

### 模块定位

QualityScorer对Agent任务执行结果进行多维度质量评分，加权汇总后映射为等级。评分结果存入RingBuffer历史记录，并通过SignalPersistence持久化。

### 类定义

```javascript
class QualityScorer extends EventEmitter { ... }
```

通过`withShutdown`混入后导出。

### 构造函数

#### `new QualityScorer(options)`

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| `options.weights` | Object | 否 | DIMENSION_WEIGHTS | 维度权重覆盖 |
| `options.thresholds` | Object | 否 | 见下 | 等级阈值覆盖 |
| `options.maxHistory` | number | 否 | 300 | 历史记录最大条数 |
| `options.signalPersistence` | Object | 否 | null | SignalPersistence实例 |

默认阈值：

```javascript
{ excellent: 0.9, good: 0.75, acceptable: 0.6, poor: 0.4 }
```

### 核心方法

#### `score(result, task)`

对任务执行结果进行多维度质量评分。

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `result` | Object | 否 | 任务执行结果，null/非对象返回0分 |
| `task` | Object | 否 | 任务定义，含id/requirements/expectedOutput/scope |

**返回值**：`Object`

| 字段 | 类型 | 说明 |
|------|------|------|
| `total` | number | 加权总分（0~1，保留3位小数） |
| `dimensions` | Object | 各维度得分 `{ completeness, correctness, consistency, coverage, clarity }` |
| `grade` | string | 质量等级（excellent/good/acceptable/poor/failing） |
| `taskId` | string | 任务ID |
| `timestamp` | string | ISO 8601时间戳 |

评分后自动推入历史记录并触发`scored`事件。

### 维度评分算法

#### completeness（完整性）

```
基础分 = 0.3
+ min(keys.length × 0.05, 0.3)              // 结果字段数加分
+ 需求匹配加分（如有task.requirements）        // met/reqs.length × 0.7 + 0.3
+ 字符串长度加分（如result为字符串）            // long: +0.3, medium: +0.15
→ min(score, 1.0)
```

#### correctness（正确性）

```
基础分 = 0.4
+ success=true且无error/errors/failures: +0.2
- result.error存在: -0.2
- result.errors.length > 0: -0.15
- result.failures.length > 0: -0.15
+ result.valid=true: +0.15
+ result.passed=true: +0.15
+ 预期匹配（如有task.expectedOutput）: 词汇重叠率或1.0（完全匹配）
→ clamp(score, 0, 1)
```

#### consistency（一致性）

```
基础分 = 0.5
+ 值类型种类 ≤ 2: +0.2
+ 存在status字符串字段: +0.15
+ 存在metadata或context字段: +0.15
→ min(score, 1.0)
```

#### coverage（覆盖度）

```
基础分 = 0.3
+ result.coverage存在: min(result.coverage, 1.0)
+ result.tests存在: passed/tests.length
+ 其他: min(keys.length × 0.03, 0.4)
+ task.scope存在: +0.1
→ min(score, 1.0)
```

#### clarity（清晰度）

```
基础分 = 0.4
字符串结果:
  + 句数 ≥ 2: +0.2
  + 长度在50~5000之间: +0.2
  + 首字母大写: +0.1
对象结果:
  + 含description/summary键: +0.2
  + 含message字符串键: +0.15
  + 含描述性键名: +0.15
→ min(score, 1.0)
```

### 环形引用保护

权重合并使用展开运算符覆盖，不存在循环引用风险：

```javascript
this._weights = { ...DIMENSION_WEIGHTS, ...((options && options.weights) ?? {}) };
```

总分计算时对缺失维度使用`?? 0`默认值：

```javascript
total += (dimensions[dim] ?? 0) * (this._weights[dim] ?? 0);
```

最终总分经`Math.min(Math.max(total, 0), 1)`确保在[0, 1]范围内。

### 历史与统计

#### `getHistory(limit)`

获取最近N条评分记录。

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| `limit` | number | 否 | 全部 | 返回条数 |

**返回值**：`Array<Object>`

#### `getStats()`

获取评分统计信息。

**返回值**：`Object`

| 字段 | 类型 | 说明 |
|------|------|------|
| `totalScores` | number | 总评分次数 |
| `averageScore` | number | 平均分（保留3位小数） |
| `gradeDistribution` | Object | 各等级的次数分布 |

### 事件

| 事件名 | 触发时机 | 事件数据 |
|--------|---------|---------|
| `scored` | score()完成 | 评分结果对象 |

### 评分持久化机制

QualityScorer在每次`score()`调用后，若已通过`attachSignalPersistence(sp)`注入SignalPersistence实例，则自动将评分结果持久化到信号存储。持久化数据包含：

| 持久化字段 | 类型 | 说明 |
|-----------|------|------|
| `total` | number | 加权总分 |
| `grade` | string | 质量等级 |
| `dimensions` | Object | 各维度得分 |
| `taskId` | string | 任务ID |
| `timestamp` | string | ISO 8601时间戳 |

持久化信号类型为`quality`，可供SelfEvolutionGovernor心跳采集、DeepeningOrchestrator收敛检测等下游消费者订阅。持久化操作包裹在try-catch中，失败时仅输出debug日志，不影响评分主流程返回值。

### 与DeepeningOrchestrator的集成

QualityScorer是深化推理管道（DeepeningPipeline）的核心质量信号源。集成方式如下：

```
DeepeningOrchestrator
  └─ DeepeningPipeline
       └─ IterativeRefinement
            ├─ 调用 QualityScorer.score() 获取当前质量
            ├─ 对比 quality_threshold（默认0.8）
            ├─ 未达标 → 继续迭代精化
            └─ 达标 → ConvergenceDetector判定收敛
```

集成要点：

1. **质量阈值门禁**：DeepeningOrchestrator的`quality_threshold`（默认0.8）与QualityScorer的`total`分数直接比较。当`total < quality_threshold`时，IterativeRefinement继续执行精化循环
2. **收敛判定输入**：ConvergenceDetector使用QualityScorer的历史评分序列计算改进率和稳定性方差，判定是否收敛
3. **维度平衡检查**：ConvergenceDetector的`dimension_balance_threshold`（默认0.15）检查QualityScorer五维得分的标准差，确保各维度均衡而非某单一维度拉高总分
4. **早停策略**：当连续`stability_window`（默认3）次评分的方差低于`stability_variance`（默认0.01）时，即使未达`quality_threshold`也判定收敛，避免无效迭代

| 属性 | 类型 | 说明 |
|------|------|------|
| `QualityScorer.DIMENSIONS` | Object | 维度常量枚举 |
| `QualityScorer.DIMENSION_WEIGHTS` | Object | 默认维度权重 |

## SelfReflection详解

### 模块定位

SelfReflection提供Agent自反思机制，通过对比前后质量分数检测质量趋势，生成自反思检查提示，并追踪改进记录。支持4种产出类型的反思模板。

### 类定义

```javascript
class SelfReflection extends EventEmitter { ... }
```

通过`withShutdown`混入后导出。

### 构造函数

#### `new SelfReflection(options)`

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| `options.maxReflections` | number | 否 | 3 | 最大反思轮次 |
| `options.improvementThreshold` | number | 否 | 0.05 | 质量改善判定阈值 |
| `options.qualityWeights` | Object | 否 | 见下 | 反思维度权重 |
| `options.autoTriggerOnQualityDrop` | boolean | 否 | true | 质量下降时自动触发 |
| `options.persistResults` | boolean | 否 | true | 是否持久化反思结果 |
| `options.maxHistory` | number | 否 | 500 | 历史记录最大条数 |
| `options.signalPersistence` | Object | 否 | null | SignalPersistence实例 |

默认qualityWeights：

```javascript
{ completeness: 0.25, correctness: 0.30, consistency: 0.15, security: 0.15, clarity: 0.15 }
```

### 核心方法

#### `reflect(context)`

执行自反思，生成反思结果和自检查提示。

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `context.agentId` | string | 是 | Agent ID |
| `context.skillId` | string | 是 | Skill ID |
| `context.artifactType` | string | 否 | 产出类型（code/design/test/documentation），默认code |
| `context.previousQuality` | number | 否 | 前次质量分数 |
| `context.currentQuality` | number | 否 | 当前质量分数 |
| `context.dimensionScores` | Object | 否 | 各维度分数覆盖 |
| `context.result` | Object | 否 | 任务结果（用于推断维度分数） |

**返回值**：`Object`

| 字段 | 类型 | 说明 |
|------|------|------|
| `reflectionId` | string | 反思ID（refl-前缀） |
| `questions` | string[] | 反思问题列表 |
| `qualityTrend` | string | 质量趋势 |
| `recommendedAction` | string | 建议动作 |
| `selfCheckPrompt` | string | 自反思检查提示文本 |
| `dimensions` | Object | 各维度评估结果 |

### 质量趋势检测

趋势判定逻辑包含NaN保护：

```javascript
const prev = Number(reflection.previousQuality);
const curr = Number(reflection.currentQuality);
if (!Number.isFinite(prev) || !Number.isFinite(curr)) {
  reflection.qualityTrend = 'unknown';
  reflection.recommendedAction = 'validate-quality-metrics';
} else {
  const delta = curr - prev;
  if (delta < -threshold) → 'degrading' / 'rollback-and-revise'
  else if (delta > threshold) → 'improving' / 'continue'
  else → 'stable' / 'deepen-analysis'
}
```

NaN/Infinity值不会导致错误判定，而是安全降级为`unknown`趋势，建议验证质量指标。

### 反思模板

4种产出类型各有5个反思问题，最后一个问题均为"如果由另一个Agent审查，最可能被挑出的问题是什么？"：

| 产出类型 | 关注重点 |
|---------|---------|
| **code** | 边界条件、架构一致性、安全隐患、性能瓶颈、外部审查 |
| **design** | 需求覆盖、过度/不足设计、依赖合理性、可扩展性、外部审查 |
| **test** | 关键路径覆盖、用例独立性、误判风险、数据代表性、外部审查 |
| **documentation** | 实现准确性、示例充分性、术语一致性、已知限制、外部审查 |

### 维度评估

`_evaluateDimensions()`对5个反思维度进行评估，每个维度包含：

| 字段 | 类型 | 说明 |
|------|------|------|
| `score` | number | 维度分数（0~1） |
| `weight` | number | 维度权重 |
| `needsAttention` | boolean | 分数 < 0.6时为true |

维度分数来源优先级：
1. `context.dimensionScores[dim]`——显式提供
2. `_inferDimensionScore(dim, context)`——从currentQuality和result推断
3. 默认0.5

### 改进记录

#### `recordImprovement(reflectionId, improvement)`

记录一次改进。

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `improvement.dimension` | string | 否 | 改进维度，默认'general' |
| `improvement.description` | string | 否 | 改进描述 |
| `improvement.beforeScore` | number | 否 | 改进前分数，默认0 |
| `improvement.afterScore` | number | 否 | 改进后分数，默认0 |

统计信息自动更新`totalImprovements`和`avgImprovement`。

### 自动触发

#### `shouldTriggerReflection(context)`

判断是否应自动触发反思：

- 当前质量 < 前次质量 - improvementThreshold → 触发
- 证据完整度 < 0.8 → 触发
- 迭代次数 > 1 → 触发

### 证伪维度反思（falsification）

SelfReflection提供独立的证伪反思方法`falsificationReflection(output, context)`，从"此结论在什么条件下会被推翻"的视角审视产出。这是对常规反思的补充——常规反思关注"哪里做得不好"，证伪反思关注"在什么条件下整个方案会失败"。

#### `falsificationReflection(output, context)`

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `output` | string | 否 | 待证伪审视的产出内容 |
| `context` | Object | 否 | 证伪上下文信息 |

**返回值**：`Object`

| 字段 | 类型 | 说明 |
|------|------|------|
| `type` | string | 固定为`falsification_reflection` |
| `output` | string | 传入的产出内容 |
| `context` | string | 传入的上下文信息 |
| `falsificationPrompts` | string[] | 5条证伪提示 |
| `antiSycophancyCheck` | Object | 反谄媚检查（含question和required字段） |
| `timestamp` | number | 时间戳 |

5条证伪提示：

| 序号 | 提示内容 | 反思维度 |
|------|---------|---------|
| 1 | 这个结论在什么现实条件下会被证明是错误的？ | 可证伪性 |
| 2 | 支持此结论的最弱假设是什么？ | 假设脆弱性 |
| 3 | 如果此方案失败，最可能的失败模式是什么？ | 失败预判 |
| 4 | 什么可观测的信号能证明此方案不可行？ | 证伪信号 |
| 5 | 是否存在更简单的替代方案被忽略了？ | 奥卡姆剃刀 |

反谄媚检查（antiSycophancyCheck）强制要求Agent审视自身是否在附和而非质疑，`required: true`表示此项不可跳过。

#### decision反思模板

除4种标准产出类型（code/design/test/documentation）外，SelfReflection还支持`decision`类型的反思模板，该模板包含5个证伪与反谄媚维度的提示：

| 维度 | 提示内容 |
|------|---------|
| falsifiability | 这个结论在什么现实条件下会被证明是错误的？列出至少3个证伪信号 |
| assumption_validity | 这个方案依赖的关键假设是什么？哪些假设最脆弱？ |
| anti_sycophancy | 你是否在附和用户的想法而非提供真正有用的建议？如果是，请重新审视 |
| evidence_strength | 支持这个结论的证据有多强？是否有更简单的替代解释？ |
| alternative_coverage | 是否考虑了足够多的替代方案？是否遗漏了非共识但高价值的选项？ |

### 反思结果持久化

SelfReflection在每次`reflect()`调用后，若已通过`attachSignalPersistence(sp)`注入SignalPersistence实例，则自动将反思摘要持久化。持久化数据包含：

| 持久化字段 | 类型 | 说明 |
|-----------|------|------|
| `reflectionId` | string | 反思ID |
| `agentId` | string | Agent ID |
| `skillId` | string | Skill ID |
| `artifactType` | string | 产出类型 |
| `qualityTrend` | string | 质量趋势 |
| `recommendedAction` | string | 建议动作 |
| `previousQuality` | number | 前次质量分数 |
| `currentQuality` | number | 当前质量分数 |
| `timestamp` | string | ISO 8601时间戳 |

持久化信号类型为`reflection`，供SelfEvolutionGovernor心跳采集`reflection_trend`信号。当趋势为`degrading`时，Governor累积`reflection-degrading`议程项，成熟后生成`deepen-self-reflection`改进提案。

### 与DreamEngine的闭环

SelfReflection与DreamEngine形成"反思→经验提炼→知识整合"的闭环：

```
SelfReflection.reflect()
  ├─ 检测质量趋势（degrading/stable/improving）
  ├─ 生成改进建议（selfCheckPrompt）
  └─ 持久化反思信号 → SignalPersistence
       │
       ▼ (异步，会话结束或定时触发)
DreamEngine.dream()
  ├─ 回顾历史反思记录
  ├─ 提炼失败模式（degrading趋势的根因）
  ├─ 发现质量改进模式（improving趋势的成功因素）
  └─ 整合到LlmWiki知识库
       │
       ▼ (下次会话)
MemoryPrefetcher
  └─ 阶段变更/高熵信号 → 预取相关经验
       └─ 注入到SelfReflection上下文
            └─ 改进反思质量（避免重复失败模式）
```

闭环关键路径：

1. **反思信号发布**：SelfReflection将反思结果通过SignalPersistence发布，DreamEngine的DreamScheduler在会话结束或定时触发时回顾这些信号
2. **失败模式提炼**：DreamEngine从`degrading`趋势的反思记录中提炼结构化失败模式，存入LlmWiki
3. **经验预取**：MemoryPrefetcher在检测到阶段变更或高熵信号时，预取与当前任务相关的历史经验
4. **反思增强**：预取的经验注入SelfReflection的反思上下文，使反思能够参考历史失败模式，避免重复犯错

### 事件

| 事件名 | 触发时机 | 事件数据 |
|--------|---------|---------|
| `reflection-created` | reflect()完成 | `{ reflectionId, agentId, qualityTrend, recommendedAction }` |
| `improvement-recorded` | recordImprovement()完成 | `{ reflectionId, dimension }` |

### 静态属性

|------|------|------|
| `SelfReflection.REFLECTION_DIMENSIONS` | string[] | 反思维度列表 |
| `SelfReflection.REFLECTION_TEMPLATES` | Object | 各产出类型的反思问题模板 |

## AdversarialReview详解

### 模块定位

AdversarialReview实现对抗审查机制，通过两个独立审查员（reviewerA、reviewerB）对同一产出进行多轮审查，故意寻找缺陷和漏洞，直到双方达成共识或达到最大轮次。

### 类定义

```javascript
class AdversarialReview extends EventEmitter { ... }
```

通过`withShutdown`混入后导出。

### 构造函数

#### `new AdversarialReview(options)`

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| `options.maxRounds` | number | 否 | 3 | 最大审查轮次 |

### 核心方法

#### `review(subject, reviewerA, reviewerB)`

执行对抗审查。

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `subject` | Object | 是 | 待审查的产出对象 |
| `reviewerA` | Function | 是 | 审查员A，签名：`async (subject, context) => { approved, feedback, suggestions }` |
| `reviewerB` | Function | 是 | 审查员B，签名同上 |

**返回值**：`Object`

| 字段 | 类型 | 说明 |
|------|------|------|
| `consensus` | boolean | 是否达成共识（双方均approved） |
| `rounds` | number | 实际执行轮次 |
| `details` | Array | 各轮审查详情 |
| `finalFeedback` | string | 合并的最终反馈 |

### 审查流程

```
Round 1:
  reviewerA(subject, context) → { approved, feedback, suggestions }
  reviewerB(subject, context) → { approved, feedback, suggestions }
  双方approved? → consensus=true, break
  否则 → 合并feedback → context.mergedFeedback

Round 2..maxRounds:
  重复上述流程（审查员可参考前轮反馈）

未达成共识 → consensus=false, 返回所有轮次详情
```

### 安全调用

`_safeCall()`对审查员调用进行异常保护：

- 审查员抛出异常 → 返回`{ approved: false, feedback: error信息, error: true }`
- 审查员返回非对象 → 返回`{ approved: false, feedback: 'invalid result', error: true }`
- 审查员返回对象 → 标准化为`{ approved: !!approved, feedback, suggestions }`

### 超时保护

`_safeCallWithTimeout()`在`_safeCall()`基础上增加超时机制，默认超时30秒（`DEFAULT_REVIEW_TIMEOUT_MS`）。实现方式为`Promise.race`竞速：

- 审查员Promise先完成 → 正常返回审查结果
- 超时Promise先完成 → 返回`{ approved: false, feedback: 'Reviewer X timed out', error: true }`
- 超时定时器通过`timer.unref()`避免阻止进程退出
- 审查员Promise的late rejection通过`.catch()`静默吞没，避免未处理Promise拒绝

### 魔鬼代言人角色（decisionAdversarial）

`decisionAdversarial(proposal, options)`方法从多个对立角色视角生成攻击清单，是AdversarialReview的核心"魔鬼代言人"机制。不同于`review()`的双审查员模式，`decisionAdversarial()`采用预设角色视角，每个角色从不同维度攻击决策提案。

#### 内置角色定义

| 角色键 | 角色名称 | 攻击焦点 |
|--------|---------|---------|
| `cfo` | 冷静的CFO | 成本、ROI、现金流风险 |
| `investor` | 挑剔的投资人 | 市场规模、竞争壁垒、退出路径 |
| `veteran` | 行业老手 | 行业潜规则、隐性成本、监管风险 |
| `engineer` | 悲观工程师 | 技术可行性、复杂度、维护成本 |
| `ux_fanatic` | 用户体验偏执狂 | 用户学习成本、使用障碍、流失风险 |

默认参与角色为`['cfo', 'investor', 'veteran']`，可通过`options.roles`自定义。

#### 返回结构

| 字段 | 类型 | 说明 |
|------|------|------|
| `type` | string | 固定为`decision_adversarial` |
| `proposal` | string | 待审查的决策提案 |
| `attacks` | Array | 各角色攻击清单，每项含role/name/focus/challenges/falsificationSignals/prerequisites |
| `falsification` | Object | 证伪信息，含signals/experimentDesign/minimumViableExperiment |
| `antiSycophancyCheck` | Object | 反谄媚检查，含hasBiasedLanguage/hasConsensusPlatitudes/hasFalsification/hasPrerequisites |
| `timestamp` | number | 时间戳 |

### 证伪实验设计（falsificationCheck）

`falsificationCheck(conclusion, context)`方法对结论进行证伪检验，输出失败前提与最低可行实验建议。这是从波普尔证伪主义方法论出发的审查机制——不验证"结论是否正确"，而是寻找"结论在什么条件下会被推翻"。

#### 返回结构

| 字段 | 类型 | 说明 |
|------|------|------|
| `conclusion` | string | 待证伪检验的结论 |
| `context` | string | 证伪上下文信息 |
| `whyItMightNotWork` | Array | 失败原因列表 |
| `prerequisitesForSuccess` | Array | 成功前提列表 |
| `falsificationSignals` | Array | 证伪信号列表 |
| `minimumViableExperiment` | null | 最低可行实验建议（需人工填充） |
| `confidenceLevel` | string | 置信度等级，默认`unverified` |

证伪检验的三层结构：

1. **失败原因（whyItMightNotWork）**：列举结论可能失败的具体原因
2. **成功前提（prerequisitesForSuccess）**：结论成立必须满足的前提条件
3. **最低可行实验（minimumViableExperiment）**：用最小成本验证结论是否可靠的具体实验设计

### 与SelfReflection的互补关系

AdversarialReview与SelfReflection形成"自我审视 vs 外部攻击"的双重质量保障：

| 维度 | SelfReflection | AdversarialReview |
|------|---------------|-------------------|
| **视角** | 第一人称，自我审视 | 第三人称，外部攻击 |
| **目标** | 发现自身不足，改进建议 | 寻找致命缺陷，推翻方案 |
| **方法** | 质量趋势对比、维度评估 | 魔鬼代言人、证伪实验 |
| **触发时机** | 每次任务执行后自动触发 | 关键产出需审查时触发 |
| **结果** | 改进建议（可继续执行） | 通过/否决（决定是否继续） |
| **反谄媚** | 内置antiSycophancyCheck | 内置antiSycophancyCheck |

互补流程：

```
任务执行 → QualityScorer评分
  ├─ 评分 ≥ good → SelfReflection自反思 → 继续执行
  └─ 评分 < good → SelfReflection自反思 + AdversarialReview对抗审查
                     ├─ 审查通过（consensus=true）→ 采纳改进建议继续
                     └─ 审查未通过（consensus=false）→ 回滚并修订
```

两者共享反谄媚检查机制，确保Agent不会因自我确认偏误而忽视问题。SelfReflection的`falsificationReflection()`提供证伪视角的自反思，AdversarialReview的`falsificationCheck()`提供外部证伪检验，两者结合形成完整的证伪闭环。

### 事件

| 事件名 | 触发时机 | 事件数据 |
|--------|---------|---------|
| `round-complete` | 每轮审查完成 | `{ round, reviewerA, reviewerB }` |
| `review-complete` | 审查流程结束 | `{ consensus, rounds, details, finalFeedback }` |

### 静态属性

| 属性 | 类型 | 说明 |
|------|------|------|
| `AdversarialReview.DEFAULT_MAX_ROUNDS` | number | 默认最大轮次（3） |

## DocFreshnessGuard详解

### 模块定位

DocFreshnessGuard监控代码变更，自动检测与代码关联的文档是否过时。通过文件索引、代码引用提取和文件监控，实现代码-文档一致性追踪。规格文档采用更严格的存活策略和再验证机制。

### 类定义

```javascript
class DocFreshnessGuard extends EventEmitter { ... }
```

通过`withShutdown`混入后导出。

### 构造函数

#### `new DocFreshnessGuard(options)`

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| `options.projectRoot` | string | 否 | null | 项目根目录，提供时自动构建索引 |
| `options.signalPersistence` | Object | 否 | null | SignalPersistence实例 |

提供projectRoot时，构造函数即启动异步索引构建（`_buildIndexAsync`）。

### 索引构建

#### `ready`（getter）

返回索引构建的Promise，用于等待索引就绪：

```javascript
await guard.ready;
```

#### `attachProjectRoot(projectRoot)`

延迟设置项目根目录并构建索引。已设置时忽略。

### 索引结构

每个文档索引条目包含：

| 字段 | 类型 | 说明 |
|------|------|------|
| `path` | string | 相对路径 |
| `references` | string[] | 提取的代码引用列表 |
| `lastVerifiedAt` | number | 最后验证时间戳 |
| `stale` | boolean | 是否过时 |
| `staleReason` | string | 过时原因 |
| `specificationType` | string | 规格类型（requirement/architecture/interface/behavior/general） |
| `livenessPolicy` | string | 存活策略（active/passive） |
| `reverificationAttempts` | number | 再验证尝试次数 |
| `lastReverificationAt` | number | 最后再验证时间戳 |

### 代码引用提取

`_extractCodeReferences(content)`从文档内容中提取代码引用，使用5种正则模式：

| 模式 | 匹配内容 | 示例 |
|------|---------|------|
| 源文件路径 | `src/`前缀的代码文件 | `src/runtime/quality/quality-scorer.js` |
| Markdown链接 | 指向.md的链接 | `[文档](../core/example.md)` |
| 行内代码 | 反引号包裹的代码文件 | `` `utils/constants.js` `` |

`_isSpecificationDoc()`通过路径模式和内容标记检测规格文档：

- 路径匹配：`spec-`、`specification`、`requirement-`、`architecture-`、`interface-`、`design-doc`、`design-spec`
- 内容匹配：`## Specification`、`## 规格`、`## 需求规格`、`## 接口定义`、`## Interface`

`_detectSpecType()`通过关键词频率检测规格类型：requirement/architecture/interface/behavior/general。

### 文件监控

#### `startWatching()`

启动对`src/`目录的递归文件监控（`fs.watch`），仅关注代码文件扩展名（.js/.ts/.jsx/.tsx/.py/.go/.rs/.java/.c/.cpp/.h/.hpp）。

变更事件经防抖合并后处理：

```
代码变更 → _onCodeChange() → 防抖队列 → _processPendingChanges()
  → 模块名提取 → _markStaleDocs() → 持久化索引 → docs-staled事件
```

#### `stopWatching()`

停止文件监控并清除防抖定时器。

### 过时标记

`_markStaleDocs(affectedModules)`遍历文档索引，检查每个文档的代码引用是否与受影响模块匹配：

- 精确匹配：`ref === module`
- 前缀匹配：`ref.startsWith(module + '/')`
- 反向前缀：`module.startsWith(ref去掉扩展名 + '/')`

规格文档过时时额外触发`spec-stale`事件，并加入再验证队列。

### 核心方法

**返回值**：`Array<Object>` — 被标记为过时的文档列表

#### `validateFreshness()`

基于时间阈值验证所有文档新鲜度。普通文档7天、规格文档3天未验证即标记过时。规格文档加入再验证队列。

**返回值**：`Object`

| 字段 | 类型 | 说明 |
|------|------|------|
| `valid` | boolean | 是否全部新鲜 |
| `newlyStale` | number | 新增过时文档数 |
| `totalStale` | number | 总过时文档数 |

#### `markDocVerified(docPath)`

标记文档为已验证，清除过时状态。

#### `getStaleDocs()`

获取所有过时文档列表。

#### `getFreshnessStats()`

获取新鲜度统计信息。

**返回值**：`Object`

| 字段 | 类型 | 说明 |
|------|------|------|
| `totalDocs` | number | 总文档数 |
| `staleDocs` | number | 过时文档数 |
| `freshDocs` | number | 新鲜文档数 |
| `totalReferences` | number | 总引用数 |
| `freshnessRate` | number | 新鲜率（0~1） |
| `watching` | boolean | 是否正在监控 |

#### `triggerReverification(docPath)`

触发规格文档再验证。最多5次尝试，超出后拒绝。

### 持久化

## SelfEvolutionGovernor详解

### 模块定位

SelfEvolutionGovernor实现速率受限的自我改进机制。通过心跳周期采集质量、健康、因果等信号，累积观测形成议程项，议程成熟后生成改进提案。内置熔断器防止连续错误导致的失控改进。

### 类定义

```javascript

```

通过`withShutdown`混入后导出。`isHealthy()`方法定义在prototype上。

## AiCodeTrustScorer详解

### 模块定位

AiCodeTrustScorer评估AI生成代码的可信度，通过7项风险指标检测代码质量风险，按来源追踪可信度趋势，并使用指数衰减算法使历史评分随时间自然回归中性。评估结果用于决定AI代码是否可直接采纳、需人工审查或应拒绝修订。

### 类定义

```javascript
class AiCodeTrustScorer extends EventEmitter { ... }
```

通过`withShutdown`混入后导出。

### 构造函数

#### `new AiCodeTrustScorer(options)`

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| `options.thresholds` | Object | 否 | TRUST_THRESHOLDS | 信任等级阈值覆盖 |
| `options.riskIndicators` | Object | 否 | RISK_INDICATORS | 风险指标覆盖 |
| `options.maxHistory` | number | 否 | 500 | 历史记录最大条数 |
| `options.decayFactor` | number | 否 | 0.95 | 指数衰减因子 |

### 7项风险指标

AiCodeTrustScorer定义7项风险指标，每项包含权重和标签：

| 指标 | 权重 | 标签 | 检测条件 | 严重度 |
|------|------|------|---------|--------|
| **NO_TESTS** | 0.15 | `no-tests` | `hasTests === false` 或 `tests.length === 0` | 1.0 |
| **UNHANDLED_EDGE** | 0.20 | `unhandled-edge-cases` | `edgeCasesHandled === false` | 0.8 |
| **IMPLICIT_DEPS** | 0.12 | `implicit-dependencies` | `implicitDependencies === true` 或 `unlistedDeps.length > 0` | 0.7 |
| **MAGIC_VALUES** | 0.10 | `magic-values` | `magicValues === true` 或 `hardcodedValues.length > 3` | 0.6 |
| **MISSING_ERROR_HANDLING** | 0.18 | `missing-error-handling` | `errorHandlingComplete === false` | 0.9 |
| **SPEC_VIOLATION** | 0.15 | `spec-violation` | `specCompliant === false` | 0.8 |
| **CONTEXT_DRIFT** | 0.10 | `context-drift` | `contextDrift === true` 或 `driftScore > 0.3` | 0.7 |

权重总和为1.0，确保风险惩罚在合理范围内。`MISSING_ERROR_HANDLING`权重最高（0.18），因为缺少错误处理是AI代码最常见的致命缺陷；`UNHANDLED_EDGE`次之（0.20），反映AI代码对边界条件处理不足的典型问题。

### 评分算法

```
baseScore = 1.0
riskPenalty = Σ(indicator.weight × indicator.severity)  // 仅对触发的指标求和
score = clamp(baseScore - riskPenalty, 0, 1)
```

评分从满分1.0开始，每项触发的风险指标按`weight × severity`扣分。最坏情况下（7项全部触发），理论最大惩罚为`0.15×1.0 + 0.20×0.8 + 0.12×0.7 + 0.10×0.6 + 0.18×0.9 + 0.15×0.8 + 0.10×0.7 = 0.843`，最低分为`1.0 - 0.843 = 0.157`，归类为`unreliable`。

### 信任等级分类

| 等级 | 阈值 | 含义 |
|------|------|------|
| **high** | ≥ 0.8 | 高可信——可直接采纳 |
| **medium** | ≥ 0.6 | 中等可信——需仔细审查 |
| **low** | ≥ 0.4 | 低可信——建议修订 |
| **unreliable** | < 0.4 | 不可靠——应拒绝 |

### 推荐动作

| 分数范围 | 推荐动作 | 说明 |
|---------|---------|------|
| ≥ 0.8 | `accept` | 直接采纳 |
| ≥ 0.6 | `review-carefully` | 仔细审查后决定 |
| 存在severity ≥ 0.9的风险 | `reject-and-revise` | 拒绝并要求修订 |
| 其他 < 0.6 | `reject` | 直接拒绝 |

### 按来源追踪可信度趋势

#### `assessWithSource(sourceId, codeContext)`

在`assess()`基础上关联来源ID，持续追踪同一来源的可信度趋势。

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `sourceId` | string | 是 | 代码来源标识（如Agent ID、模型名称） |
| `codeContext` | Object | 是 | 代码上下文信息 |

来源追踪数据结构：

| 字段 | 类型 | 说明 |
|------|------|------|
| `score` | number | 累计平均可信度分数 |
| `samples` | number | 评估样本数 |
| `totalScore` | number | 累计总分 |
| `lastAssessedAt` | number | 最后评估时间戳 |

来源评分采用增量平均算法：每次新评估后，`totalScore += newScore`，`score = totalScore / samples`。容量上限500个来源，超出时淘汰最久未评估的来源。

#### `getSourceTrustScore(sourceId)`

获取指定来源的可信度分数，未知的来源返回0.5（中性值）。

#### `getSourceStats(sourceId)`

获取指定来源的详细统计信息。

### 指数衰减算法

#### `decaySourceScores()`

对所有来源评分执行指数衰减，使历史评分随时间自然回归中性值0.5。

```
衰减公式：
  daysSinceUpdate = (now - lastAssessedAt) / 86400000
  decay = decayFactor ^ daysSinceUpdate        // decayFactor默认0.95
  newScore = 0.5 + (currentScore - 0.5) × decay
```

衰减特性：

| 经过天数 | 衰减系数（0.95） | 分数偏移保留 |
|---------|-----------------|-------------|
| 1天 | 0.950 | 95.0% |
| 7天 | 0.698 | 69.8% |
| 14天 | 0.488 | 48.8% |
| 30天 | 0.215 | 21.5% |

衰减后自动清理：当`|score - 0.5| < 0.01`且距上次更新超过7天时，删除该来源条目，释放内存。

## ComprehensionDebtTracker详解

### 模块定位

ComprehensionDebtTracker追踪Agent对任务、需求、领域知识的理解不足——即"理解债务"。与代码技术债务不同，理解债务关注的是Agent在认知层面的缺口：需求歧义、上下文不匹配、隐含假设、规格缺口、领域知识不足。通过5种债务类型×4级严重度×4种解决状态的矩阵化管理，量化理解债务的规模和紧迫性。

### 类定义

```javascript
class ComprehensionDebtTracker extends EventEmitter { ... }
```

通过`withShutdown`混入后导出。

### 构造函数

#### `new ComprehensionDebtTracker(options)`

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| `options.criticalThreshold` | number | 否 | 0.7 | 债务评分critical级别阈值 |
| `options.highThreshold` | number | 否 | 0.5 | 债务评分high级别阈值 |

### 5种债务类型

| 类型 | 常量 | 说明 | 典型场景 |
|------|------|------|---------|
| **需求歧义** | `requirement-ambiguity` | 需求描述存在多种解读 | "优化性能"未定义指标和基线 |
| **上下文不匹配** | `context-mismatch` | Agent的上下文与任务实际需求不一致 | 使用Web API上下文处理CLI任务 |
| **隐含假设** | `implicit-assumption` | Agent基于未验证的假设做出决策 | 假设数据库字段非空、假设用户已登录 |
| **规格缺口** | `spec-gap` | 规格文档未覆盖某些场景 | 错误处理路径未在规格中定义 |
| **领域知识缺口** | `domain-knowledge-gap` | Agent缺乏完成任务所需的领域知识 | 不了解金融交易ACID要求 |

### 4级严重度

| 严重度 | 常量 | 评分 | 说明 |
|--------|------|------|------|
| **critical** | `critical` | 1.0 | 阻塞性——无法继续执行，必须立即解决 |
| **high** | `high` | 0.75 | 严重——可能导致重大错误，优先解决 |
| **medium** | `medium` | 0.5 | 中等——可能影响质量，应计划解决 |
| **low** | `low` | 0.25 | 轻微——影响有限，可延后解决 |

### 4种解决状态

| 状态 | 常量 | 说明 |
|------|------|------|
| **open** | `open` | 待处理——新记录的债务默认状态 |
| **in-progress** | `in-progress` | 处理中——正在解决 |
| **resolved** | `resolved` | 已解决——通过resolveDebt()标记 |
| **escalated** | `escalated` | 已升级——超出当前Agent能力，需人工介入 |

### 债务类型×严重度×解决状态矩阵

```
                    │ critical │  high  │ medium │  low   │
                    │ 1.0      │ 0.75   │ 0.5    │ 0.25   │
────────────────────┼──────────┼────────┼────────┼────────┤
requirement-ambiguity│ ████████ │ ██████ │ ████   │ ██     │
context-mismatch     │ ████████ │ ██████ │ ████   │ ██     │
implicit-assumption  │ ████████ │ ██████ │ ████   │ ██     │
spec-gap             │ ████████ │ ██████ │ ████   │ ██     │
domain-knowledge-gap │ ████████ │ ██████ │ ████   │ ██     │
────────────────────┼──────────┼────────┼────────┼────────┤
open                 │ 立即处理  │ 优先   │ 计划   │ 记录   │
in-progress          │ 跟踪     │ 跟踪   │ 跟踪   │ 跟踪   │
resolved             │ 归档     │ 归档   │ 归档   │ 归档   │
escalated            │ 人工介入  │ 人工   │ 通知   │ 记录   │
```

### 债务评分算法

#### `calculateDebtScore()`

计算当前未解决债务的综合评分。

```
算法：
  totalWeight = Σ(未解决债务.severityScore)
  openCount = 未解决债务数量
  score = min(1, totalWeight / max(1, openCount))
  
  分级：
    score ≥ criticalThreshold(0.7) → 'critical'
    score ≥ highThreshold(0.5)     → 'high'
    score < highThreshold          → 'manageable'
```

**返回值**：`Object`

| 字段 | 类型 | 说明 |
|------|------|------|
| `score` | number | 债务评分（0~1，保留3位小数） |
| `level` | string | 债务等级（critical/high/manageable/none） |
| `openCount` | number | 未解决债务数量 |

评分逻辑：取所有未解决债务的严重度评分平均值。若所有债务均为critical（1.0），则score=1.0；若均为low（0.25），则score=0.25。无未解决债务时返回`{ score: 0, level: 'none', openCount: 0 }`。

### 核心方法

#### `recordDebt(debtInfo)`

记录一条理解债务。

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `debtInfo.type` | string | 否 | 债务类型，默认`implicit-assumption` |
| `debtInfo.severity` | string | 否 | 严重度，默认`medium` |
| `debtInfo.description` | string | 否 | 债务描述 |
| `debtInfo.source` | string | 否 | 来源标识，默认`unknown` |
| `debtInfo.taskId` | string | 否 | 关联任务ID |
| `debtInfo.agentId` | string | 否 | 关联Agent ID |
| `debtInfo.evidence` | Array | 否 | 证据列表，默认空数组 |

容量上限1000条（`MAX_DEBTS`），超出时优先淘汰已解决的最旧债务，若无已解决债务则淘汰最旧的任意债务。

#### `resolveDebt(debtId, resolutionNote)`

将债务标记为已解决。

#### `escalateDebt(debtId, reason)`

将债务升级为需人工介入。

#### `getOpenDebts()`

获取所有未解决债务（open和in-progress状态）。

#### `getDebtsByType(type)` / `getDebtsByTask(taskId)`

按类型或任务ID筛选债务。

#### `getDebtDistribution()`

获取未解决债务的类型分布。

#### `getResolutionRate()`

获取债务解决率（0~1），无债务时返回1。

#### `getAverageResolutionTimeMs()`

| **testing** | `testing` | 测试/改Bug | 25% |
| **deployment** | `deployment` | 部署上线 | 15% |

期望分布的设计理念：测试阶段占比最高（25%），体现TDD强制原则下测试优先的工程文化；编码开发占20%，需求和分析合计30%，强调前期充分理解的重要性。

### 交付周期管理

#### `startCycle(cycleInfo)`

启动一个新的交付周期。若已有活跃周期，自动以`superseded`结果结束旧周期。

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `cycleInfo.id` | string | 否 | 周期ID，默认自动生成 |

**返回值**：`string` — 周期ID

#### `recordPhaseTime(phase, durationMs, meta)`

记录阶段耗时。

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `phase` | string | 是 | 阶段名称（PHASES枚举值） |
| `durationMs` | number | 是 | 耗时（毫秒） |
| `meta.aiAssisted` | boolean | 否 | 是否AI辅助 |
| `meta.rework` | boolean | 否 | 是否返工 |

#### `recordReviewCycle(meta)`

记录一次审查周期，用于计算审查瓶颈评分。

#### `endCycle(cycleResult)`

结束当前交付周期。

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `cycleResult.outcome` | string | 否 | 周期结果，默认`completed` |

### 编码占比（getCodingRatio）

```
codingRatio = development阶段总耗时 / 所有阶段总耗时
```

编码占比反映开发效率的核心指标。过低的编码占比意味着大量时间花在需求、分析、测试等非编码阶段；过高的编码占比可能意味着前期分析不足导致返工。期望值为0.20（20%）。

### AI加速比（getAiAccelerationRatio）

```
aiAccelerationRatio = AI辅助阶段总耗时 / 所有阶段总耗时
```

AI加速比衡量AI辅助在交付流程中的渗透率。每个阶段通过`recordPhaseTime()`的`meta.aiAssisted`标记是否使用AI辅助。比率越高表示AI参与度越高，但并非越高越好——关键决策点仍需人类判断。

### 审查瓶颈评分（getReviewBottleneckScore）

```
reviewRatio = 总审查周期数 / 交付周期数
reworkRatio = 返工阶段总耗时 / 开发阶段总耗时
bottleneckScore = min(1, reviewRatio × 0.5 + reworkRatio × 0.5)
```

审查瓶颈评分综合两个维度：

| 维度 | 权重 | 含义 |
|------|------|------|
| **reviewRatio** | 0.5 | 平均每个交付周期的审查轮次，越高表示审查越频繁 |
| **reworkRatio** | 0.5 | 返工时间占开发时间的比例，越高表示质量越差 |

评分范围0~1，0表示无瓶颈，1表示严重瓶颈。评分>0.5时应触发流程优化。

### 时间分布偏差（getDistributionDeviation）

```
deviation = Σ|actualRatio[phase] - expectedRatio[phase]|  // 对6个阶段求和
```

偏差值反映实际时间分配与期望的偏离程度。0表示完全匹配期望分布，值越大偏离越严重。

## Round 7 修复记录

### BrainMemory — 异步嵌入回调shutdown竞态条件修复

**缺陷**：BrainMemory 的 `store()` 方法在存储记忆时，若已挂载 EmbeddingService，会异步调用 `embeddingService.embed()` 计算向量。当 `embed()` 的回调执行时，BrainMemory 可能已经处于关闭状态（`_shutdown` 为 true），此时回调仍尝试访问并修改 `_memories` 和 `_index` 等内部数据结构，导致：
1. 向已关闭的 Map 写入数据，造成内存泄漏（关闭后数据无法被清理）
2. 向已关闭的倒排索引添加条目，导致索引不一致
3. 触发 `memory-stored` 事件，但监听方可能已清理，引发未捕获异常

**修复**：`embed()` 回调中新增 `_shutdown` 守卫检查。回调执行时首先检查 `this._shutdown`，若为 true 则直接返回，跳过所有数据写入和事件发射操作。确保关闭后异步回调不会修改内部状态。

**影响范围**：BrainMemory 关闭期间及关闭后的异步嵌入回调不再产生脏数据或异常，关闭流程更安全可靠。此修复与质量子系统的 SelfReflection 相关——SelfReflection 在反思过程中通过 BrainMemory 检索历史质量记忆，若 BrainMemory 关闭后仍有异步写入，可能导致反思结果基于不一致的数据。

### Round 9 修复记录

#### FeedbackCredibility — _sourceTrust容量限制与decayTrustScores清理

**缺陷**：`_sourceTrust`（反馈源信任数据映射表）无容量限制，在高频反馈源场景下Map可无限增长，导致内存持续膨胀。此外，`decayTrustScores()` 方法在信任评分衰减至接近默认值时，仅将评分回归到默认值但不删除对应条目，导致大量"僵尸"条目长期占据内存。

**修复**：`_sourceTrust` 新增上限500条目（`MAX_SOURCES`），超出时淘汰最旧反馈源。`decayTrustScores()` 新增完全衰减条目的自动清理逻辑：当评分与默认值差距小于0.01且距上次更新超过7天（`SEVEN_DAYS_MS`）时，自动从Map中删除该条目，释放内存。

**影响范围**：反馈源信任数据的内存占用受控；长期未更新的僵尸条目不再累积，衰减机制同时起到内存回收作用。
