# 核心功能-六阶段执行流程

> 版本：2.73.4 | 模块：src/runtime/workflow/phase-orchestrator.js | 常量：src/utils/constants.js

---

## 概述

六阶段执行流程是 Harness 框架的核心工程化方法论，将软件开发生命周期严格划分为六个有序阶段，通过有限状态机管控阶段流转、TDD门禁强制质量、因果数据总线保障一致性，实现"流程管控+容错自愈"的工程化目标。

### 为什么需要六阶段流程

| 问题 | 六阶段流程的解决方式 |
|------|---------------------|
| 需求模糊导致返工 | 阶段0-1强制需求探索与分析，消除模糊点 |
| 架构设计缺失导致重构 | 阶段2在编码前完成架构设计 |
| 代码质量不可控 | 阶段3强制TDD门禁，先测试后实现 |
| 模块集成问题堆积 | 阶段4专项集成测试，提前发现接口不匹配 |
| 部署风险高 | 阶段5三步部署流程，验证后才上线 |

### 架构位置

```
用户请求 → CommandRouter(命令解析) → SkillRouter(技能匹配)
    → PhaseOrchestrator(阶段验证) → RBACEnforcer(权限检查)
    → Skill执行 → TDDGate(门禁检查) → 阶段推进
```

PhaseOrchestrator 在框架中充当"流程管控器"角色，与以下模块协作：

| 模块 | 关系 |
|------|------|
| SkillRouter | 根据当前阶段匹配可执行技能 |
| CausalDataBus | 提供因果就绪性数据，验证阶段间数据传递 |
| SessionManager | 持久化当前阶段状态，支持会话恢复 |
| TDDGate | 阶段推进时的TDD门禁检查 |
| AR Context | 阶段推进时注入自回归上下文 |
| ExecutionModeManager | 阶段转换审批控制 |

## 六阶段详解

### 阶段总览

| 序号 | 阶段标识 | 中文名称 | 英文名称 | Token预算占比 | 执行级别 |
|------|---------|---------|---------|--------------|---------|
| 0 | `brainstorming` | 需求探索 | Exploration | 5% | recommended |
| 1 | `requirement-analysis` | 需求分析与规划 | Requirement Analysis | 10% | recommended |
| 2 | `architecture-design` | 架构设计 | Architecture Design | 20% | recommended |
| 3 | `module-development` | 模块开发 | Module Development | 35% | strict |
| 4 | `integration-testing` | 集成测试 | Integration Testing | 20% | strict |
| 5 | `deployment` | 部署上线 | Deployment | 10% | strict |

---

### 阶段0：需求探索（brainstorming）

**目的**：通过苏格拉底式提问，帮助用户从模糊想法中提炼出清晰、可执行的设计方案。

**进入条件**：
- 用户提出模糊需求或新项目想法
- 无现有设计文档
- 项目初始启动

**退出条件**：
- 所有核心问题已向用户确认，无未解决的模糊点
- 至少探索了5种不同思路并进行了对比
- 设计方案已分段获得用户确认
- 输出的设计文档清晰、完整、可执行

**关键技能**：

| 技能ID | 名称 | 执行级别 | 说明 |
|--------|------|---------|------|
| `brainstorming` | 头脑风暴 | recommended | 苏格拉底式提问，方案探索 |
| `idea-validation` | 想法验证 | recommended | 验证创业想法或商业假设 |

**关键交付物**：
- 设计方案文档（`outputs/`）
- 假设清单
- 可行性评估

**TDD门禁**：无（本阶段为需求探索，不涉及代码）

**适用Agent**：Domain Analyst、Team Lead、Planner

---

### 阶段1：需求分析与规划（requirement-analysis）

**目的**：将原始需求转化为结构化的需求规格说明书，明确功能边界、验收标准和优先级。

**进入条件**：
- brainstorming阶段完成，输出设计方案文档
- 或用户直接提供明确的项目需求

**退出条件**：
- 所有功能需求有明确的用户故事和验收标准
- 非功能需求有可量化的指标
- 优先级排序合理，P0功能覆盖核心场景
- 需求间依赖关系清晰，无循环依赖

**关键技能**：

| 技能ID | 名称 | 执行级别 | 说明 |
|--------|------|---------|------|
| `requirement-analysis` | 需求分析 | recommended | 需求分类、细化、优先级排序 |

**关键交付物**：
- 需求规格说明书
- 任务拆解清单
- 验收标准
- 优先级矩阵

**TDD门禁**：无（本阶段为需求分析，不涉及代码）

**适用Agent**：Domain Analyst、Team Lead、Planner

---

### 阶段2：架构设计（architecture-design）

**目的**：根据需求规格说明书，设计系统整体架构、模块划分、接口定义和数据模型。

**进入条件**：
- requirement-analysis阶段完成，输出需求规格说明书
- 需求已通过评审

**退出条件**：
- 架构图清晰，模块职责明确
- 所有模块间接口已定义
- 数据模型完整，关系明确
- 非功能需求有对应的架构保障
- 技术选型有明确的理由

**关键技能**：

| 技能ID | 名称 | 执行级别 | 说明 |
|--------|------|---------|------|
| `architecture-design` | 架构设计 | recommended | 架构选型、模块划分、接口设计 |
| `cloud-ai-blueprint` | AI系统蓝图规划 | recommended | AI系统架构规划（按需） |
| `design-md` | 设计语言文档 | recommended | 前端设计语言定义（按需） |

**关键交付物**：
- 架构设计文档（`docs/architecture/`）
- 接口设计文档
- 模块划分方案
- 数据模型设计

**TDD门禁**：无（本阶段为架构设计，不涉及代码）

**适用Agent**：Domain Analyst、Planner

---

### 阶段3：模块开发（module-development）

**目的**：严格按照TDD驱动开发流程，实现架构设计中定义的各模块功能。

**进入条件**：
- architecture-design阶段完成，输出架构设计文档和接口设计
- 模块划分和接口定义已确认

**退出条件**：
- 所有严格技能已完成（tdd-implement、module-development、code-review、verification-before-completion）
- 测试覆盖率 ≥ 80%
- 所有测试通过，无跳过、无禁用
- 代码审查通过
- 完成前验证通过（证据验证）

**关键技能**：

| 技能ID | 名称 | 执行级别 | 说明 |
|--------|------|---------|------|
| `tdd-implement` | TDD驱动开发 | **strict** | RED-GREEN-REFACTOR强制循环 |
| `module-development` | 模块开发 | **strict** | 编码实现，TDD门禁 |
| `dispatching-parallel` | 并行子代理调度 | optional | 多模块并行开发 |
| `code-review` | 代码审查 | **strict** | 代码质量审查 |
| `verification-before-completion` | 完成前验证 | **strict** | 证据验证，不可跳过 |
| `systematic-debugging` | 系统化调试 | recommended | Bug定位与修复 |
| `bug-fix` | 缺陷修复 | recommended | 缺陷修复流程 |
| `security-audit` | 安全审计 | recommended | 安全漏洞检测 |
| `performance-optimization` | 性能优化 | recommended | 性能调优 |
| `refactor-code` | 系统化重构 | recommended | 代码结构改善 |
| `iterative-deepening` | 迭代深化推理 | recommended | 高复杂度任务深化 |
| `multi-agent-fusion` | 多Agent协同融合 | recommended | 多Agent协作 |
| `mvp-builder` | MVP构建 | recommended | 快速构建最小可行产品 |

**关键交付物**：
- 模块源代码
- 模块测试代码
- 覆盖率报告
- 代码审查报告
- 完成验证证据

**TDD门禁**：**强制执行**。本阶段是TDD门禁的核心执行区域：
- 严格技能（tdd-implement、module-development、code-review、verification-before-completion、bug-fix、security-audit、iterative-deepening）必须完成才能推进到下一阶段
- 任何实现代码必须在对应的失败测试之后编写
- 先写代码则删除，从测试重新开始

**适用Agent**：Task Worker、Test Writer

---

### 阶段4：集成测试（integration-testing）

**目的**：验证多个模块组合后的整体功能正确性，发现模块间接口不匹配、数据流异常等集成问题。

**进入条件**：
- module-development阶段完成
- 所有模块代码审查通过
- 单元测试全部通过

**退出条件**：
- 所有P0场景测试通过
- 接口调用测试100%覆盖
- 缺陷报告包含完整的复现步骤
- 测试报告包含覆盖率和风险评估

**关键技能**：

| 技能ID | 名称 | 执行级别 | 说明 |
|--------|------|---------|------|
| `integration-testing` | 集成测试 | **strict** | 模块间协作验证 |

**关键交付物**：
- 集成测试结果
- 缺陷报告
- 覆盖率统计
- 风险评估报告

**TDD门禁**：**强制执行**。integration-testing为严格技能，必须完成才能推进。

**适用Agent**：Quality Assurance、Test Writer

---

### 阶段5：部署上线（deployment）

**目的**：将通过测试的代码安全、稳定地部署到目标环境，确保服务可用且可回滚。

**进入条件**：
- integration-testing阶段完成，所有测试通过
- verification-before-completion验证通过

**退出条件**：
- 部署成功，服务健康检查通过
- 冒烟测试全部通过
- 监控和告警配置完成
- 回滚方案验证可行
- 部署文档完整

**关键技能**：

| 技能ID | 名称 | 执行级别 | 说明 |
|--------|------|---------|------|
| `deployment` | 部署上线 | **strict** | 3步部署流程（准备→验证→部署） |
| `documentation` | 文档编写 | recommended | 部署文档、运维手册 |
| `auto-doc-generation` | 自动文档生成 | recommended | 文档自动生成 |
| `ai-native-scaling` | AI原生规模化 | recommended | 产品规模化扩展（按需） |

**关键交付物**：
- 部署记录
- 健康检查报告
- 上线检查清单
- 运维手册
- 回滚操作指南

**TDD门禁**：**强制执行**。deployment为严格技能，必须完成。

**适用Agent**：DevOps Engineer

## 阶段转换规则

### 正向流转

阶段只能按序号递增方向推进，每个阶段只能前进到下一个阶段：

```
brainstorming → requirement-analysis → architecture-design → module-development → integration-testing → deployment
```

| 源阶段 | 允许的目标阶段 |
|--------|--------------|
| `brainstorming` | `requirement-analysis` |
| `requirement-analysis` | `architecture-design` |
| `architecture-design` | `module-development` |
| `module-development` | `integration-testing` |
| `integration-testing` | `deployment` |

### 回退流转

当后续阶段发现问题时，允许回退到前一阶段进行返工。回退需要审批，且会自动标记受影响技能为无效：

| 源阶段 | 允许回退的目标阶段 |
|--------|------------------|
| `requirement-analysis` | `brainstorming` |
| `architecture-design` | `requirement-analysis` |
| `module-development` | `architecture-design` |
| `integration-testing` | `module-development` |
| `deployment` | `integration-testing` |

### 转换验证流程

阶段转换时，PhaseOrchestrator执行以下验证：

```
setCurrentPhase(target, reason)
  ├── 1. 目标阶段合法性检查（PHASE_INDEX验证）
  ├── 2. 转换路径合法性检查（PHASE_TRANSITIONS_SET验证）
  ├── 3. 执行模式审批检查（ExecutionModeManager）
  ├── 4. 源阶段Spec门禁检查（spec-gate-blocked事件）
  ├── 5. 目标阶段Spec门禁检查
  ├── 6. 记录阶段历史（from, to, reason, timestamp）
  ├── 7. AR上下文注入（PREVIOUS_RESULT, ORIGINAL_GOAL）
  └── 8. 触发phase-changed事件
```

### 回滚安全机制

回退时自动计算受影响的阶段和技能：

```javascript
validateRollback(fromPhase, toPhase, completedSkills)
// 返回：
// {
//   allowed: true,
//   requiresApproval: true,
//   phasesToRollback: ['module-development'],
//   skillsToInvalidate: ['tdd-implement', 'module-development', 'code-review', ...]
// }
```

回滚会标记目标阶段与源阶段之间的所有已完成技能为无效，防止脏状态传播到后续流程。

### 跳跃限制

六阶段流程**不允许跳跃**。例如，不能从`brainstorming`直接跳到`module-development`，必须依次经过`requirement-analysis`和`architecture-design`。这确保了每个阶段的交付物都经过验证，为后续阶段提供可靠输入。

## TDD门禁执行

### 门禁机制

TDD门禁在阶段边界强制执行，确保代码质量。门禁通过"严格技能"（STRICT_SKILLS）集合实现：

```
STRICT_SKILLS = {
  'tdd-implement',           // TDD驱动开发
  'module-development',      // 模块开发
  'code-review',             // 代码审查
  'verification-before-completion', // 完成前验证
  'bug-fix',                 // 缺陷修复
  'security-audit',          // 安全审计
  'integration-testing',     // 集成测试
  'deployment',              // 部署上线
  'iterative-deepening',     // 迭代深化推理
}
```

### 阶段完成性判定

一个阶段被认为"完成"，需同时满足三个条件：

1. **严格技能完成**：该阶段所有严格技能均已完成
2. **Spec门禁通过**：该阶段所有注册的Spec需求已验证
3. **因果数据就绪**：CausalDataBus中所有严格技能的接口和输出可用（如已附加）

```javascript
isPhaseComplete(phase, completedSkills)
  ├── 严格技能全部完成？
  ├── Spec门禁全部验证？
  └── 因果数据全部就绪？（如已附加CausalDataBus）
```

### Spec门禁

Spec门禁允许为阶段注册必须验证的规格需求，阶段完成前必须全部通过：

```javascript
// 注册规格需求
orchestrator.registerSpecRequirement('module-development', 'api-design-reviewed');
orchestrator.registerSpecRequirement('module-development', 'security-checklist-done');

// 标记已验证
orchestrator.markSpecVerified('module-development', 'api-design-reviewed');

// 查询门禁状态
orchestrator.getSpecGateState('module-development');
// { requiredSpecs: ['api-design-reviewed', 'security-checklist-done'],
//   verifiedSpecs: ['api-design-reviewed'],
//   unverifiedSpecs: ['security-checklist-done'] }
```

### 因果就绪性检查

当PhaseOrchestrator附加了CausalDataBus后，阶段完成性检查会自动验证因果数据：

```javascript
getCausalReadiness(phase, completedSkills)
// 返回：
// {
//   phase: 'module-development',
//   ready: false,
//   missingSkills: ['code-review'],
//   missingCausalOutputs: ['tdd-implement'],
//   missingSpecs: ['api-design-reviewed']
// }
```

## 代码示例

### 基本阶段流转

```javascript
const PhaseOrchestrator = require('./src/runtime/workflow/phase-orchestrator');

const po = new PhaseOrchestrator();

// 设置初始阶段
await po.setCurrentPhase('brainstorming', 'initial');

// 推进到下一阶段
await po.setCurrentPhase('requirement-analysis', 'brainstorming-complete');

// 检查是否可以推进
const completedSkills = ['brainstorming', 'idea-validation'];
po.canAdvanceToNext(completedSkills); // true/false

// 获取当前阶段
po.getCurrentPhase(); // 'requirement-analysis'

// 获取下一阶段
po.getNextPhase('requirement-analysis'); // 'architecture-design'
```

### 附加因果数据总线

```javascript
const CausalDataBus = require('./src/runtime/causal/causal-data-bus');

const bus = new CausalDataBus();
po.attachCausalDataBus(bus);

// 现在isPhaseComplete会自动检查因果接口和输出
po.isPhaseComplete('module-development', completedSkills);
```

### 回滚验证

```javascript
// 验证回滚合法性
const result = po.validateRollback('integration-testing', 'module-development', completedSkills);
// {
//   allowed: true,
//   requiresApproval: true,
//   phasesToRollback: ['integration-testing'],
//   skillsToInvalidate: ['integration-testing']
// }

if (result.allowed && result.requiresApproval) {
  // 请求人工审批后执行回滚
  await po.setCurrentPhase('module-development', 'rollback-defects-found');
}
```

### Spec门禁管理

```javascript
// 为阶段注册规格需求
po.registerSpecRequirement('architecture-design', 'architecture-reviewed');
po.registerSpecRequirement('architecture-design', 'interface-design-approved');
po.registerSpecRequirement('module-development', 'tdd-coverage-met');

// 标记已验证
po.markSpecVerified('architecture-design', 'architecture-reviewed');

// 查询门禁状态
const gateState = po.getSpecGateState('architecture-design');
// { requiredSpecs: ['architecture-reviewed', 'interface-design-approved'],
//   verifiedSpecs: ['architecture-reviewed'],
//   unverifiedSpecs: ['interface-design-approved'] }
```

### 事件监听

```javascript
po.on('phase-changed', ({ from, to, reason }) => {
  console.log(`阶段变更: ${from} → ${to}，原因: ${reason}`);
});

po.on('spec-gate-blocked', ({ from, to, missing, gatePhase }) => {
  console.log(`门禁阻断: ${from} → ${to}，缺失: ${missing.join(', ')}`);
});

po.on('spec-verified', ({ phase, specId }) => {
  console.log(`规格验证通过: ${phase}/${specId}`);
});
```

### 因果就绪性查询

```javascript
const readiness = po.getCausalReadiness('module-development', completedSkills);
if (!readiness.ready) {
  console.log('缺失技能:', readiness.missingSkills);
  console.log('缺失因果输出:', readiness.missingCausalOutputs);
  console.log('缺失规格:', readiness.missingSpecs);
}
```

## 配置

### 阶段预算分配

在`.harness/config.json`中配置各阶段的Token预算占比：

```json
{
  "phase_budget_allocation": {
    "brainstorming": 0.05,
    "requirement-analysis": 0.1,
    "architecture-design": 0.2,
    "module-development": 0.35,
    "integration-testing": 0.2,
    "deployment": 0.1
  }
}
```

模块开发阶段分配最大预算（35%），因为它是TDD循环的核心执行阶段，Token消耗最高。

### 阶段转换规则

转换规则定义在`src/utils/constants.js`的`PHASE_TRANSITIONS`中。修改转换规则需要同步更新：

1. `PHASE_TRANSITIONS`对象（源→目标列表）
2. `PHASE_SKILLS`对象（阶段→技能列表）
3. `STRICT_SKILLS`集合（严格技能列表）
4. 相关Skill的`phase`和`depends_on`字段

### 执行模式审批

通过附加ExecutionModeManager，可对阶段转换启用审批机制：

```javascript
const emm = new ExecutionModeManager();
po.attachExecutionModeManager(emm);

// 当emm.requiresApproval('phase-transition')为true时，
// 每次阶段转换都需要调用emm.requestApproval()获取审批
```

### 阶段历史

- 每次阶段转换自动记录`{ from, to, reason, timestamp, specVerificationPassed }`
- 历史上限100条，超出后裁剪至50条
- 通过`getPhaseHistory()`获取副本
