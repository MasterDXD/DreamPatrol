# 核心功能-因果数据总线与一致性

> 版本：2.73.4 | 模块：src/runtime/causal/（6个源文件）

---

## 1. 概述

因果子系统（Causal Subsystem）是 Harness Engineering 框架中多Agent协作的数据一致性基石。在多Agent并行执行场景下，Agent之间通过因果数据总线传递输出，形成有向无环的因果链（Causal Chain）。子系统围绕"因果有序、版本可溯、最终一致"三大原则，确保Agent间数据流动的正确性、可恢复性和可审计性。

### 为什么需要因果子系统？

| 问题场景 | 因果子系统的解决方式 |
|---------|-------------------|
| 多Agent并行输出同一字段，数据冲突 | CausalDataBus 提供4种合并策略 + 冲突检测 |
| Agent执行顺序错误，缺少上游输入 | SkillInterface 定义因果输入/输出，`enforcePublishOutput` 强制校验 |
| 进程崩溃后因果链丢失 | WAL（Write-Ahead Log）持久化 + 恢复重放 |
| 上下文过长需要压缩，但关键数据被误删 | CausalBufferManager 基于注意力权重提供因果感知的压缩策略 |
| 配置文件与运行时状态不一致 | CausalConsistencyChecker 双层一致性检查 |
| 因果记忆随时间失效 | CausalMemoryStore 时间衰减 + TTL过期 + 置信度降级 |
| 需要语义级检索因果数据 | CausalVectorIndex 向量相似度搜索 + EmbeddingService 降级方案 |

### 6个模块一览

| 模块 | 源文件 | 核心职责 |
|------|--------|---------|
| **CausalDataBus** | causal-data-bus.js | 因果数据总线——事件发布/订阅、因果排序、版本追踪、WAL持久化 |
| **CausalBufferManager** | causal-buffer-manager.js | 因果缓冲管理器——注意力权重计算、压缩策略映射、缓存管理 |
| **CausalConfigValidator** | causal-config-validator.js | 因果配置验证器——依赖图构建、循环检测、配置漂移、影响分析 |
| **CausalConsistencyChecker** | causal-consistency-checker.js | 因果一致性检查器——运行时vs静态、内存vs运行时双层一致性验证 |
| **CausalMemoryStore** | causal-memory-store.js | 因果内存存储——关键词/语义搜索、时间衰减、因果链追踪、冲突检测 |
| **CausalVectorIndex** | causal-vector-index.js | 因果向量索引——向量相似度搜索、Embedding管理、词哈希降级 |

## 2. 核心概念

### 2.1 因果排序（Causal Ordering）

因果排序是因果子系统的核心原则。每个因果事件通过 `walSeq`（WAL序列号）严格递增，确保事件的全局有序性。因果链（`_causalChain`）按 `walSeq` 排列，消费输入时从链尾向前搜索，保证消费到最新数据。

**因果ID生成规则**：`{skillId}-{walSeq}`，例如 `skill:requirement-analysis-42`，既标识来源Skill，又携带序列号信息。

### 2.2 事件版本追踪（Event Versioning）

CausalDataBus 为每个Skill维护输出版本历史（`_outputVersions`），最多保留 `MAX_VERSIONS_PER_SKILL = 5` 个版本。版本追踪支持：

- **回滚**：`rollbackToSequence(targetSeq)` 将因果链、pendingOutputs、outputKeyIndex、outputVersions 全部回退到指定序列号
- **时间戳回滚**：`rollbackToTimestamp(targetTs)` 先查找目标时间戳对应的 `walSeq`，再执行序列号回滚
- **因果感知驱逐**：`_evictCausalAware()` 优先驱逐引用计数为0的条目，保护被依赖的数据

### 2.3 最终一致性（Eventual Consistency）

因果子系统采用最终一致性模型，而非强一致性。CausalConsistencyChecker 提供两层一致性检查：

1. **运行时 vs 静态**：验证 CausalDataBus 中已注册的接口与 config.json 中的依赖声明是否对齐
2. **内存 vs 运行时**：验证 CausalMemoryStore 中的记忆条目与 CausalDataBus 因果链数据的一致性

问题按严重度分为 high / medium / low 三级，high级问题可能导致数据丢失，low级问题仅影响数据质量。

### 2.4 向量索引（Vector Index）

CausalVectorIndex 提供128维向量空间中的相似度搜索能力。两种向量生成方式：

- **语义嵌入**：通过 EmbeddingService 将文本转为高维语义向量，精度高但依赖外部服务
- **词哈希降级**：`_generateFallbackVector()` 使用 djb2 哈希变体将文本映射到128维空间，无需外部依赖但精度较低

查询时通过余弦相似度（Cosine Similarity）计算向量距离，返回 topK 个最相似的结果。

### 2.5 WAL（Write-Ahead Log）

WAL 是 CausalDataBus 持久化的核心机制，确保进程崩溃后因果链可恢复。WAL采用三层架构：

| 层级 | 文件 | 说明 |
|------|------|------|
| 状态快照 | `causal-state.json` | 防抖持久化，保存因果链、pendingOutputs、skillInterfaces、walSequence |
| 操作日志 | `wal-operations.jsonl` | 每行一个JSON操作（publish/define_interface/rollback），追加写入 |
| 归档日志 | `wal-operations.jsonl.{timestamp}.archived` | 日志轮转后的归档文件 |

**恢复流程**：启动时先加载 `causal-state.json` 恢复状态，再逐行重放 `wal-operations.jsonl` 中 `seq > _walSequence` 的操作。

    ├── 检测冲突
    ├── 按策略合并（last-wins/first-wins/deepest-wins/union）

## 4. CausalDataBus 详解

### 4.1 事件生命周期

一个因果事件从产生到消费的完整生命周期：

```
1. 定义接口  defineSkillInterface(skillId, definition)
   │         → 注册 causalInputs / causalOutputs / invariants / scenarios
   │         → 写入WAL（define_interface操作）
   │         → 发射 interface-defined 事件
   │
2. 发布输出  publishOutput(skillId, outputData)
   │         → 递增 walSequence
   │         → 消毒输出数据（_sanitizeOutputData）
   │         → 提取自回归上下文（_sanitizeARContext）
   │         → 验证输出完整性（_validateOutputs）
   │         → 验证不变量（_validateInvariants）
   │         → 追加到因果链（_causalChain）
   │         → 更新待处理输出（_pendingOutputs）
   │         → 更新输出键索引（_outputKeyIndex）
   │         → 维护版本历史（_outputVersions）
   │         → 写入WAL（publish操作）
   │         → 持久化到SQLite
   │         → 发射 output-published / invariant-violation 事件
   │
3. 消费输入  consumeInputs(targetSkillId)
   │         → 查找目标Skill的接口定义
   │         → 按source从pendingOutputs查找，或从因果链尾部搜索
   │         → 递增引用计数（_incrementRefCount）
   │         → 返回输入数据
   │
4. 回滚     rollbackToSequence(targetSeq)
   │         → 过滤因果链，移除walSeq > targetSeq的条目
   │         → 清理pendingOutputs、outputKeyIndex、outputVersions
   │         → 清理悬空引用计数
   │         → 写入WAL（rollback操作）
   │         → 发射 causal-rollback 事件
```

### 4.2 发布/订阅机制

CausalDataBus 继承 EventEmitter，通过事件通知实现发布/订阅：

| 事件名 | 触发时机 | 事件数据 |
|--------|---------|---------|
| `output-published` | `publishOutput()` 成功 | `{ skillId, causalId }` |
| `interface-defined` | `defineSkillInterface()` 成功 | `{ skillId, inputCount, outputCount, scenarioCount }` |
| `invariant-violation` | 不变量验证失败 | `{ skillId, causalId, violations }` |
| `parallel-conflicts-detected` | 并行冲突检测发现冲突 | `{ skillIds, conflictCount, overlappingKeys }` |
| `parallel-outputs-merged` | 并行输出合并完成 | `{ skillIds, strategy, conflictCount, mergedKeys }` |
| `causal-rollback` | 因果链回滚 | `{ targetSequence, removedChainEntries, removedPendingKeys }` |
| `causal-chain-evicted` | 因果感知驱逐 | `{ evicted, remaining }` |
| `wal-initialized` | WAL初始化完成 | — |
| `wal-backpressure` | WAL写入流背压 | `{ operation, seq }` |
| `wal-drain` | WAL写入流恢复 | `{ seq }` |
| `wal-log-rotated` | WAL日志轮转 | `{ previousSize }` |
| `wal-queue-overflow` | WAL待写队列溢出 | `{ queueSize, seq }` |
| `persist-error` | 持久化失败 | Error对象 |
| `wal-init-error` | WAL初始化失败 | Error对象 |
| `wal-write-error` | WAL写入失败 | Error对象 |
| `wal-rotation-error` | WAL轮转失败 | Error对象 |
| `wal-stream-lost` | WAL轮转后重开失败 | Error对象 |

### 4.3 WAL写入流程

```
publishOutput() / defineSkillInterface() / rollbackToSequence()
    │
    ▼
_writeWALEntry(operation, data, seq)
    │
    ├── 获取写锁（_walWriteLock Promise链）
    │
    ▼
_writeWALEntryInner(entry)
    │
    ├── WAL流不可用或正在轮转？
    │   ├── 是 → 加入_walPendingQueue（上限MAX_WAL_PENDING_QUEUE）
    │   │        超限则发射 wal-queue-overflow
    │   └── 否 → 先刷写pending队列（_flushWALPending）
    │            │
    │            ▼
    │         写入JSON行到_walLogStream
    │            │
    │            ├── 流不可写 → 发射 wal-backpressure，注册drain回调
    │            ├── 写入成功 → 递增_walOpCount
    │            │            每50条触发_persistWALImmediate()
    │            └── 写入异常 → 发射 wal-write-error
    │
    ▼
_rotateWALLogIfNeeded()
    │
    ├── 日志文件 < MAX_JSON_FILE_SIZE → 不轮转
    └── 日志文件 ≥ MAX_JSON_FILE_SIZE
        ├── 关闭当前流
        ├── 立即持久化状态
        ├── 重命名为 .archived
        ├── 重新打开日志流
        └── 发射 wal-log-rotated
```

### 4.4 错误发射机制

CausalDataBus 使用 `emitError()` 工具函数发射错误事件，所有错误事件以 `wal-` 或 `persist-` 为前缀，便于上层统一监听：

```javascript
bus.on('wal-write-error', (err) => { /* WAL写入失败处理 */ });
bus.on('persist-error', (err) => { /* 持久化失败处理 */ });
bus.on('wal-init-error', (err) => { /* WAL初始化失败处理 */ });
```

关键设计：WAL写入失败不会阻塞主流程，`publishOutput()` 仍然返回 `true`，因为内存中的因果链已更新。WAL仅影响持久化可靠性，不影响运行时正确性。

### 4.5 输出数据消毒

`_sanitizeOutputData()` 在写入因果链前对输出数据进行深度消毒：

| 消毒规则 | 说明 |
|---------|------|
| 深度限制 | 最大10层，超出返回空对象 |
| 循环引用检测 | 使用 `visited` Set，检测到返回 `{ _circular: true }` |
| 数组截断 | 最多保留 `MAX_SANITIZE_ARRAY_LENGTH = 1000` 个元素 |
| 对象键截断 | 最多保留 `MAX_SANITIZE_OBJECT_KEYS = 1000` 个键 |
| 字符串截断 | 超过 `MAX_STRING_LENGTH = 65536` 的字符串被截断 |
| 危险键过滤 | `DANGEROUS_KEYS` 集合中的键被移除（如 `__proto__`、`constructor`） |

## 5. CausalBufferManager 详解

### 5.1 注意力权重计算

CausalBufferManager 的核心价值在于为上下文压缩引擎提供因果感知的压缩策略。其核心算法是注意力权重计算：

```
输入：currentSkillId（当前正在执行的Skill）

步骤1：提取直接依赖
  → 从SkillRouter.registry中获取当前Skill的causal_inputs
  → 提取所有source引用，权重设为1.0

步骤2：传播衰减
  → BFS遍历依赖图
  → 每层距离权重 = attentionDecay ^ distance
  → 最大传播距离 = maxCausalDistance（默认5）

步骤3：分配背景权重
  → 因果链中存在但无依赖关系的Skill，权重0.1
```

**权重衰减示例**（attentionDecay = 0.7）：

| 因果距离 | 权重值 | 压缩策略 |
|---------|--------|---------|
| 0（自身） | — | — |
| 1（直接依赖） | 1.0 | full |
| 2 | 0.7 | full |
| 3 | 0.49 | summary |
| 4 | 0.343 | summary |
| 5 | 0.240 | discard |
| 无依赖 | 0.1 | discard |

### 5.2 压缩策略映射

`getCompressionStrategy(skillId, currentSkillId)` 将注意力权重映射为三种压缩策略：

| 策略 | 权重范围 | 含义 | 上下文压缩引擎行为 |
|------|---------|------|------------------|
| `full` | ≥ 0.7 | 高因果相关 | 保留完整原文，不压缩 |
| `summary` | 0.3 ~ 0.7 | 中等因果相关 | 摘要压缩，保留关键信息 |
| `discard` | < 0.3 或无权重 | 低因果相关 | 可安全丢弃 |

### 5.3 缓存与失效

- **缓存结构**：`_attentionCache`（Map），键为 `currentSkillId`，值为 `{ weights, _cachedAt }`
- **缓存上限**：`MAX_ATTENTION_CACHE_SIZE = 100`，超出时淘汰最早条目
- **TTL**：`DEFAULT_TTL_CACHE_MS`，过期后重新计算
- **手动失效**：`invalidateAttentionCache()` 清除所有缓存
- **自动失效**：`attachCausalDataBus()` 或 `attachSkillRouter()` 时自动清除

## 6. CausalConfigValidator 详解

### 6.1 依赖图构建

`buildDependencyGraph()` 构建包含6类节点的完整依赖图，涵盖配置层和源码层：

```
config.json
    │
    ├── skill_registry → graph.skills
    │     属性：id, phase, enforcement, dependsOn, dependsOnSet,
    │           blocks, applicableAgents, fileExists, specificationBindings
    │
    ├── agent_permissions → graph.agents
    │     属性：id, allowedTools, restrictedOps, fileExists
    │
    ├── hooks → graph.hooks
    │     属性：id, handlers
    │
    └── mcp_servers → graph.mcp
          属性：id, enabled, type

.harness/rules/ → graph.rules
      属性：id, fileExists

src/**/*.js → graph.sourceCode
      属性：id, exports, imports, dependsOnSet,
            specificationBindings, resolvedImports, dependedOnBy
```

### 6.2 源码依赖分析

CausalConfigValidator 独特地扫描 `src/` 目录下所有 `.js` 文件，构建源码级依赖图：

1. **导入提取**（`_extractImports`）：正则匹配 `require('...')` 调用，提取相对路径导入
2. **导出提取**（`_extractExports`）：匹配 `class` 声明、`module.exports =` 和 `exports.xxx =`
3. **路径解析**（`_resolveImport`）：将相对路径解析为项目内绝对路径，尝试 `.js` 和 `/index.js` 后缀
4. **边构建**（`_buildSourceCodeEdges`）：建立 Skill 的 `specificationBindings` 与源码节点的双向关联

### 6.3 循环依赖检测

`detectCircularDependencies()` 使用 DFS + 递归栈算法检测 Skill 间的循环依赖：

```
DFS遍历：
  visited：全局已访问节点
  recursionStack：当前递归路径

  对每个Skill节点：
    标记为visited，加入recursionStack
    遍历其dependsOn列表：
      若目标未访问 → 递归DFS
      若目标在recursionStack中 → 发现环
    从recursionStack中移除
```

返回环路径数组，如 `[['skill-a', 'skill-b', 'skill-c', 'skill-a']]`。

### 6.4 配置漂移检测

配置漂移检测用于发现运行期间配置文件是否被外部修改：

```
snapshotConfig()    →  对当前config.json做JSON序列化快照
                        重置 _driftDetected = false

detectConfigDrift() →  比较当前config.json与快照
                        若不同 → _driftDetected = true
                        返回 { drifted, added, removed, reason }
                        added/removed为顶层键的增减
```

### 6.5 影响分析

`getImpactAnalysis(nodeId, nodeType)` 分析指定节点变更的影响范围：

| nodeType | 搜索范围 | 关系类型 |
|----------|---------|---------|
| `skill` | 依赖此Skill的其他Skill | `depends_on` |
| `skill` | 使用此Agent的Skill | `used_by_agent` |
| `agent` | 使用此Agent的Skill | `uses_agent` |
| `sourceCode` | 导入此源码的其他源码 | `imports` |
| `sourceCode` | specificationBinding到此源码的Skill | `spec_bound` |

## 7. CausalConsistencyChecker 详解

### 7.1 双层一致性模型

CausalConsistencyChecker 实现双层一致性检查，分别验证不同维度的一致性：

**第一层：运行时 vs 静态（`checkRuntimeVsStatic`）**

```
CausalDataBus.getDefinedInterfaces()  →  运行时已注册的接口列表
CausalConfigValidator.buildDependencyGraph()  →  静态配置中的依赖图

比较逻辑：
  对依赖图中每个有dependsOn的Skill：
    检查是否在运行时接口列表中存在
    若不存在 → 报告 missing_runtime_interface（severity: medium）
```

**第二层：内存 vs 运行时（`checkMemoryVsRuntime`）**

```
CausalDataBus.getCausalChain()  →  运行时因果链
CausalMemoryStore.searchByCausalSimilarity()  →  内存中的因果记忆

比较逻辑：
  对因果链中每个Skill的每个causalOutput：
    在CausalMemoryStore中搜索
    若搜索结果的confidence < 0.3 → 报告 low_confidence_memory（severity: low）
```

### 7.2 完整一致性检查

`checkFullConsistency()` 汇总两层检查结果，按严重度分类：

```javascript
const result = await checker.checkFullConsistency();
// {
//   consistent: boolean,        // 是否完全一致
//   totalIssues: number,        // 问题总数
//   highIssues: number,         // 高严重度问题数
//   mediumIssues: number,       // 中严重度问题数
//   lowIssues: number,          // 低严重度问题数
//   issues: Array,              // 所有问题详情
//   runtimeVsStatic: boolean,   // 第一层是否一致
//   memoryVsRuntime: boolean,   // 第二层是否一致
// }
```

### 7.3 事件通知

| 事件名 | 触发时机 |
|--------|---------|
| `runtime-vs-static-checked` | 第一层检查完成 |
| `memory-vs-runtime-checked` | 第二层检查完成 |
| `full-consistency-checked` | 完整检查完成 |
| `attach-error` | 注入组件失败 |

## 8. CausalMemoryStore 详解

### 8.1 内存索引结构

CausalMemoryStore 维护两级索引实现快速查询：

**主缓存**（`_memoryCache`）：Map，键为条目ID，值为完整因果记忆对象。上限 `DEFAULT_MAX_CAUSAL_MEMORIES = 500`，超出时淘汰最早条目。

**相似度索引**（`_similarityIndex`）：Map，键为关键词，值为 `RingBuffer(100)` 存储的条目ID列表。用于关键词搜索的快速候选集查找。

**嵌入缓存**（`_embeddingCache`）：Map，键为条目ID，值为向量。上限500，避免重复计算嵌入。

### 8.2 搜索模式详解

**关键词搜索**（默认模式）：

```
输入查询文本
    │
    ▼
_extractKeywords(queryContext)
    │  → 转小写 → 去除非字母数字字符 → 分词 → 过滤停用词
    │
    ▼
遍历queryKeywords，从_similarityIndex中收集候选条目ID
    │  → 每个匹配的候选累加得分
    │
    ▼
计算相似度 = 候选得分 / queryKeywords.length
    │  → 过滤低于threshold的候选
    │
    ▼
按相似度降序排序，返回topK
```

**语义向量搜索**：

```
输入查询文本
    │
    ▼
EmbeddingService.embed(queryContext) → queryVec
    │
    ▼
遍历_memoryCache：
    │  若_embeddingCache有缓存 → 使用缓存向量
    │  若无缓存 → embed(cause + context + effect) → 缓存
    │
    ▼
_cosineSimilarity(queryVec, entryVec) → similarity
    │
    ▼
过滤 + 排序 + 返回topK
```

**语义分组搜索**（`searchBySemanticGroup`）：

在基础搜索结果上叠加过滤和加权：

- 按 category、tags、minConfidence 过滤
- 计算加权分数：`weightedScore = similarity × 0.6 + decayedConfidence × 0.4`
- 时间衰减：`decayedConfidence = max(0.01, confidence × decayFactor^ageDays)`

**上下文链搜索**（`searchByContextChain`）：

```
1. 对查询文本执行语义分组搜索 → directResults
2. 对每个completedSkill：
     扩展查询 = queryContext + ' ' + skillId
     执行语义分组搜索 → chainResults
3. 合并去重，按weightedScore排序
```

**因果链追踪**（`traceCausalChain`）：

```
BFS从effectKeyword出发：
  搜索与当前关键词匹配的记忆
  将匹配记忆的cause作为下一轮搜索关键词
  最大深度5，最大50条结果
```

### 8.3 TTL与时间衰减

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `_ttlMs` | 30天（2,592,000,000 ms） | 记忆有效期 |
| `_decayFactor` | 0.98 | 每天衰减2% |
| `_conflictThreshold` | 0.7 | 冲突检测的原因相似度阈值 |

**TTL过期处理**（`verifyCausalConsistency`）：

- 记忆超过TTL → 置信度乘以0.5，标记 `_degraded = true`
- 发射 `causal-memory-degraded` 事件
- 仍视为有效（`valid: true`），但标记为降级（`degraded: true`）

**时间衰减公式**：

```
decayedConfidence = max(0.01, confidence × 0.98^ageDays)
```

| 天数 | 衰减后置信度（原始1.0） |
|------|----------------------|
| 0天 | 1.000 |
| 7天 | 0.868 |
| 30天 | 0.545 |
| 90天 | 0.162 |
| 180天 | 0.026 |

### 8.4 因果冲突检测

`detectCausalConflicts()` 检测"相似原因导致不同结果"的矛盾记忆：

```
对每对记忆条目(a, b)：
  causeSimilarity = Jaccard(a.cause关键词, b.cause关键词)
  effectSimilarity = Jaccard(a.effect关键词, b.effect关键词)

  若 causeSimilarity ≥ 0.7 且 effectSimilarity < 0.3：
    → 报告冲突
```

## 9. CausalVectorIndex 详解

### 9.1 向量索引结构

CausalVectorIndex 维护一个 `Map<causalId, VectorEntry>`，每个条目包含：

```javascript
{
  causalId: string,       // 因果条目ID
  text: string,           // 原始文本
  vector: number[],       // 128维向量
  metadata: Object,       // 元数据
  indexedAt: string,      // ISO时间戳
}
```

上限 `MAX_VECTORS = 5000`，超出时淘汰最早条目。

### 9.2 词哈希降级算法

当 EmbeddingService 不可用时，`_generateFallbackVector(text)` 生成128维词哈希向量：

```
1. 初始化 Float32Array(128)，全零
2. 文本按空格分词
3. 对每个词：
   a. 计算 djb2 哈希值：hash = ((hash << 5) - hash + charCode) | 0
   b. 维度索引 = |hash| % 128
   c. 该维度累加 1.0 / (词位置 + 1)
      → 越靠前的词权重越高（位置0: 1.0, 位置1: 0.5, 位置2: 0.33...）
4. L2归一化：vector /= sqrt(Σvi²)
```

**降级触发条件**：

- `EmbeddingService` 未注入
- `EmbeddingService.embed()` 调用失败
- 统计指标：`stats.fallbackQueries` 记录降级查询次数

### 9.3 查询流程

```
query(queryText, { topK, threshold })
    │
    ├── 生成查询向量
    │   ├── 有EmbeddingService → embed(queryText)
    │   └── 无或失败 → _generateFallbackVector(queryText)
    │
    ├── 遍历所有已索引向量
    │   └── _cosineSimilarity(queryVec, entryVec)
    │       → 过滤低于threshold的结果
    │
    ├── 按相似度降序排序
    │
    └── 返回topK结果
        每个结果包含：{ causalId, text, metadata, similarity }
        similarity保留3位小数（roundTo）
```

### 9.4 统计指标

| 指标 | 说明 |
|------|------|
| `totalVectors` | 当前索引向量数 |
| `maxVectors` | 最大向量容量 |
| `indexed` | 累计索引次数 |
| `queries` | 累计查询次数 |
| `hits` | 命中次数（返回非空结果） |
| `misses` | 未命中次数 |
| `hitRate` | 命中率 = hits / queries |
| `fallbackQueries` | 降级查询次数 |
| `embeddingServiceAvailable` | EmbeddingService是否可用 |

const CausalDataBus = require('./src/runtime/causal/causal-data-bus');

  causalInputs: [{ name: 'idea', source: 'skill:brainstorming', required: true }],
