# 多Agent协作使用准则

## 概述
本文档提供多Agent协作的最佳实践和使用准则（2.73.4），确保项目高效、规范地运行。包含TDD强制准则、Skill自动路由准则和证据验证准则。

## 核心准则

### 1. 任务拆解原则
- 每个任务应有明确的单一目标
- 任务粒度适中，既不过大导致难以管理，也不过小导致开销过大
- 明确任务间的依赖关系，避免循环依赖
- 为每个任务设定清晰的验收标准

### 2. Agent选择原则
- 根据任务类型选择合适的Agent角色
- 考虑Agent的当前负载和能力
- 避免同一Agent同时处理过多任务
- 关键任务应有备份Agent

### 3. TDD强制原则
- **铁律**：NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST
- 所有开发任务必须先写测试后写代码（RED→GREEN→REFACTOR）
- 先写实现代码则删除，从测试重新开始
- 每个RED-GREEN-REFACTOR循环控制在2-5分钟内
- 测试覆盖率目标≥80%
- tdd-implement Skill为strict enforcement，不可跳过

### 4. Skill自动路由原则
- 收到新任务时，自动扫描Skill的trigger_conditions
- 任务匹配某个Skill的触发条件时，必须按该Skill的步骤执行
- 前序Skill完成后，自动检查后继Skill是否需要激活
- enforcement为strict的Skill不可跳过
- 不确定激活哪个Skill时，按阶段和优先级排序选择

### 5. 证据验证原则
- 声称"完成了"不算完成，提供证据才算完成
- 每项验收标准都需要对应的完成证据
- verification-before-completion为strict enforcement，不可跳过
- 证据类型：测试输出、Lint结果、覆盖率报告、安全扫描结果
- 未通过验证不允许标记任务完成

### 6. 上下文管理原则
- 只加载当前任务所需的上下文
- 定期压缩过长的上下文
- 重要决策和状态变更必须持久化
- 避免在上下文中存储敏感信息

### 7. 文档编写原则
- 文档必须及时更新，与代码保持同步
- 使用双向链接关联相关文档
- 代码示例必须可运行
- 技术术语必须明确定义

### 8. 质量保证原则
- 每个交付物必须经过审核
- 审核必须基于明确的验收标准
- 缺陷必须跟踪到修复确认
- 关键功能必须有测试覆盖

## 常见错误与解决方案

| 错误 | 原因 | 解决方案 |
|------|------|----------|
| 上下文过长 | 加载了过多无关信息 | 触发Compact机制，按需加载 |
| 工具调用失败 | 参数错误或权限不足 | 检查参数，确认权限 |
| 任务超时 | 任务粒度过大或模型响应慢 | 拆分任务，增加超时时间 |
| 模型幻觉 | 缺乏事实核查 | 增加核查步骤，引用可靠来源 |
| 并发冲突 | 多Agent同时修改同一文件 | 加锁，串行化写入 |

## 最佳实践

### 任务分配
1. 优先处理阻塞性任务
2. 并行执行无依赖的任务
3. 预留缓冲时间处理意外情况
4. 定期同步进度，及时调整计划

### 代码开发
1. 遵循项目编码规范
2. 编写可测试的代码
3. 及时提交，避免大量未提交的修改
4. 修改他人代码前先了解上下文

### 文档维护
1. 代码变更时同步更新文档
2. 定期审查文档的准确性和完整性
3. 新增模块时创建对应的文档
4. 使用双向链接保持文档网络的一致性

## 协作模式选择准则

v2.7新增6种协作模式，由 `CollaborationModeRouter` 根据任务特征自动选择。以下为各模式的适用场景和选择指南：

### 模式对比表

| 模式 | 适用场景 | Agent数量 | 关键特征 | 触发信号 |
|------|---------|----------|---------|---------|
| solo | 简单任务、单Agent可完成 | 1 | 无协作开销 | 默认回退 |
| generator-verifier | 质量优先：代码审查、报告撰写、数据校验 | 2-3 | 一个生成、一个独立验证 | 审查/验证/校验/review/verify/audit |
| orchestrator-subagent | 任务可拆解：多模块并行开发、大规模研究 | 3-5 | Lead分解任务，Subagents并行执行 | 拆解/并行/分配/decompose/parallel |
| agent-teams | 成员需沟通：复杂重构、跨模块协调 | 3-5 | Agent间直接通信，维护持久状态 | 协调/沟通/团队/coordinate/team |
| message-bus | 事件驱动扩展：微服务编排、动态能力接入 | 2-10 | 通过共享消息总线通信 | 事件/订阅/通知/event/subscribe |
| shared-state | 多源实时协作：实时文档编辑、多数据源同步 | 2-8 | 通过共享存储实时协作 | 同步/共享/实时/sync/shared |

### 选择决策树

1. **任务是否需要多个Agent？** → 否 → `solo`
2. **是否需要独立验证？** → 是 → `generator-verifier`
3. **任务是否可拆解为独立子任务？** → 是 → `orchestrator-subagent`
4. **Agent间是否需要频繁沟通？** → 是 → `agent-teams`
5. **是否为事件驱动架构？** → 是 → `message-bus`
6. **是否需要实时共享状态？** → 是 → `shared-state`
7. **默认** → `orchestrator-subagent`

### 手动覆盖

可通过 `overrideMode(sessionId, mode)` 手动覆盖自动选择，覆盖在1小时TTL后自动失效：

```javascript
router.overrideMode('session-123', 'generator-verifier');
```

### 降级策略

当所需执行器未附加时，自动降级为 `solo` 模式并发出 `mode-degraded` 事件。降级场景：
- `orchestrator-subagent` 或 `generator-verifier` 需要 `SubagentExecutor` 未附加
- `agent-teams`、`message-bus`、`shared-state` 需要 `AgentChannel` 未附加

## 目标执行准则

### 何时创建目标

- 任务需要多轮迭代才能收敛时（如代码优化、方案精化）
- 任务可分解为多个子任务且子任务间存在依赖关系时
- 需要量化质量评分和收敛检测时
- 单次执行无法确定最优结果时

### 收敛阈值设定

`GoalExecutor` 的 `convergenceThreshold` 默认为 `0.85`，可根据任务类型调整：

| 任务类型 | 推荐阈值 | 说明 |
|---------|---------|------|
| 代码审查 | 0.90 | 质量要求高，需更严格收敛 |
| 功能开发 | 0.85 | 默认值，平衡效率与质量 |
| 方案探索 | 0.75 | 探索性任务，降低阈值避免过度迭代 |
| 数据校验 | 0.95 | 精确性要求极高 |

### 子任务分解原则

- 每个目标最多20个子任务（`maxSubtasks`）
- 子任务间通过 `dependencies` 声明依赖关系
- 循环依赖会被自动检测并标记为 `BLOCKED`
- 无依赖的子任务自动并行执行
- 有依赖的子任务在依赖完成后串行执行

### 停滞检测

当最近5次迭代的质量评分改善幅度小于 `0.02`（`STAGNATION_RATIO`）时，判定为停滞并提前终止。避免在无法继续改善的场景中浪费Token。

## 深化推理使用准则

### 深度级别选择

`DeepeningOrchestrator` 支持4种深度级别：

| 级别 | 迭代次数 | Token消耗预估 | 适用场景 |
|------|---------|-------------|---------|
| quick | 1 | 低（1x） | 快速验证、简单查询 |
| standard | 2 | 中（2x） | 常规开发、一般性任务 |
| deep | 3 | 高（3x） | 复杂架构设计、多方案比较 |
| intensive | 4 | 极高（4x+） | 关键决策、安全审计、性能调优 |

### 何时使用 deep/intensive 级别

- **deep**：任务涉及3个以上模块的协调修改、架构方案需要多轮评审
- **intensive**：安全相关代码审查、性能关键路径优化、不可逆决策前的深度分析

### Token消耗预估

深化推理的Token消耗与迭代次数、Agent数量、缓存命中率相关：

```
预估Token = 基础Token × 迭代次数 × Agent数量 × (1 - 缓存命中率)
```

- `quick`：约 2,000-5,000 Token
- `standard`：约 5,000-15,000 Token
- `deep`：约 15,000-40,000 Token
- `intensive`：约 40,000-100,000 Token

### 缓存利用

- 深化推理支持缓存命中：若缓存中存在满足质量阈值的结果，直接返回
- 缓存键基于任务对象，相同任务不会重复执行
- 通过 `attachCache()` 挂载缓存模块

## 容错与恢复准则

### Checkpoint使用时机

- 目标执行每轮迭代后自动持久化到 `.harness/goals/` 目录
- 关键决策点前手动创建Checkpoint
- 长时间运行的任务每5分钟自动创建Checkpoint
- 进程异常退出后，`GoalExecutor` 自动从持久化文件恢复目标状态

### 目标状态恢复

进程重启后，`GoalExecutor` 自动恢复目标：

- `EXECUTING`/`ITERATING`/`DECOMPOSING` 状态的目标恢复为 `PAUSED`
- 超过TTL（默认7天）的目标自动清理
- 恢复后的目标可通过 `resume()` 继续执行

### 模型降级策略

当主模型不可用时，按以下顺序降级：

1. 主模型（高质量）→ 备用模型（中等质量）
2. 备用模型 → 低价模型（基础质量）
3. 所有模型不可用 → 暂停任务，等待恢复

降级触发条件：
- API调用连续3次超时
- API返回429（速率限制）
- API返回5xx（服务端错误）

### 失败重试

- 子任务失败后，下一轮迭代会自动重试（状态重置为 `PENDING`）
- 子任务超时由 `iterationTimeout` 控制（默认5分钟）
- 目标级超时由 `AbortController` + `Promise.race` 实现

## 成本控制准则

### Token预算分配

项目总Token预算为 1,000,000,000，按以下原则分配：

| 阶段 | 预算占比 | 说明 |
|------|---------|------|
| 需求分析 | 10% | brainstorming + requirement-analysis |
| 架构设计 | 15% | architecture-design + design-md |
| 模块开发 | 50% | tdd-implement + module-development |
| 集成测试 | 15% | integration-testing |
| 部署上线 | 10% | verification + deployment |

### 低价模型使用策略

- 80%预算预警：切换到低价模型处理简单任务
- 95%预算预警：所有任务切换到低价模型
- 100%预算耗尽：暂停所有任务

### Token节省技巧

1. **优先使用缓存**：深化推理缓存、推理缓存（InferenceCache）
2. **选择合适的深度级别**：简单任务用 `quick`，避免过度深化
3. **控制上下文长度**：使用 `ContextCompressionEngine` 压缩过长上下文
4. **批量处理**：将相似任务合并，减少重复的上下文加载
5. **精确代码定位**：使用 `code-locator` 避免全量代码扫描

### Token消耗记录

每次对话轮次结束后，必须通过 `/api/token/record` 端点记录Token消耗：

```javascript
{
  sessionId: 'session-123',
  tokens: 5000,
  inputTokens: 3000,
  outputTokens: 1500,
  toolCallTokens: 500
}
```

## 反模式警示

以下是多Agent协作中的常见反模式，必须避免：

### 1. 单Agent瓶颈

**表现**：所有任务都路由到同一个Agent，其他Agent空闲
**危害**：吞吐量下降、响应延迟增加、单点故障
**解决**：使用 `CollaborationModeRouter` 自动分配，启用 `orchestrator-subagent` 模式

### 2. 过度分解

**表现**：将简单任务拆分为过多子任务（如一个函数修改拆成5个子任务）
**危害**：协调开销超过执行开销、Token浪费、收敛困难
**解决**：子任务粒度以"一个Agent一次可完成"为准，单个目标不超过20个子任务

### 3. 忽略收敛信号

**表现**：质量评分已达到阈值但仍继续迭代
**危害**：Token浪费、边际收益递减
**解决**：严格遵循 `convergenceThreshold`，达到阈值立即停止

### 4. 循环依赖

**表现**：子任务A依赖B，B又依赖A
**危害**：死锁、任务永远无法完成
**解决**：`GoalExecutor` 自动检测循环依赖并标记为 `BLOCKED`，设计时避免

### 5. 上下文爆炸

**表现**：每个Agent都加载完整项目上下文
**危害**：Token消耗指数增长、模型注意力分散
**解决**：使用 `IsolatedContextManager` 隔离上下文，按需加载

### 6. 忽略降级信号

**表现**：`mode-degraded` 事件触发后仍按原模式预期执行
**危害**：实际执行与预期不符、结果质量不可控
**解决**：监听 `mode-degraded` 事件，降级后调整任务策略

### 7. 同步阻塞等待

**表现**：一个Agent同步等待另一个Agent的结果
**危害**：死锁风险、资源浪费
**解决**：使用异步模式（`message-bus`/`shared-state`），通过事件通知结果

### 8. 无证据完成

**表现**：Agent声称任务完成但未提供验证证据
**危害**：质量不可控、缺陷遗漏
**解决**：严格执行 `verification-before-completion`，所有完成声明必须附带证据

### 9. 过度深化

**表现**：所有任务都使用 `intensive` 深度级别
**危害**：Token消耗4倍以上增长、响应时间过长
**解决**：根据任务复杂度选择深度级别，80%任务用 `standard` 即可

### 10. 忽略停滞检测

**表现**：质量评分停滞但仍强制继续迭代
**危害**：浪费Token、无实际改善
**解决**：尊重 `STAGNATION_RATIO` 检测结果，停滞时应调整策略而非继续迭代

## 常见错误与解决方案

| 错误 | 原因 | 解决方案 |
|------|------|----------|
| 上下文过长 | 加载了过多无关信息 | 触发Compact机制，按需加载 |
| 工具调用失败 | 参数错误或权限不足 | 检查参数，确认权限 |
| 任务超时 | 任务粒度过大或模型响应慢 | 拆分任务，增加超时时间 |
| 模型幻觉 | 缺乏事实核查 | 增加核查步骤，引用可靠来源 |
| 并发冲突 | 多Agent同时修改同一文件 | 加锁，串行化写入 |
| 协作模式降级 | SubagentExecutor或AgentChannel未附加 | 检查依赖注入，附加所需执行器 |
| 目标停滞 | 质量评分连续5轮无改善 | 调整策略或降低收敛阈值 |
| 循环依赖 | 子任务间存在环形依赖 | 重新设计任务分解，消除循环 |
| Token预算超限 | 深化级别过高或任务过多 | 切换低价模型，减少并发目标 |
| Checkpoint恢复失败 | 持久化文件损坏 | 清理损坏文件，从最近有效快照恢复 |
| Agent间通信失败 | AgentChannel未初始化或已关闭 | 检查通道状态，重新初始化 |
| 收敛阈值过高 | 任务实际可达质量低于设定阈值 | 降低阈值或增加迭代次数 |
| 子任务超时 | 单个子任务执行时间过长 | 增加iterationTimeout，拆分子任务 |
| 模型降级后质量下降 | 低价模型能力不足 | 降级任务范围，简化输出要求 |
| 事件监听器泄漏 | 模块关闭后未移除监听器 | 确保使用withShutdown，自动removeAllListeners |
