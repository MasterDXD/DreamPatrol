# Skill速查表

> Harness Engineering 多Agent框架 2.73.4 — 全部84个技能

## 需求探索阶段

### /brainstorming — 头脑风暴
**何时使用**：用户提出模糊需求或新想法时
**核心流程**：苏格拉底式提问 → 方案探索（2-3种）→ 分段验证 → 输出设计文档
**关键规则**：逐个问题提问，不一次性抛出所有问题

### /decision-loop — 七层闭环决策
**何时使用**：用户提出战略决策、商业判断或方案选择等非纯技术决策需求时
**核心流程**：背景层 → 选项层 → 假设层 → 反驳层 → 标准层 → 实验层 → 复盘层
**关键规则**：反驳层强制反谄媚机制，对每个关键假设进行"反对者审判"

### /idea-validation — 想法验证
**何时使用**：用户提出创业想法或需要验证商业假设时
**核心流程**：提取核心假设 → 构建假设验证矩阵 → 竞争格局扫描 → 不确定性量化 → 生成验证报告
**关键规则**：不确定性评分>0.7回退brainstorming，0.4-0.7小规模实验，<0.4进入需求分析

## 需求分析阶段

### /requirement-analysis — 需求分析
**何时使用**：收到新项目或新功能需求时
**核心流程**：收集需求 → 分类（功能/非功能/约束）→ 细化（用户故事+验收标准）→ 排优先级 → 生成文档
**关键规则**：不自行假设，模糊点必须向用户确认

### /necessity-review — 需求必要性审查
**何时使用**：需求分析完成后，审查需求是否必要和合理时
**核心流程**：需求清单 → 必要性评估 → 优先级调整 → 输出审查报告
**关键规则**：每个需求必须有明确的业务价值支撑

## 架构设计阶段

### /architecture-design — 架构设计
**何时使用**：需求分析完成，需要设计系统架构时
**核心流程**：理解需求 → 架构选型 → 模块划分 → 接口设计 → 架构评审 → 输出文档
**关键规则**：技术选型必须有明确理由，优先保证MVP可用

### /design-md — 设计文档规范 🔴 STRICT
**何时使用**：架构设计完成后，需要规范化设计文档时
**核心流程**：设计审查 → 文档规范检查 → 格式修正 → 合规输出
**关键规则**：设计文档必须符合六层文档体系规范

### /taste-skill — 设计品味审查
**何时使用**：设计完成后，审查设计品味和审美质量时
**核心流程**：设计评估 → 品味标准对照 → 改进建议 → 输出审查报告
**关键规则**：设计必须符合行业最佳实践和用户体验标准

### /cloud-ai-blueprint — AI系统蓝图规划
**何时使用**：需要规划AI系统架构或集成AI能力时
**核心流程**：模型层规划（角色分工+降级链）→ 工具层规划（能力边界+安全级别）→ 数据流层规划（流转路径+验证节点）→ 工作流层规划（执行模式+状态转换）→ 输出蓝图文档
**关键规则**：未完成蓝图规划不得进入module-development阶段；每个模型角色必须有降级链

## 模块开发阶段

### /tdd-implement — TDD驱动开发 🔴 STRICT
**何时使用**：设计文档完成，需要编码实现时
**核心流程**：RED（写失败测试）→ GREEN（写最小实现）→ REFACTOR（优化）
**铁律**：NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST
**关键规则**：先写代码则删除；每个循环2-5分钟；覆盖率≥80%

### /module-development — 模块开发 🔴 STRICT
**何时使用**：设计文档完成，进入开发阶段时
**核心流程**：理解需求 → 环境准备 → TDD开发循环 → 集成验证 → 文档编写 → 完成验证 → 提交审核
**TDD门禁**：自动激活tdd-implement Skill
**关键规则**：任何实现代码必须在失败测试之后编写

### /mvp-builder — MVP构建
**何时使用**：用户需要快速构建最小可行产品或原型时
**核心流程**：定义MVP范围 → 架构先行 → AI辅助编码 → 技术债管理 → 安全从零开始 → MVP测试与交付
**关键规则**：MVP只实现一条完整用户路径；P0级技术债上线前必须清偿

### /code-locator — 精准代码定位
**何时使用**：需要修改代码但不确定涉及哪些文件，或需要理解跨文件依赖时
**核心流程**：关键词召回（文件名/导出名/字符串/注释匹配）→ 依赖链展开（向上+向下追踪）→ 影响范围评估 → 生成定位报告
**关键规则**：不靠猜，靠算法；两阶段检索可定位隐藏依赖（懒加载/事件总线/配置）

### /source-driven-development — 源码驱动开发
**何时使用**：使用框架特定API、引入新依赖、或怀疑训练数据可能过时时
**核心流程**：检测技术栈和版本 → 获取官方文档 → 按文档模式实现 → 引用来源
**关键规则**：每个框架特定的代码决策必须由官方文档支撑；文档与现有代码冲突时必须暴露

### /deprecation-and-migration — 废弃与迁移管理
**何时使用**：替换旧系统/API/库、下线功能、合并重复实现、或移除死代码时
**核心流程**：废弃决策评估 → 确定废弃类型（建议性/强制性）→ 构建替代方案 → 公告和文档 → 增量迁移 → 移除旧系统
**关键规则**：不在没有替代方案时废弃；代码是负债不是资产；僵尸代码必须获得投资或被移除

### /web-interaction — 网页交互
**何时使用**：用户要求访问网页数据、操作网页界面、从网站提取信息或控制桌面应用时
**核心流程**：环境检查（OpenCLI+Chrome Bridge）→ 工具发现（80+网站适配器）→ 执行操作（导航/提取/交互）→ 结果验证
**关键规则**：仅操作用户明确授权的网站；复用已登录Chrome会话；敏感操作需用户确认

### /cli-anything — 软件操控
**何时使用**：用户需要通过CLI操控本地专业软件或将软件转化为AI可调用工具时
**核心流程**：环境检查（Python 3.10+/CLI-Hub）→ 发现可用CLI → 安装CLI → 执行操作 → 结果验证
**关键规则**：与web-interaction互补（web操控网页，cli操控本地软件）；仅操作用户明确授权的软件

### /impeccable — 代码无瑕疵追求
**何时使用**：追求代码极致质量，消除所有潜在问题时
**核心流程**：代码审查 → 瑕疵识别 → 修复建议 → 验证确认
**关键规则**：不放过任何代码异味和潜在问题

### /ui-skills — UI/UX开发技能
**何时使用**：开发用户界面和交互体验时
**核心流程**：设计规范解读 → 组件开发 → 交互实现 → 无障碍验证 → 响应式测试
**关键规则**：必须符合设计系统和无障碍标准

### /iterative-deepening — 迭代深化推理
**何时使用**：复杂问题需要多轮迭代精化时
**核心流程**：初始方案 → 质量评分 → 收敛检测 → 迭代精化 → 最终输出
**关键规则**：每轮迭代必须有可衡量的质量改进

### /multi-agent-fusion — 多Agent融合输出
**何时使用**：需要多个Agent协作产出融合结果时
**核心流程**：任务分解 → 多Agent执行 → 输出融合 → 冲突解决 → 最终输出
**关键规则**：融合策略必须与任务类型匹配

### /motion-ai-kit — 动效AI工具包
**何时使用**：开发动画和交互动效时
**核心流程**：动效需求 → 预设选择 → 参数调整 → 性能验证 → 输出CSS/JS
**关键规则**：动效必须符合性能预算和可访问性要求

### /better-icons — 图标优化
**何时使用**：优化图标使用和图标系统时
**核心流程**：图标审计 → 优化建议 → SVG优化 → 图标系统集成 → 验证
**关键规则**：图标必须使用SVG格式，支持主题切换

### /dispatching-parallel — 并行子代理调度
**何时使用**：存在多个可并行执行的独立任务时
**核心流程**：任务独立性分析 → Git Worktree隔离 → 子代理分配 → 并行执行监控 → 结果合并 → 清理
**关键规则**：修改同一文件的任务不可并行

## 质量保障阶段

### /code-review — 代码审查 🔴 STRICT
**何时使用**：Task Worker提交代码后
**核心流程**：获取代码 → 规范检查 → 逻辑检查 → 安全检查 → 测试检查 → 生成报告
**关键规则**：测试覆盖不足标记为"不通过"

### /verification-before-completion — 完成前验证 🔴 STRICT
**何时使用**：Agent声称任务完成时
**核心流程**：验收标准回顾 → 功能验证 → 质量验证 → 安全验证 → 文档验证 → 生成验证报告
**铁律**：声称"完成了"不算完成，提供证据才算完成
**关键规则**：未通过验证不允许标记任务完成

### /systematic-debugging — 系统化调试
**何时使用**：遇到难以定位的Bug或复杂故障时
**核心流程**：隔离（复现+缩小范围）→ 假设（3-5个可验证假设）→ 验证（设计实验）→ 修复（先写失败测试）
**关键规则**：不猜测、不跳跃、不盲改、不遗漏

### /bug-fix — 缺陷修复 🔴 STRICT
**何时使用**：QA报告缺陷或用户反馈Bug时
**核心流程**：理解缺陷 → 复现问题 → 定位根因 → 制定方案 → 实施修复 → 提交审核
**关键规则**：修复必须添加覆盖缺陷场景的测试

### /security-audit — 安全审计 🔴 STRICT
**何时使用**：模块开发完成或定期安全审查时
**核心流程**：确定范围 → 敏感信息扫描 → 输入验证检查 → 认证授权检查 → 数据安全检查 → 生成报告
**关键规则**：严重和高危漏洞必须立即修复

### /performance-optimization — 性能优化
**何时使用**：系统性能不达标或响应时间超过阈值时
**核心流程**：性能基线 → 瓶颈定位 → 优化方案 → 实施优化 → 效果验证
**关键规则**：只优化达到瓶颈的部分，不提前优化

### /refactor-code — 系统化重构
**何时使用**：代码结构需要改善但功能行为不变时
**核心流程**：建立安全网（测试覆盖）→ 识别重构目标 → 制定计划 → 逐步重构 → 验证行为不变
**核心原则**：重构 = 行为不变 + 结构改善
**关键规则**：重构与功能修改绝不混合进行

## 集成测试阶段

### /integration-testing — 集成测试 🔴 STRICT
**何时使用**：多个模块开发完成，需要验证模块间协作时
**核心流程**：理解范围 → 制定计划 → 编写用例 → 执行测试 → 缺陷跟踪 → 生成报告
**关键规则**：P0场景必须100%通过

## 部署上线阶段

### /deployment — 部署上线 🔴 STRICT
**何时使用**：集成测试通过，需要部署到目标环境时
**核心流程**：部署前检查 → 准备部署包 → 执行部署 → 部署后验证 → 配置监控 → 生成文档
**关键规则**：生产部署必须有回滚方案

### /ai-native-scaling — AI原生规模化
**何时使用**：产品需要从MVP阶段扩展到规模化运营，或需要构建自动化运营系统时
**核心流程**：评估规模化就绪度（PMF信号）→ 制定AI优先扩展路径 → 构建自动化运营系统 → 设计非线性增长模型 → 人力引入决策框架 → 输出规模化策略
**关键规则**：AI优先扩展，再人力补充；人效比目标为行业平均3倍+；AI覆盖率目标80%+

### /documentation — 文档编写
**何时使用**：代码开发完成、接口变更、新功能上线时
**核心流程**：收集信息 → 确定类型 → 编写文档 → 审核校对 → 发布更新
**关键规则**：代码示例必须可运行

### /auto-doc-generation — 自动文档生成
**何时使用**：需要从代码自动生成API文档和变更日志时
**核心流程**：代码扫描 → 文档模板匹配 → 内容生成 → 格式化输出 → 审核确认
**关键规则**：自动生成的文档必须经过人工审核

**何时使用**：需要优化AI交互提示词或代码生成质量不佳时
**核心流程**：提示词分析 → 模板优化 → 防幻觉策略 → 质量验证 → 输出优化提示词

**关键规则**：skill_id全局唯一，每个Skill聚焦单一职责

**何时使用**：Skill自动发现、匹配、激活
