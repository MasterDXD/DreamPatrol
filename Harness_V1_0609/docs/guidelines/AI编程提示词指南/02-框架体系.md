## 2.1 框架全景对比

不同场景适合不同框架，以下是六大主流框架的对比：

| 框架 | 全称 | 核心要素 | 最佳场景 | 复杂度 |
|------|------|---------|---------|--------|
| **RGIO** | Role-Goal-Input-Output | 角色+目标+输入+输出 | 通用编程任务 | ⭐ |
| **CRISPE** | Capacity-Role-Insight-Statement-Personality-Experiment | 能力+角色+洞察+陈述+个性+实验 | 创意+技术混合任务 | ⭐⭐ |
| **CO-STAR** | Context-Objective-Style-Tone-Audience-Response | 上下文+目标+风格+语气+受众+响应 | 面向特定受众的内容 | ⭐⭐ |
| **RISEN** | Role-Instructions-Steps-End-Narrow | 角色+指令+步骤+终点+收窄 | 多步骤复杂任务 | ⭐⭐⭐ |
| **五段式** | Role-Goal-Input-Process-Output | 角色+目标+输入+过程约束+输出格式 | 工程化编程任务（推荐） | ⭐⭐ |
| **三层式** | TechContext-FunctionalReqs-IntegrationEdges | 技术上下文+功能需求+集成与边缘 | 生产级功能开发 | ⭐⭐⭐ |

## 2.2 五段式工程模型（推荐）

结合Google白皮书、Anthropic指南和社区实践，编程场景最有效的提示词结构：

```
[1. Role 角色] + [2. Goal 目标] + [3. Input 输入] + [4. Process 过程与约束] + [5. Output 输出格式]
```

**完整示例：**

```
# Role（角色）
你是一位拥有10年经验的资深后端架构师，擅长编写高可用、健壮的Python代码。

# Goal（目标）
编写一个Python Redis连接工具类，用于高并发电商系统。

# Input（输入）
- 技术栈：Python 3.11 + redis-py 5.x
- 部署环境：Kubernetes集群，3节点Redis Sentinel

# Process（过程与约束）
1. 使用redis-py库
2. 必须包含连接池（Connection Pool）配置
3. 必须包含异常处理和重试机制
4. 支持Sentinel模式自动故障转移
5. 代码中要有详细的中文注释
6. 不要解释代码原理，直接输出代码块

# Output（输出格式）
以Markdown代码块格式输出，包含完整的类定义和单元测试
```

## 2.3 三层提示词结构（生产级推荐）

Supabase官方推荐，特别适合需要交付生产级代码的场景：

```
Create a TodoItem component with the following specifications:

Technical context:
- React component using TypeScript
- Styled with Tailwind CSS using our design system
- Uses Lucide React icons for UI elements
- Follows existing component patterns with proper props interface

Functional requirements:
- Display todo text with completion checkbox
- Show edit button that toggles inline editing mode
- Include delete button with confirmation dialog
- Visual distinction between completed and pending todos
- Smooth transitions between view and edit modes

Integration and edge cases:
- Integrates with Supabase for state management
- Handle empty or whitespace-only todo text gracefully
- Optimistic UI updates during API calls
- Keyboard shortcuts: Enter to save, Escape to cancel
- Loading states for delete and update operations
- Prevent double-clicks on action buttons
```

## 2.4 CO-STAR框架示例

```
# Context（上下文）
我们正在开发一个面向金融行业的合规报告系统，需要处理敏感数据。

# Objective（目标）
编写一个数据脱敏工具函数，对用户PII数据进行加密替换。

# Style（风格）
遵循我们现有的 src/utils/crypto.ts 中的编码风格。

# Tone（语气）
专业、精确，注重安全性。

# Audience（受众）
中级Python开发者，有基本的安全意识。

# Response（响应格式）
输出包含：函数代码 + 类型定义 + 3个测试用例 + 安全审查清单
```

## 2.5 框架选择决策树

```
你的任务是什么？
│
├─ 通用编程任务 ────────────────→ RGIO（最简单）
│
├─ 工程化编程任务 ──────────────→ 五段式（推荐）
│
├─ 生产级功能开发 ──────────────→ 三层式（最严谨）
│
├─ 面向特定受众 ────────────────→ CO-STAR
│
├─ 创意+技术混合 ───────────────→ CRISPE
│
└─ 多步骤复杂任务 ──────────────→ RISEN
```

---

## 关键要点

1. **五段式是编程场景的推荐框架**——平衡了完整性和易用性
2. **三层式适合生产级代码**——技术上下文+功能需求+集成与边缘
3. **框架选择取决于场景**——简单任务用简单框架，复杂任务用复杂框架
4. **所有框架的核心都是结构化**——结构化输入产生结构化输出

## 2.7 五段式深度实战（冠军方法论）

> 来源：Claude黑客松冠军团队实战沉淀，核心是"结构化Prompt框架"让AI精准对齐需求。

### 五段式完整定义

| 段落 | 名称 | 作用 | 示例 |
|------|------|------|------|
| 第1段 | 身份定义 | 明确AI角色+专业背景 | "你是一位5年B2B SaaS产品经验的资深产品经理" |
| 第2段 | 场景约束 | 说明场景、限制条件 | "预算10万内，面向下沉市场用户，3天内交付" |
| 第3段 | 目标拆解 | 拆分为2-3个可量化子目标 | "短视频脚本需达到3秒完播率≥40%、转化率≥5%" |
| 第4段 | 输出规范 | 指定格式、长度、结构 | "分3部分撰写，每部分不超过500字，附数据支撑" |
| 第5段 | 反馈机制 | 告知后续协作方式 | "先出大纲，确认后再细化，有修改会标注具体章节" |

### 与RGIO/五段式公式的映射关系

| 开源五段式 | 项目五段式公式 | 差异说明 |
|-----------|--------------|---------|
| 身份定义 | Role 角色 | 完全一致 |
| 场景约束 | Process 过程与约束 | 开源版强调"场景"，项目版强调"过程"——两者互补 |
| 目标拆解 | Goal 目标 | 开源版强调"量化拆解"，项目版强调"单一目标"——开源版更精细 |
| 输出规范 | Output 输出格式 | 完全一致 |
| 反馈机制 | — | **开源版独有**，项目版缺失——建议补充 |

### 增强建议：五段式+反馈机制

在项目现有五段式公式基础上，增加第6段"反馈机制"：

```
[Role 角色] + [Goal 目标] + [Input 输入] + [Process 过程与约束] + [Output 输出格式] + [Feedback 反馈机制]
```

**Feedback段模板**：
- 单次交付：`"直接输出最终结果，无需解释过程"`
- 迭代协作：`"先输出大纲/方案，等我确认后再细化实现"`
- 逐步验证：`"每完成一个步骤，暂停等我确认后再继续下一步"`

### 多场景五段式实战案例

#### 案例1：产品需求文档生成
```
[Role] 你是一位5年B2B SaaS产品经验的资深产品经理，擅长将模糊需求转化为可执行的产品方案
[Goal] 为"企业知识库AI助手"功能撰写PRD，核心目标：①用户能在30秒内找到准确答案 ②知识库维护成本降低50%
[Input] 现有产品：企业IM工具，日活10万；用户痛点：内部文档分散，搜索效率低；技术栈：Node.js + Vue3 + Elasticsearch
[Process] 约束：不引入新外部服务；需兼容现有IM权限体系；优先考虑搜索准确率而非覆盖率；输出分4部分（背景/方案/指标/排期）
[Output] Markdown格式PRD，每部分不超过800字，附数据支撑和竞品对比
[Feedback] 先输出方案框架和核心指标定义，确认后再细化功能描述和排期
```

#### 案例2：代码架构设计
```
[Role] 你是一位10年Node.js后端架构经验的资深工程师，精通微服务和事件驱动架构
[Goal] 设计"实时协作编辑"后端架构，核心目标：①支持100人同时编辑 ②冲突解决延迟<100ms
[Input] 现有系统：单体Node.js应用，MySQL + Redis；技术约束：必须使用OT算法；部署环境：K8s集群
[Process] 约束：不引入新数据库；需兼容现有认证体系；优先保证一致性而非可用性；输出架构图+核心接口定义+数据流图
[Output] 架构设计文档，含Mermaid架构图、接口定义(TypeScript类型)、数据流说明
[Feedback] 先输出架构选型对比和核心数据流，确认后再细化接口和部署方案
```

#### 案例3：数据分析报告
```
[Role] 你是一位3年数据分析经验的商业分析师，擅长从数据中提取业务洞察
[Goal] 分析用户流失原因，核心目标：①识别Top3流失因素 ②提出可落地的挽回策略
[Input] 数据源：用户行为日志(30天)、客服工单、NPS调研；工具：SQL + Python；业务背景：SaaS产品，月流失率8%
[Process] 约束：仅使用已有数据源；分析需包含统计显著性检验；策略需预估ROI；输出分3部分（发现/归因/建议）
[Output] 结构化分析报告，每部分附数据图表描述和统计指标，建议部分含ROI预估
[Feedback] 先输出初步发现和假设，确认分析方向后再深入归因和建议
```
