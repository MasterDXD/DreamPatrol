## 1.1 LLM的本质：概率预测机

LLM本质上是"基于已生成token + 输入上下文"预测下一个token的概率预测机。你给的信息越少，模型越容易"自由发挥"；你提供结构（角色、步骤、格式、示例）越多，模型越容易"按图索骥"。

**关键事实：**

| 事实 | 含义 | 实践指导 |
|------|------|---------|
| 模型不会"理解意图"，只会预测"最可能后续" | 模糊输入→模型从训练分布找"它觉得你想要的" | 必须精确表达需求 |
| Prompt = 控制输入空间 | 信息越少→自由发挥越多 | 提供结构（角色、步骤、格式、示例） |
| 配置参数和Prompt同等重要 | 参数错了也会跑偏 | Prompt文本 + 配置工程 = 完整方案 |

---

## 1.2 三大核心原则

| 原则 | 说明 | 数据支撑 |
|------|------|---------|
| **具体性（Specificity）** | 模糊提示→模糊代码；精确提示→精确代码 | OpenAI数据：优化提示词使准确率提升47% |
| **上下文（Context）** | 始终假设AI对你的项目一无所知 | PromptPerfect报告：迭代次数从5.2次降至1.8次 |
| **约束（Constraints）** | 约束反而改善AI输出——开放请求给AI太多选择 | 实践验证：减少80%重写 |

## 1.3 好提示 vs 坏提示：全场景对比

### 代码生成

**❌ 坏提示：**
```
创建一个登录表单
```

**✅ 好提示：**
```
创建一个React登录表单，要求：
- 邮箱输入（使用正则验证）
- 密码输入（最少8位，显示/隐藏切换）
- "记住我"复选框
- 提交按钮（加载时禁用）
- 表单下方显示错误信息
- 使用Tailwind CSS样式
- 使用react-hook-form进行表单验证
```

### Bug修复

**❌ 坏提示：**
```
这段代码有bug，帮我修一下
```

**✅ 好提示：**
```
Bug描述：调用 UserService.getUserById() 当数据库无匹配记录时，
抛出 TypeError: Cannot read property 'id' of null
预期行为：返回 null
实际行为：抛出 TypeError
环境：Node.js 20 + TypeORM 0.3.x + PostgreSQL 15
代码位置：src/services/user.service.ts 第45行
```

### 代码重构

**❌ 坏提示：**
```
优化这段代码
```

**✅ 好提示：**
```
重构 src/utils/validator.ts 中的 validateUser() 函数：
- 目标：提升可读性和可测试性
- 拆分为单一职责的小函数
- 使用依赖注入替代硬编码的数据库连接
- 保持现有行为不变（所有现有测试必须通过）
- 遵循 src/utils/parser.ts 的代码风格
```

---

## 关键要点

1. **LLM是概率预测机**——你控制输入空间，就控制输出质量
2. **三大原则缺一不可**——具体性、上下文、约束共同作用
3. **约束反而改善输出**——这是最反直觉但最重要的发现
4. **参数和提示词同等重要**——完整的方案 = 文本 + 配置
