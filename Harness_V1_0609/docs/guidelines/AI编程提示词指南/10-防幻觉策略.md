# 模块10：应对AI幻觉的专项策略

> 所属层级：质量层 | 前置模块：[03-十大核心技巧](03-十大核心技巧.md) | 后续模块：[12-反模式与常见错误](12-反模式与常见错误.md)

---

> AI幻觉是编程场景最大的痛点之一——编造不存在的API、虚构依赖库、生成看似正确但无法编译的代码。

---

## 10.1 幻觉的常见类型

| 幻觉类型 | 表现 | 频率 |
|---------|------|------|
| **虚构API** | 调用不存在的方法或参数 | ⭐⭐⭐⭐⭐ |
| **编造依赖** | import不存在的库 | ⭐⭐⭐⭐ |
| **版本混淆** | 使用错误版本的API | ⭐⭐⭐⭐ |
| **逻辑幻觉** | 代码看起来对但逻辑有bug | ⭐⭐⭐ |
| **注释不一致** | 注释说的和代码做的不一样 | ⭐⭐⭐ |

---

## 10.2 七大防幻觉策略

### 策略1：约束锚定——禁止引入新依赖

```
请仅使用项目已有的依赖（见package.json），不要引入任何新的npm包。
如果需要新功能，用已有依赖实现。
```

### 策略2：要求引用文档

```
请为每个API调用注明官方文档链接。如果不确定某个API是否存在，
请明确标注"需验证"。
```

### 策略3：要求可运行证据

```
请确保生成的代码可以直接运行。包含所有必要的import语句。
如果某个库可能不存在，请提供替代方案。
```

### 策略4：分步验证

```
请分步实现，每一步后列出验证方法：
1. 实现步骤1 → 验证：运行xxx命令应得到yyy输出
2. 实现步骤2 → 验证：调用xxx接口应返回zzz
```

### 策略5：自我审查

```
代码生成后，请自我审查：
1. 所有import的库是否真实存在？
2. 所有API调用是否符合最新版本文档？
3. 是否有TODO占位符需要实现？
4. 代码能否直接编译/运行？
```

### 策略6：提供参考实现

```
以下是官方文档中的示例代码：
{粘贴官方示例}

请基于这个示例实现类似功能，不要偏离官方API用法。
```

### 策略7：设置防幻觉红线（Claude官方推荐）

在提示词中加入强硬指令，要求AI在不确定时明确承认，这是让AI输出可靠的关键。

**模板：**
```
如果你对某个API、方法或库的存在不确定，就直接说"我不确定这个API是否存在"。
只在非常确定的情况下才下结论。不要编造任何API调用或依赖。
```

**为什么有效：**
- 默认情况下，AI倾向于"帮到你"——即使不确定也会尝试回答
- 红线指令改变了AI的决策阈值：从"尽量回答"变为"不确定就不答"
- 与防幻觉三件套配合使用，形成四重保障：约束锚定+可运行证据+自我审查+红线指令

**红线指令的三个层次：**

| 层次 | 指令强度 | 适用场景 |
|------|---------|---------|
| 温和 | "如果不确定，请标注'需验证'" | 信息收集、调研 |
| 标准 | "如果不确定，就直接说不知道" | 代码生成、API调用 |
| 严格 | "任何不确定的结论都必须标注置信度，低于80%的禁止输出" | 生产级代码、安全相关 |

---

## 关键要点

1. **虚构API是最常见的幻觉**——约束锚定和引用文档是首选对策
2. **七种策略可组合使用**——约束+自我审查+可运行证据三重保障
3. **红线指令是Claude官方推荐的最强防幻觉手段**——改变AI的决策阈值，从"尽量回答"变为"不确定就不答"
4. **提供参考实现是最直接的防幻觉方法**——锚定在真实代码上
5. **分步验证让幻觉无处藏身**——每步都有验证标准
