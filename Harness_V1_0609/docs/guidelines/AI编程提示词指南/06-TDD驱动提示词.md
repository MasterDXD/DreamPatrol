> 研究表明：提示工程本质上是TDD原则在AI通信中的应用。LLM的概率特性使得TDD比传统开发中更加关键——测试提供了可验证的规格说明，确保生成代码的可预测性和可靠性。

---

## 6.1 TDD提示词模式：先测试后实现

### 第一步：写测试（RED）

```
我需要实现一个 {功能描述} 的函数。请先编写测试用例：

技术栈：{语言} + {测试框架}

测试用例应覆盖：
1. 正常输入的预期输出
2. 空输入 / null / undefined
3. 边界值（0、负数、极大值）
4. 非法输入类型
5. 并发场景（如适用）

先只写测试，不要写实现代码。
```

### 第二步：写实现（GREEN）

```
基于上面的测试用例，现在请编写实现代码。
要求：
- 通过所有测试用例
- 使用最简单直接的实现
- 不要过度设计
```

### 第三步：重构（REFACTOR）

```
现在代码已经通过所有测试。请重构以提升：
1. 可读性
2. 性能
3. 代码复用

约束：重构后所有测试必须仍然通过。
```

---

## 6.2 测试即规格说明模式

将测试用例作为需求规格，让AI根据测试生成实现：

```
以下是函数的测试用例（即需求规格）。请编写能通过所有测试的实现：

```python
def test_calculate_discount():
    assert calculate_discount(100, "regular") == 0
    assert calculate_discount(100, "silver") == 5
    assert calculate_discount(100, "gold") == 10
    assert calculate_discount(100, "platinum") == 15
    assert calculate_discount(0, "gold") == 0
    assert calculate_discount(-100, "gold") == 0
    with pytest.raises(ValueError):
        calculate_discount(100, "invalid")
```

请实现 calculate_discount 函数。
```

---

## 6.3 TDD提示词的三重保障

| 保障层 | 机制 | 效果 |
|--------|------|------|
| **规格保障** | 测试用例即需求规格 | AI不会偏离需求 |
| **验证保障** | 代码必须通过测试 | 输出可验证、可量化 |
| **回归保障** | 重构后测试仍通过 | 不会引入新bug |

---

## 关键要点

1. **先写测试再写实现**——测试即规格，消除歧义
2. **测试即规格说明模式**——用测试替代自然语言描述需求
3. **RED-GREEN-REFACTOR三步法**——每步都有明确的提示词模板
4. **TDD是防幻觉的最有效手段**——测试提供了可验证的规格
