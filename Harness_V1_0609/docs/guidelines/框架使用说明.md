## 一、框架概述

### 1.1 这是什么
Harness Engineering 多Agent框架是一套**"分层分责+文档驱动+流程管控+容错自愈"**的工程化开发范式。你只需提供需求，框架自动驱动多个AI Agent协作完成从需求分析到部署上线的全流程开发。

### 1.2 核心理念
- **框架即引擎**：你提供方向，框架驱动执行
- **文档即代码**：所有决策和交付物以文档形式存在和流转
- **渐进式交付**：从宏观到微观逐批推进，每批可验收、可回滚

## 二、快速开始

### 2.1 三步启动

**第1步：填写需求**

编辑 `requirements.md`，填写你的项目需求：

```markdown
# 项目需求

## 项目名称
在线书店系统

## 项目目标
为小型书店提供在线图书管理和销售平台

## 核心功能
1. 图书管理：增删改查图书信息
2. 用户系统：注册、登录、个人中心
3. 购物车：添加、修改、结算
4. 订单管理：下单、支付、查看历史

## 技术偏好
- 语言：Python
- 框架：FastAPI
- 数据库：PostgreSQL
- 部署：Docker

## 非功能需求
- 性能：API响应 < 200ms
- 安全：JWT认证
```

**第2步：调整配置**（可选）

编辑 `.harness/config.json`：

```json
{
  "project_name": "在线书店系统",
  "default_model": "gpt-4o",
  "token_budget": 1000000000
}
```

**第3步：启动开发**

在AI对话中输入：

```
请作为Team Lead，阅读 requirements.md，按照六阶段执行流程启动项目开发。
```

### 2.2 六阶段自动流转

框架将自动按以下流程推进，你只需在关键节点审核确认：

```
阶段0:需求探索 → 阶段1:需求分析 → 阶段2:架构设计 → 阶段3:模块开发(TDD) → 阶段4:集成测试 → 阶段5:部署上线
   ↓确认方案      ↓审核            ↓审核            ↓关注进度         ↓确认测试         ↓确认部署
```

### 2.3 各阶段详细输入/输出

#### 阶段0：需求探索
Team Lead + Domain Analyst 自动执行（brainstorming Skill）：

| 项目 | 说明 |
|------|------|
| **输入** | 你的需求文档（可以是模糊想法） |
| **输出** | `outputs/设计方案文档.md` — 通过苏格拉底式提问细化的需求方案 |
| **你需要做的** | 回答Agent的提问，确认需求方向 |

#### 阶段1：需求分析与规划
Team Lead + Domain Analyst 自动执行：

| 项目 | 说明 |
|------|------|
| **输入** | 你的需求文档 |
| **输出** | `outputs/项目计划书.md` — 整体规划、里程碑、时间线；`outputs/需求规格说明书.md` — 详细功能需求和非功能需求；`outputs/任务拆解清单.md` — 所有任务及依赖关系 |
| **你需要做的** | 审核这些文档，确认需求理解正确 |

#### 阶段2：架构设计
Domain Analyst 自动执行：

| 项目 | 说明 |
|------|------|
| **输入** | 需求规格说明书 |
| **输出** | `docs/architecture/架构分析-XXX系统.md` — 系统架构图和模块划分；`outputs/接口设计文档.md` — API接口定义；`outputs/数据模型设计.md` — 数据库表结构 |
| **你需要做的** | 审核架构设计，确认技术选型合理 |

#### 阶段3：模块开发
各模块 Analyst + Worker 自动执行：

| 项目 | 说明 |
|------|------|
| **输入** | 架构设计文档 |
| **输出** | `src/` 下的源码文件；单元测试文件；`docs/modules/` 下的模块文档 |
| **你需要做的** | 关注进度，必要时调整优先级 |

#### 阶段4：集成测试
QA Agent 自动执行：

| 项目 | 说明 |
|------|------|
| **输入** | 各模块交付物 |
| **输出** | `outputs/集成测试报告.md`；`outputs/缺陷报告.md` |
| **你需要做的** | 确认关键功能测试通过 |

#### 阶段5：部署上线
DevOps Agent 自动执行：

| 项目 | 说明 |
|------|------|
| **输入** | 测试通过的代码 |
| **输出** | `outputs/部署文档.md`；Docker配置文件；CI/CD配置 |
| **你需要做的** | 确认部署环境配置正确 |

## 三、28个Agent角色详解

### 3.1 职能型Agent（6个）

#### Team Lead（团队负责人）

| 属性 | 说明 |
|------|------|
| **层级** | L1 - 最高层 |
| **核心职责** | 项目拆解、任务分配、进度监控、成果验收 |
| **何时出现** | 全程参与，每个阶段的起点和终点 |
| **可用Skill** | brainstorming, requirement-analysis, dispatching-parallel, writing-skills |

**你与Team Lead的交互**：
- 向Team Lead提交需求 → Team Lead拆解任务
- 向Team Lead询问进度 → Team Lead汇报全局状态
- 向Team Lead提出变更 → Team Lead评估影响并调整

#### Domain Analyst（领域分析师）

| 属性 | 说明 |
|------|------|
| **层级** | L2 - 设计层 |
| **核心职责** | 需求分析、架构设计、代码审核、技术攻关 |
| **何时出现** | 阶段1-4，负责设计决策和质量把关 |
| **可用Skill** | brainstorming, requirement-analysis, architecture-design, code-review, security-audit, performance-optimization, systematic-debugging, refactor-code, writing-skills |

**你与Domain Analyst的交互**：
- 审核架构设计文档 → 确认技术选型
- 审核代码审查报告 → 确认代码质量

#### Task Worker（任务执行者）

| 属性 | 说明 |
|------|------|
| **层级** | L3 - 执行层 |
| **核心职责** | 编码实现、工具调用、过程记录 |
| **何时出现** | 阶段3-4，负责具体的代码编写和Bug修复 |
| **可用Skill** | tdd-implement, module-development, bug-fix, performance-optimization, systematic-debugging, refactor-code, verification-before-completion, writing-skills |

**你与Task Worker的交互**：
- 通常不直接交互，通过Team Lead调度

#### Quality Assurance（质量保证）

| 属性 | 说明 |

| **核心职责** | 质量检查、测试设计、缺陷管理 |

| **可用Skill** | code-review, integration-testing, security-audit, verification-before-completion |

**你与QA的交互**：
- 审核测试报告 → 确认功能正确性
- 审核缺陷报告 → 确认修复优先级

#### DevOps Engineer（运维工程师）

**你与DevOps的交互**：
- 确认部署环境配置
- 确认生产部署（敏感操作需用户确认）

**你与Technical Writer的交互**：

### 4.2 每个Skill的执行步骤概览

**brainstorming（头脑风暴）**
```
理解初始想法 → 苏格拉底式提问 → 方案探索(2-3种) → 分段验证 → 输出设计文档
```

**idea-validation（想法验证）**
```
定义假设 → 设计验证实验 → 收集数据 → 分析结果 → 输出验证报告
```

**decision-loop（七层闭环决策）**
```
背景梳理 → 列出选项 → 形成假设 → 提出反驳 → 制定标准 → 设计实验 → 复盘总结
```

**requirement-analysis（需求分析）**
```
收集需求 → 分类(功能/非功能/约束) → 细化(用户故事+验收标准) → 排优先级 → 生成文档 → 评审
```

**architecture-design（架构设计）**
```
理解需求 → 架构选型 → 模块划分 → 接口设计 → 架构评审 → 输出文档
```

**cloud-ai-blueprint（AI系统蓝图规划）**
```
理解AI需求 → 架构选型 → 模型服务设计 → 数据管道设计 → 集成方案 → 输出蓝图文档
```

**tdd-implement（TDD驱动开发）🔴 STRICT**
```
RED(写失败测试) → GREEN(写最小实现) → REFACTOR(优化) → 循环直至完成
铁律：NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST
```

**module-development（模块开发）🔴 STRICT**
```
理解需求 → 环境准备 → TDD开发循环(激活tdd-implement) → 集成验证 → 文档编写 → 完成验证 → 提交审核
```

**source-driven-development（源码驱动开发）**
```
定位官方文档 → 提取权威信息 → 验证代码决策 → 标注信息来源 → 输出验证报告
```

**deprecation-and-migration（废弃与迁移管理）**
```
识别废弃代码 → 评估影响范围 → 制定迁移计划 → 逐步迁移 → 验证行为不变 → 清理旧代码
```

**code-locator（精准代码定位）**
```
关键词召回 → 依赖链扩展 → BM25+AST调用图定位 → 输出定位结果
```

**web-interaction（Web交互技能）**
```
选择适配器 → 建立连接 → 执行操作 → 提取数据 → 输出结果
```

**cli-anything（软件操控）**
```
注册软件 → 生成CLI接口 → 执行命令 → 解析输出 → 输出结果
```

**mvp-builder（MVP构建）**
```
定义核心功能 → 搭建最小架构 → 实现关键路径 → 验证可行性 → 输出MVP
```

**ai-native-scaling（AI原生规模化）**
```
评估规模化需求 → 设计自动化架构 → 实现运营系统 → 验证扩展性 → 输出规模化方案
```

**dispatching-parallel（并行子代理调度）**
```
任务独立性分析 → Git Worktree隔离 → 子代理分配 → 并行执行监控 → 结果合并 → 清理
```

**code-review（代码审查）**
```
获取代码 → 规范检查 → 逻辑检查 → 安全检查 → 测试检查 → 生成审查报告
```

**verification-before-completion（完成前验证）🔴 STRICT**
```
验收标准回顾 → 功能验证 → 质量验证 → 安全验证 → 文档验证 → 生成验证报告
铁律：声称"完成了"不算完成，提供证据才算完成
```

**systematic-debugging（系统化调试）**
```
隔离(复现+缩小范围) → 假设(3-5个可验证假设) → 验证(设计实验) → 修复(先写失败测试)
```

**bug-fix（缺陷修复）**
```
理解缺陷 → 复现问题 → 定位根因 → 制定方案 → 实施修复 → 提交审核
```

**security-audit（安全审计）**
```
确定范围 → 敏感信息扫描 → 输入验证检查 → 认证授权检查 → 数据安全检查 → 生成报告
```

**performance-optimization（性能优化）**
```
性能基线 → 瓶颈定位 → 优化方案 → 实施优化 → 效果验证
```

**refactor-code（系统化重构）**
```
建立安全网(测试覆盖) → 识别重构目标 → 制定计划 → 逐步重构 → 验证行为不变
核心原则：重构 = 行为不变 + 结构改善
```

**integration-testing（集成测试）**
```
理解范围 → 制定计划 → 编写用例 → 执行测试 → 缺陷跟踪 → 生成报告
```

**deployment（部署上线）**
```
部署前检查 → 准备部署包 → 执行部署 → 部署后验证 → 配置监控 → 生成文档
```

**documentation（文档编写）**
```
收集信息 → 确定类型 → 编写文档 → 审核校对 → 发布更新
```

**writing-skills（技能编写）**
```
识别需求 → 定义元数据 → 编写内容 → 验证质量 → 测试技能 → 注册技能
```

### 5.2 关键规则摘要

**任务超时**：默认20分钟，超时自动告警 → 重试3次（指数退避） → 重分配 → 上报Team Lead

**Token预算**：总量1,000,000,000 → 80%预警 → 95%切换低价模型 → 100%暂停任务

**上下文压缩**：Token使用率达80%时自动触发 → 保留核心决策和状态 → 丢弃冗余过程

**权限控制**：每次操作前检查 → 敏感操作需用户确认 → 所有操作记录审计日志

**Checkpoint**：每30分钟自动创建 → 阶段完成时创建 → 失败时从最近Checkpoint恢复

## 十、常见问题

### Q1: 如何控制开发成本？
1. 简单任务指定使用低价模型（修改config.json的default_model）
2. 精简需求文档，避免模糊描述导致反复修改
3. 利用Skill复用已有流程，减少重复Token消耗
4. 设置合理的phase_budget_allocation

### Q2: 如何确保代码质量？
1. 依赖自动门禁（lint + 测试 + 安全扫描）
2. 要求所有代码经过Domain Analyst审核
3. QA执行集成测试后才允许合并
4. 定期运行security-audit

### Q3: 项目中途需求变更怎么办？
1. 向Team Lead说明变更内容
2. Team Lead评估影响范围
3. 调整任务计划和优先级
4. 受影响的Agent刷新上下文继续工作

### Q4: Agent输出不符合预期怎么办？
1. 在需求文档中增加更具体的描述和示例
2. 在规则文件中增加更严格的验收标准
3. 要求Agent先输出方案再执行，确认后再继续
4. 利用Hook在关键节点插入人工确认

### Q5: 如何处理Token预算不足？
1. 查看当前消耗：`请汇报当前Token使用情况`
2. 切换到低价模型：修改config.json的default_model
3. 增加预算：修改config.json的token_budget
4. 触发上下文压缩：`请触发上下文压缩`

### Q6: 如何回滚到之前的版本？
1. 查看Checkpoint列表
2. 选择目标Checkpoint
3. 执行恢复：`请从Checkpoint [ID] 恢复项目状态`

### Q7: 多人如何协作使用同一框架？
1. 每人负责不同的模块，通过staging区提交代码
2. Team Lead统一协调任务分配
3. 代码审查流水线确保合并质量
4. 变更日志和审计日志确保可追溯
