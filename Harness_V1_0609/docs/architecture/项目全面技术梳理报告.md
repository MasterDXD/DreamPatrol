## 一、项目整体框架结构分析
### 1.1 项目定位

Harness Engineering 是一个面向 AI 辅助编程的 **多 Agent 协作运行框架**，核心理念是"从 Prompt 工程到软件工程的关键跨越"——将规则从 Markdown 文档转化为 **可强制执行的代码**，实现 `分层分责 + 文档驱动 + 流程管控 + 容错自愈` 的工程化方法论。

## 二、核心设计理念阐述
### 2.1"一键设计"理念

Harness 工程的"一键设计"理念体现在三个层面：

#### 2.1.1 斜杠命令 = 一键触发完整工作流

用户只需输入一个斜杠命令（如 `/plan`、`/build`、`/deploy`），系统自动完成从命令路由 → Skill 匹配 → Agent 分配 → 阶段检查 → 门禁验证 → 执行反馈的 **全链路自动化**。
```javascript
// 一键设计的核心实现：CommandRouter + SkillRouter + PhaseOrchestrator 联动
用户输入 "/plan"
  → CommandRouter.resolve("/plan")
  → 返回执行计划: { skills: ["brainstorming", "requirement-analysis", "architecture-design"], agent: "team-lead", phase: "brainstorming" }
  → SkillRouter.match({ userMessage, agent: "team-lead" })
  → 自动按阶段匹配相关 Skill
  → PhaseOrchestrator 验证阶段转换合法性
  → RBACEnforcer 验证权限
  → TDDGate 检查（如果进入开发阶段）
  → 执行 Skill →
```

#### 2.1.2 Skill 自动路由 = 一句话匹配最佳 Skill

用户只需描述需求意图，SkillRouter 通过**四层匹配机制**自动找到最合适的 Skill：
1. **语义匹配**：基于 22 个语义组（tdd, architecture, deploy, debug...）的中英文模糊匹配
2. **触发条件匹配**：逐一检查 Skill 的 `trigger_conditions` 关键词列表
3. **自动触发检查**：项目关键词（"新模块"、"添加依赖"）自动触发对应 Skill
4. **规范状态加分**：有活跃规格文档时，相关 Skill 自动提升优先级
```javascript
// 示例：用户说"帮我部署上线"，系统自动匹配 deployment skill
router.match({ userMessage: "帮我部署上线", agent: "task-worker" })
// → [{ skill_id: "deployment", phase: "deployment", priority: 7, enforcement: "strict" }, ...]
```

#### 2.1.3 PhaseOrchestrator = 自动阶段流转

六阶段（需求探索 → 需求分析 → 架构设计 → 模块开发 → 集成测试 → 部署上线）的流转完全由 PhaseOrchestrator 自动管理，强制阶段转换规则，禁止跳过阶段。
```javascript
// 阶段流转规则（硬编码，不可跳过）
const PHASES = ['brainstorming', 'requirement-analysis', 'architecture-design',
                'module-development', 'integration-testing', 'deployment'];

// 合法转换：brainstorming → requirement-analysis
// 非法转换：brainstorming → module-development（跳过需求分析和架构设计）
```

### 2.2 核心设计原则

#### 2.2.1 分层分责（Layered Responsibility）
```

│ L1: 编辑器适配层 (CMA Adapter)       │ 与编辑器交互
├─────────────────────────────────────┤
│ L2: 命令/意图层 (CommandRouter)      │ 解析用户意图
├─────────────────────────────────────┤
│ L3: Skill 匹配层 (SkillRouter)       │ 路由到合适 Skill
├─────────────────────────────────────┤
│ L4: Agent 执行层 (AgentRuntime)      │ 分配 Agent 执行
├─────────────────────────────────────┤
│ L5: 门禁/验证层 (Gate + Permission)  │ 合规检查
├─────────────────────────────────────┤
│ L6: 持久化层 (Session + Causal)      │ 状态持久化
└─────────────────────────────────────┘
```

#### 2.2.2 文档驱动（Document-Driven）
所有规则、Agent 定义、Skill 模板、命令定义均以 **Markdown 文件**存储在 `.harness/` 目录下，通过 YAML Frontmatter 描述元数据：

```yaml
---
skill_id: brainstorming
name: 头脑风暴
phase: brainstorming
priority: 0
enforcement: recommended
trigger_conditions:
  - "用户需要头脑风暴"
  - "用户需要需求探索"
  - "用户不知道从哪开始"
---
# Skill 正文（Markdown 指令）
```

这种设计使得：
- 规则可读、可编辑、可 Git 版本管理
- 运行时引擎自动解析并强制执行
- 非技术人员也能理解和维护规则

#### 2.2.3 TDD 强制门禁

框架在每个开发阶段的关键节点强制执行 TDD 原则：
```
RED 阶段   → 先写测试，测试必须失败
GREEN 阶段 → 写最小实现使测试通过
REFACTOR   → 重构代码，保持测试通过

违规情况：
  - 实现文件存在但测试文件不存在 → BLOCKED
  - 代码变更后测试未运行 → WARNING
```

#### 2.2.4 容错自愈（Resilience & Self-Healing）
- **重试引擎**（RetryEngine）：指数退避策略，最多重试 3 次
- **梦境引擎**（DreamEngine）：离线分析失败模式，自动生成预防规则
- **错误预防守卫**（ErrorPreventionGuard）：基于历史错误模式，预判并阻止潜在问题
- **代码漂移检测**（CodeDriftDetector）：检测代码偏离架构设计的程度

  }
}

| **L1 路由缓存** | Map 存储匹配结果，TTL 过期 | 减少重复 Skill 匹配开销 |
| **L2 指令缓存** | 按需加载 + LRU 淘汰 | 避免重复读取 Markdown 文件 |
| **L3 资源缓存** | 文件内容去重索引 | 节省内存 + 减少 Token 消耗 |
| **KeyedDebouncer** | 按 key 防抖，300ms 合并写入 | 减少磁盘 I/O |
| **RingBuffer** | 执行历史限制 100 条 | 防止内存无限增长 |
| **BoundedArray** | 事件历史限制 1000 条 | 防止事件总线内存泄漏 |
| **Lazy Exports** | 94 模块延迟加载 | 减少冷启动时间 |
| **InferenceCache** | 推理结果缓存，TTL 30 分钟 | 避免重复 LLM 调用 |
| **模型降级链** | gpt-4o → claude-3-opus → deepseek-v3 | 故障自动切换 |

### 5.4 技术难点与解决方案

#### 难点 1：多 Skill 冲突解决

**问题**：同一用户意图可能匹配多个语义相关的 Skill，如何选择最优？

**解决方案**：
1. 按阶段优先级排序（`PHASE_INDEX`）
2. 按 Skill 优先级数字排序（越小越优先）
3. 规范状态加分机制（活跃规范 → +10，过期规范 → -5）
4. `matchTopK()` 方法：核心 Skill 优先占位，领域 Skill 填充剩余槽位

#### 难点 2：上下文窗口管理

**问题**：多 Skill 叠加导致上下文 Token 爆炸

**解决方案**：
1. 上下文压缩引擎（阈值 0.8）
2. 三层缓存按需加载（L1→L2→L3）
3. Token 预算分配：按阶段按比例：5%/10%/20%/35%/20%/10%
4. Skill 效能评估（`skill-effectiveness`）：最多激活 12 个 Skill，自适应 Top-K

#### 难点 3：TDD 门禁与开发灵活性平衡
**问题**：严格 TDD 执行可能在快速原型阶段过于僵化
**解决方案**：
1. `enforcement` 分级：strict / recommended / optional / always
2. `deviation-approval` 偏差审批机制
3. `execution_mode_manager` 支持模式切换
4. 可配置的覆盖率阈值（默认 80%）

#### 难点 4：多 Agent 协作一致性
**问题**：多 Agent 并行执行如何保证结果一致性？

**解决方案**：
1. `CausalDataBus` 因果数据总线：保证数据因果顺序
2. `AgentDiversityManager`：确保 Agent 多样性（阈值 0.3）
3. `ContributionTracker`：追踪每个 Agent 的贡献度
4. 三种集成模式按需选择（Bagging/Boosting/Stacking）

#### 难点 5：Skill 自演化安全
**问题**：自动生成的 Skill 可能引入错误或降低质量
**解决方案**：
1. `SkillCanary` 金丝雀发布：10% 流量 + 10 轮评估 + 80% 成功率阈值
2. `SkillCurator` 策展机制：自动归档过期 Skill，保留快照可回滚
3. `SkillEvolver` 演化引擎：基于使用率和成功率演变
4. `SkillAuditTrail` 审计追踪：所有 Skill 变更可追溯

**修复文件**：[health-data.js](file:///e:/Harness_V1_0429/src/web/dashboard/data-providers/health-data.js)

#### 修复 2：Deepening 懒加载模块健康状态误判
**问题**：Deepening 子系统 52 个模块中 30+ 个是懒加载的（存储在 `DeepeningModuleRegistry` 中），health-data 直接检查 `rt.deepeningXxx` 属性导致全部显示 `false`
**修复方式**：
1. 添加驼峰转连字符映射（`deepeningCircuitBreaker` → `deepening-circuit-breaker`），与 Registry 中的定义名匹配
2. 在 Registry 中已定义但未加载的模块标记为 `'lazy'` 状态（而非 `false`）
3. `'lazy'` 状态不影响整体健康判定

**效果**：68 个 Deepening 注册项从 `false` 变为 `'lazy'`，整体状态从 `degraded` 变为 `healthy`

#### 修复 3：36 个 Skill 未验证标记
**问题**：33 个 Skill 有 46 个缺少 `verified: true` 或 `stability` 字段
**修复方式**：批量添加 `verified: true` 和 `stability: stable/beta`（根据 enforcement 类型自动判断）
**效果**：84/84 Skills 全部 verified

#### 修复 4：可选依赖容错处理
**问题**：`sqliteStore` 和 `skillImprovementLoop` 依赖 `better-sqlite3` 原生模块，初始化失败时导致整体状态降级
**修复方式**：将 `sqliteStore` 和 `skillImprovementLoop` 标记为可选依赖，缺失时不影响整体健康状态。移除了非运行时组件 `capacityConfig` 的健康检查。
