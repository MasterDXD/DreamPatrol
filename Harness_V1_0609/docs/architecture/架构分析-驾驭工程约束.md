# 驾驭工程（Harness Engineering）架构分析

## 一、背景与目标

### 1.1 Harness Engineering 定义

**驾驭工程（Harness Engineering）** 是一套让 AI Agent 像工业系统一样稳定、可控运行的软件工程规范。其核心理念源自工业控制领域——正如工程师通过仪表盘、安全阀和冗余系统来驾驭复杂的工业流程，驾驭工程通过分层约束、自验证循环和熵治理机制来驾驭 AI Agent 的行为。

传统软件工程关注的是确定性系统的构建，而驾驭工程关注的是**在不确定性系统中建立确定性边界**。AI Agent 的输出具有概率性，其行为轨迹不可完全预测，因此需要一套不同于传统软件工程的约束体系。

### 1.2 核心问题

AI Agent 在实际运行中面临三大核心问题：

| 问题 | 表现 | 后果 |
|------|------|------|
| **不可控** | Agent 偏离任务目标，自行扩展范围 | 资源浪费、结果偏离预期 |
| **不可预测** | 相同输入产生不同输出，行为路径不确定 | 无法复现、难以调试 |
| **容易跑偏** | 上下文污染、记忆混淆、技能退化 | 长期运行后质量下降 |

这三个问题相互关联：不可预测导致不可控，跑偏是不可控的长期累积效应。驾驭工程的目标就是建立一套系统化的约束机制，将这三个问题控制在可接受范围内。

### 1.3 核心原则

> **解决已经出现的，而不是预防未来的错误**

这一原则是驾驭工程的哲学基石，它明确反对过度设计：

- **不追求完美的零故障预测**：AI 系统的本质决定了不可能预见所有失败模式
- **不构建假设性的防护层**：基于"可能出错"的假设来添加约束，往往导致系统复杂度爆炸
- **而是建立快速反馈环**：当错误发生时，能够迅速发现、精准定位、及时修复

这一原则与"防御性编程"有本质区别：防御性编程试图覆盖所有可能的异常路径，而驾驭工程只针对**已观测到的失败模式**建立约束。这保证了约束体系的精简和高效。

### 1.4 本项目融合目标

本项目（Harness V1）已实现了大量与驾驭工程理念一致的组件，但各组件之间存在实现差距。本分析的目标是：

1. **评估六大架构约束的现有实现完成度**
2. **识别每个约束的最大差距**
3. **设计最小化的增强方案**，补强实现差距
4. **确保增强方案不破坏现有架构**，通过事件桥接而非接口修改实现集成

## 二、六大架构约束评估

### 2.1 渐进式披露（Progressive Context Disclosure）

#### 概念

渐进式披露的核心思想是：**不把所有信息一次性给 AI，按任务阶段只披露当前必须的信息**。

#### 比喻

> 就像导航软件不会一次性展示全程地图，而是每到一个路口只告诉你下一步该往哪走。信息过载会导致 AI 注意力分散，产生幻觉和偏航。

#### 技术原理

AI 模型的注意力机制存在"中间遗忘"效应——当上下文中包含大量与当前任务无关的信息时，模型对关键指令的遵从度显著下降。渐进式披露通过控制信息供给的时机和粒度，确保 AI 在每个决策点只面对最小必要信息集。

#### 已有实现

| 组件 | 位置 | 功能 | 与渐进式披露的关系 |
|------|------|------|---------------------|
| **PhaseContextInjector** | `src/runtime/context/` | 阶段规则注入 | 按阶段注入上下文，是渐进式披露的核心执行者 |
| **SkillRouter L1/L2/L3** | `src/skills/` | 三层缓存路由 | L1 精确匹配→L2 语义匹配→L3 LLM 推理，逐层扩大搜索范围 |
| **ContextCompressionEngine** | `src/runtime/context/` | 上下文压缩 | 压缩冗余信息，为必要信息腾出空间 |
| **TokenManager** | `src/runtime/context/` | 预算管理 | 控制 Token 预算，间接约束信息量 |
| **MemoryPrefetcher** | `src/runtime/context/` | 记忆预取 | 按需预取相关记忆，而非全量加载 |

#### 完成度：75%

#### 最大差距

**缺少统一编排器**。当前各组件独立运行，缺乏协调：

- `PhaseContextInjector` 知道当前阶段，但不控制 `MemoryPrefetcher` 的预取范围
- `TokenManager` 管理预算，但不感知 `ContextCompressionEngine` 的压缩策略
- `SkillRouter` 的三层降级与上下文披露阶段无关联

这导致信息披露仍然存在"全量倾倒"的局部问题——虽然每个组件都在做信息控制，但缺少一个全局视角的编排器来协调"在什么阶段、披露什么信息、以什么粒度"。

#### 增强组件

**ProgressiveDisclosureOrchestrator**：统一编排渐进式披露流程，协调各组件按阶段、按优先级、按预算控制信息披露。

### 2.2 三重防线（Soft Constraints + Hardcoding + Linter）

#### 概念

三重防线是驾驭工程最核心的约束机制，由三个递进的防御层组成：

| 层级 | 机制 | 强度 | 示例 |
|------|------|------|------|
| **第一层：软约束** | Prompt 引导 | 弱——AI 可能忽略 | "请遵循 RESTful 风格" |
| **第二层：硬编码** | 代码强制 | 强——AI 无法绕过 | RBAC 权限检查，未授权直接拒绝 |
| **第三层：Linter** | 自动检查 | 中——事后发现 | 代码风格检查、安全漏洞扫描 |

三层防线的关系是递进的：软约束提供方向引导，硬编码提供底线保障，Linter 提供事后兜底。任何单一层都无法提供完整保障，但三层叠加可以覆盖绝大多数失败模式。

#### 已有实现

**第一层：软约束**

位于 `.harness/rules/` 目录下的 15 个规则文件，覆盖：

- 代码风格规则
- 安全规则
- 架构规则
- 测试规则
- 文档规则

**第二层：硬编码**

| 组件 | 功能 |
|------|------|
| **RBACEnforcer** | 基于角色的访问控制，强制权限检查 |
| **PermissionGuard** | 权限守卫，拦截未授权操作 |
| **ToolCallSecurityChain** | 工具调用安全链，校验工具调用参数 |
| **IronRuleEngine** | 铁律引擎，不可违反的硬性规则 |
| **TDDGate** | TDD 门禁，强制测试先行 |

**第三层：Linter**

| 组件 | 功能 |
|------|------|
| **EvidenceVerifier** | 5 维度证据验证，验证输出是否有据可依 |
| **FrameworkComplianceChecker** | 框架合规检查，验证代码是否符合架构规范 |
| **QualityScorer** | 质量评分器，多维度评估输出质量 |
| **PostTaskReviewer** | 任务后审查，事后检查任务完成质量 |

#### 完成度：60%

#### 最大差距

**三层防线无协调框架，软约束到硬编码无映射**。具体问题：

1. **软约束与硬编码脱节**：`.harness/rules/` 中的规则是自然语言描述，与 `IronRuleEngine` 中的硬编码规则没有映射关系。同一条规则可能同时存在于软约束和硬编码中，但两者独立维护，容易不一致。

2. **防线间无升级机制**：当软约束被反复违反时，没有自动将其升级为硬编码规则的机制。理想的流程是：观察到软约束被违反→分析违反模式→将高频违反模式升级为硬编码→在 Linter 中添加对应检查。

3. **Linter 结果无反馈闭环**：`PostTaskReviewer` 发现的问题不会自动回流到软约束或硬编码层，导致同类问题反复出现。

#### 增强组件

**TripleDefenseCoordinator**：协调三层防线的运行，建立软约束→硬编码→Linter 的升级路径和反馈闭环。

### 2.3 自验证循环（Self-Verification Loop）

#### 概念

自验证循环要求 AI Agent 在**执行前后都插入验证**，类似 TDD 的测试驱动思想：

```
验证前置条件 → 执行操作 → 验证后置条件 → 发现偏差 → 自动修正 → 重新验证
```

与 TDD 的 RED-GREEN-REFACTOR 循环类似，但作用范围更广——不仅验证代码正确性，还验证行为合规性、输出质量、上下文一致性等。

#### 已有实现

| 组件 | 功能 | 验证阶段 |
|------|------|----------|
| **TDDGate** | RED-GREEN-REFACTOR 循环 | 执行前（RED）+ 执行后（GREEN） |
| **EvidenceVerifier** | 5 维度证据验证 | 执行后 |
| **PostTaskReviewer** | 任务后审查 | 执行后 |
| **SelfReflection** | 5 维度自评 | 执行后 |
| **AutoReinLearningLoop** | 学习闭环 | 执行后（长期） |

#### 完成度：70%

#### 最大差距

**执行前/后验证无统一闭环，多文件修改无强制审查**。具体问题：

1. **前后验证割裂**：`TDDGate` 的 RED 阶段（执行前）和 GREEN 阶段（执行后）是独立的，没有形成一个"前置条件→执行→后置条件→偏差检测→修正→重新验证"的完整闭环。

2. **多文件修改无强制审查**：当 Agent 一次修改多个文件时，`PostTaskReviewer` 只审查单个文件的变更，缺乏跨文件一致性验证。例如，修改了接口定义但未更新所有实现类。

3. **验证结果无持久化**：每次验证都是独立的，不记录历史验证结果，无法识别"反复出现同一类验证失败"的模式。

#### 增强组件

**VerificationLoop**：统一编排执行前/后验证，形成完整闭环，支持多文件修改的强制审查。

### 2.4 上下文隔离（Context Isolation）

#### 概念

上下文隔离要求**不同 Agent 拥有独立记忆库，不共享记忆**。这是防止上下文污染的核心机制。

#### 技术原理

在多 Agent 协作场景中，如果 Agent 之间共享记忆，会出现：

- **记忆混淆**：Agent A 的任务上下文污染 Agent B 的决策
- **权限泄露**：Agent A 获得了 Agent B 才应该拥有的信息
- **级联偏航**：一个 Agent 的偏航通过共享记忆传播到所有 Agent

上下文隔离通过为每个 Agent 建立独立的记忆空间，从物理层面杜绝这些问题。

#### 已有实现

| 组件 | 功能 | 隔离程度 |
|------|------|----------|
| **IsolatedContextManager** | 隔离上下文管理 | 按 Agent ID 隔离上下文 |
| **SubagentExecutor WORKER 模式** | 隔离执行 | 子 Agent 在隔离环境中执行 |
| **SessionManager** | 会话隔离 | 按会话 ID 隔离状态 |

#### 完成度：65%

#### 最大差距

**隔离是可选非强制，读写权限未分离，全局组件无命名空间**。具体问题：

1. **隔离可选非强制**：`IsolatedContextManager` 提供了隔离能力，但使用隔离是可选的。Agent 可以选择不使用隔离，直接访问全局上下文。在安全敏感场景中，隔离应该是默认行为。

2. **读写权限未分离**：当前隔离模型只有"可访问/不可访问"两种状态，没有更细粒度的读写权限控制。Agent A 可能只需要读取 Agent B 的部分上下文，但当前要么全部可见，要么全部不可见。

3. **全局组件无命名空间**：`EventBus`、`CausalDataBus` 等全局组件没有命名空间隔离，所有 Agent 的事件共享同一命名空间，存在事件名冲突和意外订阅的风险。

#### 增强方向

**增强 `IsolatedContextManager` 权限模型**：

- 将隔离模式从可选改为默认开启
- 引入读写权限分离（read-only / read-write / no-access）
- 为全局组件添加命名空间前缀（如 `agent:agent-id:event-name`）

### 2.5 熵治理（Entropy Governance）

#### 概念

熵治理要求 Agent **定期清理冗余、冲突、过时信息，重构文档**，防止系统在长期运行中因信息熵增而退化。

#### 比喻

> 就像给自动驾驶的船只定期清理船舱——藤壶会附着在船底增加阻力，货物堆积会导致重心偏移，管道老化会引发泄漏。如果不定期清理，船只的性能会持续下降，最终失去控制。AI Agent 也一样：冗余记忆会降低检索精度，冲突规则会导致行为不一致，过时技能会浪费资源。

#### 已有实现

| 组件 | 功能 | 治理维度 |
|------|------|----------|
| **EntropyGovernanceOrchestrator** | 6 大熵指标治理 | 统一治理入口 |
| **SkillReducer** | 技能精简 | 技能冗余 |
| **ThoughtDeduplicator** | 思维去重 | 思维冗余 |
| **DreamEngine** | 离线整合 | 记忆整合 |
| **BrainMemory** | 记忆整合 | 记忆冗余 |
| **SkillRetirementManager** | 技能退休 | 技能过时 |

#### 完成度：70%

#### 最大差距

**治理动作不彻底，各熵减组件无联动，缺少效果验证**。具体问题：

1. **治理动作不彻底**：`SkillReducer` 标记了冗余技能但不自动清理，`ThoughtDeduplicator` 检测到重复思维但只合并不删除源头。治理停留在"识别"阶段，缺少"执行"阶段的彻底性。

2. **各熵减组件无联动**：`SkillReducer`、`ThoughtDeduplicator`、`SkillRetirementManager` 各自独立运行，没有通过 `EntropyGovernanceOrchestrator` 形成联动。例如，一个技能被标记为冗余后，相关的思维记录和规则文件不会自动关联清理。

3. **缺少效果验证**：治理动作执行后，没有验证治理效果。例如，清理冗余技能后，是否真的减少了 Token 消耗？合并重复思维后，检索精度是否提升？没有效果验证，就无法判断治理是否有效。

#### 增强方向

**增强 `EntropyGovernanceOrchestrator` 治理流水线**：

- 将治理流程从"识别→标记"扩展为"识别→标记→执行→验证"四阶段
- 建立各熵减组件的联动机制，实现跨维度治理
- 添加治理效果度量，验证每次治理动作的实际效果

### 2.6 可拆卸性（Detachability / Modularity）

#### 概念

可拆卸性要求**每个功能模块可独立插拔、替换或升级**，这是系统长期可维护性的基础。

#### 技术原理

在 AI Agent 系统中，模块间的耦合是不可避免的，但耦合方式决定了系统的可维护性：

- **紧耦合**：模块 A 直接调用模块 B 的方法，禁用 B 会导致 A 崩溃
- **松耦合**：模块 A 通过事件总线与模块 B 通信，禁用 B 只会导致 A 的事件无人处理

可拆卸性要求所有模块间通信采用松耦合方式，并通过统一的模块注册表管理模块的生命周期。

#### 已有实现

| 组件 | 功能 | 可拆卸性贡献 |
|------|------|---------------|
| **withShutdown 混入** | 优雅关闭 | 模块可安全关闭，释放资源 |
| **PluginManager** | 插件管理 | 插件可动态加载/卸载 |
| **DeepeningModuleRegistry** | 模块注册 | 深化模块的注册与发现 |
| **attach\* 依赖注入** | 依赖注入 | 依赖通过注入而非硬编码 |
| **EventBus** | 事件总线 | 模块间松耦合通信 |

#### 完成度：55%

#### 最大差距

**无全局模块注册表，依赖图不完整，禁用级联效应未处理**。具体问题：

1. **无全局模块注册表**：`DeepeningModuleRegistry` 只管理深化模块，`PluginManager` 只管理插件，缺少一个统一的全局模块注册表来管理所有模块的生命周期、依赖关系和健康状态。

2. **依赖图不完整**：模块间的依赖关系没有完整记录。`attach*` 依赖注入虽然解耦了依赖获取方式，但没有记录"谁依赖谁"的完整图谱。当需要禁用某个模块时，无法预知哪些模块会受影响。

3. **禁用级联效应未处理**：禁用模块 A 后，依赖 A 的模块 B 不会收到通知，可能导致 B 在运行时因缺少依赖而崩溃。需要建立级联禁用机制：禁用 A → 通知所有依赖 A 的模块 → 这些模块决定是降级运行还是也禁用。

#### 增强方向

**新增 `GlobalModuleRegistry`**：

- 统一管理所有模块的注册、发现、生命周期
- 维护完整的模块依赖图
- 实现级联禁用/降级机制

## 三、融合方案

### 3.1 集成路径

融合方案分三个阶段实施，每个阶段都可在不修改现有模块接口的前提下完成：

#### Phase 1（已完成）

- 核心增强模块实现（`ProgressiveDisclosureOrchestrator`、`TripleDefenseCoordinator`、`VerificationLoop`）
- Skill 定义文件（`.harness/skills/harness-engineering.md`）
- 架构文档（本文档）

#### Phase 2

- 与 `PhaseContextInjector` 的桥接：通过事件监听阶段切换，触发渐进式披露
- 与 `SkillRouter` 的桥接：将路由层级与披露阶段关联
- 与 `TDDGate` 的桥接：将 TDD 循环纳入统一验证闭环
- 与 `EvidenceVerifier` 的桥接：将证据验证作为验证闭环的一环

#### Phase 3

- 全局模块注册表（`GlobalModuleRegistry`）实现
- 上下文隔离增强（`IsolatedContextManager` 权限模型）
- 熵治理流水线增强（`EntropyGovernanceOrchestrator` 四阶段流水线）

### 3.2 代码适配策略

#### 新增模块

```
src/runtime/patterns/harness-engineering.js
```

该文件包含三个增强组件的实现，通过 `EventBus` 与现有模块通信，不修改任何现有模块的接口。

#### Skill 定义

```
.harness/skills/harness-engineering.md
```

定义驾驭工程 Skill 的触发条件、执行流程和输出规范，供 `SkillRouter` 路由使用。

#### 集成原则

1. **不修改现有模块接口**：所有增强通过事件桥接实现
2. **渐进式集成**：每个增强组件可独立启用/禁用
3. **零侵入回退**：移除增强组件不影响现有功能

### 3.3 接口设计规范

### 3.4 潜在冲突与解决方案

#### 事件命名冲突

**问题**：增强组件通过 `EventBus` 与现有模块通信，事件名可能与现有事件冲突。

**解决方案**：所有增强组件的事件使用 `harness:` 前缀命名空间：

| 增强组件 | 事件前缀 | 示例 |
|----------|----------|------|
| ProgressiveDisclosureOrchestrator | `harness:disclosure:` | `harness:disclosure:phase-switch` |
| TripleDefenseCoordinator | `harness:defense:` | `harness:defense:rule-upgrade` |
| VerificationLoop | `harness:verification:` | `harness:verification:check-fail` |

#### 与现有 PhaseOrchestrator 的协调

**问题**：`ProgressiveDisclosureOrchestrator` 的阶段切换与现有 `PhaseOrchestrator` 的阶段编排可能产生冲突——两个编排器同时控制阶段流转。

**解决方案**：`ProgressiveDisclosureOrchestrator` 不独立控制阶段流转，而是**监听** `PhaseOrchestrator` 的阶段切换事件，在阶段切换时自动调整信息披露策略：

```
PhaseOrchestrator 发布 phase:switch 事件
  → ProgressiveDisclosureOrchestrator 监听事件
    → 根据新阶段调整披露策略
    → 通知 MemoryPrefetcher 调整预取范围
    → 通知 ContextCompressionEngine 调整压缩策略
```

#### 与 TDDGate 的验证闭环集成

**问题**：`VerificationLoop` 的验证循环与 `TDDGate` 的 RED-GREEN-REFACTOR 循环可能重叠。

**解决方案**：`VerificationLoop` 将 `TDDGate` 作为验证闭环的一个检查点纳入，而非替代：

```
VerificationLoop.execute():
  1. 执行前置条件检查（包括 TDDGate.RED）
  2. 执行操作
  3. 执行后置条件检查（包括 TDDGate.GREEN）
  4. 如果后置条件失败，进入修正循环
  5. 修正后重新执行后置条件检查（TDDGate.REENABLE）
```

### 3.5 回滚机制

增强方案的设计遵循"可独立移除"原则，确保回滚零风险：

#### 模块独立，可单独禁用

每个增强组件是独立的模块，可单独禁用而不影响其他增强组件和现有模块：

| 禁用组件 | 影响范围 | 回滚方式 |
|----------|----------|----------|
| ProgressiveDisclosureOrchestrator | 渐进式披露退回到各组件独立运行 | 移除事件监听 |
| TripleDefenseCoordinator | 三重防线退回到无协调状态 | 移除事件监听 |
| VerificationLoop | 验证退回到 TDDGate 独立运行 | 移除事件监听 |

#### 通过配置开关控制

在 `config.json` 中添加增强组件的开关配置：

```json
{
  "harnessEngineering": {
    "enabled": true,
    "components": {
      "progressiveDisclosure": {
        "enabled": true,
        "options": {}
      },
      "tripleDefense": {
        "enabled": true,
        "options": {
          "upgradeThreshold": 5
        }
      },
      "verificationLoop": {
        "enabled": true,
        "options": {
          "maxRetries": 3
        }
      }
    }
  }
}
```

#### 不修改现有模块，移除无副作用

由于增强组件仅通过事件桥接与现有模块通信，不修改任何现有模块的接口或内部逻辑，因此移除增强组件不会产生任何副作用：

- 现有模块不会因缺少事件监听者而报错（`EventBus` 的发布-订阅模式天然支持无订阅者）
- 现有模块的行为完全不受影响（增强组件只是额外的事件消费者）

## 四、核心原则

> **解决已经出现的，而不是预防未来的错误**

这一原则贯穿驾驭工程的所有设计决策，值得在此深入阐述其内涵和实践意义。

### 4.1 为什么不预防未来错误？

AI 系统的失败模式具有长尾分布特征——绝大多数失败集中在少数已知模式上，而未知的失败模式虽然数量众多，但每个单独出现的概率极低。投入资源预防低概率的未知失败，不如集中资源快速解决高概率的已知失败。

```
投入产出比分析：

预防未知错误：
  - 投入：高（需要预见所有可能失败模式）
  - 产出：低（大部分预防措施永远不会被触发）
  - 副作用：系统复杂度增加，反而引入新的失败模式

解决已知错误：
  - 投入：低（只需针对已观测到的失败模式）
  - 产出：高（每次修复都直接消除一个实际失败模式）
  - 副作用：低（修复是针对性的，不会引入不必要的复杂度）
```

### 4.2 实践中的三个机制

驾驭工程通过三个机制将这一原则落地：

1. **快速反馈**：通过自验证循环，在错误发生后立即发现，而不是等到用户报告
2. **精准定位**：通过三重防线的分层约束，快速定位错误发生在哪一层、哪个规则
3. **及时修复**：通过熵治理和可拆卸性，确保修复动作可以快速执行且不引入新问题

### 4.3 长期稳定运行的保证

这一原则并不排斥预防——它只是将预防建立在已观测事实的基础上。当同一个错误反复出现时，三重防线的升级机制会自动将其从软约束升级为硬编码，从"事后修复"转变为"事前预防"。这是一种**数据驱动的渐进式预防**，而非基于假设的过度预防。

```
错误生命周期：

首次出现 → 快速发现（自验证循环）→ 精准定位（三重防线）→ 及时修复
  ↓
反复出现 → 软约束升级为硬编码（TripleDefenseCoordinator）→ 事前预防
  ↓
长期稳定 → 熵治理清理冗余 → 可拆卸性确保模块健康 → 系统持续进化
```
