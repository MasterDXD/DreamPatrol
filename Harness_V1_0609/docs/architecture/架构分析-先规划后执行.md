# 先规划后执行（Plan-then-Execute）双架构分析

> 版本：2.73.4 | 核心模块：`src/runtime/patterns/plan-execute-enhancer.js`、`src/runtime/workflow/plan-execute-orchestrator.js`、`src/runtime/workflow/goal-executor.js`、`src/runtime/workflow/plan-persistence.js`

---

## 一、背景与目标

### 1.1 核心逻辑

**规划是执行的"导航图"**。Agent先像"项目经理"一样拆解任务，再像"执行者"一样落地。没有规划的执行是"盲人摸象"——每一步都可能是无效劳动；没有执行的规划是"空中楼阁"——再完美的计划也无法产出结果。

先规划后执行（Plan-then-Execute）范式的核心主张：

```
原始需求 → [规划层：拆解+排序+预判] → 结构化计划 → [执行层：逐步+反馈+纠偏] → 确定性交付
```

### 1.2 核心价值

| 维度 | 无规划执行 | 先规划后执行 |
|------|-----------|-------------|
| 任务成功率 | ~50% 概率性完成 | ~85% 确定性落地 |
| 执行效率 | 大量无效试错 | 步步有据，减少返工 |
| 失败恢复 | 从头重试 | 局部重规划，保留已完成果 |
| 可解释性 | 黑盒过程 | 每步有计划、有记录、有原因 |
| 复用性 | 每次从零开始 | 模板化积累，越用越准 |

### 1.3 本项目融合目标

本项目（Harness V1）已实现了规划-执行范式的多个核心模块：

- **PlanExecuteOrchestrator**：完整的"规划→执行→验证→重新规划"闭环编排器
- **GoalExecutor**：目标分解、迭代收敛、子任务并行执行的自主执行引擎
- **PlanPersistence**：计划持久化、版本追踪、防漂移上下文注入
- **PlanExecuteEnhancer**：融合4大子组件的增强模块（RollingPlanner + RequirementBoundary + PlanSchema + PlanMemoryBridge）

但在11个关键组件维度上仍存在实现差距。**融合目标**：补强11个组件的实现差距，建立完整的规划-执行双架构。

---

## 二、11个组件评估

### 2.1 规划层（3步精准任务拆解）

规划层承担"项目经理"角色，将模糊需求转化为可执行的结构化计划。包含3个核心步骤：

#### 2.1.1 需求解析与边界锁定（60%）

**概念**：将原始输入解析为结构化需求，明确范围内外边界，锁定后不可修改，确保执行过程不会偏离需求范围。完整性低于阈值时自动触发澄清请求。

**现有实现**：

| 模块 | 文件 | 已有能力 | 缺口 |
|------|------|---------|------|
| RequirementBoundary | `src/runtime/patterns/plan-execute-enhancer.js` | 需求解析（字符串/对象→结构化）、边界定义（inclusions/exclusions）、边界锁定（lockBoundary）、完整性评估（assessCompleteness）、澄清触发 | 需求解析仅支持简单的分号/换行分割，缺乏语义理解；边界定义需手动指定，无自动推断；完整性评估基于启发式规则，缺乏LLM辅助的深度理解 |
| PlanPersistence | `src/runtime/workflow/plan-persistence.js` | 计划创建/更新/加载、防漂移上下文注入（injectContext）、版本追踪 | 防漂移注入仅格式化Markdown文本，缺乏语义漂移检测；无需求变更追踪机制 |

**差距分析**：
- 需求解析精度不足：当前仅做文本分割，无法提取隐含约束和依赖关系
- 边界自动推断缺失：需人工指定inclusions/exclusions，无法从需求描述中自动推断
- 语义漂移检测缺失：防漂移仅做文本拼接，无法检测执行过程是否语义偏离原始需求
- 需求变更管理缺失：无需求变更追踪和影响分析机制

**增强方向**：
- 引入LLM辅助的需求解析，提取功能需求、非功能需求、隐含约束
- 基于需求描述的边界自动推断（关键词→范围映射）
- 语义漂移检测：对比当前执行上下文与原始需求的向量相似度
- 需求变更追踪：记录需求变更历史，分析变更对已执行步骤的影响

**完成度**：60%

---

#### 2.1.2 步骤拆分与优先级排序（70%）

**概念**：将目标分解为可执行的原子步骤，按P0/P1/P2优先级排序，确保核心步骤优先执行，可选步骤可安全跳过。

**现有实现**：

| 模块 | 文件 | 已有能力 | 缺口 |
|------|------|---------|------|
| PlanSchema | `src/runtime/patterns/plan-execute-enhancer.js` | P0/P1/P2优先级枚举、标准化步骤对象（createStep）、计划验证（validatePlan）、模板实例化（createFromTemplate） | 优先级排序仅按位置推断（第1步P0、第2步P1、其余P2），缺乏依赖感知排序；步骤间依赖关系未建模 |
| PlanExecuteOrchestrator | `src/runtime/workflow/plan-execute-orchestrator.js` | 步骤规范化（_normalizeSteps）、顺序执行循环、失败升级策略 | 步骤执行严格按数组顺序，无依赖图排序；不支持步骤间数据传递 |
| GoalExecutor | `src/runtime/workflow/goal-executor.js` | 自动分解子任务（_decomposeGoal）、子任务依赖检测（_hasUnmetDeps）、循环依赖检测（_detectCircularDependencies）、并行执行独立子任务 | 分解结果依赖LLM返回格式，无结构化约束；优先级仅按索引赋值 |

**差距分析**：
- 优先级排序过于简单：当前仅按位置推断，未考虑步骤间的依赖关系和关键路径
- 步骤依赖图缺失：PlanSchema和PlanExecuteOrchestrator均未建模步骤间依赖，GoalExecutor虽有依赖检测但仅限于子任务层
- 关键路径分析缺失：无法识别哪些步骤在关键路径上，哪些可以延迟执行
- 步骤粒度不一致：不同模块对"步骤"的定义不同（PlanSchema.step vs GoalExecutor.subtask vs PlanExecuteOrchestrator.step）

**增强方向**：
- 统一步骤模型：定义跨模块一致的步骤接口（id, description, priority, dependencies, resources, requiresHumanApproval）
- 引入DAG依赖图：基于SkillGraph已有的DAG能力，构建步骤依赖图
- 关键路径分析：基于依赖图计算关键路径，优先调度关键路径上的步骤
- 智能优先级推断：基于步骤类型、依赖关系和风险等级自动推断优先级

**完成度**：70%

---

#### 2.1.3 资源与风险预判（40%）

**概念**：在规划阶段预判执行所需的资源（工具、模型、数据）和潜在风险（依赖缺失、超时、冲突），提前准备应对策略。

**现有实现**：

| 模块 | 文件 | 已有能力 | 缺口 |
|------|------|---------|------|
| PlanSchema | `src/runtime/patterns/plan-execute-enhancer.js` | risks字段（description/severity/mitigation）、resources字段（type/name/required） | risks和resources仅为静态声明，无运行时验证；风险缓解策略无执行入口 |
| PlanExecuteOrchestrator | `src/runtime/workflow/plan-execute-orchestrator.js` | 三级升级策略（retry→replan→decompose）、步骤超时配置 | 升级策略是被动触发，非主动预判；无资源可用性检查 |
| GoalExecutor | `src/runtime/workflow/goal-executor.js` | 子任务超时、并发目标数限制、停滞检测 | 资源分配仅在AgentRuntime层，GoalExecutor层无资源感知 |

**差距分析**：
- 资源预检缺失：规划阶段不检查工具/模型/数据是否可用，执行时才发现缺失
- 风险量化不足：风险仅有高/中/低三级，无概率和影响量化
- 缓解策略不可执行：风险缓解策略仅为文本描述，无法自动触发
- 跨步骤风险传播缺失：无法分析一个步骤失败对后续步骤的级联影响

**增强方向**：
- 资源预检机制：规划完成后自动检查所需工具（MCPClient）、模型（ModelSelector）、数据（MemoryStore）的可用性
- 风险量化模型：引入概率×影响的二维量化，替代简单的三级分类
- 可执行缓解策略：将缓解策略绑定到具体执行动作（如"超时风险"→自动设置stepTimeoutMs）
- 级联风险分析：基于步骤依赖图，分析单点失败的影响范围

**完成度**：40%

---

### 2.2 执行层（按规划落地，实时纠偏）

执行层承担"执行者"角色，按规划逐步落地，同时监控执行偏差并实时纠偏。包含2个核心步骤：

#### 2.2.1 分步执行+结果反馈（75%）

**概念**：按规划步骤逐步执行，每步完成后记录结果，为下一步提供上下文，形成"执行→反馈→调整"的微循环。

**现有实现**：

| 模块 | 文件 | 已有能力 | 缺口 |
|------|------|---------|------|
| RollingPlanner | `src/runtime/patterns/plan-execute-enhancer.js` | 小步规划（planningHorizon=3）、步骤完成回调（onStepCompleted）、规划状态快照（getPlanStatus） | 步骤执行与规划分离，RollingPlanner仅规划不执行；反馈仅记录状态，不传递给规划层 |
| PlanExecuteOrchestrator | `src/runtime/workflow/plan-execute-orchestrator.js` | 步骤执行循环（_executeLoop）、步骤验证（_verifyStep）、事件通知（step-started/completed/failed） | 步骤间无上下文传递；验证函数需外部注入，无内置验证逻辑 |
| GoalExecutor | `src/runtime/workflow/goal-executor.js` | 迭代执行循环（_runGoalLoop）、质量评分（_evaluateIteration）、反漂移注入（_buildIterationContext）、OODA态势感知（_runOodaCycle） | 迭代上下文构建良好但与PlanExecuteEnhancer未桥接；子任务结果不回流到规划层 |

**差距分析**：
- 执行-反馈断裂：RollingPlanner规划步骤但无法执行，PlanExecuteOrchestrator执行步骤但无法反馈给规划层
- 步骤间上下文缺失：PlanExecuteOrchestrator的步骤执行是独立的，前一步结果不自动传递给下一步
- 验证逻辑外置：步骤验证需外部提供verifyFn，无内置的常见验证模式
- 结果回流缺失：GoalExecutor的迭代结果和OODA态势感知不回流到PlanExecuteEnhancer

**增强方向**：
- 执行-反馈闭环：将RollingPlanner的onStepCompleted与PlanExecuteOrchestrator的step-completed事件桥接
- 步骤上下文传递：在PlanExecuteOrchestrator的context中注入前一步执行结果（利用AR注入机制）
- 内置验证模式：提供常见验证策略（输出非空、类型匹配、Schema验证、质量评分阈值）
- 结果回流桥接：GoalExecutor的迭代结果通过CausalDataBus回流到PlanExecuteEnhancer

**完成度**：75%

---

#### 2.2.2 动态调整规划（80%）

**概念**：执行失败或环境变化时，动态调整规划——不是从头重做，而是局部修正，保留已完成果，仅重规划受影响的部分。

**现有实现**：

| 模块 | 文件 | 已有能力 | 缺口 |
|------|------|---------|------|
| RollingPlanner | `src/runtime/patterns/plan-execute-enhancer.js` | 失败重规划（replanOnFailure）、最大重规划次数限制（maxReplanCount=5）、失败原因附加到新步骤 | 重规划策略简单：将失败步骤重新加入目标队列；无差异化重规划策略 |
| PlanExecuteOrchestrator | `src/runtime/workflow/plan-execute-orchestrator.js` | 三级升级策略（retry→replan→decompose）、步骤替换（splice插入新步骤）、重新规划次数限制 | 升级策略是线性递进，无条件分支；replanFn和decomposeFn需外部注入 |
| GoalExecutor | `src/runtime/workflow/goal-executor.js` | 停滞检测（_isStagnant）、收敛检测（_shouldStopLoop）、OODA自适应决策、暂停/恢复/取消 | 停滞检测仅基于质量评分趋势，无根因分析；OODA决策结果未反馈到规划层 |

**差距分析**：
- 重规划策略单一：当前仅有"重新加入队列"和"外部注入"两种方式，缺乏基于失败类型的差异化策略
- 根因分析缺失：失败后直接重规划，不分析失败根因（资源不足？需求不清？步骤设计有误？）
- 部分重规划缺失：当前重规划是全量替换，无法仅重规划受影响的子图
- OODA-规划断裂：GoalExecutor的OODA态势感知结果未反馈到PlanExecuteEnhancer的规划层

**增强方向**：
- 差异化重规划策略：基于失败类型选择策略（资源不足→等待重试，需求不清→澄清后重规划，步骤设计有误→分解重规划）
- 根因分析模块：分析失败步骤的上下文（输入、输出、环境状态），推断失败根因
- 部分重规划：基于步骤依赖图，仅重规划受失败影响的子图
- OODA-规划桥接：将GoalExecutor的OODA orientation结果注入到RollingPlanner的规划上下文

**完成度**：80%

---

### 2.3 关键落地技巧

#### 2.3.1 规划模板固化（50%）

**概念**：将成功验证的规划模式固化为可复用模板，新任务可直接从模板实例化，避免每次从零规划。

**现有实现**：

| 模块 | 文件 | 已有能力 | 缺口 |
|------|------|---------|------|
| PlanSchema | `src/runtime/patterns/plan-execute-enhancer.js` | 模板实例化（createFromTemplate）、变量替换（{{var}}占位符）、计划验证（validatePlan） | 模板需手动定义，无自动提取；变量替换仅支持简单字符串替换 |
| PlanMemoryBridge | `src/runtime/patterns/plan-execute-enhancer.js` | 模板注册（registerPlanTemplate）、模板推荐（getRecommendedPlan）、模式提取（extractPlanningPatterns） | 模板推荐仅基于任务类型精确匹配，无语义相似度；模式提取仅统计频率，无结构化提取 |
| WorkflowTemplate | `src/runtime/workflow/workflow-template.js`（通过index.d.ts引用） | 工作流模板创建/获取/列表/实例化/删除 | 工作流模板与PlanSchema模板是两套独立体系，未统一 |

**差距分析**：
- 模板自动提取缺失：成功执行的计划不会自动固化为模板，需人工注册
- 模板语义匹配缺失：推荐仅基于任务类型精确匹配，无法处理语义相似但表述不同的任务
- 模板体系割裂：PlanSchema模板、PlanMemoryBridge模板、WorkflowTemplate模板三套独立
- 模板版本管理缺失：模板无版本概念，无法追踪模板的演进和退化

**增强方向**：
- 自动模板提取：计划执行成功后自动提取为模板（基于PlanMemoryBridge.recordExecutionOutcome + PlanSchema.createFromTemplate）
- 语义模板匹配：利用EmbeddingService计算任务描述与模板目标的向量相似度，推荐最相关模板
- 统一模板体系：将三套模板体系统一为PlanSchema + PlanMemoryBridge双层架构
- 模板版本管理：为模板增加版本号、使用次数、成功率统计，支持模板演进追踪

**完成度**：50%

---

#### 2.3.2 小步规划+快速执行（30%）

**概念**：不一次性规划所有步骤，而是每次仅规划前方N步（planningHorizon），执行完一步后立即滚动规划下一批。避免长程规划的不确定性，同时保持执行的方向性。

**现有实现**：

| 模块 | 文件 | 已有能力 | 缺口 |
|------|------|---------|------|
| RollingPlanner | `src/runtime/patterns/plan-execute-enhancer.js` | planningHorizon配置（默认3步）、planNextBatch滚动规划、onStepCompleted步骤完成回调 | 滚动规划与执行未集成，需外部编排；planningHorizon固定，无动态调整 |
| PlanExecuteOrchestrator | `src/runtime/workflow/plan-execute-orchestrator.js` | 一次性规划所有步骤后顺序执行 | 不支持滚动规划模式，所有步骤一次性生成 |
| GoalExecutor | `src/runtime/workflow/goal-executor.js` | 迭代执行循环（_runGoalLoop）、收敛检测 | 迭代是"重复执行同一目标"而非"滚动规划新步骤" |

**差距分析**：
- 滚动规划与执行脱节：RollingPlanner仅规划，PlanExecuteOrchestrator仅执行，两者未集成
- planningHorizon固定：无法根据任务复杂度和执行反馈动态调整前瞻步数
- 无执行-规划交替循环：当前架构不支持"规划N步→执行1步→规划N步"的交替模式
- 与GoalExecutor的迭代模式冲突：GoalExecutor的迭代是收敛驱动的重复执行，与滚动规划的目标驱动逐步执行是不同范式

**增强方向**：
- 滚动规划执行器：新建RollingPlanExecutor，集成RollingPlanner的规划能力和PlanExecuteOrchestrator的执行能力
- 动态planningHorizon：基于AdaptiveDepthController的复杂度评估，动态调整前瞻步数
- 执行-规划交替循环：实现"planNextBatch→executeStep→onStepCompleted→planNextBatch"的交替循环
- 与GoalExecutor融合：在GoalExecutor的迭代循环中注入RollingPlanner，实现"迭代收敛+滚动规划"双驱动

**完成度**：30%

---

#### 2.3.3 人工审核节点（65%）

**概念**：在关键步骤设置人工审核节点，高风险操作需人工确认后才执行，防止Agent自主执行不可逆操作。

**现有实现**：

| 模块 | 文件 | 已有能力 | 缺口 |
|------|------|---------|------|
| PlanSchema | `src/runtime/patterns/plan-execute-enhancer.js` | requiresHumanApproval步骤字段 | 仅是标记字段，无运行时强制执行机制；无审核流程定义 |
| PermissionGuard | `src/permission/permission-guard.js` | 文件读写权限检查、命令执行权限检查、确认有效期管理 | 权限检查是资源级，非步骤级；无与PlanSchema.requiresHumanApproval的集成 |
| HumanApprovalGate | `src/index.d.ts`（类型声明） | requestApproval/isApproved接口 | 仅有类型声明，无实际实现 |

**差距分析**：
- 审核标记无强制执行：requiresHumanApproval仅为标记，PlanExecuteOrchestrator执行时不检查此字段
- 审核流程缺失：无审核请求→等待→批准/拒绝的完整流程
- 审核与权限割裂：PlanSchema的审核标记与PermissionGuard的权限检查是两套独立机制

### 3.4 潜在冲突与解决方案

| 冲突点 | 描述 | 解决方案 |
|--------|------|---------|
| 步骤状态枚举不一致 | PlanExecuteEnhancer用PLANNED/EXECUTING/COMPLETED/FAILED/SKIPPED，PlanExecuteOrchestrator用PENDING/RUNNING/COMPLETED/FAILED/SKIPPED/REPLANNED | 统一为PlanStep.status，映射关系：PLANNED↔PENDING，EXECUTING↔RUNNING，新增REPLANNED |
| 优先级枚举不一致 | PlanExecuteEnhancer用P0/P1/P2，GoalExecutor用数字索引 | 统一为P0/P1/P2，GoalExecutor的数字索引映射为：0→P0，1→P1，其余→P2 |
| 规划-执行循环冲突 | RollingPlanner的滚动规划与PlanExecuteOrchestrator的一次性规划冲突 | 通过Feature Flag切换模式：rolling（滚动规划）vs full（一次性规划） |
| 记忆体系冲突 | PlanMemoryBridge的内存存储与BrainMemory/MemoryStore/SqliteStore的持久化存储冲突 | PlanMemoryBridge作为上层抽象，底层委托给MemoryPipeline统一调度 |
| 事件风暴风险 | 多模块事件转发可能导致事件风暴 | 事件去重：同一planId+stepId的事件仅转发一次；事件节流：batch-planned事件100ms内仅触发一次 |

### 3.5 回滚机制

| 场景 | 回滚策略 | 触发条件 |
|------|---------|---------|
| PlanExecuteEnhancer集成失败 | 通过attach*注入，detach即可回滚 | Feature Flag `plan-execute-enhancer.enabled = false` |
| 滚动规划模式异常 | 切换回一次性规划模式 | Feature Flag `plan-execute.mode = 'full'` |
| 人工审核阻塞执行 | 跳过审核节点，降级为自动执行 | Feature Flag `plan-execute.human-approval.required = false` |
| 规划记忆持久化失败 | 降级为内存存储，不影响核心功能 | PlanMemoryBridge.brainMemory为null时自动降级 |
| AgentChannel字段不兼容 | 新增字段均为可选，旧版Agent忽略即可 | planId/stepId/boundaryId字段可选 |

## 四、核心方法论

### 4.1 规划层3步法

│                      规划层3步精准任务拆解                        │

│                                                                 │
│  Step 1: 需求解析与边界锁定                                      │

│  │      → 资源预检         → 可用性验证                  │       │
│  └─────────────────────────────────────────────────────┘       │
│                           ↓                                     │
│  Step 3: 资源与风险预判                                          │
│  ┌─────────────────────────────────────────────────────┐       │
│  │ PlanSchema.risks     → 风险识别与量化                  │       │
│  │ PlanSchema.resources → 资源清单与预检                  │       │
│  │ 缓解策略绑定         → 可执行缓解动作                  │       │
│  │ 级联风险分析         → 依赖图上的影响传播              │       │
│  └─────────────────────────────────────────────────────┘       │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘

### 4.2 执行层2步法

```
┌─────────────────────────────────────────────────────────────────┐
│                      执行层按规划落地，实时纠偏                    │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  Step 1: 分步执行+结果反馈                                       │
│  ┌─────────────────────────────────────────────────────┐       │

│  │      ↓                                                    │
│  │ executeStep()   → 执行单步骤                             │       │
│  │      ↓                                                    │
│  │ verifyStep()    → 验证步骤结果                           │       │
│  │      ↓ passed                                             │
│  │ onStepCompleted() → 记录结果，更新上下文                  │       │
│  │      ↓                                                    │
│  │ planNextBatch() → 滚动规划下一批（循环）                  │       │
│  └─────────────────────────────────────────────────────┘       │
│                           ↓ failed                              │
│  Step 2: 动态调整规划                                            │
│  ┌─────────────────────────────────────────────────────┐       │
│  │ 失败检测 → 根因分析                                     │       │
│  │      ↓                                                    │
│  │ 升级策略选择：                                            │       │
│  │   Level 1: retry     → 重试（maxStepRetries次）          │       │
│  │   Level 2: replan    → 重新规划（maxReplanCount次）       │       │
│  │   Level 3: decompose → 分解为更小步骤（maxDecomposeDepth层）│       │
│  │      ↓                                                    │
│  │ replanOnFailure() → 生成新步骤，保留已完成果              │       │
│  │      ↓                                                    │
│  │ 继续执行循环                                              │       │
│  └─────────────────────────────────────────────────────┘       │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```
