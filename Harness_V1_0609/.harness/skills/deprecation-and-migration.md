## 目标

建立代码生命周期纪律，通过系统化的废弃评估、迁移计划和替代方案构建，确保旧代码被有序移除，降低维护成本和技术债务。

## 步骤

1. 废弃决策评估（独特价值、用户依赖、替代方案、迁移成本、维护成本）
2. 确定废弃类型（建议性/强制性）
3. 构建替代方案（覆盖所有关键用例、已验证）
4. 公告和文档（废弃通知、迁移指南）
5. 增量迁移（逐个消费者迁移并验证）
6. 移除旧系统（验证零活跃使用后清理代码、测试、文档和配置）

# 废弃与迁移管理 — 代码生命周期纪律

## 触发条件
- 用新系统替换旧系统、API或库时
- 下线不再需要的功能时
- 合并重复实现时
- 移除无人维护但被依赖的死代码时
- 规划新系统的生命周期时（废弃规划从设计时开始）
- 决定是维护遗留系统还是投资迁移时

## 核心原则

### 代码是负债，不是资产
每行代码都有持续成本：需要测试、文档、安全补丁、依赖更新、新工程师入职培训。当代码可以用更少代码、更少复杂性或更好抽象提供相同功能时——旧代码应该被移除。

### Hyrum定律使移除变得困难
有足够多的用户时，每个可观察行为都会被依赖——包括bug、时序怪癖和未文档化的副作用。这就是为什么废弃需要主动迁移，而非仅发布公告。

### 废弃规划从设计时开始
构建新东西时，问："3年后我们如何移除它？"具有清晰接口、特性标志和最小表面积的系统能更容易被废弃。

## 执行流程

### 第一步：废弃决策评估
废弃任何东西之前，回答以下问题：

```
1. 此系统是否仍提供独特价值？
   → 如果是，维护它。如果否，继续。
2. 有多少用户/消费者依赖它？
   → 量化迁移范围。
3. 替代方案是否存在？
   → 如果否，先构建替代方案。不要在没有替代方案时废弃。
4. 每个消费者的迁移成本是多少？
   → 如果可以自动化，做。如果手动且高成本，权衡维护成本。
5. 不废弃的持续维护成本是多少？
   → 安全风险、工程师时间、复杂性的机会成本。
```

### 第二步：确定废弃类型

| 类型 | 何时使用 | 机制 |
|------|----------|------|
| **建议性** | 迁移可选，旧系统稳定 | 警告、文档、推动。用户按自己的时间表迁移。 |
| **强制性** | 旧系统有安全问题、阻碍进展或维护成本不可持续 | 硬性截止日期。旧系统将在日期X前移除。提供迁移工具。 |

**默认使用建议性。** 仅当维护成本或风险证明强制迁移合理时才使用强制性。强制性废弃需要提供迁移工具、文档和支持——不能只宣布截止日期。

### 第三步：构建替代方案
不要在没有可用替代方案时废弃。替代方案必须：
- 覆盖旧系统的所有关键用例
- 有文档和迁移指南
- 已在生产中验证（而非仅"理论上更好"）

### 第四步：公告和文档
```markdown
## 废弃通知：OldService
**状态：** 自 2026-05-21 起废弃
**替代方案：** NewService（见下方迁移指南）
**移除日期：** 建议性——暂无硬性截止日期
**原因：** OldService 需要手动扩展且缺乏可观测性。
            NewService 自动处理两者。

### 迁移指南
1. 将 `import { client } from 'old-service'` 替换为 `import { client } from 'new-service'`
2. 更新配置（见下方示例）
3. 运行迁移验证脚本：`npx migrate-check`
```

### 第五步：增量迁移
逐个迁移消费者，而非一次性全部迁移。对每个消费者：
```
1. 识别与废弃系统的所有接触点
2. 更新为使用替代方案
3. 验证行为匹配（测试、集成检查）
4. 移除对旧系统的引用
5. 确认无回归
```

**搅动规则：** 如果你拥有正在被废弃的基础设施，你有责任迁移你的用户——或提供无需迁移的向后兼容更新。不要宣布废弃后让用户自己解决。

### 第六步：移除旧系统
仅在所有消费者迁移完成后：
```
1. 验证零活跃使用（指标、日志、依赖分析）
2. 移除代码
3. 移除相关测试、文档和配置
4. 移除废弃通知
5. 庆祝——移除代码是一种成就
```

## 迁移模式

### 绞杀者模式
新旧系统并行运行。逐步将流量从旧系统路由到新系统。当旧系统处理0%流量时，移除它。

### 适配器模式
创建一个适配器，将旧接口的调用转换为新实现。消费者继续使用旧接口，同时你迁移后端。

### 特性标志迁移
使用特性标志逐个将消费者从旧系统切换到新系统。

## 僵尸代码识别
僵尸代码是无人维护但被所有人依赖的代码。信号：
- 6个月以上无提交但有活跃消费者
- 无指定维护者或团队
- 没人修复的失败测试
- 无人更新的已知漏洞依赖
- 引用不再存在系统的文档

**响应：** 要么分配所有者并正确维护它，要么用具体迁移计划废弃它。僵尸代码不能停留在不确定状态——要么获得投资，要么被移除。

## 反合理化表

| 合理化 | 现实 |
|--------|------|
| "它还能用，为什么要移除？" | 无人维护的工作代码会积累安全债务和复杂性。维护成本在暗中增长。 |
| "以后可能有人需要" | 如果以后需要，可以重建。保留未使用代码"以防万一"的成本高于重建。 |
| "迁移太昂贵了" | 将迁移成本与2-3年的持续维护成本比较。迁移通常长期更便宜。 |
| "用户会自己迁移的" | 他们不会。提供工具、文档和激励——或者自己做迁移（搅动规则）。 |

## 验收标准
- [ ] 替代方案已在生产中验证并覆盖所有关键用例
- [ ] 迁移指南包含具体步骤和示例
- [ ] 所有活跃消费者已迁移（通过指标/日志验证）
- [ ] 旧代码、测试、文档和配置已完全移除
- [ ] 代码库中无对废弃系统的残留引用
- [ ] 废弃通知已移除（它们已履行职责）

## FAQ

- **Q: 建议性废弃和强制性废弃如何选择？** A: 默认使用建议性废弃，仅当旧系统有安全问题或维护成本不可持续时使用强制性废弃。
- **Q: 没有替代方案时能否废弃？** A: 不能。必须先构建覆盖所有关键用例的替代方案，才能废弃旧系统。
- **Q: 迁移过程中如何处理消费者依赖？** A: 逐个迁移消费者，若你拥有废弃基础设施，你有责任迁移用户或提供向后兼容更新。
