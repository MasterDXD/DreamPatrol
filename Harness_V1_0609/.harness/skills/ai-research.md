## 目标

在遇到实现细节不确定时，通过系统化调研（搜索最佳实践、对比技术方案、查找代码库模式）消除不确定性，基于调研结果做出有依据的决策，避免凭猜测编码导致的返工。

## 步骤

1. 识别所有实现细节不确定的点
2. 制定调研计划（官方文档/最佳实践/代码库模式/方案对比）
3. 执行调研（搜索外部资源、查找代码库模式、对比候选方案）
4. 整理结构化调研报告（背景/发现/方案对比/推荐方案/代码示例）
5. 与source-driven-development交叉验证调研结果

# AI自主调研 — 不确定时先调研再编码

## 触发条件
- 遇到实现细节不确定的技术问题
- 需要选择技术方案或进行技术选型
- 对某个API、库或框架的用法不熟悉
- 需要对比多种实现方案的优劣
- 需要查找最佳实践或设计模式
- 需要验证某个技术假设是否可行

**不触发条件**：纯逻辑代码（循环、条件、数据结构）、重命名变量、修复拼写错误、已有明确实现方案的任务

## 核心原则

**不确定时先调研，不凭猜测编码。** 每个不确定的实现细节都应该通过系统化调研来消除——搜索最佳实践、对比技术方案、验证可行性，然后基于调研结果做出有依据的决策。调研不是浪费时间，猜测才是。

## 执行流程

### 第一步：识别不确定点
在开始编码前，列出所有实现细节不明确的点：
- 哪些API或库的用法不确定？
- 哪些技术方案需要对比选择？
- 哪些最佳实践需要查找？
- 哪些边界条件或异常情况不清楚？
- 哪些现有代码模式需要参考？

明确声明不确定点：
```
调研需求识别：
- 不确定点1：WebSocket心跳机制的最佳实现方式
- 不确定点2：大文件上传的断点续传方案选型
- 不确定点3：项目现有代码中的类似实现模式
→ 需要调研后再确定实现方案。
```

### 第二步：制定调研计划
为每个不确定点制定调研策略：

| 调研维度 | 方法 | 工具 |
|----------|------|------|
| 官方文档 | 获取官方API文档和推荐模式 | web-fetch |
| 最佳实践 | 搜索社区最佳实践和经验总结 | web-search |
| 代码库模式 | 查找项目中已有的类似实现 | code-locator |
| 方案对比 | 对比2-3种候选方案的优劣 | web-search + web-fetch |

调研计划格式：
```
调研计划：
1. [不确定点1] → 搜索官方文档 + 查找代码库模式
2. [不确定点2] → 对比方案A vs 方案B vs 方案C
3. [不确定点3] → 查找项目现有实现 + 搜索最佳实践
```

### 第三步：执行调研
按调研计划逐项执行：

**3.1 搜索外部资源**
- 使用web-search搜索最佳实践和技术方案
- 使用web-fetch获取官方文档的具体页面
- 优先参考官方文档和权威来源，而非博客或教程

**3.2 查找代码库模式**
- 使用code-locator定位项目中已有的类似实现
- 分析现有代码的设计模式和风格
- 确保新实现与项目风格一致

**3.3 对比方案**
- 列出每种方案的优缺点
- 评估与项目现有架构的兼容性
- 考虑性能、可维护性、扩展性等维度

### 第四步：整理调研报告
生成结构化调研报告，包含以下内容：

```
## 调研报告：[调研主题]

### 1. 调研背景
- 问题陈述
- 不确定点列表

### 2. 调研发现
#### 2.1 官方文档/权威来源
- [发现1]：...（附来源URL）
- [发现2]：...（附来源URL）

#### 2.2 代码库现有模式
- [模式1]：...（附文件路径和行号）
- [模式2]：...（附文件路径和行号）

#### 2.3 方案对比
| 维度 | 方案A | 方案B | 方案C |
|------|-------|-------|-------|
| 性能 | ... | ... | ... |
| 复杂度 | ... | ... | ... |
| 兼容性 | ... | ... | ... |
| 可维护性 | ... | ... | ... |

### 3. 推荐方案
- 推荐方案：[方案X]
- 推荐理由：...
- 风险和注意事项：...

### 4. 备选方案
- 备选方案：[方案Y]
- 适用场景：...

### 5. 代码示例
- 推荐方案的代码示例
- 关键API用法示例

### 6. 参考资料
- [来源1]：URL
- [来源2]：URL
```

### 第五步：验证调研结果
与source-driven-development技能交叉验证：
- 调研结论是否与官方文档一致？
- 推荐的API是否为当前版本推荐用法？
- 代码示例是否经过验证？
- 是否存在已废弃的方案被误推荐？

如果发现调研结果与官方文档冲突，以官方文档为准，并在报告中标注冲突。

## 反合理化表

| 合理化 | 现实 |
|--------|------|
| "我大概知道怎么实现" | 大概知道≠确定知道。一个API签名错误就能浪费数小时调试。调研10分钟，省去2小时返工。 |
| "调研太浪费时间" | 凭猜测编码导致的返工时间远超调研时间。错误的方案选择会导致架构级重构。 |
| "这个很简单，不需要调研" | 简单任务用错模式会变成模板。把过时模式复制到十个文件后才发现有更好的方式。 |
| "先写再说，后面再改" | 后面改的成本是前面的5-10倍。调研是最低成本的方案验证。 |

## FAQ

- **Q: 什么情况下不需要触发调研？** A: 纯逻辑代码、重命名变量、修复拼写错误、已有明确实现方案的任务。
- **Q: 调研需要多长时间？** A: 通常10-15分钟，但能避免数小时的返工和方案级重构。
- **Q: 调研结果与官方文档冲突怎么办？** A: 以官方文档为准，并在报告中标注冲突。
