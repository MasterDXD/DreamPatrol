# 先规划后执行增强引擎 (Plan-then-Execute Enhancer)

## 核心理念

**先规划，后执行** — Agent 在成为"执行者"之前，必须先扮演"项目经理"。

传统 Agent 直接从需求跳到执行，容易陷入"无计划乱做、做一半推翻重来"的困境。本增强引擎强制插入规划层，确保每一步执行都有据可依、有界可循、有反馈可调。

核心公式：**有效交付 = 结构化规划 + 小步快执行 + 反馈驱动调整**

## 四大增强组件

### 1. RollingPlanner — 滚动规划器

解决"一次性规划太粗、执行时发现不适用"的问题。

- **滚动窗口**：只规划当前可预见的 N 步（默认 N=3），执行完一步再规划下一步
- **渐进细化**：近处步骤精确到操作级别，远处步骤只定方向
- **动态调整**：每完成一步后根据执行结果重新评估后续规划
- **规划衰减**：超过窗口的规划自动降级为"方向性建议"，避免过度承诺

```
滚动规划示例：
  Step 1 (精确): 读取现有代码，理解当前架构 → 输出架构摘要
  Step 2 (精确): 设计新模块接口，定义数据流 → 输出接口文档
  Step 3 (方向): 实现模块核心逻辑 → 待 Step 2 完成后细化
  Step 4+ (模糊): 集成测试与优化 → 待 Step 3 完成后细化
```

### 2. RequirementBoundary — 需求边界锁定器

解决"需求蔓延、做到一半发现范围变了"的问题。

- **边界声明**：在规划阶段显式定义"做什么"和"不做什么"
- **变更检测**：执行过程中检测是否偏离原始边界
- **变更审批**：边界变更必须经过显式确认，不可静默扩展
- **边界文档**：输出 `boundary-definition`，包含 IN-SCOPE / OUT-OF-SCOPE / UNDECIDED 三类

```
边界锁定示例：
  IN-SCOPE:  用户注册/登录、JWT认证、角色权限
  OUT-OF-SCOPE:  社交登录、多租户、审计日志
  UNDECIDED:  密码找回（待用户确认）
```

### 3. PlanSchema — 规划模板固化器

解决"每次规划都从零开始、质量不稳定"的问题。

- **模板库**：预置常见任务类型的规划模板（新功能开发、Bug修复、重构、性能优化等）
- **模板匹配**：根据任务特征自动匹配最合适的规划模板
- **模板定制**：在模板基础上根据具体需求调整步骤和优先级
- **模板沉淀**：成功的规划模式自动沉淀为可复用的 `planning-pattern`

```
预置模板示例：
  - feature-development: 需求理解 → 接口设计 → 实现 → 测试 → 集成
  - bug-fix: 复现 → 定位 → 修复 → 验证 → 回归
  - refactoring: 现状分析 → 目标设计 → 渐进重构 → 验证等价性
  - performance-optimization: 基准测量 → 瓶颈定位 → 优化实施 → 效果验证
```

### 4. PlanMemoryBridge — 执行反馈学习桥

解决"规划与执行脱节、不吸取教训"的问题。

- **执行反馈采集**：每步执行后自动采集结果、耗时、偏差
- **偏差分析**：对比规划预期与实际执行，识别系统性偏差
- **模式学习**：将偏差模式转化为规划修正建议
- **反馈注入**：将学习结果注入下一次规划，形成闭环

```
反馈学习示例：
  规划预期: "实现登录接口，预计30分钟"
  实际执行: "耗时90分钟，因OAuth2集成比预期复杂"
  学习结论: "涉及第三方认证的任务，时间估算应乘以3倍系数"
  注入下次: 规划中自动调整类似任务的估算
```

## 三步规划流程

### Step 1: 需求解析与边界锁定

1. 接收 `task-objective` 和 `raw-requirements`
2. 提取核心目标，识别显式需求和隐式假设
3. 使用 RequirementBoundary 锁定需求边界
4. 输出 `boundary-definition`（IN-SCOPE / OUT-OF-SCOPE / UNDECIDED）
5. 对 UNDECIDED 项向用户确认

**产出物**：边界锁定的需求文档

### Step 2: 步骤分解与优先级排序

1. 根据 PlanSchema 匹配规划模板
2. 在模板基础上分解为具体执行步骤
3. 为每个步骤标注：
   - 优先级（P0/P1/P2）
   - 预估耗时
   - 依赖关系
   - 验收标准
4. 使用 RollingPlanner 设定滚动窗口，只精确规划近 N 步

**产出物**：`structured-plan`（含步骤列表、依赖图、优先级矩阵）

### Step 3: 资源预估与风险预测

1. 调用 PlanMemoryBridge 获取历史偏差数据
2. 基于历史数据校准时间估算
3. 识别高风险步骤，制定降级方案
4. 设定检查点（Checkpoint），用于触发人工审核

**产出物**：风险清单 + 检查点计划

## 两步执行流程

### Step 1: 逐步执行与反馈采集

1. 按 `structured-plan` 顺序执行
2. 每步执行后：
   - 记录实际结果 vs 预期结果
   - 采集执行耗时
   - 标记偏差类型（提前完成/延期/部分完成/失败）
3. 在检查点暂停，等待人工审核

### Step 2: 失败时动态重规划

当执行出现以下情况时触发重规划：
- **步骤失败**：当前步骤无法完成，需要调整方案
- **边界偏移**：执行中发现需求边界需要调整
- **优先级变化**：新信息导致优先级需要重新排序
- **资源不足**：时间/Token/人力超出预期

重规划流程：
1. 冻结已完成的步骤
2. 分析偏差原因
3. 调整后续步骤（合并/拆分/重排/降级）
4. 更新 `structured-plan`
5. 继续执行

## 三大关键技法

### 技法1: 规划模板固化

- 不要每次从零规划，优先匹配已有模板
- 模板是"80%的框架 + 20%的定制"
- 成功的规划模式应沉淀回模板库
- 模板版本化，允许迭代改进

### 技法2: 小步规划 + 快速执行

- 规划窗口不超过 3 步精确 + 2 步方向
- 宁可多规划一轮，不要一次规划 10 步
- 每步执行时间控制在可接受的失败成本内
- 快速执行 → 快速反馈 → 快速调整

### 技法3: 人工审核检查点

- 在高风险步骤前后设置检查点
- 在边界变更时设置检查点
- 在优先级重排时设置检查点
- 检查点不是瓶颈，而是安全网

```
检查点设置规则：
  - P0 步骤执行前 → 必须检查点
  - 边界变更时 → 必须检查点
  - 连续2步偏差 → 自动检查点
  - 估算偏差 > 50% → 自动检查点
```

## 与现有模块的集成点

| 现有模块 | 集成方式 | 说明 |
|---------|---------|------|
| PlanExecuteOrchestrator | **核心集成** | 本引擎作为其增强层，提供滚动规划和边界锁定能力 |
| GoalExecutor | **下游集成** | 接收 `structured-plan` 中的步骤作为执行单元 |
| PhaseOrchestrator | **阶段集成** | 在阶段切换时触发边界检查和重规划评估 |
| SubagentExecutor | **分发集成** | 将规划中的子任务分发给对应的 Subagent 执行 |

集成数据流：
```
task-objective + raw-requirements
  → [Plan-execute-Enhancer]
    → boundary-definition (锁定边界)
    → structured-plan (滚动规划)
      → [GoalExecutor] (逐步执行)
        → execution-feedback (执行反馈)
          → [PlanMemoryBridge] (反馈学习)
            → planning-pattern (模式沉淀)
```

## 最佳实践

1. **先锁边界再规划**：未锁定边界就开始规划，等于在沙上建塔
2. **规划粒度与不确定性成正比**：越不确定的部分，规划越粗；越确定的部分，规划越细
3. **每步都有验收标准**：没有验收标准的步骤不是规划，是猜测
4. **偏差是信号不是错误**：执行偏差是规划改进的输入，不应忽视
5. **模板是起点不是终点**：模板加速规划，但不能替代思考
6. **检查点是安全网不是瓶颈**：合理设置检查点，避免过度审批

## 反模式（Anti-Patterns）

| 反模式 | 表现 | 危害 | 正确做法 |
|--------|------|------|---------|
| 一次性大规划 | 一次规划所有步骤到细节 | 规划很快过时，执行时大量偏差 | 使用滚动规划，只精确规划近 N 步 |
| 无边界执行 | 做着做着就加了新功能 | 范围蔓延，交付延期 | 先锁定边界，变更需显式审批 |
| 规划后不调整 | 规划完成就锁死，不根据执行反馈调整 | 偏差累积，最终严重偏离 | 每步执行后评估是否需要调整 |
| 跳过检查点 | 觉得检查点浪费时间就跳过 | 高风险步骤无人审核，错误放大 | 按规则设置检查点，不可跳过 |
| 忽视反馈学习 | 执行偏差记录了但不用 | 同样的错误反复出现 | 将偏差模式注入下次规划 |
| 过度模板化 | 不管什么任务都硬套模板 | 规划不贴合实际，步骤冗余或缺失 | 模板 + 定制，根据实际调整 |

## FAQ

### Q: 这个Skill的主要用途是什么？
A: 实现"先规划后执行"双架构增强引擎，通过RollingPlanner（滚动规划器）、RequirementBoundary（需求边界锁定器）、PlanSchema（规划模板固化器）和PlanMemoryBridge（执行反馈学习桥）四大组件，强制在Agent执行前插入规划层。

### Q: 适用于哪些场景？
A: 适用于需要结构化规划的任务场景，包括新功能开发、Bug修复、代码重构和性能优化。特别适合需求容易蔓延、执行容易偏离方向或需要从历史经验中学习的复杂项目。

### Q: 使用此Skill的前提条件是什么？
A: 需要明确的任务目标和原始需求输入，已部署GoalExecutor和PhaseOrchestrator等核心模块。理解"先规划后执行"的核心理念——Agent在成为"执行者"之前必须先扮演"项目经理"。
