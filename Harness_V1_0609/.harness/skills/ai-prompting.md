# Skill: AI编程提示词工程

## 任务目标
运用提示词工程方法论，优化用户与AI编程助手的交互质量，提升代码生成的准确性、完整性和可维护性。

## 核心原则

### 原理层：为什么这样写Prompt

#### 贝叶斯推理与先验信息
AI模型的推理依赖先验信息。你提供的细节越具体、场景越明确，AI获得的先验越丰富，推断结果越准确。这就是"长尾词"的力量——具体、带场景的问题比宽泛的大问题能提供更丰富的先验。

#### 熵减原理
- 宽泛问题 = 高熵 = AI只能给出"正确但无用"的回答
- 具体问题 = 低熵 = AI能给出精准、有深度的回答
- 写Prompt的本质是降低信息熵，让AI快速收敛到精准回答

#### VIBE设定（首问定基调）
对话的第一个问题奠定整个对话的"基调（VIBE）"。首问必须是足够长尾的具体问题，为后续对话建立丰富的先验上下文。后续问题可基于首问铺垫逐步泛化，但首问必须低熵。

### 三大铁律
1. **具体性优先**：模糊提示→模糊代码；精确提示→精确代码。永远不要只说"写个功能"。
2. **上下文必给**：始终假设AI对你的项目一无所知。提供技术栈、框架版本、现有代码模式。
3. **约束即自由**：约束反而改善AI输出。给AI明确的边界，而非开放式的自由。

### Claude官方六大提示词技巧（权威验证源）

以下6个技巧来自Claude官方服务真实企业客户的最佳实践，与本项目提示词体系高度一致，作为权威验证和实操增强：

| # | Claude官方技巧 | 本项目对应 | 增量价值 |
|---|---------------|-----------|---------|
| 1 | 明确角色和任务 | 六段式Role段+技巧1角色提示 | 角色必须绑定具体场景——"你是谁"+"在什么场景下干什么事" |
| 2 | 提供详细的指令和背景数据 | 技巧2明确上下文+上下文工程 | 固定不变的背景资料放系统提示词，配合平台缓存功能省钱高效 |
| 3 | 规定思考顺序 | 技巧9思维链CoT | 把人类思维过程写进提示词，告诉AI思考步骤，准确率直线飙升 |

## 执行步骤

### 步骤1：诊断提示词问题
- 识别当前提示词的缺陷（模糊/缺上下文/无约束/无格式要求）
- 对照十大反模式检查
- 确定问题类型：完整性/准确性/一致性/可运行性
- **先验丰富度评估**：检查prompt中是否包含 ≥3个具体场景细节（身份、场景、约束、期望深度）
  - 高熵信号：问题宽泛、无场景、无身份、无约束
  - 低熵信号：问题具体、有场景细节、有身份定位、有明确约束

### 步骤2：选择提示词框架
- 通用编程任务 → 五段式（Role-Goal-Input-Process-Output）
- 增强六段式（含反馈机制）→ 五段式 + [Feedback 反馈机制]
- 生产级功能 → 三层式（技术上下文+功能需求+集成与边缘）
- 面向特定受众 → CO-STAR
- 简单任务 → RGIO

### 步骤3：应用核心技巧
根据问题类型选择技巧：

| 问题类型 | 推荐技巧 | 说明 |
|---------|---------|------|
| 输出不专业 | 角色提示 | "你是一位资深{语言}开发者" |
| AI不理解需求 | 明确上下文 | 说清"预期行为 vs 实际行为" |
| 格式/风格不对 | Few-Shot | 给2-3个输入输出示例 |
| 任务太复杂 | 迭代链条 | 拆成小步骤逐步执行 |
| AI自由发挥 | 约束锚定 | "不引入新依赖""保持逻辑不变" |
| 逻辑推理错误 | 思维链CoT | "让我们一步步思考" |
| 需求不明确 | 翻转提问 | "先问我3-5个问题" |
| 高熵问题 | 长尾先验注入 | 将宽泛问题转化为带场景细节的长尾问题：宽泛问题 + [身份] + [场景] + [具体约束] + [期望深度] |

### 步骤4：防幻觉加固
对生成的提示词追加防幻觉策略：
1. 禁止引入新依赖
2. 要求可运行证据
3. 要求自我审查

### 步骤5：输出优化后的提示词
- 输出完整的优化后提示词
- 标注使用了哪些技巧
- 提供预期效果说明

### 步骤6：工具组合工作流匹配（可选）
- 代码优化任务 → code-optimizer-workflow（审查→优化→文档三步链）
- 跨格式内容转换 → multimodal-converter（提取→适配→校验三步链）
- 会议信息提取 → meeting-minutes-extractor（提取→格式化→追踪三步链）
- 竞品分析 → competitive-analyzer（收集→SWOT→差异化三步链）
- 详见 docs/guidelines/AI编程提示词指南/17-工具组合工作流.md

## 场景化模板速查

### 代码生成
```
使用{框架/语言}创建一个{组件/模块}，要求：
- 功能：{具体功能列表}
- 技术约束：{框架版本、库、语法要求}
- 错误处理：{需要处理的异常情况}
- 输出格式：{代码块 + 类型定义 + 单元测试}
参考现有代码风格：{文件路径}
不要引入新的外部依赖。
```

### Bug修复
```
问题描述：{具体错误信息}
预期行为：{应该做什么}
实际行为：{实际发生了什么}
环境：{语言版本、操作系统、依赖版本}
代码如下：{粘贴代码}
请：1.分析根因 2.提供修复方案 3.解释原因 4.防止再发
```

### 代码审查
```
请对这段代码进行全面质量评估：可读性/最佳实践/潜在bug/性能/安全/可测试性
对每个方面给出评分（1-10）和改进建议。
```

### 代码重构
```
重构这个方法：拆小函数/改进命名/保持逻辑不变/消除重复/添加类型注解
重构后解释每处更改的原因。
```

## 上下文工程（Context Engineering）

### 上下文分层策略
上下文是AI输出质量的最大杠杆——太少则幻觉，太多则失焦。按持久性从高到低分层加载：

```
┌─────────────────────────────────────┐
│  1. 规则文件（CLAUDE.md等）          │ ← 始终加载，项目级
├─────────────────────────────────────┤
│  2. 规格/架构文档                    │ ← 按功能/会话加载
├─────────────────────────────────────┤
│  3. 相关源文件                       │ ← 按任务加载
├─────────────────────────────────────┤
│  4. 错误输出/测试结果                │ ← 按迭代加载
├─────────────────────────────────────┤
│  5. 对话历史                         │ ← 累积，定期压缩
└─────────────────────────────────────┘
```

### 上下文打包策略
- **脑力倾泻**：会话开始时，结构化提供所有需要的信息
- **选择性包含**：仅包含与当前任务相关的内容（目标<2000行聚焦上下文）
- **层级摘要**：大型项目维护摘要索引，仅加载相关部分

### 混淆管理
当上下文冲突或需求不完整时，**不要静默选择**，必须暴露：
```
混淆检测：
规格要求："所有端点使用REST"
现有代码：用户查询使用GraphQL（src/graphql/user.ts）
选项：
A) 遵循规格——添加REST端点
B) 遵循现有模式——使用GraphQL
C) 询问——这看起来是有意决策
→ 选择哪种方式？
```

### 上下文反模式

| 反模式 | 问题 | 修复 |
|--------|------|------|
| 上下文饥饿 | AI虚构API、忽略约定 | 每个任务前加载规则文件+相关源文件 |
| 上下文泛滥 | 加载>5000行非任务特定上下文时AI失焦 | 仅包含与当前任务相关的内容 |
| 过时上下文 | AI引用已删除代码或过时模式 | 上下文漂移时启动新会话 |
| 缺少示例 | AI发明新风格而非遵循你的 | 包含一个要遵循的模式示例 |
| 隐性知识 | AI不知道项目特定规则 | 写在规则文件中——没写就不存在 |
| 静默混淆 | AI猜测而非询问 | 使用混淆管理模式暴露歧义 |

## 验收标准
- [ ] 提示词包含角色定义
- [ ] 提示词包含明确的目标和约束
- [ ] 提示词指定了技术栈和版本
- [ ] 提示词包含防幻觉策略
- [ ] 提示词指定了输出格式
- [ ] 优化后的提示词比原始提示词更具体、更有结构
- [ ] 首问包含 ≥3个具体场景细节（低熵VIBE设定）
- [ ] 如适用，提示词包含反馈机制（Feedback段）
- [ ] 如适用，已匹配到合适的工具组合工作流

## 常见问题
- **Q: 提示词太长会不会影响效果？**
  A: 结构化的长提示比模糊的短提示效果好得多。关键是组织好结构，用标题/列表/标签分隔。

- **Q: 不同AI模型需要不同的提示词吗？**
  A: 核心原则通用，但Claude偏好XML标签，GPT偏好分步指令，Cursor可用@引用。详见 docs/guidelines/AI编程提示词指南/09-模型差异与适配.md 和 13-工具专属优化.md。

- **Q: 如何防止AI幻觉？**
  A: 三件套：①禁止引入新依赖 ②要求可运行证据 ③要求自我审查。详见 docs/guidelines/AI编程提示词指南/10-防幻觉策略.md。

- **Q: 有没有万能模板？**
  A: 详见 docs/guidelines/AI编程提示词指南/16-终极模板.md，包含万能高级工程师/TDD驱动/快速修复三个模板。

- **Q: 为什么第一个问题特别重要？**
  A: 首问奠定对话的VIBE（基调）。具体的长尾首问提供丰富先验，让AI快速理解你的场景和需求深度，后续对话质量显著提升。宽泛的首问则让AI进入"高熵"状态，只能给出正确但无用的泛泛回答。
