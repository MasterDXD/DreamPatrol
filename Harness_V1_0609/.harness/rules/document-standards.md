# 文档规范

## 六层文档体系

### 1. 架构层（docs/architecture/）
- 整体设计、模块关系、系统架构图
- 命名规范：`架构分析-xxx系统.md`

### 2. 核心功能层（docs/core/）
- 生命周期、核心流程、关键机制
- 命名规范：`核心功能-xxx流程.md`

### 3. 模块详解层（docs/modules/）
- 具体实现、API接口、模块间交互
- 命名规范：`模块详解-xxx模块.md`

### 4. 工具详解层（docs/tools/）
- 所有工具的使用说明、参数、示例
- 命名规范：`工具详解-xxx工具.md`

### 5. 深度拆解层（docs/deep-dive/）
- 源码级执行链路、性能分析、边界情况
- 命名规范：`深度拆解-xxx链路.md`

### 6. Agent准则层（docs/guidelines/）
- 规范、最佳实践、编码标准
- 命名规范：`xx使用准则.md`

## 文档内容要求
每个文档必须包含以下部分：
1. **概述**：文档的目的和范围
2. **核心功能**：主要功能和特性
3. **实现原理**：技术实现细节
4. **API接口**：对外暴露的接口（如适用）
5. **使用示例**：可运行的代码示例
6. **注意事项**：限制、已知问题、最佳实践

## 文档质量标准
- 所有技术术语必须明确定义
- 关键流程必须配有流程图
- 所有代码示例必须可运行
- 文档间通过双向链接关联

## 双向链接规范
- docs/目录使用标准Markdown链接 `[显示文本](相对路径/文件名.md)`，确保在GitHub/编辑器中可直接点击
- .harness/rules/目录使用 `[[规则名称]]` 创建框架内部规则引用
- 每个模块文档必须链接到其依赖的模块和上层架构文档
- 每个工具文档必须链接到使用该工具的场景文档
- 链接必须指向实际存在的文档，避免悬空链接

## 工具注册文档规范
```markdown
# 工具名称：xxxTool
## 功能描述
一句话描述工具的功能

## 参数说明
| 参数名 | 类型 | 必填 | 描述 |
|--------|------|------|------|
| param1 | string | 是 | 参数1的描述 |
| param2 | int | 否 | 参数2的描述 |

## 返回值
返回值的描述

## 使用示例
xxxTool(param1="value1", param2=123)

## 注意事项
使用该工具的注意事项
```

## Skill编写标准
- 每个Skill对应一个具体的重复任务
- Skill必须包含：任务目标、执行步骤、验收标准、常见问题
- Skill必须经过测试验证，确保可重复执行
- Skill执行过程中产生的经验教训必须更新到Skill文档中

## 文档去重与合并原则
- 跨区域文档重叠时，根目录文件（README/SETUP/CONTRIBUTING）定位为**精简入口**，docs/内文件为**完整参考**
- 重叠度超过60%的文档对必须合并，保留信息更完整的版本，另一份改为重定向链接
- 合并后的文档必须在原位置保留重定向文件，指向新位置
- 六层文档体系内的层级重叠（如核心功能层vs模块详解层）属于设计意图，不视为冗余

## 文档命名扩展规范
- 接口文档：`接口文档-xxx.md`（如 接口文档-Web API.md）
- 功能说明：`功能说明-xxx.md`（如 功能说明-全部模块清单.md）
- 开发指南：`开发指南-xxx.md`（如 开发指南-代码贡献规范.md）
- 子目录文档：使用数字前缀排序（如 AI编程提示词指南/01-核心原则.md）
- 重定向文件：在文件头部标注 `> 本文档已合并至 [目标](路径)`

## 运行时数据管理
- `.harness/goals/`、`.harness/archive/`、`.harness/sessions/` 中的JSON文件为运行时历史数据
- 运行时数据不纳入文档体系管理，定期清理即可
- `outputs/` 目录仅保留模板文件，临时报告在任务完成后清理
