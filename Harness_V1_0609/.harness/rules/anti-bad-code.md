# AI劣质代码防护规则

## 核心理念

AI编程工具是"效率放大器"而非"质量保证器"——它能快速写出"能跑的代码"，但"好代码"仍需工程思维和质量把控。盲目依赖AI，最终会让项目被劣质代码拖垮。

## 一、三类核心危害识别

### 1.1 隐性技术债

AI为快速跑通功能，常用"省事写法"：

| 反模式 | 示例 | 正确做法 |
|--------|------|---------|
| 硬编码 | `if (env === 'production')` | 使用配置常量或环境变量 |
| 冗余嵌套 | `if(a){if(b){if(c){...}}}` | 提前返回/guard clause |
| 非标准命名 | `var d1 = getData()` | 遵循项目命名规范 |
| 魔法数字 | `setTimeout(fn, 30000)` | 使用命名常量 `DEFAULT_TIMEOUT_MS` |
| 重复代码 | 相同逻辑复制粘贴 | 提取公共函数 |

### 1.2 隐性漏洞

AI忽略边界场景，埋下隐患：

| 漏洞类型 | AI典型遗漏 | 最低防护要求 |
|----------|-----------|-------------|
| 空值处理 | 直接访问属性不检查null/undefined | 所有外部输入必须做空值校验 |
| 并发冲突 | 共享状态无锁保护 | 共享可变状态必须加锁或使用不可变数据 |
| 类型安全 | 隐式类型转换 `==` vs `===` | 严格等号，参数类型校验 |
| 安全漏洞 | 拼接SQL/HTML/命令 | 参数化查询，输出编码，白名单过滤 |
| 资源泄漏 | 定时器/监听器/连接未清理 | 必须在finally或shutdown中清理 |

### 1.3 极端化编码

| 极端方向 | 表现 | 判定标准 |
|----------|------|---------|
| 过度工程 | 添加不必要抽象层/设计模式 | YAGNI四问：用户要吗？现在要？不加会死？加后更简单？ |
| 过度简化 | 省略错误处理/日志/边界检查 | 错误处理完整性清单：null检查✓ 类型校验✓ 边界处理✓ 资源清理✓ |

## 二、必要vs不必要错误处理的判定标准

> **关键澄清**：karpathy-principles中"禁止不必要的错误处理"指的是**不增加安全性的冗余try-catch**，而非允许省略必要的防护。

### 必要的错误处理（不可省略）

1. **外部输入校验**：函数参数、HTTP请求体、文件内容、环境变量
2. **资源操作保护**：文件I/O、网络请求、数据库操作、定时器
3. **并发场景防护**：共享状态访问、异步操作竞态、锁获取/释放
4. **边界条件处理**：空数组/空对象、数值溢出、字符串超长、索引越界
5. **优雅降级**：服务不可用时的回退方案、超时处理、重试策略

### 不必要的错误处理（可省略）

1. 纯函数内部的冗余try-catch（如`Math.max`调用）
2. 已由上层统一处理的重复catch
3. 空catch块（`catch(e) {}`）——必须至少记录日志
4. 对不可能失败的同步操作加try-catch

## 三、AI特异性劣质代码模式

以下模式是AI生成代码的特有问题，需专项检查：

| 模式 | 描述 | 检测方法 |
|------|------|---------|
| 占位符代码 | 生成`// TODO: implement`后标记完成 | 搜索TODO/FIXME/HACK/stub |
| 幻觉依赖 | 引用不存在的库/API | 运行时验证require/import是否可解析 |
| 正确但无用 | 语法正确、测试通过，但不解决实际问题 | 人工审查业务逻辑匹配度 |
| 过度泛化 | 生成通用方案而非针对具体场景 | 检查抽象层级是否超出需求 |
| 静默失败 | `catch(e) {}` 或 `.catch(function() {})` | 搜索空catch模式 |
| NaN陷阱 | `parseInt(x) ?? default`（NaN ?? default = NaN） | 搜索数值转换+??组合 |

## 四、四项强制缓解措施

### 4.1 强制人工审查门禁

AI生成代码合入共享区前，以下类型**必须**经人工审批：

- 认证/授权相关代码
- 数据库迁移/Schema变更
- 安全相关配置（CSP、CORS、权限）
- 外部API集成
- 并发/多线程代码
- 支付/交易逻辑

审批流程：staging → 人工审查 → shared，使用`HumanApprovalGate`强制门禁。

### 4.2 编码标准注入AI提示词

在AI代码生成前，自动将以下关键规则注入提示词Process段：

```
编码约束：
- 禁止硬编码：所有配置值使用常量或环境变量
- 强制错误处理：外部输入必须校验，资源操作必须try-catch-finally
- 严格类型：使用===，参数类型校验
- 命名规范：遵循项目现有命名模式
- 最小实现：只实现当前需求，不做提前优化或过度抽象
```

### 4.3 TDD/BDD双重约束

- **TDD强制**：先写测试后写代码，RED-GREEN-REFACTOR无例外
- **BDD补充**：复杂需求先用Given-When-Then格式描述行为，再TDD实现
- **覆盖率门禁**：核心模块≥80%，错误处理路径必须有测试

### 4.4 限制AI自由编码

| 限制项 | 约束规则 |
|--------|---------|
| 单次生成量 | 单次生成不超过200行，超出需拆分 |
| 修改范围 | 只修改与需求直接相关的代码，surgical change |
| 依赖引入 | 新依赖需经必要性审查（necessity-review技能） |
| 抽象层级 | 新增抽象层需YAGNI四问验证 |
| 代码复用 | 优先使用项目现有工具函数，禁止重复实现 |

## 五、检测与执行

### 代码审查检查清单（AI特异项）

- [ ] 无硬编码敏感信息或配置值
- [ ] 所有外部输入有空值/类型校验
- [ ] 资源操作有try-catch-finally
- [ ] 共享状态有并发保护
- [ ] 无空catch块（至少记录日志）
- [ ] 无NaN/??误用（数值转换后用\|\|而非??）
- [ ] 无占位符代码标记为完成
- [ ] 错误处理路径有测试覆盖
- [ ] 修改范围与需求匹配（无多余变更）
- [ ] 新增依赖经必要性审查

### 自动化检测模式

框架合规检查器（FrameworkComplianceChecker）将自动检测以下AI劣质代码模式：
- `HARDCODED_VALUE`：硬编码配置值
- `EMPTY_CATCH`：空catch块
- `NAN_NULLISH`：数值转换+??误用
- `PLACEHOLDER_CODE`：占位符代码
- `MISSING_NULL_CHECK`：外部输入缺少空值校验
