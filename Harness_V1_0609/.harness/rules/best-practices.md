# 最佳实践与错误预防规则

## TDD最佳实践

### 测试先行
- **铁律**：NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST
- 先写测试后写代码，不是建议，是强制要求
- 如果先写了实现代码，必须删除，从测试开始
- 每个RED-GREEN-REFACTOR循环控制在2-5分钟内

### 测试质量
- 测试覆盖率目标≥80%
- 每个公开接口至少有1个正向测试+1个边界测试
- 测试命名清晰描述预期行为
- 测试必须可独立运行，不依赖执行顺序
- 使用Fixture或Factory替代硬编码测试数据

### 重构安全
- 重构前确认测试覆盖充分
- 每次重构后立即运行测试
- 重构与功能修改绝不混合进行
- 测试失败时立即回退

## 完成验证最佳实践

### 证据驱动
- 声称"完成了"不算完成，提供证据才算完成
- 必须通过verification-before-completion Skill验证
- 每项验收标准都需要对应的完成证据
- 证据类型：测试输出、Lint结果、覆盖率报告、安全扫描结果

### 验证清单
- 所有测试通过（测试运行输出为证）
- Lint零错误（Lint输出为证）
- 测试覆盖率≥80%（覆盖率报告为证）
- 无硬编码敏感信息（安全扫描为证）> 详见 [[security-permissions]]
- 无遗留TODO/FIXME（代码搜索为证）

## 常见错误解决方案

### 上下文过长
- **症状**：Agent响应变慢，Token消耗剧增，信息丢失
- **原因**：加载了过多无关信息，未及时压缩
> 详见 [[context-management]]（上下文压缩策略、Skill按需加载、Session生命周期管理）

### 工具调用失败
- **症状**：工具返回错误，任务执行中断
- **原因**：参数错误、权限不足、服务不可用
- **解决方案**：
  1. 检查参数类型和格式是否正确
  2. 确认Agent是否有该工具的使用权限
  3. 检查目标服务是否可用
  4. 切换到备用工具或方案
> 失败重试策略详见 [[monitoring-fault-tolerance]]（指数退避、重试次数上限）

### 任务超时
- **症状**：任务执行超过配置的超时时间
- **原因**：任务粒度过大、模型响应慢、依赖阻塞
> 详见 [[monitoring-fault-tolerance]]（任务监控、超时告警、Checkpoint恢复、模型降级）

### 模型幻觉
- **症状**：Agent输出不准确或虚构的信息
- **原因**：缺乏事实核查、上下文不足、模型局限性
- **解决方案**：
  1. 增加事实核查步骤
  2. 引用可靠来源验证输出
  3. 提供更充分的上下文信息
  4. 对关键输出进行交叉验证
  5. 使用verification-before-completion强制证据验证

### Agent间信息不同步
- **症状**：多个Agent对同一问题有不同理解
- **原因**：上下文未及时同步，信息传递不完整
- **解决方案**：
  1. 使用共享的知识状态
  2. 关键决策必须持久化并广播
  3. 定期进行状态同步
  4. 使用统一的消息格式

### TDD流程被跳过
- **症状**：实现代码没有对应的失败测试先行
- **原因**：赶进度、不熟悉TDD、测试难以编写
- **解决方案**：
  1. 严格执行tdd-implement Skill，enforcement为strict
  2. 先写代码则删除，从测试重新开始
  3. 功能切片不够小——拆分为2-5分钟可完成的粒度
  4. 不知道怎么写测试——从最简单的行为开始

### 完成验证被绕过
- **症状**：Agent声称完成但无实际证据
- **原因**：赶进度、验证步骤繁琐、忘记验证
- **解决方案**：
  1. 严格执行verification-before-completion Skill，enforcement为strict
  2. 在pre_task_submit Hook中自动触发验证
  3. 未通过验证的任务不允许标记为完成
  4. 跳过验证需Team Lead明确授权并记录在案

## 并发安全

### 文件并发修改
- **规则**：避免多个Agent同时修改同一个文件
- **策略**：
  1. 使用乐观锁处理并发冲突
  2. 文件修改前检查最新版本号
  3. 关键操作加锁，确保原子性
  4. 冲突时自动合并或提示人工处理
  5. 并行开发使用dispatching-parallel Skill + Git Worktree隔离

### 资源竞争
- **规则**：共享资源必须有序访问
- **策略**：
  1. 限制同时访问同一资源的Agent数量
  2. 使用队列串行化资源请求
  3. 设置资源访问超时，避免死锁
  4. 监控资源使用情况，及时预警

### 状态一致性
- **规则**：所有状态变更必须原子化
- **策略**：
  1. 状态变更前创建快照
  2. 变更失败时自动回滚
  3. 关键状态变更需多Agent确认
  4. 定期校验状态一致性

## 边界处理

### 输入边界
- 空输入：返回明确的错误提示，不静默忽略
- 非法输入：验证并拒绝，附带合法输入说明
- 超长输入：截断或分片处理，通知用户
- 特殊字符：转义处理，防止注入攻击

### 输出边界
- 空输出：检查是否为正常情况，记录日志
- 超长输出：分片输出或生成摘要
- 格式异常：验证输出格式，不符合则重试
- 编码问题：统一使用UTF-8编码

### 外部异常
- 网络中断：自动重试，超过次数后降级处理
- 服务不可用：切换到备用服务或缓存结果
- 超时：设置合理超时时间，超时后优雅降级
- 限流：实现退避策略，尊重服务端限流

### 用户交互
- 用户中断：保存当前进度，创建Checkpoint
- 取消操作：回滚已完成的部分操作
- 修改需求：评估影响范围，调整任务计划
- 紧急干预：暂停所有任务，等待用户指令

## 错误预防清单
- [ ] 所有外部输入是否经过验证
- [ ] 所有关键操作是否有回滚机制
- [ ] 所有并发访问是否有同步机制
- [ ] 所有异常是否有明确的处理策略
- [ ] 所有敏感操作是否有权限检查
- [ ] 所有长时间操作是否有超时设置
- [ ] 所有状态变更是否有持久化
- [ ] 所有用户交互是否有友好提示
- [ ] 所有实现代码是否有失败测试先行（TDD门禁）
- [ ] 所有任务完成是否有验证证据（verification-before-completion）
