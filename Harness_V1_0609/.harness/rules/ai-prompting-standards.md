# AI编程提示词工程标准规则

## 核心原则

### 具体性原则
- **禁止模糊指令**：不允许只说"写个功能""修个bug""优化一下"
- **必须指定**：技术栈+版本、框架、库、语法标准
- **必须提供**：具体错误信息（含stack trace）、预期行为vs实际行为
- **必须指定输出格式**：代码块+类型定义+单元测试+文档

### 上下文原则
- **始终假设AI对项目一无所知**：每次交互都提供必要的项目上下文
- **引用现有代码**：使用"遵循src/xxx的模式"而非让AI重新发明
- **提供技术栈版本**：如"Next.js 14 with App Router"而非仅"Next.js"
- **描述数据流**：帮助AI理解架构而非仅理解单个函数

### 约束原则
- **约束即自由**：给AI明确边界，而非开放式自由
- **必须约束**：是否可引入新依赖、代码风格、命名规范、修改范围
- **重构必加**："保持逻辑不变（所有现有测试必须通过）"
- **范围必限**："只修改这个函数""不要改动其他文件"

### 先验丰富度原则
- **首问必须低熵**：对话的第一个问题必须包含 ≥3个具体场景细节（身份、场景、约束、期望深度），奠定对话VIBE
- **长尾词优先**：具体、带场景细节的问题（长尾词）比宽泛的大问题能提供更丰富的先验，让AI推断更准确
- **宽泛问题必须先转化**：遇到宽泛问题，必须先转化为长尾问题再提交
  - ❌ "如何优化GDN效果"（高熵，宽泛）
  - ✅ "GDN里的Banner Blindness为何出现及如何解决"（低熵，长尾）
- **后续可泛化**：基于首问的丰富先验铺垫，后续问题可逐步泛化或对比，AI仍能给出有深度的回答
- **无需背诵模板**：理解"先验→推断"的贝叶斯原理，该方法适用于所有AI模型，且随模型迭代愈发有效

### Claude官方技巧强化原则

以下原则来自Claude官方服务真实企业客户的最佳实践，作为现有规则的权威强化：

#### 角色场景绑定原则
- 角色定义必须同时包含"你是谁"和"在什么场景下干什么事"
- ❌ "你是一位资深开发者"
- ✅ "你是一位资深Node.js开发者，在微服务架构项目中审查HTTP中间件的并发安全性"

#### 系统提示词缓存原则
- 固定不变的背景资料（技术栈、项目规范、代码风格）应放在系统提示词中
- 配合平台的缓存功能（如Claude的system prompt caching），减少重复Token消耗
- 变化的任务指令放在用户消息中，与固定的系统提示词分离

#### 思考顺序显式化原则
- 将人类的思维过程写进提示词，告诉AI思考的步骤
- 结构化思考模板比"让我们一步步思考"更有效
- 示例："请按以下顺序思考：1)理解需求 2)识别约束 3)设计方案 4)评估风险 5)编写代码"

#### 案例优先于描述原则
- 一个完美案例比一大堆文字描述更有效
- 优先提供以前处理得非常完美的案例作为参考
- 案例应包含完整的输入→思考→输出链路

#### 防幻觉红线原则
- 在提示词中加入强硬指令，要求AI"如果不确定，就直接说不知道"
- 红线指令应使用绝对语气："只在非常确定的情况下才下结论"
- 红线指令与防幻觉三件套配合使用，形成四重保障

#### XML标签输出原则
- 要求AI将结果放在指定的XML标签中，方便程序一键抓取
- 常用标签对：<result></result>、<analysis></analysis>、<code></code>
- XML标签输出使结果干净利落、拿来就能用，特别适合多步骤工作流

## 提示词结构标准

### 六段式公式（推荐，含反馈机制）
所有编程提示词应遵循以下结构：
```
[Role 角色] + [Goal 目标] + [Input 输入] + [Process 过程与约束] + [Output 输出格式] + [Feedback 反馈机制]
```
Feedback段模板：
- 单次交付：`"直接输出最终结果，无需解释过程"`
- 迭代协作：`"先输出大纲/方案，等我确认后再细化实现"`
- 逐步验证：`"每完成一个步骤，暂停等我确认后再继续下一步"`

### 三层式结构（生产级）
生产级功能开发应使用三层结构：
1. Technical context — 技术上下文和约束
2. Functional requirements — 功能需求和用户故事
3. Integration and edge cases — 集成需求和边缘情况

## 防幻觉规则

### 三件套（每次代码生成都必须包含）
1. **禁止引入新依赖**："仅使用项目已有的依赖，不要引入新的包"
2. **要求可运行证据**："确保代码可以直接运行，包含所有必要的import"
3. **要求自我审查**："检查所有import的库是否真实存在，代码能否编译"

### 额外防幻觉措施（含Claude官方红线）
- **设置红线指令**：在提示词中加入"如果不确定，就直接说不知道，只在非常确定的情况下才下结论"，这是让AI输出可靠的关键
- 提供官方文档示例作为参考实现
- 要求为每个API调用注明文档链接
- 分步实现并要求每步验证

## 场景化提示词规范

### 代码生成
- 必须指定：框架/语言/版本/功能列表/错误处理/输出格式
- 必须引用：现有代码风格文件路径
- 必须约束：不引入新外部依赖

### Bug修复
- 必须提供：具体错误信息/预期行为/实际行为/环境信息
- 必须要求：根因分析（不修表面症状）/防止再发建议

### 代码重构
- 必须包含："保持逻辑不变（所有现有测试必须通过）"
- 必须要求：解释每处更改的原因
- 必须引用：现有代码风格文件路径

### 代码审查
- 必须覆盖：可读性/最佳实践/潜在bug/性能/安全/可测试性
- 必须给出：评分+具体改进建议+优先级排序

## 反模式黑名单

### 绝对禁止的提示词模式
| 反模式 | 示例 | 正确做法 |
|--------|------|----------|
| 模糊指令 | "修复bug" | "修复UserService.getUser()第45行的NullPointerException" |
| 一次性过多 | "构建完整认证系统" | 分阶段实现，每次一个功能 |
| 无上下文 | "添加认证" | "添加JWT认证到NestJS API，使用TypeORM" |
| 无约束 | "创建用户模型" | "创建TS接口+JSDoc+导出interface和class" |
| 不引用现有代码 | 让AI自由发挥 | "遵循src/entities/User.ts的模式" |
| 高熵首问 | "如何优化性能" | "在Node.js v20的HTTP服务器中，当并发连接超过1000时响应时间从50ms升到500ms，如何优化事件循环" |

### Claude

- 解释约束背后的"为什么"
- 复杂问题开启extended thinking

## 工具组合工作流规范

### 适用场景
当任务需要多步骤、多格式的协同处理时，使用工具组合工作流替代单次提示词。

### 四大工具组合
| 工具组合 | 适用场景 | 映射技能链 |
|---------|---------|-----------|
| 代码优化器 | 代码质量提升+文档生成 | code-review → refactor-code → documentation |
| 多模态转换器 | 跨格式内容转换 | ai-prompting（多步骤模式） |
| 会议纪要提炼器 | 会议信息结构化提取 | brainstorming → requirement-analysis |
| 竞品分析工具 | 竞品SWOT分析+差异化建议 | brainstorming → architecture-design |

### 设计原则
1. 三步法则：提取→转换→校验
2. 格式中立：核心内容以JSON结构化表示
3. 可组合：工具组合之间可串联
4. 可回滚：每个步骤独立输出
