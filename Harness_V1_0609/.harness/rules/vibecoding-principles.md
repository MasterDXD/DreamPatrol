# VibeCoding 工程化原则

> 融合自 Codex VibeCoding 实战指南（2026），适配 Harness 框架架构。

## 核心规则

### 1. 先想再写
- 不确定就问，别瞎猜；有多种理解就列出来，别偷偷自己选
- 修改前必须理解现有代码的意图和上下文
- 架构决策必须经过评估，不得凭直觉跳过

### 2. 简单优先
- 只做需求内的事，别过度设计
- 用一次的代码就别抽象，三处复用再提取
- 优先使用项目已有的工具函数和模式，不引入新依赖

### 3. 精准修改
- 只改该改的地方，别顺手优化旁边的代码
- 每一行改动都要追溯到需求
- 重构和功能变更必须分开提交

### 4. 目标驱动
- 先确定清晰的目标和验收标准
- 写完必须验证，优先写测试再实现功能
- 不允许"我觉得做完了"，必须通过自动化测试验证

## 行为契约

### 沟通规范
- 日常沟通用中文，技术报错保留英文原文便于搜索
- 沟通直奔主题，不需要频繁确认，以结果为导向
- 遇到错误直接报告，不要尝试隐瞒或美化

### 安全红线
- 绝对不允许将 API 密钥、密码、令牌写入代码，必须从环境变量读取
- 禁止提交 .env 文件、credentials.json 等敏感文件
- 禁止执行 rm -rf、DROP TABLE 等高危命令

### 代码规范
- 禁止使用 utils_v3_final 这类模糊文件名
- 提交信息必须包含"类型：内容"格式（feat/fix/refactor/docs/test）
- 变量命名必须语义清晰，禁止单字母变量（循环变量除外）

## 验证标准

### 必须验证
- 所有新增功能必须有对应的测试用例
- ESLint 检查必须 0 错误通过
- 关闭/异常路径必须测试覆盖
- 异步操作必须处理 Promise 拒绝

### 禁止行为
- 跳过验证：绝对不能相信"我做完了"，必须通过自动化测试
- 过度依赖：复杂架构设计、核心业务逻辑必须由人来做
- 无边界任务：不给 AI 明确的任务边界和验收标准
- 硬编码敏感信息：任何密码、密钥、令牌都不能写在代码里

## Harness 架构适配

### 状态机调度
- 将规则文件作为 Sub Agent 的行为契约
- 主 Agent 只负责状态转移和结果验证
- Sub Agent 必须遵循规则约束，不得自由发挥

### JSON 通信
- Agent 间通信强制使用 JSON 格式
- 输入输出接口必须类型明确
- 错误信息必须包含错误码和可读描述

### Skill 蒸馏
- 将重复使用的流程提炼为原子 Skill
- Skill 必须有明确的输入/输出契约
- Skill 不得产生副作用（除非显式声明）

### 派生实验
- 使用 DeriveExecutor 在隔离环境中实验新想法
- 验证通过后合并回主线，不满意直接丢弃
- 派生分支必须设置验收标准
